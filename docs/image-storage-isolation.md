# 이미지 저장소 환경 분리 (#286)

이 변경은 애플리케이션의 S3 접근 경계와 배포 설정 검증을 추가한다. 실제 S3 복사, DB 갱신, 서버 `.env` 수정과 배포는 별도 전환 작업이다. **기존 DB key를 그대로 두고 새 코드를 먼저 배포하지 않는다.**

## 책임과 동작

| 담당 코드 | 책임 |
| --- | --- |
| `S3StorageProperties` | `DEPLOY_ENV`와 생성·기준 이미지 prefix가 정확히 일치하는지 시작 시 검사 |
| `S3ImageAccessPolicy` | 현재 환경의 어떤 파일을 어떤 용도로 접근할 수 있는지 판단 |
| `S3ImageStorage` | S3 요청 전 정책 확인, 업로드 전체 사전 검사, 조건부 저장과 누락 복구 |
| `S3ImageUrlProvider` | 현재 환경의 생성 이미지만 URL 서명 |
| 배포 검증 스크립트 | CodeDeploy 대상과 서버 `.env`의 환경명·버킷·생성/기준 prefix 대조 |

조회·존재 확인·없는 파일 복구는 자기 환경의 생성 이미지와 기준 이미지에 허용한다. 일반 저장·삭제·URL 발급은 자기 환경의 생성 이미지에만 허용한다. 반대 환경, 기존 공용 경로, 다른 프로젝트 경로, `..`·중복 구분자·백슬래시·인코딩된 모호한 경로는 거절한다.

일반 저장도 `If-None-Match: *`로 요청하므로 기존 파일을 덮어쓰지 않는다. 업로드 실패 시 이번 요청에서 저장 성공이 확인된 파일만 정리하고, 충돌한 파일이나 결과가 불명확한 파일은 삭제하지 않는다. 복구는 기존 원본·상세·썸네일을 선삭제하지 않는다. 상세 저장이 충돌하면 기존 상세로 누락 썸네일을 만든다. 원본·상세 없이 썸네일만 남은 경우 자동 재생성은 409로 중단하고 검수를 요구한다.

이 경계는 게스트 여부와 무관하게 모든 이미지 접근에 적용된다. 콘솔·CLI 또는 같은 IAM Role을 사용하는 별도 도구까지 차단하는 IAM 정책은 이번 변경에 포함하지 않는다.

## 조사 기준과 남겨야 할 기록

2026-09-30 읽기 전용 조사에서는 두 서버가 같은 버킷과 공용 prefix를 쓰고 있었다. dev는 `DEPLOY_ENV=dev`, prod는 해당 값이 없었으며, Spring 프로필은 둘 다 `prod`였다. 고아 이미지 정리 작업 제거는 양쪽 배포에서 확인했다. 아래 수치는 당시 스냅샷이며 전환 직전에 다시 대조해야 한다.

- 복사 후보: dev 267개 + prod 1,289개 = 1,556개 사본, 약 2.08GB. 기준 이미지 환경별 사본 포함.
- 누락: 삭제된 비게스트 일기 50개 + 삭제되지 않은 게스트 일기 34개. 모두 스토리보드와 성공 기록이 남아 있었다.
- 누락 84개는 HEAD 404였고 조회 가능한 객체 버전/삭제 마커에서도 발견되지 않았다. 과거 복구한 1,077개와 겹치지 않았다.
- 과거 사고 #254에서는 dev DB만 보고 공용 S3를 정리해 prod 이미지를 지우는 경로가 확인됐다. 개별 84개 객체의 삭제 시각·주체까지 확인한 것은 아니다.
- 게스트 34개는 이번 자동 재생성 대상에서 제외한다. 삭제된 일기 50개도 자동 복구하지 않는다. 일기·생성 기록·스토리보드는 보존한다.

개별 key·DB ID가 든 조사 명세는 로컬 작업 폴더의 `artifacts/image-isolation-preflight-2026-09-30/`에서 관리하며 저장소에 커밋하지 않는다. `implementation-context.md`가 후속 재분류와 구현 진행 기록이다. 초기 `object-manifest`와 `db-reference-manifest`의 84개 보류 상태를 정상 복사 완료로 바꾸지 않는다.

## 사용자가 설정할 값

각 서버의 `/opt/harudle/.env`에서 아래 항목을 **추가 또는 교체**한다. 같은 변수를 중복해서 덧붙이지 않는다. 기존 DB 연결·인증·AI 비밀값은 유지한다. prefix 끝에는 `/`를 붙이지 않고 환경명·버킷·두 prefix에는 변수 치환이나 줄 끝 주석을 쓰지 않는다. 초기화용 기준 이미지 key는 초기화 기능을 사용할 때 설정하며 배포 검사에서는 필수로 요구하지 않는다.

개발 서버:

```dotenv
DEPLOY_ENV=dev
S3_BUCKET=techcourse-project-2026
S3_GENERATED_PREFIX=harudle/generated/diary-images/dev
S3_REFERENCE_PREFIX=harudle/references/generation/dev
HARUDLE_GENERATION_PROMPT_BOOTSTRAP_IMAGE_ASSET_OBJECT_KEY=harudle/references/generation/dev/05-reference-style-asset.png
```

운영 서버:

```dotenv
DEPLOY_ENV=prod
S3_BUCKET=techcourse-project-2026
S3_GENERATED_PREFIX=harudle/generated/diary-images/prod
S3_REFERENCE_PREFIX=harudle/references/generation/prod
HARUDLE_GENERATION_PROMPT_BOOTSTRAP_IMAGE_ASSET_OBJECT_KEY=harudle/references/generation/prod/05-reference-style-asset.png
```

`AWS_REGION=ap-northeast-2`와 `SPRING_PROFILES_ACTIVE=prod`는 두 서버 모두 현재 값으로 유지한다. 이미지 환경을 구분하려고 Spring 프로필을 dev로 바꾸지 않는다. `HARUDLE_GENERATION_ADAPTERS_ENABLED`도 현재 운영 방침대로 유지한다. 어댑터가 꺼진 로컬 단위 테스트에서는 S3 설정 없이 실행할 수 있지만 배포 스크립트는 항상 환경 조합을 검사한다.

`DEPLOYMENT_GROUP_NAME`은 CodeDeploy가 제공한다. dev 그룹은 `harudle-dev`, prod 그룹은 `harudle-prod`여야 한다. 이 변수는 `.env`에 추가하지 않는다. 환경명만 prod로 바꾸거나 설정 전체를 prod 값으로 바꿔도 dev 배포 그룹과 다르면 중단한다. 이미지 설정은 서버 `.env`에서만 관리하며 Compose나 별도 Spring·Java 옵션으로 덮어쓰지 않는다. 배포 검사는 그 외 설정 경로까지 추적하지 않는다.

기준 파일 `05-reference-style-asset.png`는 조사 시 bootstrap 설정값이다. 실제 DB 프롬프트는 dev에서 06번 파일, prod에서 05·06번 파일을 참조했다. **05와 06 파일 모두 환경별로 복사·검증하고, DB의 각 참조는 같은 파일의 새 key로 바꾼다.** 기존 프롬프트를 모두 05로 통일하지 않는다. `GenerationPromptInitializer`는 기존 행이 있으면 초기화를 건너뛰므로 환경변수 변경만으로 DB가 갱신되지 않는다.

## 전환 순서: dev 완료 후 prod

1. **변경 전 기록을 보관한다.** 배포 버전, 버킷/DB명/환경 설정, DB 백업과 행별 기존 key, S3 객체 및 버전 목록을 기록한다. `.env` 백업은 서버 안에 제한된 권한으로 보관하고 Git에 넣지 않는다. 기존 코드의 고아 이미지 정리 작업이 제거된 버전인지 재확인한다.
2. **최신 이전 명세를 만든다.** 환경·DB ID·기존 key·새 key·종류·크기·SHA-256·검증 상태를 기록한다. 원본 `image.png/jpg/webp`, 상세 `image-960.webp`, 썸네일 `image-240.webp` 중 실제 존재하는 파일을 묶어서 대조한다. 과거 단일 이미지는 그대로 복사하며 없는 파생 이미지를 정상 복사로 기록하지 않는다. 양쪽에서 쓰는 기준 파일은 각각 복사한다. 복구 임시 파일과 소유 불명 파일은 그대로 보존한다.
3. **새 key로 복사하고 검증한다.** S3 폴더를 미리 만들 필요는 없다. 원본은 남긴다. 목적지가 이미 있으면 덮어쓰지 말고 내용이 같은지 확인해 재실행 완료 또는 충돌로 분류한다. 크기·MIME뿐 아니라 실제 GET 바이트의 체크섬과 이미지 디코딩을 확인한다. ETag만으로 내용 동일성을 단정하지 않는다.
4. **이미지 쓰기를 통제한다.** 최종 대조 전 신규 생성, 관리자 복구·업로드와 진행 중 작업을 포함해 쓰기를 멈춘다. 마지막 생성 완료/실패를 확인한 뒤 추가 파일을 대조·복사한다. 단순히 화면의 생성 버튼만 막는 것으로 끝내지 않는다. 복사 리허설의 소요 시간으로 중단 구간을 정한다.
5. **누락 84행을 별도 명세로 처리한다.** 재생성 제외는 key 전환 완료를 뜻하지 않는다. 기존 공용 key를 남기면 새 검증이 게스트 조회·관리자 복구에서도 거절한다. 기록을 보존하면서 새 환경 key로 참조만 옮기는 방식을 택한다면, 각 행을 `MISSING_NOT_RESTORED`로 별도 기록하고 새 key에 파일이 없다는 사실을 유지한다. 이는 정상 복사와 분리된 수동 DB 전환이며 실행 전 행 목록을 검토한다. 이번 코드에 자동 처리나 공용 key 우회는 없다. 처리 방침이 정해지지 않은 채 엄격한 경계를 켜지 않는다.
6. **DB 참조와 설정을 같은 전환 구간에서 바꾼다.** `diary_generations.image_object_key`와 `generation_prompts.image_asset_object_key`가 대상이다. 환경·DB명 재확인 후 트랜잭션 안에서 명세의 ID와 기존 key가 모두 일치하는 행만 갱신한다. 예상/실제 변경 건수, 중복·충돌을 확인하고 불일치 시 롤백한다. 일기 내용·상태·스토리보드·생성 완료 시각은 변경하지 않는다. 정상 복사 행은 검증 완료가 전제이며 누락 행은 위 별도 명세에 따른다.
7. **서버 `.env`를 적용하고 배포한다.** 이 문서의 값과 대상 그룹을 맞춘다. 새 코드의 시작 검사와 배포 검사에 통과한 뒤 실제 조회·생성을 확인한다. 검증이 배포를 막으면 값과 명세를 확인하며 검사 코드를 해제하지 않는다.
8. **검증 결과를 남긴 뒤 쓰기를 재개한다.** 아래 항목을 모두 확인하고 dev에서 되돌리기 연습까지 마친 절차를 prod에 적용한다. 기존 객체 삭제는 이번 전환 작업에서 수행하지 않는다.

파일 존재 검증과 DB 전환은 하나의 S3/DB 원자적 트랜잭션이 아니다. 쓰기 통제·조건부 행 갱신·전후 명세 비교로 전환 구간을 관리한다. 애플리케이션 시작 시 S3 복사나 DB key 일괄 변경을 실행하지 않는다.

## 배포 전 설정만 확인하기

Bash로 실행한다. 대상 서버에서 **배포 묶음 루트**를 기준으로 실행하며, 개발 서버에는 `/opt/harudle/compose.dev.yaml`이 설치되어 있어야 한다. 아래는 dev 예시이며 운영에서는 그룹을 `harudle-prod`로 바꾼다.

```bash
DEPLOYMENT_GROUP_NAME=harudle-dev bash -c '
  source deploy/scripts/compose_environment.sh
  configure_compose /opt/harudle
'
```

이 명령은 `.env`만 확인하며 컨테이너를 시작하거나 S3/DB를 변경하지 않는다. 성공해도 파일 복사와 DB 전환이 완료됐다는 뜻은 아니다. 실제 CodeDeploy는 ApplicationStart에서 컨테이너 재생성 전에 검사한다. 전체 환경변수나 `docker compose config` 결과를 그대로 로그/채팅에 출력하지 않는다.

## 실제 확인할 사용 흐름

- 정상 이전한 기존 일기의 목록·상세·공유·다운로드가 열리는지 확인한다. 게스트 동작도 정상 파일이 있는 기록으로 확인한다.
- 새 일기 한 건을 만들고 DB key와 원본·상세·썸네일이 자기 환경 아래에 저장되는지 확인한다.
- 프롬프트별 기준 이미지 GET과 실제 생성 요청이 성공하는지 확인한다.
- 반대 환경 key의 조회·저장·삭제·복구·URL 발급이 거절되는지 확인한다. 삭제/쓰기 차단의 운영 검증에 실제 사용자 파일을 넣지 않고 검증용 객체를 사용한다. 로컬 테스트는 SDK 및 presigner 호출 0회를 확인한다.
- 누락 보류 목록과 정상 이전 목록을 분리한다. 사진 몇 장이 보이는 것으로 전체 전환 성공을 판단하지 않는다.
- 복구 API의 `RESTORED`는 해당 작업이 파일을 채웠다는 의미다. 남아 있던 원본·상세·썸네일이 같은 그림인지까지 보장하지 않는다. 충돌·부분 복구는 파일 묶음의 시각적 검수를 추가한다. 스토리보드 재생성은 원본 그림의 동일한 복원이 아니다.

## 문제가 있을 때

쓰기 통제를 유지하고 복사 검증, DB 변경 내역, `.env`, 배포 버전을 함께 확인한다. 가장 먼저 코드만 되돌릴지, DB/설정까지 되돌릴지 결정한다. 이전 코드가 환경별 새 key를 지원하면 검증된 새 key와 prefix를 유지한 코드 롤백이 데이터 되돌림보다 단순하다. 과거 공용 청소 작업이 포함된 버전으로 롤백하지 않는다.

DB와 설정까지 되돌릴 때는 보관한 명세의 ID·현재 새 key가 일치하는 행만 복원한다. 전환 이후 생성된 기록을 일괄 문자열 치환하지 않는다. 이전 `.env` 복원과 코드 롤백도 같은 쓰기 통제 구간에서 수행한다. 복사한 새 파일, 기존 파일, 부분 복구 파일은 삭제하지 않아야 다시 검증할 수 있다.

구 경로 삭제는 별도 후속 작업이다. 양쪽 DB·모든 프롬프트·유효한 공유/서명 URL·복구 및 되돌리기 참조가 남지 않았는지 전수 대조하고 보존 기간과 복구 가능성을 검토한 뒤 결정한다. “화면에서 사진이 보인다”만으로 삭제하지 않는다.
