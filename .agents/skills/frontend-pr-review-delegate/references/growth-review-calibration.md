# 성장형 리뷰 보정 기준

이 문서는 [shopping-cart-full-stack PR #47](https://github.com/woowacourse/shopping-cart-full-stack/pull/47)에서 `eastroots92`가 진행한 리뷰의 방식을 분석해 정리한 보정 기준이다. 특정 문장을 흉내 내기보다 작성자가 자기 기준을 세우게 만든 상호작용을 재현한다.

## 관찰된 리뷰 방식

- 첫 라운드에서 테스트 부재와 중복 상태처럼 중요한 문제는 우선순위를 높여 명확히 지적했다.
- 설계 선택에는 곧바로 정답을 주기보다 선택 이유, 실패 상황과 분리의 실익을 물었다.
- 서버 상태, 클라이언트 상태와 파생 상태처럼 사고에 도움이 되는 분류 기준을 제시했다.
- 필수 수정과 시간이 되면 해볼 UX 실험을 분리해 학습 범위를 조절했다.
- 작성자가 PR 본문에 남긴 질문에는 현재 조건에서의 답과 선택이 달라질 미래 조건을 함께 설명했다.
- 답변이 "가독성"이나 "UX"처럼 추상적이면 실제로 무엇이 좋아졌는지 후속 질문했다.
- 답변을 이해했다는 사실과 설계에 동의한다는 판단을 구분했다.
- 추상적인 책임 분리 논의가 반복될 때는 일상적인 비유를 사용한 뒤 다시 코드의 책임과 변경 비용으로 연결했다.
- 여러 리뷰 라운드에서 후속 변경과 답변을 확인하고 작성자의 기준이 생겼을 때 선택을 인정했다.
- 낮은 우선순위 의견은 지금도 충분하다고 밝혀 불필요한 수정 압박을 줄였다.

## 좋은 질문의 형태

좋은 질문은 다음 세 요소 중 둘 이상을 포함한다.

1. 코드에서 관찰한 구체적인 사실
2. 그 구조가 만든 이점 또는 비용
3. 작성자가 설명해야 할 선택 기준이나 실패 조건

예시:

- 이 컴포넌트는 로딩 분기만 맡지만 한 단계의 Props 전달을 추가합니다. 이 분리로 현재 어떤 코드가 더 쉬워졌고, 그 이점이 추가된 깊이보다 크다고 본 이유가 무엇인가요?
- 서버 응답과 브라우저 저장소가 같은 선택 상태를 각각 보관합니다. 한쪽 갱신이 실패하면 어떤 값이 원본이어야 하며, 동기화 책임을 어디에 두는 것이 좋을까요?
- 이 Hook은 화면 코드를 짧게 만들지만 서로 다른 상태와 행동을 함께 모읍니다. 단순히 Page 전용이라는 점 외에 이 책임들이 함께 변경될 이유가 있을까요?
- 현재는 재사용자가 하나뿐입니다. 지금 추상화를 추가하지 않았을 때 생기는 구체적인 불편과, 추가했을 때 생기는 간접 비용을 비교해볼 수 있을까요?

## 피해야 할 질문

- 코드 근거 없이 "왜 이렇게 했나요?"만 남기는 질문
- 리뷰어가 원하는 답이 하나뿐인 유도 질문
- 실제 버그를 발견하고도 작성자가 맞혀보게 하는 질문
- 동일한 추상화 원칙을 모든 컴포넌트에 기계적으로 묻는 질문
- 사소한 취향을 여러 개의 숙제로 만드는 질문
- 작성자의 답변을 읽지 않고 최초 의견을 반복하는 질문
- 프론트엔드 지식이 없는 리뷰 요청자에게 구현 대안을 선택하게 하는 질문

## 라운드별 대화 흐름

### 첫 리뷰

- 구체적인 장점이나 시행착오를 짚어 PR 본문을 읽었다는 신뢰를 만든다.
- 병합 전 필요한 문제와 선택적으로 고민할 내용을 구분한다.
- 중심 성장 주제 1~3개를 제시한다.
- 코드 인라인에는 각 주제를 촉발한 구체적인 위치와 질문을 남긴다.
- PR 작성자가 요청한 논의 항목에는 빠짐없이 답한다.

### 답변 이후

- 작성자의 논리를 가장 설득력 있는 형태로 다시 말한다.
- 근거가 충분하면 다른 선택이어도 인정한다.
- 근거가 추상적이면 실제 변경 효과, 반례나 비용을 한 단계 더 묻는다.
- 새로운 구현이 처음 제기한 문제를 해결했는지 호출부와 테스트에서 확인한다.

### 마지막 리뷰

- 남은 병합 차단 문제가 없는지 확인한다.
- 어떤 코드가 바뀌었는지만 말하지 않고 작성자의 판단 기준이 어떻게 구체화됐는지 피드백한다.
- 다음 미션에서 이어갈 하나의 관점만 남기고 리뷰를 닫는다.

## 내부 품질 게이트

리뷰 초안을 제출하거나 게시하기 전에 아래 항목을 스스로 점검한다. 하나라도 충족하지 못하면 댓글을 고친다.

- 모든 중요한 질문이 PR 본문 또는 특정 diff의 근거와 연결되어 있는가?
- 중심 설계 선택마다 현재 이점과 지불 비용을 모두 확인했는가?
- 적어도 하나의 실패 조건이나 요구사항 변화로 선택을 검증했는가?
- 작성자가 예/아니오가 아니라 자기 기준을 설명할 수 있는 질문인가?
- P1 문제는 질문 뒤에 숨기지 않고 조건과 영향을 명확히 썼는가?
- 필수 수정과 선택적인 학습 제안을 구분했는가?
- PR 본문에 대한 피드백과 코드 인라인 댓글의 위치가 올바른가?
- 리뷰 요청자에게 기술적인 선택을 되돌려 보내지 않았는가?
- 해결 코드를 먼저 다 보여줘 작성자의 사고 기회를 없애지 않았는가?
- 질문 수를 채우기 위한 중복이나 취향성 댓글이 없는가?
- 서로 다른 설계 주제를 하나의 넓은 질문으로 뭉개지 않았는가?
- 설계 질문만 남아 있는데 불필요하게 `Request changes`를 선택하지 않았는가?

## 보정용 시나리오

다음 세 상황을 모두 다룰 수 있어야 한다.

### 추상화만 추가된 PR

당장 오류가 없다면 무조건 분리를 요구하거나 철회를 요구하지 않는다. 현재 해결하는 문제, 실제 사용자, 추가된 간접 계층과 되돌릴 조건을 작성자가 비교하게 한다.

### 비동기 오류가 있는 PR

질문만 던지지 않는다. 요청 순서나 실패 조건, 사용자에게 보이는 결과를 명확히 설명하고 병합 전 수정을 요구한다. 그 뒤 어떤 상태를 원본으로 삼을지 생각하게 한다.

### 미래 마이그레이션을 근거로 든 PR

미래 가능성을 부정하지 않되 주된 근거로 인정하지 않는다. 현재 책임이 실제로 줄었는지, 변경 이유가 분리됐는지, 분리 비용이 얼마인지 먼저 확인하게 한다. 마이그레이션 재사용은 조건부 부가 이점으로 평가한다.
