# ADR-0003: 스타일링 도구로 Emotion 채택

- **날짜:** 2026-08-09

## 📜 맥락 (Context)

React 컴포넌트의 구조와 스타일을 어떤 단위로 작성하고 관리할지 결정해야 했다.

이 프로젝트에서는 컴포넌트가 변경될 때 함께 수정되는 JSX와 스타일을 하나의 `.tsx` 파일에 가까이 두는 Co-location을 중요하게 본다. 동시에 스타일을 적용하기 위해 실제 DOM 구조와 무관한 React 컴포넌트를 만들거나, 단순한 HTML 요소마다 이름을 정해야 하는 비용은 줄이고자 했다.

Tailwind CSS, CSS Modules, vanilla-extract, Styled Components와 Emotion을 검토했다. 빌드 타임 CSS 도구는 런타임 비용을 줄일 수 있지만 스타일 파일이 분리되거나 별도의 문법과 파일 구성이 필요했다. 런타임 CSS-in-JS는 실행 비용이 있지만 컴포넌트와 스타일을 같은 파일에서 관리하기 쉽다.

현재 MVP 규모에서는 확인되지 않은 성능 문제를 미리 최적화하기보다 팀이 선호하는 작성 방식과 컴포넌트 단위 유지보수성을 우선하기로 했다.

## 🎯 결정 (Decision)

Web 애플리케이션의 스타일링 도구로 Emotion을 사용한다.

- React 컴포넌트와 해당 컴포넌트의 스타일을 같은 `.tsx` 파일에 Co-location한다.
- JSX에서는 Emotion의 `css` prop을 사용하여 스타일을 적용한다.
- 스타일 선언은 컴포넌트의 렌더링 흐름을 먼저 읽을 수 있도록 컴포넌트 아래쪽에 두는 것을 기본 방식으로 한다.
- 단순한 스타일 적용을 위해 Styled Component를 만들지 않고 실제 HTML 요소와 DOM 구조를 유지한다.
- 여러 화면에서 실제로 공유되는 색상과 디자인 값은 Theme Token으로 분리할 수 있지만, 특정 컴포넌트의 스타일은 사용 위치 가까이에 둔다.
- Emotion의 런타임 비용을 감수하며, 실제 사용자 환경에서 스타일 계산이 성능 병목으로 확인되면 빌드 타임 CSS 도구로의 전환을 다시 검토한다.

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- JSX와 함께 변경되는 스타일을 하나의 `.tsx` 파일에서 찾고 수정할 수 있다.
- 스타일을 적용하기 위한 별도의 React 컴포넌트 없이 `css` prop으로 실제 HTML 요소에 직접 스타일을 연결할 수 있다.
- 컴포넌트 삭제 또는 이동 시 관련 스타일도 같은 파일에서 함께 처리하기 쉽다.
- 동적인 Props나 상태에 따라 스타일 값을 계산해야 할 때 React 코드와 자연스럽게 결합할 수 있다.
- 객체 스타일을 사용하는 경우 TypeScript 기반 CSS 속성 자동 완성과 타입 검사의 도움을 받을 수 있다.
- 자동으로 생성되는 클래스 이름을 통해 전역 클래스 이름 충돌을 줄일 수 있다.

### 부정적 효과 / 감수할 점

- 브라우저에서 스타일을 생성하고 삽입하는 런타임 비용이 발생한다.
- 빌드 타임에 정적 CSS를 생성하는 도구보다 JavaScript Bundle 크기와 초기 실행 비용이 증가할 수 있다.
- 컴포넌트 파일이 커지면 JSX, 상태 로직과 스타일이 한 파일에 모여 파일 길이가 길어질 수 있다.
- 정적 스타일과 동적 스타일의 경계가 흐려지면 렌더링마다 불필요한 스타일 계산이 발생할 수 있다.
- Emotion 전용 `css` prop과 JSX 설정에 의존하므로 다른 스타일링 도구로 전환할 때 수정 범위가 커진다.

## 🔄 대안 (Alternatives Considered)

### 대안 1: Tailwind CSS

- **채택하지 않은 이유:** 별도 스타일 파일 없이 빠르게 작성할 수 있지만, 유틸리티 클래스가 JSX에 누적되면 컴포넌트의 구조와 의미를 읽기 어렵다고 판단했다. 이번 프로젝트에서는 JSX 아래에 이름 있는 스타일 선언을 두는 방식을 선호했다.

### 대안 2: CSS Modules

- **채택하지 않은 이유:** 런타임 비용 없이 클래스 이름 충돌을 방지할 수 있지만, React 컴포넌트와 스타일을 별도 파일로 관리해야 하므로 `.tsx` 단위 Co-location이라는 우선순위에 맞지 않았다.

### 대안 3: vanilla-extract

- **채택하지 않은 이유:** 빌드 타임 CSS와 타입 안전성을 제공하지만 스타일을 별도의 `.css.ts` 파일로 관리해야 하고 추가 빌드 설정이 필요하다. 런타임 성능보다 한 `.tsx` 파일에서 컴포넌트와 스타일을 함께 관리하는 방식을 우선했다.

### 대안 4: Styled Components

- **채택하지 않은 이유:** 의미 있는 UI 요소를 이름 있는 컴포넌트로 표현하기에는 유용하지만, 단순히 스타일을 적용할 HTML 요소까지 Styled Component로 만들면 불필요한 컴포넌트 이름과 추상화가 늘어날 수 있다고 판단했다.

### 대안 5: 전역 CSS 또는 일반 CSS 파일

- **채택하지 않은 이유:** 별도 도구 없이 사용할 수 있지만 스타일의 적용 범위와 컴포넌트 소유 관계를 개발자가 직접 관리해야 한다. 컴포넌트 단위 Co-location과 클래스 이름 격리를 우선했다.
