# ADR-0007: Access Token 메모리 저장 및 Single-Flight 패턴 적용

- **날짜:** 2026-08-20

## 📜 맥락 (Context)

현재 서버는 인증이 필요한 API에 Bearer Access Token을 요구한다. Access Token의 유효 기간은 30분이고, 이를 다시 발급받는 데 사용하는 Refresh Token의 유효 기간은 14일이다. 프론트엔드는 두 토큰의 역할과 수명이 다른 만큼 각각의 저장 위치와 만료 시 복구 방식을 결정해야 했다.

Access Token은 요청의 `Authorization` 헤더에 담아야 하므로 프론트엔드 JavaScript가 값을 사용할 수 있어야 한다. `localStorage`나 `sessionStorage`에 저장하면 새로고침 이후의 복구는 간단하지만, 같은 Origin에서 실행되는 스크립트가 토큰을 읽을 수 있고 애플리케이션 실행이 끝난 뒤에도 토큰이 저장소에 남을 수 있다. 메모리 저장 역시 실행 중인 XSS가 토큰을 가로채거나 사용자 권한으로 요청을 보내는 것까지 막지는 못하지만, JavaScript가 읽을 수 있는 토큰의 영속 복사본을 만들지 않고 페이지 수명으로 노출 범위를 제한할 수 있다.

반면 Refresh Token은 Access Token보다 수명이 길고, 탈취되면 새로운 Access Token을 계속 발급받는 데 사용될 수 있다. 프론트엔드가 Refresh Token의 값을 직접 읽거나 가공할 필요도 없다. 따라서 새로고침 이후에도 세션 복구에 사용할 수 있으면서 JavaScript의 직접 접근은 막는 저장 방식이 필요했다. 다만 쿠키는 브라우저가 요청에 자동으로 포함하므로, 쿠키를 사용하는 Refresh와 로그아웃 요청에는 CSRF 방어도 함께 고려해야 했다.

Access Token을 메모리에만 둔다면 새로고침이나 새 탭 진입 시 토큰이 없는 상태가 정상적으로 발생한다. 사용 중인 Access Token이 만료되어 API가 `401`을 반환하는 경우에도 토큰 복구가 필요하다. 이때 페이지의 여러 컴포넌트가 인증 API를 동시에 호출하면 각 요청이 개별적으로 토큰 갱신을 시도하여 다음 문제가 발생할 수 있다.

- 동일한 Refresh Token으로 불필요한 갱신 요청이 동시에 전송된다.
- 토큰 회전 정책이 적용된 환경에서는 먼저 완료된 갱신으로 인해 나머지 갱신이 실패할 수 있다.
- 여러 요청이 같은 인증 실패를 각각 처리하여 사용자에게 만료 알림이 중복으로 표시될 수 있다.
- 한 요청이 갱신한 최신 Access Token을 다른 요청이 다시 폐기하는 Race Condition이 발생할 수 있다.

따라서 다음 요구사항을 함께 만족하는 인증 흐름이 필요했다.

- Access Token은 현재 서버의 Bearer 인증 계약에 맞게 JavaScript에서 사용할 수 있어야 한다.
- 수명이 긴 Refresh Token은 JavaScript에 노출하지 않으면서 새로고침 이후에도 세션 복구에 사용할 수 있어야 한다.
- 쿠키가 자동으로 전송되는 요청은 CSRF 공격을 방어해야 한다.
- 여러 API 요청이 동시에 토큰 복구를 시도하더라도 갱신 요청과 인증 실패 처리는 한 번만 수행되어야 한다.

## 🎯 결정 (Decision)

두 토큰의 저장 위치와 전달 방식을 다음과 같이 결정한다.

| 토큰          | 저장 위치와 전달 방식                                                                                                                    | 선택 근거                                                                                                                                                                 |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Access Token  | 프론트엔드 메모리에만 저장하고 `Authorization: Bearer` 헤더로 전달                                                                       | 현재 서버의 Bearer 인증 계약상 JavaScript가 토큰을 사용해야 한다. 브라우저 저장소에 영속화하지 않아 페이지 종료 후에도 JavaScript로 읽을 수 있는 토큰이 남는 것을 피한다. |
| Refresh Token | 서버가 설정한 `HttpOnly`, `SameSite=Lax` 쿠키에 저장하고 운영 환경에서는 `Secure`를 적용한다. 쿠키의 `Path`는 `/api/v1/auth`로 제한한다. | 프론트엔드가 값을 직접 읽을 필요가 없고 Access Token보다 수명이 길다. JavaScript 접근을 차단하면서 새로고침 이후에도 브라우저가 Refresh 요청에 토큰을 전달하도록 한다.    |

메모리의 Access Token이 없거나 만료되면 Refresh API를 호출하여 복구한다. Refresh Token 쿠키는 `HttpOnly`로 설정해 JavaScript에서 읽을 수 없게 하지만, 이는 XSS로 실행된 스크립트가 사용자의 브라우저에서 인증 요청을 보내는 것까지 방지하지는 않는다. 또한 브라우저가 쿠키를 자동으로 전송하는 특성에 대비해 `SameSite=Lax`를 적용하고, Refresh와 로그아웃처럼 쿠키를 사용하는 상태 변경 요청에는 별도로 발급받은 CSRF Token을 `X-XSRF-TOKEN` 헤더에 담는다.

인증이 필요한 요청은 공통 `authFetch` 함수를 통해 실행하며 다음 규칙을 적용한다.

1. Access Token이 없으면 API 요청 전에 토큰 복구를 시도한다.
2. 토큰 복구가 이미 진행 중이라면 새로운 갱신 요청을 만들지 않고, 진행 중인 Promise를 함께 기다리는 Single-Flight 패턴을 적용한다.
3. API 요청을 보낼 때 사용한 Access Token을 별도로 기억한다.
4. 응답이 `401`이면, 요청에 사용한 토큰과 현재 토큰이 같을 때만 현재 토큰을 폐기한다. 다른 요청이 이미 토큰을 갱신했다면 최신 토큰을 유지한다.
5. 토큰 복구 후 원래 API 요청을 최대 한 번만 다시 전송한다.
6. Refresh Token이 유효하지 않은 경우 세션 만료 알림과 로그인 페이지 이동은 한 번만 수행한다.
7. Refresh Token 만료 이외의 API 오류는 `authFetch`에서 처리하지 않고 각 요청의 호출부로 전달한다.

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- Access Token의 영속 복사본이 브라우저 저장소에 남지 않고 페이지 수명과 함께 제거된다.
- 수명이 긴 Refresh Token을 JavaScript가 직접 읽을 수 없으며, 쿠키가 전송되는 경로도 인증 API로 제한된다.
- 여러 API가 동시에 Access Token 복구를 요청하더라도 실제 Refresh 요청은 최대 하나만 실행된다.
- 토큰 갱신 과정에서 발생할 수 있는 Race Condition과 불필요한 서버 부하를 줄일 수 있다.
- 인증 헤더 추가, `401` 처리, 토큰 복구 및 재요청 정책을 API 호출부마다 반복하지 않아도 된다.
- 인증 실패 알림과 로그인 이동이 중복으로 실행되는 것을 방지할 수 있다.
- 인증 이외의 오류 처리 책임은 각 기능에 남겨 기능별 오류 UX를 구성할 수 있다.

### 부정적 효과 / 감수할 점

- 새로고침이나 새 탭 진입 시 메모리의 Access Token이 사라지므로 Refresh API 호출이 추가로 필요하다.
- Single-Flight 상태는 현재 탭의 JavaScript 실행 환경에서만 공유되며 여러 탭 사이에서는 공유되지 않는다.
- `authFetch`가 토큰 저장, 갱신, 재요청, 세션 만료 이동을 함께 담당하므로 인증 정책 변경 시 공통 함수의 복잡도가 증가할 수 있다.
- `authFetch`는 인증 요청의 `401`을 Access Token이 거부된 신호로 해석한다. 서버가 다른 원인에도 `401`을 사용하면 불필요한 갱신과 재요청이 발생할 수 있으므로, 서버의 인증 오류 상태 코드 규칙을 일관되게 유지해야 한다.
- 자동 재요청되는 상태 변경 API는 중복 실행 가능성을 고려해야 하며, 일기 생성처럼 부작용이 큰 요청에는 Idempotency Key가 필요하다.
- 전역 메모리와 브라우저 이동을 사용하는 인증 흐름은 테스트에서 상태 초기화와 브라우저 API 대체가 필요하다.

## 🔄 대안 (Alternatives Considered)

### 대안 1: Access Token을 `localStorage` 또는 `sessionStorage`에 저장

- **채택하지 않은 이유:** 새로고침 이후 토큰을 바로 재사용할 수 있지만 같은 Origin의 JavaScript가 저장소에 접근할 수 있다. 메모리 저장도 실행 중인 XSS를 막지는 못하지만, Access Token을 브라우저 저장소에 남기지 않아 페이지 종료 이후까지 이어지는 노출은 피하기로 했다.

### 대안 2: Refresh Token을 JavaScript가 읽을 수 있는 저장소에 보관

- **채택하지 않은 이유:** Refresh Token은 Access Token보다 수명이 길고 새로운 Access Token을 발급하는 자격 증명이다. 프론트엔드가 값을 직접 사용할 필요가 없으므로 `localStorage`, `sessionStorage` 또는 JavaScript로 읽을 수 있는 쿠키에 노출할 이유가 없다고 판단했다.

### 대안 3: `401`을 받은 각 API 요청이 개별적으로 Refresh API 호출

- **채택하지 않은 이유:** 여러 요청이 동시에 실패하면 동일한 Refresh 요청이 중복되고, 토큰 회전 및 응답 순서에 따라 최신 토큰이 무효화되는 Race Condition이 발생할 수 있다.

### 대안 4: 각 Custom Hook에서 인증 오류와 재요청을 처리

- **채택하지 않은 이유:** 인증 헤더 추가와 토큰 복구 정책이 기능마다 중복되며, 재시도 횟수와 세션 만료 UX가 서로 달라질 수 있다. 인증 정책은 프로젝트 전역에서 동일해야 하므로 공통 요청 계층에서 처리하기로 했다.

### 대안 5: Access Token까지 쿠키로만 전달

- **채택하지 않은 이유:** 현재 서버 API가 Bearer Access Token을 요구하는 구조이며, 쿠키 기반 인증으로 전환하려면 서버 인증 방식과 CSRF 방어 전략까지 함께 변경해야 한다. 현재 API 계약을 유지하면서 토큰의 영속 저장을 피하는 방식을 선택했다.
