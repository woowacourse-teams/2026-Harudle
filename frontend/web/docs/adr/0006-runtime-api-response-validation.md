# ADR-0006: API 응답을 unknown으로 받고 런타임 검증

- **날짜:** 2026-08-15

## 📜 맥락 (Context)

TypeScript의 타입 정보는 컴파일 이후 사라지므로 서버에서 받은 JSON 응답이 프론트엔드에 선언된 타입과 실제로 일치하는지는 보장할 수 없다. `response.json()`의 결과를 타입 단언만으로 사용하면 서버 응답의 필드가 누락되거나 타입이 변경되어도 컴파일 단계에서는 이를 발견할 수 없으며, 잘못된 값이 UI 로직 내부까지 전달된 뒤 예상하기 어려운 오류로 나타날 수 있다.

특히 하루들은 일기, 이미지 생성 상태, 사용량처럼 중첩된 응답을 다루고, 실패 응답은 Problem Details 형식을 사용한다. 성공 응답과 오류 응답 모두 서버와 프론트엔드 사이의 계약이 어긋날 가능성을 고려해야 했다.

## 🎯 결정 (Decision)

API의 JSON 응답은 애플리케이션 타입으로 바로 단언하지 않고 `unknown`으로 받는다. 이후 응답별 타입 가드로 런타임 구조를 검증한 경우에만 해당 타입의 값으로 사용한다.

구체적으로 다음 원칙을 따른다.

1. `response.json()`으로 받은 값은 `unknown`으로 선언한다.
2. 성공 응답은 각 API 응답 타입에 대응하는 타입 가드로 필수 필드, 필드 타입, 중첩 객체와 허용된 리터럴 값을 검증한다.
3. 검증에 실패하면 응답 형식이 일치하지 않는다는 일반 `Error`를 발생시키고 데이터를 UI에 전달하지 않는다.
4. 실패 응답은 공통 `isProblemDetails` 타입 가드로 검증한다.
5. Problem Details로 확인된 실패 응답은 `RequestError`로 변환하여 오류 코드, 상태 코드, 상세 내용과 필드 오류를 호출부에서 사용할 수 있게 한다.
6. Problem Details 형식에도 맞지 않는 실패 응답은 기능별 기본 오류로 처리한다.
7. 브라우저 저장소처럼 네트워크 외부에서 읽은 데이터도 신뢰 경계로 보고, 필요한 경우 동일하게 파싱 후 타입 가드와 도메인 검증을 적용한다.

현재는 검증 스키마 라이브러리를 추가하지 않고 직접 작성한 TypeScript 타입 가드를 사용한다. API 수와 응답 구조가 늘어나 수동 타입 가드의 중복 및 유지보수 비용이 커지면 Zod 등의 스키마 라이브러리를 다시 검토한다.

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- 서버 응답이 프론트엔드 타입과 다를 때 네트워크 경계에서 즉시 오류로 처리할 수 있다.
- 검증되지 않은 값이 컴포넌트와 도메인 로직 내부로 전파되는 것을 방지할 수 있다.
- 타입 가드를 통과한 이후에는 TypeScript의 타입 좁히기를 활용하여 안전하게 데이터에 접근할 수 있다.
- Problem Details를 공통 오류 객체로 변환하여 기능별 오류 처리에서 상태 코드와 오류 코드를 일관되게 사용할 수 있다.
- 별도의 런타임 스키마 라이브러리와 빌드 설정을 추가하지 않고 현재 필요한 검증을 수행할 수 있다.
- API뿐 아니라 브라우저 저장소 등 다른 외부 데이터에도 동일한 원칙을 적용할 수 있다.

### 부정적 효과 / 감수할 점

- TypeScript 타입과 타입 가드를 각각 작성해야 하므로 코드가 중복되고 응답 필드가 변경될 때 두 곳을 함께 수정해야 한다.
- 수동 타입 가드에서 필드 검증을 빠뜨리거나 실제 API 계약보다 지나치게 엄격하게 검사할 수 있다.
- API 응답 구조가 복잡해질수록 타입 가드의 가독성과 유지보수 비용이 증가한다.
- 응답마다 유사한 `response.ok`, JSON 파싱, 타입 가드 및 오류 변환 코드가 반복될 수 있다.
- 컴파일 타임 타입만 사용하는 방식에 비해 런타임 검증 비용이 추가된다.
- 타입 가드 자체가 올바른지 확인하기 위한 테스트가 필요하다.

## 🔄 대안 (Alternatives Considered)

### 대안 1: `response.json()` 결과를 타입 단언하여 사용

```ts
const data = (await response.json()) as DiaryResponse;
```

- **채택하지 않은 이유:** 타입 단언은 런타임 데이터를 검증하지 않는다. 서버 응답이 변경되거나 잘못된 응답이 전달되어도 타입이 안전한 것처럼 취급되어 오류 발견 시점이 UI 렌더링이나 후속 로직까지 늦어질 수 있다.

### 대안 2: Zod 등의 런타임 스키마 검증 라이브러리 도입

- **채택하지 않은 이유:** 스키마에서 타입을 추론하고 검증 코드를 선언적으로 작성할 수 있지만, 현재 API 규모에 비해 새로운 의존성과 학습 비용이 추가된다. 우선 타입 가드로 검증하고 수동 검증 비용이 커지는 시점에 도입을 재검토하기로 했다.
