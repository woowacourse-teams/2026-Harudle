# ADR-0009: Expo와 WebView로 모바일 앱 시작

- **날짜:** 2026-10-26

## 📜 맥락 (Context)

하루들은 이미 React로 만든 웹사이트가 있다. 이 화면을 최대한 재사용하면서 React Native 기반의 iOS와 Android 앱을 만들려고 한다.

WebView는 앱 안에서 웹사이트를 보여 주는 화면이다. 웹은 일기 작성과 피드 같은 기존 화면을 담당하고, 앱은 사진첩 저장과 공유처럼 휴대폰 기능이 필요한 부분을 담당한다.

지금은 웹을 앱에서 안정적으로 사용할 수 있게 만드는 것이 우선이다. 웹 개발 도구 교체까지 동시에 진행하면 작업이 커지고, 문제가 생겼을 때 원인을 찾기 어려워진다.

## 🎯 결정 (Decision)

**Expo로 앱의 기본 틀을 만들고, WebView에서 배포된 하루들 웹사이트를 연다. 기존 웹의 빌드 도구는 유지한다.**

| 선택할 부분     | 결정                                                | 선택 이유                                                              |
| --------------- | --------------------------------------------------- | ---------------------------------------------------------------------- |
| 앱 개발 도구    | Expo                                                | 앱 개발에 필요한 기본 도구와 설정을 활용해 빨리 시작한다.              |
| 앱 안의 웹 화면 | `react-native-webview`로 배포된 HTTPS 주소 열기     | 현재 웹 배포를 활용하고, 웹 수정은 웹 배포로 반영한다.                 |
| 앱 코드 묶기    | Metro와 Expo 기본 Babel 설정                        | React Native와 Expo의 기본 구성을 사용해 설정 부담을 줄인다.           |
| 웹 코드 묶기    | 기존 Webpack과 Babel 유지                           | 현재 동작하는 웹과 테스트와 배포 설정을 재사용한다.                    |
| 화면 이동       | 하나의 WebView와 기존 React Router                  | 기존 웹의 화면 이동을 활용한다.                                        |
| 웹과 앱의 통신  | 필요한 기능부터 작은 `postMessage` 브리지로 연결    | 사진 저장과 공유 등 실제로 필요한 기능만 연결한다.                     |
| 앱 빌드         | 일상 개발은 로컬, 팀 배포와 릴리스는 EAS Build 활용 | 개발 중에는 직접 실행하고, 배포할 때는 빌드와 서명 관리 부담을 줄인다. |
| 패키지 관리     | 기존 pnpm Workspace 유지                            | `web/`, `mobile/`, `packages/` 경계를 활용한다.                        |

번들러는 여러 코드 파일을 실행하기 좋게 묶는 도구이고, Babel은 코드 문법을 실행 환경에 맞게 바꾸는 도구다. 웹 코드와 앱 코드는 따로 묶는다. EAS Build는 앱 빌드를 실행해 설치 가능한 앱 파일을 만드는 서비스다.

Expo의 Prebuild로 설정 파일에서 Android와 iOS 프로젝트를 생성한다. 반복해서 필요한 네이티브 설정 변경은 재생성해도 유지되도록 설정 파일이나 config plugin으로 관리한다. 개발과 검증은 자체 개발 앱인 Development Build를 기준으로 한다.

브리지는 웹에서 앱에 “사진을 저장해 줘”처럼 요청하는 통로다. 수신 데이터의 형식을 확인하고, 허용한 하루들 주소에서만 앱 기능을 사용할 수 있게 한다. 앱이 지원하는 기능을 먼저 확인하며, 오래된 앱에 기능이 없으면 대체 동작이나 안내를 제공한다. 웹과 앱이 실제로 공유하는 계약과 검증 코드만 공용 패키지로 추출한다.

기존 웹의 Emotion과 테스트 도구는 유지한다. EAS Update는 처음부터 도입하지 않고, 앱 쪽 JavaScript를 별도로 업데이트할 필요가 커지면 검토한다.

### 기존 ADR과의 관계

- ADR-0001의 pnpm Workspace 구조를 유지한다.
- ADR-0002의 웹 Babel 사용을 유지한다. 다만 WebView에서는 웹 화면을 앱 번들러로 다시 변환하지 않으므로, 웹과 앱의 변환 도구를 맞추기 위한 공용 설정은 강제하지 않는다. 웹 번들러나 변환기 교체는 별도로 검토한다.
- ADR-0007의 Access Token 메모리 저장, HttpOnly Refresh Cookie, CSRF 방어와 갱신 규칙을 유지한다. 모바일 로그인 후 WebView에 세션을 연결하는 구체적인 방법은 실기기 검증 후 별도로 결정한다.

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- 기존 웹 화면을 다시 만들지 않고 앱에서 재사용할 수 있다.
- 웹 화면 수정은 웹에 배포한 뒤 앱에서 다시 불러올 때 반영할 수 있다.
- 사진 저장과 공유처럼 필요한 부분부터 휴대폰 기능을 연결할 수 있다.
- 앱 전환과 웹 개발 도구 교체를 나눠 진행해 문제의 원인을 찾기 쉽다.

### 부정적 효과 / 감수할 점

- 인터넷과 웹 서버에 의존한다. 웹 장애나 느린 로딩은 앱에도 영향을 준다.
- 화면은 웹 기술로 동작하므로 네이티브 화면의 성능과 사용감을 자동으로 얻지는 못한다.
- Expo가 지원하는 라이브러리 버전과 설정 방식에 맞춰야 한다.
- EAS Build의 외부 서비스 의존성과 사용량에 따른 비용과 대기 가능성을 감수한다. Expo를 사용해도 직접 빌드하는 방식으로 바꿀 수 있다.
- 웹은 최신인데 앱은 오래된 상황이 생긴다. 브리지 기능의 지원 여부와 호환성을 관리해야 한다.
- 웹 빌드 속도 개선은 미룬다. WebView 전환 후 불편이나 성능 문제를 확인하면 다시 검토한다.

## 🔄 대안 (Alternatives Considered)

| 대안                            | 얻을 수 있는 것                             | 지금 선택하지 않은 이유                                                                            |
| ------------------------------- | ------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| React Native를 직접 설정        | Android와 iOS 설정을 세밀하게 제어          | 초기 설정과 유지보수 부담보다 기존 도구로 빠르게 시작하는 이점이 크다.                             |
| 앱 번들러로 Re.Pack 사용        | 큰 앱의 코드를 나눠 내려받는 등 복잡한 구성 | 현재의 작은 WebView 앱에서는 필요성이 낮고 관리할 설정이 늘어난다.                                 |
| 웹을 Vite 또는 Rsbuild로 교체   | 개발 편의와 빌드 속도 개선 가능성           | 환경변수, 정적 파일, 테스트 등의 설정을 옮기고 확인해야 한다. 앱 전환과 별도 작업으로 검토한다.    |
| 웹 파일을 앱 안에 포함          | 기본 화면 파일을 인터넷 없이 로드           | 웹 수정 반영과 주소와 쿠키 처리가 복잡해진다. 서버 데이터까지 오프라인으로 쓸 수 있는 것도 아니다. |
| 처음부터 브리지 라이브러리 사용 | 비동기 요청과 응답 처리를 편하게 작성       | 우선 필요한 기능부터 작게 연결하고, 직접 관리하는 비용이 커질 때 검토한다.                         |
| 자체 CI에서 앱 빌드와 배포      | 빌드 환경을 직접 통제                       | 초기에는 서명과 iOS 빌드 환경을 관리하는 부담을 줄인다.                                            |

## 🔍 구현 전 먼저 확인할 것

1. **카카오 로그인:** 로그인 후 앱으로 돌아왔을 때 WebView에서도 세션이 이어지는지 확인한다. 외부 브라우저와 WebView가 쿠키를 자동으로 공유한다고 가정하지 않는다.
2. **이미지 저장과 공유:** 기존 웹의 다운로드와 클립보드 동작을 확인하고, 앱에서는 사진첩 저장과 공유 기능으로 연결한다.
3. **휴대폰 사용 흐름:** iOS와 Android 실기기에서 뒤로 가기, 키보드, 화면 가장자리 여백, 앱 재실행 후 로그인 복구를 확인한다.
4. **구버전 앱:** 최신 웹에서 오래된 앱에 없는 기능을 요청해도 화면 전체가 실패하지 않는지 확인한다.
