# ADR-0001: Web·Mobile 확장을 고려한 pnpm Workspace 구조 채택

- **날짜:** 2026-08-07

## 📜 맥락 (Context)

현재 프론트엔드 개발은 Web 중심으로 진행하지만, 이후 React Native 기반 Mobile 애플리케이션과 두 플랫폼이 함께 사용하는 공용 패키지를 추가할 예정이다.

Web과 Mobile을 서로 독립된 저장소나 패키지로만 관리하면 도메인 타입, API 계약, 유효성 검증과 같은 코드를 중복해서 관리하게 될 수 있다. 반대로 모든 의존성을 하나의 패키지에 모으면 플랫폼별 라이브러리의 경계가 흐려지고, 한 애플리케이션에만 설치된 패키지를 다른 애플리케이션에서 암묵적으로 사용하는 문제가 발생할 수 있다.

따라서 하나의 저장소에서 Web, Mobile, 공용 코드를 함께 관리하면서도 각 애플리케이션의 의존성 경계를 명시할 수 있는 Workspace 구조가 필요했다.

패키지 매니저로는 npm, Yarn Berry, pnpm을 검토했다. 모두 Workspace를 지원하지만 React Native 도구와의 `node_modules` 호환성, 내부 패키지 연결 방식, 의존성 격리 수준을 함께 고려해야 했다.

## 🎯 결정 (Decision)

프론트엔드를 pnpm Workspace로 구성하고 다음 패키지 경계를 사용한다.

```text
frontend/
├─ web/        # Web 애플리케이션
├─ mobile/     # React Native 애플리케이션
└─ packages/   # Web과 Mobile이 공유하는 플랫폼에 비종속적인 패키지
```

- Web과 Mobile에서만 각자 사용하는 라이브러리는 각 애플리케이션의 `package.json`에 선언한다.
- 두 플랫폼이 실제로 공유하는 코드는 `packages/*` 아래의 독립 패키지로 추출한다.
- Workspace 내부 패키지를 참조할 때는 `workspace:` 프로토콜을 사용하여 외부 레지스트리 패키지와 구분하고 로컬 패키지 연결을 명시한다.
- 공용 패키지는 DOM이나 React Native API 같은 특정 플랫폼 구현에 직접 의존하지 않는 것을 기본 원칙으로 한다.

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- Web, Mobile, 공용 코드의 소유 위치와 의존성 경계를 저장소 구조로 표현할 수 있다.
- 공용 타입과 도메인 로직을 패키지로 분리하여 플랫폼 간 중복 구현을 줄일 수 있다.
- 각 패키지는 자신이 직접 선언한 의존성만 사용하게 되어 암묵적인 의존성과 유령 의존성을 줄일 수 있다.
- `workspace:` 프로토콜을 통해 내부 패키지를 외부 패키지와 혼동하거나, 실수로 레지스트리 버전을 참조하는 문제를 방지할 수 있다.
- 하나의 Lockfile로 프론트엔드 패키지의 의존성 해석 결과를 함께 관리할 수 있다.

### 부정적 효과 / 감수할 점

- Web만 존재하는 초기 단계에도 Workspace와 패키지 경계를 관리하는 비용이 발생한다.
- 공용화 대상과 플랫폼 전용 코드의 경계를 지속적으로 판단해야 한다.
- pnpm의 의존성 격리는 Hoisting을 전제로 하는 일부 도구나 라이브러리와 호환성 문제가 발생할 수 있다.
- Mobile 도구가 요구하는 모듈 해석 방식에 따라 pnpm 설정이나 별도의 호환성 구성이 필요할 수 있다.
- 여러 패키지를 동시에 검사하고 빌드하기 위한 공통 스크립트와 CI 구성이 추가로 필요하다.
- 공용 패키지를 지나치게 일찍 추출하면 아직 같지 않은 Web과 Mobile 요구사항이 하나의 추상화에 결합될 수 있다.

## 🔄 대안 (Alternatives Considered)

### 대안 1: Web과 Mobile을 별도 저장소로 관리

- **채택하지 않은 이유:** 플랫폼별 배포와 권한을 독립적으로 관리할 수 있지만, 공용 타입과 도메인 로직의 변경을 여러 저장소에 걸쳐 동기화해야 한다. Web과 Mobile의 공용 코드 재사용이 예정되어 있어 하나의 Workspace가 더 적합하다고 판단했다.

### 대안 2: npm Workspace 사용

- **채택하지 않은 이유:** 별도의 패키지 매니저 도입 없이 Workspace를 사용할 수 있지만, 의존성 격리와 내부 패키지 연결을 더 명시적으로 관리하고 디스크 사용량을 줄일 수 있는 pnpm의 방식을 선택했다.

### 대안 3: Yarn Berry Workspace와 Plug'n'Play 사용

- **채택하지 않은 이유:** 엄격한 의존성 관리와 Workspace 기능을 제공하지만, Plug'n'Play는 일반적인 `node_modules` 구조를 가정하는 React Native 및 주변 도구와 추가적인 호환성 설정이 필요할 수 있다. React Native 확장을 고려해 `node_modules` 호환성을 유지하는 pnpm을 선택했다.

### 대안 4: 모든 프론트엔드 코드를 하나의 패키지에서 관리

- **채택하지 않은 이유:** 초기 설정은 단순하지만 플랫폼별 의존성과 공용 코드의 경계가 드러나지 않는다. Mobile 추가 시 구조를 다시 분리하는 비용이 커질 수 있다고 판단했다.
