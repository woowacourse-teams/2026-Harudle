# ADR-0004: 도메인 로직과 React UI 폴더 분리 및 Co-location 적용

- **날짜:** 2026-08-11

## 📜 맥락 (Context)

프로젝트의 본격적인 개발을 시작하기에 앞서, 향후 여러 페이지에서 같은 도메인이 공통으로 사용될 것을 대비해 UI와 도메인 로직이 엮이지 않도록 미리 분리해둘 필요가 있었다.

또한, 개발 과정에서 함께 수정될 가능성이 높은 컴포넌트, Custom Hook, State를 최대한 가까이 두어 코드를 찾기 쉽게 만들어야 했다. 뚜렷한 기준 없이 개발을 시작하면 관련 코드들이 여러 곳에 흩어져 유지보수와 코드 추적이 힘들어질 것이 자명하므로, 개발 전에 폴더 구조 기준을 확립하고자 했다.

## 🎯 결정 (Decision)

도메인 로직과 React UI 코드를 명확히 분리하고, UI 관련 코드는 사용되는 Page 폴더에 최대한 Co-location 시키는 구조를 채택합니다.

- **`domain/`**: 특정 페이지에 결합되지 않는 도메인 관련 코드 (API 요청, 도메인 타입, 비즈니스 유틸 함수 등)
- **`pages/`**: 해당 페이지에서만 독립적으로 사용하는 컴포넌트, Hook, State, UI 로직 보관. 단, 복잡도를 낮추기 위해 페이지 폴더 내 하위 디렉토리는 **최대 1 depth까지만 허용**합니다.
- **`shared/`**: 여러 페이지에서 공통으로 사용되는 UI 컴포넌트 및 범용 유틸 함수 보관.

**구조 예시:**

```md
src/
├─ app/
├─ domain/
│ ├─ diary/
│ └─ user/
├─ pages/
│ ├─ home/
│ ├─ diary-create/
│ └─ diary-detail/
└─ shared/
```

## ⚖️ 결과 (Consequences)

### 긍정적 효과

- 도메인(비즈니스) 로직과 UI가 분리되어, 디자인이 변경되더라도 도메인 로직을 안전하게 재사용할 수 있다.
- 관련 코드가 한 페이지 폴더에 모여 있어 코드를 읽을 때 빠르게 코드를 탐색하고 수정할 수 있습니다.
- depth를 1로 강제함으로써 폴더 트리가 지나치게 깊어져 발생하는 파일 탐색의 피로도를 방지합니다.

### 부정적 효과

- 특정 페이지가 매우 복잡해져 내부 컴포넌트가 많아질 경우, 1 depth 제한으로 인해 해당 페이지 폴더 안에 파일이 지나치게 많아질 수 있다.
- 새로운 컴포넌트를 만들 때 이것이 특정 `pages/`에 속하는지, 아니면 `shared/`로 가야 하는지 초기에 판단하는 리소스가 생긴다.
- shared에 UI, 유틸 등 온갖 로직이 들어올 수 있다.

## 🔄 대안 (Alternatives Considered)

- **대안 1: 역할별 폴더 분리 (`components/`, `hooks/`, `api/`)**
  - **채택하지 않은 이유:** 특정 페이지를 수정할 때마다 세 개의 폴더를 모두 돌아다녀야 하므로 Co-location 원칙에 위배되어 유지보수가 불편하다.

- **대안 2: `pages/` 내 무제한 depth 허용**
  - **채택하지 않은 이유:** 폴더를 자유롭게 나누면 정리는 잘 되는 것처럼 보이나, 결국 파일을 찾기 위해 여러 폴더를 클릭해 들어가야 하는 인지 부하가 발생하므로 최대 1 depth 제한을 두는 것으로 정했다.
