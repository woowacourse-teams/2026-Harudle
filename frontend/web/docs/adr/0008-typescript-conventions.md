# ADR-0008: TypeScript 컨벤션

- **날짜:** 2026-09-27

## 📜 맥락 (Context)

타입 선언과 외부 값의 처리 기준을 통일해 코드를 읽는 사람이 의도를 쉽게 파악하고, 검증되지 않은 값이 내부 로직으로 전달되는 것을 막는다.

## 🎯 결정 (Decision)

### 1. 기본은 `interface`, 유니온,리터럴은 `type`

- 객체, Props, API 요청, 응답 타입은 `interface`로 선언한다.
- `type` 키워드는 유니온이나 리터럴 타입을 선언할 때만 사용한다.
- 객체 타입을 확장할 때는 교차 타입(`&`)보다 `interface extends`를 우선한다.

객체의 구조와 확장 관계를 같은 방식으로 표현해 선언 방식을 고민하는 비용을 줄인다. 제한된 값이나 여러 상태의 조합은 유니온,리터럴로 표현한다.

```ts
type Role = 'USER' | 'ADMIN';

interface User {
  readonly id: string;
  role: Role;
}

interface UserProfile extends User {
  name: string;
}
```

### 2. 외부 값은 `unknown`으로 받고 좁혀서 사용한다

- API 응답, 저장소에서 파싱한 값, 라우터 state 등 타입을 보장할 수 없는 외부 값은 반드시 `unknown`으로 받는다.
- 타입 가드로 필수 필드, 중첩 구조, 배열 원소와 허용된 리터럴을 확인한 뒤 사용한다. 길이,범위 등 기능에 필요한 조건도 함께 검증한다.
- 검증하지 못한 값은 `unknown`으로 유지한다. `as T`로 검증을 대신하지 않는다.
- 검증을 통과한 값은 내부에서 같은 구조 검사를 반복하지 않는다. 저장소나 네트워크에서 다시 읽으면 다시 검증한다.

TypeScript의 타입 선언은 런타임 데이터를 검사하지 않는다. 외부 경계에서 실제 값을 확인해야 내부 코드가 선언된 타입을 믿고 사용할 수 있다.

### 3. 에러도 검증한 뒤 사용한다

- `catch`로 받은 값은 `unknown`으로 다루고, `instanceof Error`나 타입 가드로 좁힌 뒤 속성에 접근한다.
- API 실패 응답은 `isProblemDetails`로 검증한 뒤 `RequestError`로 변환한다.
- 예상한 오류 형식이 아니면 기능별 기본 오류로 처리한다.

던져진 값이나 실패 응답이 항상 예상한 에러 객체라는 보장은 없다. 오류 처리 과정에서도 검증되지 않은 속성에 접근하지 않는다.

### 4. `any`에는 반드시 이유를 주석으로 남긴다

- `any`는 기본적으로 사용하지 않는다. 우선 `unknown`, 제네릭 또는 구체적인 타입으로 표현한다.
- 불가피하게 사용한다면 해당 코드 바로 위에 **왜 `any`가 필요하고 다른 타입으로 표현하기 어려운지** 적는다.
- ESLint 예외가 필요하면 해당 줄의 `@typescript-eslint/no-explicit-any` 규칙만 해제하고, 예외 주석에 이유를 함께 적는다.

`any`는 타입 검사를 우회하므로 사용 범위를 최소화하고, 다음 사람이 예외의 필요성을 판단할 수 있게 한다.

### 5. 읽기 전용 값은 타입에도 드러낸다

- 변경하면 안 되는 속성은 `readonly`로 선언한다.
- 상수 객체와 배열은 `as const`를 사용해 리터럴과 읽기 전용 속성을 유지한다.
- 읽기 전용 배열을 받는 인자는 `readonly T[]` 또는 `ReadonlyArray<T>`로 선언한다.

`const`만으로는 객체 속성이나 배열 원소의 변경을 막을 수 없다. 읽기 전용 의도를 타입에 표현해 실수로 수정하는 코드를 컴파일 단계에서 발견한다. `readonly`와 `as const`는 런타임에서 객체를 동결하지 않는다.

### 6. 이벤트 핸들러는 필요한 입력을 명확히 한다

- JSX 인라인 핸들러의 매개변수는 타입 추론을 사용한다.
- 분리한 DOM 핸들러에는 `React.ChangeEvent<HTMLInputElement>`처럼 이벤트와 대상 요소를 지정한다.
- DOM 이벤트가 필요 없는 콜백은 `() => void`, `(value: T) => void`처럼 필요한 값만 받는다.

핸들러의 입력을 정확히 표현해 잘못된 요소 접근을 막고, 컴포넌트가 불필요하게 DOM 이벤트에 의존하지 않게 한다.

### 7. 함수의 반환 타입은 반드시 명시한다

- 함수 선언, 화살표 함수, 콜백 모두 실제 반환값에 맞는 반환 타입을 명시한다.
- 반환값이 없으면 `void`, 비동기 함수는 `Promise<T>` 또는 `Promise<void>`로 선언한다.
- 값이 없을 수 있다면 `null`,`undefined`를 반환 타입에 포함하고, 타입 가드는 `value is T`로 선언한다.

함수의 출력 계약을 구현부를 읽지 않고도 알 수 있게 하고, 구현 변경으로 의도하지 않은 값이 반환되면 타입 검사에서 발견한다.

### 8. 상태별 데이터는 구분된 유니온으로 표현한다

- 상태마다 필요한 데이터가 다르면 `status` 같은 구분된 속성을 가진 유니온으로 선언한다.
- 성공 데이터와 실패 에러처럼 상태에 종속된 필드를 하나의 객체에 선택적 속성으로 나열하지 않는다.

상태를 확인하면 필요한 데이터도 함께 좁혀지게 하고, 성공인데 데이터가 없는 것처럼 유효하지 않은 조합을 타입 단계에서 막는다.

### 9. 허용된 값이 정해져 있으면 리터럴 유니온으로 제한한다

- 역할, 생성 상태, 월처럼 가능한 값이 정해진 경우 `string`,`number` 대신 리터럴 유니온을 사용한다.

허용되지 않은 값과 오타를 컴파일 단계에서 발견하고, 호출부가 가능한 값을 타입만으로 파악할 수 있게 한다.

### 10. 기존 타입과 라이브러리 타입을 재사용한다

- 같은 의미의 타입을 중복 정의하지 않고 기존 타입을 재사용한다.
- 일부 속성이나 함수 시그니처가 필요하면 `Pick`, `Parameters`, `typeof` 등으로 추출한다.
- 라이브러리가 제공하는 타입은 직접 다시 작성하지 않고 가져다 쓴다.

원본 타입이 바뀌었을 때 사용하는 곳에도 변경이 반영되게 해, 같은 계약을 여러 곳에서 따로 관리하는 일을 줄인다.

### 11. 매개변수 사이의 관계를 타입으로 연결한다

- 한 매개변수가 다른 매개변수의 타입이나 전달 필요 여부를 결정하면 제네릭, 매핑 타입 또는 튜플로 그 관계를 표현한다.

이벤트 이름마다 다른 속성을 받는 함수처럼, 각 인자는 유효해도 함께 전달하면 잘못된 조합이 되는 호출을 막는다.

### 12. 린트를 통해 규칙을 강제한다

다음 ESLint 규칙으로 컨벤션을 검사한다. 규칙명의 `@typescript-eslint/` 접두사는 생략했다.

| 기준                              | ESLint 규칙                                                                                                   |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 객체는 `interface`로 선언         | `consistent-type-definitions`                                                                                 |
| `any`가 내부로 전파되는 것 방지   | `no-unsafe-assignment`, `no-unsafe-argument`, `no-unsafe-call`, `no-unsafe-member-access`, `no-unsafe-return` |
| `!`로 존재 여부를 단언하지 않기   | `no-non-null-assertion`                                                                                       |
| Promise 오류를 `unknown`으로 받기 | `use-unknown-in-catch-callback-variable`                                                                      |

타입 기반 규칙과 `no-non-null-assertion`은 `src`와 `jest.setup.ts`에 적용하며, `pnpm lint`와 PR CI에서 검사한다. 타입 가드의 검증 내용과 예외 사유의 타당성은 테스트와 리뷰로 확인한다.

## ⚖️ 결과 (Consequences)

타입 선언 방식을 통일해 코드를 읽고 작성할 때의 판단 비용을 줄인다. 반환 타입과 상태 간 관계를 명시해 잘못된 사용을 컴파일 단계에서 발견하고, 외부 값은 타입 가드로 검증해 예상하지 못한 데이터가 내부 로직으로 전달되는 것을 막는다.

대신 타입과 검증 코드를 함께 작성하므로 코드가 길어지고, 데이터 구조가 변경되면 타입 정의와 타입 가드도 함께 수정해야 한다. 타입 가드가 잘못된 입력을 거부하는지 테스트하는 비용도 필요하다. 작성량과 유지보수 비용이 늘더라도 오류를 사용 지점보다 앞서 발견하는 것을 우선한다.
