# EC2 PostgreSQL 전환 뒤 모니터링 확인 순서

> 이 문서는 서버 전환과 후속 작업의 적용 이력입니다. Prod 대시보드의 최종 구성과 결정 이유는 [10월 30일 ADR](2026-10-30_prod-dashboard-cleanup.md)에 모았습니다. 아래의 중간 단계보다 새 ADR을 우선합니다.

- 날짜: 2026-10-29
- 범위: Dev와 Prod CloudWatch 대시보드, Dev 앱 경보 두 개, 저장소 운영 안내

## 무엇을 바꾸나

10월 23일 전환 기록에 따라 앱 서버와 DB 서버를 따로 구분한다. 현재 서버 ID와 데이터 EBS ID는 `../targets.json`에서 관리한다. AWS에 저장한 대시보드와 경보는 팀원이 같은 계정과 리전에서 조회할 때 함께 보인다. Git 커밋이나 앱 배포만으로 AWS 설정이 바뀌지는 않는다.

대시보드는 실패와 응답 지연을 먼저 보여준다. 서버 CPU와 메모리는 그 원인을 찾을 때 본다. 기존 그래프의 계산식과 로그 검색, 연결된 경보는 유지한다. 초기 정리에서는 별도 지표 수집이나 새 경보를 추가하지 않았다. 이후 승인된 Prod 백업 감시 추가는 아래에 기록한다.

| 구역 | Dev | Prod |
| --- | --- | --- |
| 맨 위 카드 | 5xx 비율, 일반 API P95, 생성 실패, 앱 DB 연결 대기, DB 데이터 여유 공간, GC 정지 | 5xx 비율, 일반 API P95, 생성 실패, 앱 DB 연결 대기, DB 데이터 여유 공간, 최근 24시간 내 백업 성공 여부 |
| 서비스 확인 | 오류와 알림, API 속도와 요청 수, 생성 작업 | 오류와 알림, API 속도와 요청 수, 생성 작업 |
| DB 확인 | 앱 연결 대기와 시간 초과, 데이터 저장 공간 | 앱 연결 대기와 시간 초과, 데이터 저장 공간 |
| 원인 확인 | Java 메모리와 GC, DB 자원, 앱 자원 | DB 자원, 앱 자원, Java 메모리 |
| 마지막 확인 | 상세 로그와 빌드 로그 | 상세 로그 |

일반 API P95는 서버에서 처리를 마친 요청의 시간이다. 요청 수와 함께 확인한다. Dev와 Prod의 맨 위 5xx 비율 카드는 대시보드에서 선택한 전체 시간의 5xx 응답 수를 전체 HTTP 완료 수로 나눈다. 두 환경의 생성 실패 카드는 같은 선택 시간에 실패로 확정된 생성 건수를 더한다. 선택 시간에 요청이나 실패 데이터가 없으면 값이 비어 있을 수 있다. 백엔드 HTTP 응답 수 그래프는 선택한 시간 범위에 맞춰 집계 간격을 조절한다. 기존 HTTP 카운터에는 헬스체크가 포함된다. 새 API 응답 시간 로그에서는 헬스체크를 제외한다.

DB 데이터 여유 공간은 `/srv/harudle/db-data`를 대상으로 한다. GiB로 변환한 값은 그래프로 표시해 단위를 분명히 한다. EBS 지연은 밀리초다. 다른 DB 서비스에서 쓰던 초 단위 기준을 그대로 옮기지 않는다.

## 경보는 어떻게 바꾸나

`harudle-dev-ec2-cpu-high`와 `harudle-dev-ec2-status-check`의 `InstanceId`만 이전 `i-0f899d8ec0a6fb988`에서 현재 앱 `i-08ff5dddb7ac94f5c`로 바꾼다. 기준값, 평가 주기, 누락 데이터 처리와 SNS 연결은 그대로 둔다. 적용한 두 경보의 설정은 `../ec2-alarms.dev.json`에 보관한다.

이 파일은 AWS CLI의 `put-metric-alarm` 입력 형식이다. 실제 설정을 다시 조회하고 차이를 검토한 뒤 필요한 경보만 적용한다. 앱 배포에서 자동 실행하지 않는다.

## 위험을 줄이는 적용 범위

앱과 DB 컨테이너, Agent를 재시작하지 않는다. DB 데이터, 백업 정책, 방화벽, IAM 권한도 변경하지 않는다. Agent 설정 파일은 기존 전환 커밋에서 가져오되, 서버에 재적용하지 않는다. 현재 Prod 앱의 호스트 지표는 `Harudle/Prod`, 나머지 세 서버의 호스트 지표는 `CWAgent`에서 조회한다.

SSH 직접 접속은 시간 초과로 실패했다. CloudWatch 값 확인과 서버 내부 Agent 실행 상태 확인은 구분해 기록한다. CloudShell도 환경 생성 권한 부족으로 사용할 수 없어 권한을 변경하지 않았다.

## 아직 수집하지 않는 항목

PostgreSQL 직접 접속 확인, 전체 연결 수, 백업 실행 실패와 예약 누락 알림, WAL 전송 상태는 별도로 준비해야 한다. Dev 백업 감시는 미수집이다. 앱 연결 대기 0이나 EC2 상태 검사 0을 이 항목의 정상 확인으로 사용하지 않는다. 대시보드에 미수집 안내를 둔다.

Prod의 백업 일정과 복원 시험은 10월 23일 작업 기록에 있다. 이 기록이 오늘의 백업 성공을 뜻하지는 않는다. 이후 SSM으로 현재 정보를 읽고 아래 감시를 적용했다. 알림 기준은 추가하지 않았다.

## 검증

대시보드 원본과 두 경보 원본을 적용 전에 보관한다. 대시보드는 기존 지표 계산과 로그 검색, 경보 목록이 모두 남아 있는지 비교한다. 위젯이 겹치지 않고 반복 생성해도 중복되지 않는지 검사한다. 저장 후 새로고침하고 소스를 다시 읽어 입력한 내용과 비교한다. 경보는 원본과 비교해 `InstanceId` 외의 값이 바뀌지 않았는지 확인한다.

## 적용 결과

2026-10-29에 두 대시보드와 Dev 경보 두 개를 저장했다. 경보 JSON을 대조해 `InstanceId`만 바뀐 것을 확인했다. 대시보드는 기존 지표, 계산식, 로그 검색과 경보 목록을 보존했다. 원본 54개였던 Dev는 요약과 구역 안내를 포함해 63개, 원본 51개였던 Prod는 60개가 됐다.

저장 후 소스를 다시 읽어 로컬에서 생성한 배치와 일치하는지 확인했다. 최근 5분을 대상으로 네 EC2의 `mem_available_percent`를 조회했고 각 서버에서 표본 4개를 확인했다. 조회용 임시 배치는 AWS에 저장하지 않고 폐기했다. 이 결과는 최근 수집이 동작한다는 뜻이며, 서버 재부팅 후 자동 실행이나 모든 Agent 설정을 직접 확인한 결과는 아니다.

Dev 경보 두 개는 변경 후 정상 상태로 전환됐다. 모니터링 로컬 테스트 66개와 공백 검사를 통과했다.

## Prod 백업 감시 추가

사용자 요청에 따라 Prod DB에 별도 확인 작업을 설치했다. `pgbackrest info`의 유효한 성공 백업 완료 시각으로 `BackupAgeSeconds`를 계산하고, 조회 결과를 `BackupInfoCheckSuccess`로 보낸다. 주기는 5분이며 기존 Python boto3와 IAM 역할을 사용했다. 조회 실패 때 경과 시간을 0으로 만들지 않는다.

기존 백업 서비스와 타이머 파일의 SHA-256 및 DB 컨테이너 시작 시각을 전후 비교해 같음을 확인했다. 백업을 수동 실행하지 않았고, DB와 앱 및 Agent를 재시작하지 않았다. 새 감시 서비스의 실행 성공과 CloudWatch 지표 전송을 확인했다. 설치와 상태 확인은 모니터링 README를 따른다. WAL 전송과 실제 복원 검증, 새 경보는 이번 범위에 포함하지 않았다.

Prod 대시보드는 백업 지표 추가 후 61개 위젯이다. 저장 후 다시 읽은 위젯이 생성 결과와 같고, 겹침과 중복이 없음을 확인했다. 수집기와 배치 검증을 포함한 로컬 테스트 72개를 통과했다.

## 백업 확인 주기 수정

사용자 선택에 따라 5분 확인을 중단하고 매일 한국 시간 오전 5시에 한 번 확인하도록 바꿨다. 기존 백업은 오전 4시에 그대로 실행한다. 수집기는 `BackupAgeSeconds` 대신 `BackupWithin24Hours`를 전송한다. 확인 시점에서 성공 백업 완료 후 24시간 이내이면 1, 더 오래됐거나 조회에 실패하면 0이다. `BackupInfoCheckSuccess`는 조회 자체의 성공 여부를 구분하기 위해 유지한다.

맨 위에는 최근 24시간 안에 수집된 확인 결과를 표시한다. 새 결과가 없을 때 1로 채우지 않는다. 오전 5시에도 백업 중이면 별도 확인이 필요하다. 서버 중단으로 놓친 확인은 다시 켜진 뒤 한 번 실행한다. 백업 실행 일정과 DB는 변경하지 않았다. 24시간 경계값과 조회 실패, 일일 예약을 포함한 로컬 테스트 73개를 통과했다.

서버의 일일 예약과 CloudWatch 실제 수신 값 1을 확인했고, Prod 대시보드에 정상 값 1이 보이는 것을 확인했다. 최종 저장 소스가 생성 결과와 일치하며 기존 지표와 로그 검색, 경보 설정은 보존했다. 다음 오전 5시의 실제 예약 실행까지 기다린 검증은 아니다.

## 5xx 비율 그래프 정리

별도의 5분 비율 그래프는 요청이 적을 때 0으로 표시되어 오류가 없다는 뜻으로 오해할 수 있어 Dev와 Prod 대시보드에서 제거했다. 두 환경은 선택한 시간 전체의 비율 카드를 유지한다. 시간대별 5xx 발생 건수는 두 대시보드의 백엔드 HTTP 응답 수 그래프에서 계속 확인한다. 지표 수집과 알람은 바꾸지 않았다.

## Prod 생성 그래프 정리

2026-10-29에 Prod 대시보드의 생성 실행 평균 시간과 실행 수 그래프를 유지하고, 두 그래프의 기본 기간을 1분으로 설정했다. 대시보드의 `periodOverride`는 `auto`라서 CloudWatch가 선택한 시간 범위에 맞춰 표시 간격을 조정한다. Gemini 관측 토큰 그래프는 Prod 화면에서만 제거했다. 토큰 수집 설정은 바꾸지 않았다. 정리와 Gemini 요청 실패 그래프는 유지했다. Dev 대시보드는 수정하지 않았다.

추가 정리에서 Prod의 생성 실행 수 그래프를 제거했다. 생성 실행 평균 시간과 정리 및 Gemini 요청 실패 그래프만 나란히 표시한다. 실행 수 지표 수집과 기존 경보는 유지하며, Dev 대시보드는 수정하지 않았다.

Prod의 DB 연결 획득 시간은 원본 초 값을 1,000배 한 밀리초 값인데도 세로축에 초 단위가 붙어 있었다. 세로축을 `밀리초 (ms)`로 명시하고 자동 단위 표시를 껐다. 저장 후 새로고침한 화면에서 최고점 약 29.7이 밀리초로 표시되는 것을 확인했다. 대시보드 준비 스크립트도 신규 및 기존 Prod 위젯에 같은 표시를 적용한다. 관련 테스트 18개와 Prod 생성 결과 및 Dev 설정 유지 검증을 통과했다. 수집과 경보는 변경하지 않았다.

2026-10-30에 Prod의 `DB 연결 풀: 대기 요청 최댓값` 그래프를 제거했다. 같은 대기 지표와 연결 시간 초과 횟수를 함께 보여주는 `DB 연결 대기와 시간 초과` 그래프는 유지한다. 지표 수집과 경보 및 Dev 대시보드는 변경하지 않았다.

Prod의 DB EC2 구역은 CPU와 여유 메모리 숫자 위젯을 모두 유지한다. 첫 행에 CPU 숫자, 여유 메모리 숫자, CPU 사용률 그래프를 각각 6, 6, 12칸 너비로 배치하고 높이를 6칸으로 맞췄다. 대시보드 준비 스크립트에도 숫자 위젯 크기를 반영했다. 관련 테스트 18개와 첫 행 배치 검증을 통과했다. Dev는 수정하지 않았다.

Prod의 앱 EC2 구역은 CPU, 여유 메모리, Swap 사용률, 기본 디스크 사용률 숫자 위젯을 각각 너비 6칸과 높이 4칸으로 줄여 첫 행에 배치했다. 상세 그래프와 서버 상태 검사, CPU 크레딧, 네트워크 지표는 유지한다. 네트워크는 보조 진단 항목으로 본다. 저장 후 새로고침한 화면에서 네 숫자 위젯의 같은 행 배치를 확인했고, 준비 스크립트에도 반영했다. 관련 테스트 18개와 Prod 배치 및 Dev 너비 유지 검증을 통과했다. 지표 수집과 경보는 변경하지 않았다.

Prod의 EC2 Network 그래프는 바이트 합계를 1,000,000으로 나눠 MB로 표시한다. 세로축은 `전송량 (MB, 구간 합계)`로 명시하고 0부터 시작한다. 수신은 파란색, 송신은 주황색이며 범례에도 MB를 표시한다. 기존 Sum 집계와 기본 300초 기간 및 자동 기간 조정은 유지한다. 준비 스크립트와 README에도 반영했으며 관련 테스트 18개를 통과했다. Dev와 지표 수집 및 경보는 변경하지 않았다.

Prod의 Java 힙과 RSS 그래프는 이미 MiB로 변환한 값에 자동 Bytes 단위가 붙어 있었다. 두 세로축을 `메모리 (MiB)`로 명시하고 자동 단위 표시를 껐다. 원본 지표와 계산식은 유지한다. 준비 스크립트와 README에도 반영했고 관련 테스트 18개 및 신규/기존 Prod 위젯과 Dev 설정 유지 검증을 통과했다.

## Prod API 응답 시간을 경로별로 확인

기존 Prod API 그래프는 전체, 일반 API, 일기 생성의 평균, P95, P99를 한 그래프에 겹쳐 표시했다. 요청 수는 오른쪽 축에 같이 보여 선이 많고, 어느 API 경로가 느린지 바로 알기 어려웠다. 일반 API P95 요약 카드와 전체 요청 RPS는 유지한다.

상세 구역은 일반 API와 일기 생성 API를 나눈 뒤, 각 경로마다 P95 선 하나를 표시한다. 요청 수는 별도 RPS 그래프에서 본다. CloudWatch가 선택한 시간 범위에 맞춰 그래프 간격을 정하므로 고정 5분 묶음은 사용하지 않는다.

앱 로그의 `apiRoute`에는 HTTP 방식과 Spring 경로 패턴을 기록한다. 예를 들어 실제 `feedId` 대신 `GET:/api/v1/feeds/{feedId}`를 사용한다. 경로를 찾지 못한 요청은 공통 `<unmatched>`로 묶고 원본 주소를 저장하지 않는다. Prod 로그 필터는 `ApiGroup`과 `ApiRoute`를 지표 차원으로 사용한다. 일반 API 그래프는 선택 기간에 P95가 가장 높았던 경로 5개만 표시하고, 일기 생성 그래프는 요청이 있는 모든 경로를 표시한다. 그래프에 보이는 선만 줄어들며, 경로별 사용자 정의 지표 생성 수는 줄지 않는다. Dev 대시보드와 Dev 로그 필터는 이 변경에서 수정하지 않는다.

## Prod 상세 로그 검색 수정

2026-10-30에 Prod 상세 로그 검색 세 곳을 수정했다. OAuth는 `event` 필드 검색에 메시지 검색과 추출을 추가했다. 최근 24시간의 기존 오류 4건에서 제공자와 실패 이유가 표시되는 것을 확인했다. 앱 로거 변경이나 재배포는 필요하지 않다.

외부 실패 추이는 `provider`, `operation`, `failureType`을 함께 묶어 시계열로 표시할 수 없었다. 시간과 실패 수만 집계하도록 수정했다. 같은 조회 범위에서 기존 실패 1건을 확인했다. 세부 분류는 옆의 실패 로그에서 확인한다. 기존 `bin(5m)` 간격은 유지하며, 조회 범위는 대시보드 시간 선택을 따른다.

Nginx 검색은 정상 JSON 로그의 `upstreamConnectSeconds` 같은 이름을 오류로 잘못 잡고 있었다. 502와 504 응답, 실제 오류 등급의 upstream 또는 시간 초과 로그만 검색하도록 좁혔다. 최근 24시간에서 502 응답 48건과 상태 코드가 없는 오류 로그 54건이 조회됐고, 정상 200 응답은 결과에서 제외됐다. 같은 요청의 응답과 오류가 각각 기록될 수 있으므로 102건을 서로 다른 실패 요청 수로 해석하지 않는다.

Prod 대시보드에 저장하고 준비 스크립트와 운영 안내에도 반영했다. 관련 테스트 19개를 통과했다. Dev와 앱 실행 코드, 수집기 및 경보는 변경하지 않았으며, 장애를 직접 발생시키는 시험은 하지 않았다.

후속 화면 정리에서 `External Failure Trend`를 제거했다. `Gemini & S3 Failures` 표는 상세 로그 구역의 첫 행에서 너비 24칸 전체를 사용한다. 실패 횟수만 표시하는 대신 기존 상세 로그의 발생 시간, 제공자, 작업, 실패 유형과 응답 코드 등을 넓게 확인한다. 로그 검색 조건과 수집 및 경보는 유지한다. 같은 배치를 준비 스크립트에도 반영했고 관련 테스트 20개를 통과했다. Dev는 변경하지 않았다.

Prod 상단 카드 이름을 `백엔드 5xx 비율 (선택 기간)`, `DB 백업 상태 (1 정상, 0 주의)`, `최근 DB 연결 대기 최댓값`으로 변경했다. 각각 백엔드 응답만 계산하는 범위, 백업 정보 조회 실패도 포함하는 0의 의미, 최근 표시 구간의 최댓값이라는 뜻을 명확히 했다. 실제 대시보드에서는 세 제목만 변경했고 계산식, 배치, 수집과 경보는 유지했다. 준비 스크립트와 운영 안내도 같은 이름으로 맞췄다. 관련 테스트 20개를 통과했으며 Dev 이름은 유지한다.
