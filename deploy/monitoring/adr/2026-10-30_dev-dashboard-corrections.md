# ADR: Dev 대시보드의 표시 오류를 수정하고 부하 테스트에 필요한 지표를 정리한다

- 날짜: 2026-10-30
- 상태: 결정하고 Dev에 적용함
- 대상: 서울 리전의 `DASHBOARD-harudle-dev`
- 기준: [Prod 정리 결정](2026-10-30_prod-dashboard-cleanup.md), [EC2 PostgreSQL 전환 기록](2026-10-29_ec2-postgresql-monitoring.md)

## 배경과 범위

Prod 정리 후 Dev의 실제 대시보드 소스를 읽어 비교했다. Dev에도 단위 표시 오류, 잘못된 로그 검색 조건과 중복 그래프가 남아 있었다. 같은 문제를 수정하되 Prod 화면을 그대로 복사하지 않기로 했다.

Dev는 부하 테스트에서 응답 시간 분포, 처리량, 메모리와 GC를 비교하는 용도가 있다. 이 용도의 지표는 유지한다. 앱과 DB, Agent, 경보, 로그 필터 및 백업 일정은 변경하지 않는다. 이번 AWS 변경 대상은 Dev 대시보드 한 개다.

## 수정한 표시와 계산

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 5xx 카드 | `5xx 비율 (선택 기간)` | `백엔드 5xx 비율 (선택 기간)`으로 이름을 바꿔 Nginx 오류를 포함하지 않는 범위를 명시 |
| DB 대기 카드 | `앱 DB 연결 대기 최댓값` | `최근 DB 연결 대기 최댓값`으로 이름을 바꿔 최근 표시 구간의 값임을 명시 |
| API 응답 시간 3개 | 자동 단위 표시 | 왼쪽 `응답 시간 (ms)`, 오른쪽 `요청 수`로 명시 |
| API RPS | 응답 시간 지표의 단위를 따라 `Milliseconds`로 표시 | 세로축을 `요청/초`로 명시. 기존 요청 수를 구간 초 수로 나누는 계산은 유지 |
| 작업별 TPS | 자동 단위 표시 | 세로축을 `성공한 작업/초`로 명시. 성공 건수를 구간 초 수로 나누는 계산은 유지 |
| DB 연결 획득 시간 | 초 원본을 1,000배 했지만 자동 단위가 남아 있음 | 계산은 유지하고 세로축을 `밀리초 (ms)`로 명시 |
| Java 힙 | 이미 MiB로 바꾼 값에 원본 단위가 붙을 수 있음 | 세로축을 `메모리 (MiB)`로 명시 |
| Java RSS | `실제 메모리 (MiB)` | 힙과 비교하기 쉽도록 `메모리 (MiB)`로 통일. 원본과 계산은 유지 |
| EC2 네트워크 | 바이트 합계를 자동 축약해 표시 | 1,000,000으로 나누고 `전송량 (MB, 구간 합계)`로 표시. 수신은 파란색, 송신은 주황색 |

단위를 직접 명시한 축은 자동 단위 표시를 끈다. 네트워크는 초당 속도가 아니라 각 구간의 전송량 합계다. 기존 Sum 집계는 유지한다. DB 저장 공간의 GiB, EBS 지연의 ms, GC 시간의 ms와 횟수, 힙 외 메모리의 MiB는 계산과 표시가 맞아 그대로 둔다.

## 생성 그래프의 고정 5분 표현을 제거한다

다음 세 제목을 수정하고 기본 표시 기간을 300초에서 60초로 바꾼다.

| 수정 전 | 수정 후 |
| --- | --- |
| 생성 실행 평균 시간에 붙은 5분 표기 | 생성 실행 평균 시간 (초) |
| 평균 시간의 실행 표본 수 (5분) | 평균 시간의 실행 표본 수 |
| Gemini 관측 토큰 total (5분) | Gemini 관측 토큰 total |

`periodOverride=auto`는 유지한다. 실제 표시 간격은 선택한 시간 범위에 따라 CloudWatch가 조정하므로, 기본 기간 60초가 모든 화면에서 1분 표시를 강제하는 것은 아니다. 원본 수집 간격은 바꾸지 않는다.

안내문에서도 같은 5분 구간이라는 표현을 제거한다. 평균은 표시 구간의 실행 시간 합을 실행 수로 나눈 값이며, 표본이 없으면 비워 둔다. `returned`와 `threw`의 의미, DB 최종 성공과 실행기 반환의 차이, 토큰 값이 사용자 차감량이나 청구 비용이 아니라는 설명은 유지한다.

## 중복 그래프와 로그 검색을 정리한다

- `DB 연결 풀: 대기 요청 최댓값`은 제거한다. 맨 위 최근 대기 카드와 `DB 연결 대기와 시간 초과`에서 같은 값을 확인할 수 있다.
- `External Failure Trend`는 제거한다. 실패 수만으로 원인을 찾기 어렵고, 기존 검색 결과 형식도 시계열 표시에 맞지 않았다.
- `Gemini & S3 Failures`를 상세 로그 구역 첫 행의 전체 너비 24칸으로 넓힌다. 기존 시간, 제공자, 작업, 실패 유형, 응답 코드 등의 검색 필드는 유지한다.
- OAuth는 구조화된 `event` 필드뿐 아니라 메시지에 기록된 이벤트도 찾는다. 메시지에서 제공자와 실패 이유를 추출해 표시한다.
- Nginx는 502와 504 응답 및 실제 오류 등급의 upstream 또는 시간 초과 로그만 찾는다. 정상 요청의 `upstreamConnectSeconds` 같은 필드 이름을 오류로 처리하지 않는다.
- 중복 위젯 제거와 상세 표 확대에 맞춰 기존 구역 안에서 빈자리를 정리한다. API, DB, Java, 서버 자원과 로그의 구역 순서는 유지한다.

로그 검색은 `/harudle/dev/backend`와 `/harudle/dev/frontend-nginx`를 사용한다. Prod 로그 그룹이나 인스턴스를 복사하지 않는다. 조회 범위는 대시보드에서 선택한 시간을 따르며 검색문에 고정 시작과 종료 시각을 넣지 않는다.

## Dev에서 유지한 차이

- 전체, 일반, 일기 생성 API의 평균과 P95 및 P99, 요청 수를 유지한다. Prod의 경로별 상위 5개 그래프와 경로별 로그 필터를 Dev에 추가하지 않는다.
- 작업별 TPS, 생성 실행 표본 수, Gemini 토큰은 부하와 생성 작업을 비교할 때 사용하므로 유지한다.
- Java 힙의 사용량과 확보량, RSS, GC 정지 시간과 횟수, 힙 외 메모리를 유지한다. Java 구역은 서버 자원보다 먼저 둔다.
- CodeBuild Gradle cache 로그 표와 기존 경보 위젯을 유지한다.
- Dev에는 백업 감시가 설치되어 있지 않으므로 Prod 백업 카드를 추가하지 않는다. 맨 위 GC 카드와 DB 구역의 백업 미수집 안내를 유지한다.
- 최초 표시 오류 수정에서는 DB와 앱 카드 크기를 유지했다. 이후 사용자 요청으로 서버 자원 구역에 Prod의 압축 배치를 적용했다. 최종 배치는 아래 후속 결정에 기록한다.

## 적용과 검증

변경 전 AWS 소스를 보관하고, 저장 직전에도 원본이 달라지지 않았는지 대조했다. 앱 EC2 `i-08ff5dddb7ac94f5c`, DB EC2 `i-04fca55979b3240d6`, 데이터 EBS `vol-00886d19a64c23e1f`를 유지했다. 준비 스크립트도 두 환경의 공통 오류를 같은 방식으로 수정하도록 맞췄다.

| 확인 항목 | 결과 |
| --- | --- |
| 전체 위젯 | 62개에서 60개로 변경 |
| 지표 위젯 | 44개에서 43개로 변경. 중복 DB 대기 그래프 1개 제거 |
| 로그 표와 그래프 | 7개에서 6개로 변경. 외부 실패 추이 1개 제거 |
| 안내와 경보 위젯 | 안내 10개와 경보 위젯 1개 유지 |
| 기존 경보 | 위젯에 연결된 19개 목록과 설정 참조 보존. 경보 API는 변경하지 않음 |
| 대상과 배치 | Prod 대상 미포함, RDS 지표 미포함, 위젯 겹침 없음 |
| 반복 생성 | 같은 설정으로 다시 생성한 결과가 같음 |
| 저장 결과 | 저장 후 새로고침한 AWS 소스가 검증한 수정안과 같음 |
| 로컬 검사 | 모니터링 테스트 80개 통과 |

화면에서 수정한 단위와 제목을 확인했다. 최근 24시간의 외부 실패, OAuth와 Nginx 오류 표는 검색 결과가 없었다. 생성 실행 평균도 실행 표본이 없어 비어 있었다. 이 결과를 실패가 절대 없다는 보장이나 모든 실패 분기의 검증으로 해석하지 않는다. 실제 실패 로그가 있는 Prod에서 검증했던 공통 검색 조건을 재사용했다.

이번에는 부하나 장애를 새로 발생시키지 않았고, 실제 알림 발송과 백업 복원 시험은 하지 않았다. Prod 대시보드는 변경하지 않았다.

## 후속 결정: 서버 자원 카드도 한 행에 배치한다

사용자 요청에 따라 Dev의 서버 자원 구역에도 Prod 배치를 적용했다.

| 구역 | 최종 첫 행 | 너비와 높이 |
| --- | --- | --- |
| 앱 EC2 | CPU, 여유 메모리, Swap 사용률, 루트 디스크 사용률 카드 | 각각 너비 6칸, 높이 4칸. 한 행에 4개 |
| DB EC2 | CPU 카드, 여유 메모리 카드, CPU 사용률 그래프 | 너비 6칸, 6칸, 12칸. 높이 모두 6칸. 한 행에 3개 |

카드를 줄여 생긴 빈자리에 맞춰 아래 위젯의 위치를 당겼다. Java와 GC를 서버 자원보다 먼저 보는 Dev 순서는 유지한다. 상세 자원 그래프, TPS, 생성 표본 수와 토큰, CodeBuild 로그도 모두 유지한다.

변경 전후의 위젯 60개에서 위치와 크기를 제외한 모든 속성이 같은지 확인했다. 계산식, 지표 대상, 단위, 검색 조건과 경보 참조는 바꾸지 않았다. 위젯 겹침이 없고 반복 배치 결과가 같은지 검사했다. 배치 검증을 추가한 준비 스크립트 테스트 22개가 통과했다. Dev에 저장 후 새로고침해 앱 카드 4개와 DB 첫 행 3개의 배치를 확인했다. Prod 대시보드와 서버 실행 설정은 변경하지 않았다.

## 2026-11-02 후속 결정: Dev에도 API 경로별 P95를 추가한다

어느 API가 느린지 Dev에서도 구분하기 위해 일반 API 상위 5개와 일기 생성 전체 경로의 P95 그래프를 추가한다. 이전의 경로별 그래프를 추가하지 않는 결정은 변경한다. 기존 평균과 P95, P99, RPS, TPS 및 부하 테스트 지표는 유지한다. 두 그래프는 API 구역의 첫 행에 나란히 놓고, 세로축은 ms로 명시한다. 기본 기간은 60초이며 `periodOverride=auto`를 유지한다.

`/harudle/dev/backend`에 `harudle-dev-ApiResponseTimeByRouteMs-by-group-route` 필터를 추가했다. `durationMs`를 밀리초로 읽고 `ApiGroup`과 `ApiRoute` 차원으로 구분한다. 실제 사용자 ID 대신 Spring 경로 패턴을 사용하며, 기본값은 비워 둔다. 기존 Dev 필터 6개는 유지하고 준비 스크립트가 만드는 7번 파일에 경로별 필터를 담는다. 경로별 지표 비용은 화면에서 표시하는 5개로 제한되지 않는다.

상단 일반 API P95 숫자 카드에는 1ms 미만의 값이 자동으로 μs로 표시됐다. 숫자 카드의 축 설정과 정밀도 옵션만으로는 이를 고정할 수 없었다. 처음에는 같은 원본과 P95 통계를 사용하는 작은 시계열 그래프로 바꾸고 세로축을 ms로 고정했다. 이후 아래 후속 결정에 따라 숫자 카드로 되돌렸다. 수집 값이나 계산 배율은 바꾸지 않았으며 Prod도 변경하지 않았다.

Dev 대시보드는 60개에서 62개 위젯이 됐다. 기존 위젯은 모두 남겼으며, 기존 위젯의 속성 변경은 상단 P95 표시 방식뿐이다. 두 그래프가 들어갈 공간에 맞춰 아래 구역을 내렸다. 저장 후 새로고침하고 다시 읽은 구성과 [Dev 복구 JSON](../dashboards/dev.json)을 대조했다. 이 파일은 실제 측정값이 아닌 배치와 조회 설정을 보관한다. DB 백업과 R2 백업 카드는 추가하지 않았다.

최근 24시간 완료 로그 126개를 읽기 전용으로 집계한 결과 `apiRoute`가 있는 로그는 없었다. 경로별 그래프는 아직 비어 있다. 백엔드 코드 배포 후 새 요청에서 경로 필드와 지표 수신을 확인해야 하며, 필터는 이전 로그를 소급 집계하지 않는다. 백엔드 재배포와 서버 재시작, Agent 및 경보 변경은 하지 않았다.

모니터링 테스트 84개가 통과했다. 복구 JSON을 다시 준비해도 같은 구성이 나오는지, 두 경로 그래프가 같은 행을 쓰는지, 위젯 겹침이 없는지 확인했다. 기존 경보 참조 19개를 유지했고, 변경 전 코드와 비교해 Prod 생성 결과와 Prod 지표 필터가 같은지도 확인했다.

## 2026-11-02 후속 결정: 상단 P95를 Prod와 같은 숫자 카드로 표시한다

사용자 요청에 따라 Dev 상단의 일반 API P95를 `singleValue`와 `sparkline=true`로 표시한다. Prod와 같이 최신 구간의 P95를 큰 숫자로 보고 아래 작은 그래프에서 추이를 확인한다. `setPeriodToTimeRange=false`와 원본 밀리초 지표 및 P95 통계는 유지한다. 숫자 카드의 단위는 값에 따라 μs 등으로 자동 표시될 수 있다.

상단 P95의 표시 속성만 변경하고 위치와 크기는 유지한다. 추가한 경로별 P95 그래프 두 개는 그대로 두며 세로축의 ms 표시도 유지한다. 위젯 62개와 경보 참조 19개는 같다. AWS 저장 구성과 Dev 복구 JSON 및 준비 스크립트에 같은 형식을 반영했다. 관련 준비 스크립트 테스트 25개가 통과했다.

## 2026-11-03 후속 결정: Prod를 참고해 Dev 대시보드를 정리하고 P99를 남긴다

사용자 요청에 따라 Prod를 기준으로 Dev의 불필요한 위젯을 제거한다. 앞의 "Dev에서 유지한 차이" 중 전체 API 그래프, 작업별 TPS, 생성 표본 수, Gemini 토큰, CodeBuild 로그와 백업 미수집 안내를 유지한다는 결정은 이 결정으로 변경한다. GC와 힙 외 메모리, 힙 확보량은 부하 테스트 분석에 쓰므로 유지하고, Java 구역을 서버 자원보다 먼저 두는 순서도 유지한다. DB 백업과 R2 카드는 Dev에서 수집하지 않으므로 추가하지 않는다.

| 변경 | 항목 | 대신 확인할 위치 |
| --- | --- | --- |
| 제거 | API 응답 시간 (전체, 일반, 일기 생성) | 새 P95·P99 그래프, 경로별 P95, RPS |
| 제거 | 작업별 TPS | RPS와 DB 최종 확정 수. 지표와 필터는 계속 수집 |
| 제거 | 평균 시간의 실행 표본 수, Gemini 관측 토큰 total | DB 최종 확정 수, CloudWatch 지표 화면 |
| 제거 | CodeBuild Gradle cache logs | CodeBuild 로그 그룹 |
| 제거 | 백업 감시 미수집 안내 | [운영 안내](../README.md) |

| 수정 | 생성 구역 안내 | Prod의 `생성 시간과 관련 실패` 문구와 동일 |
| 수정 | 맨 위 카드 | 제목이 잘리지 않도록 너비 8칸, 높이 5칸으로 3개씩 2줄 배치 |

경로별 P95에 아직 값이 없고 부하 테스트에서는 일부 요청의 지연이 P99에 먼저 드러나므로 P99를 대시보드에 남긴다. 새 그래프는 기존 `ApiResponseTimeMs`의 통계만 사용하므로 수집 설정을 바꾸지 않는다. 평균, 전체 API의 P95와 P99, 그룹별 요청 수는 대시보드에서 볼 수 없게 된다. 작업별 성공 필터 4개와 토큰 수집은 화면에서만 제거했으므로 비용은 계속 발생한다.

준비 스크립트는 완성된 Dev 콘솔 배치를 Prod처럼 그대로 유지한다. 아직 구성이 갖춰지지 않은 원본에는 위 구성을 적용한다.

저장 전 AWS 소스를 보관하고 해시로 대조했다. 저장 후 새로고침해 다시 읽은 소스와 [Dev 복구 JSON](../dashboards/dev.json)이 같고, 위젯은 55개, 경보 참조는 19개이며 위젯 겹침이 없다. 화면에서 맨 위 카드의 전체 제목과 P99 그래프의 일반 API 선을 확인했다. 조회 시점에 일기 생성 요청이 없어 일기 생성 선은 값이 없었고, 경로별 P95도 비어 있었다. Prod와 경보, 로그 필터, Agent와 서버 설정은 변경하지 않았다.

## 2026-11-03 후속 결정: Nginx 502/504와 예상 밖 생성 실패를 그래프로 표시한다

백엔드가 응답하지 못하면 백엔드 5xx 비율에는 잡히지 않고 상세 로그 표에서만 확인할 수 있었다. `frontend-nginx` 로그 그룹에 지표 필터를 추가하고 `Nginx 502/504 응답 수` 그래프를 서비스 오류 구역에 둔다. 현재 접근 로그는 JSON이므로 필터 패턴은 `{ $.status = 502 || $.status = 504 }`로 한다. 처음 AWS에 등록한 공백 구분 패턴은 이전 combined 형식의 502 로그만 맞아 현재 로그의 502를 세지 못했으므로, 같은 날 두 환경의 필터를 같은 이름으로 교체했다. 로그가 들어오면 기본값 0이 게시되므로 그래프의 값만으로 필터가 502를 잡는지 판단하지 않는다. 필터는 과거 로그를 소급하지 않으며, 오류 로그 줄은 세지 않으므로 응답 건수로 해석한다.

`일기 생성: DB 최종 확정 수`에는 경보와 같은 원본인 `GenerationUnexpectedFailureLogs`를 추가한다. Prometheus 카운터는 첫 수집 전 오류가 빠질 수 있어 로그 지표를 쓴다. 상단 생성 실패 카드의 계산에는 포함하지 않는다.

저장 직전 AWS 소스가 복구 JSON과 같은지 해시로 확인했고, 저장 후 새로고침해 다시 읽은 소스가 복구 JSON과 같음을 확인했다. 위젯은 55개에서 56개가 됐다. 경보, Agent와 서버 설정은 변경하지 않았다. 이 그래프의 경보 추가는 별도로 결정한다. 교체 후 실제 502 응답으로 값이 오르는지는 아직 확인하지 못했다.

## 2026-11-03 후속 결정: 작업별 TPS를 조회와 쓰기로 나눠 되살린다

제거했던 작업별 TPS는 읽기 어려워서 뺀 그래프였다. 최근 2주 Dev 값을 나눠 보니 조회는 최고 약 23건/초, 쓰기는 최고 약 0.13건/초로 약 180배 차이가 나서 한 축에서는 쓰기 선이 바닥에 붙었다. `조회 TPS (성공 건수/초)`와 `쓰기 TPS (성공 건수/초)`로 나눠 RPS 아래 행에 둔다. 기존 지표와 필터를 그대로 쓰므로 수집 변경은 없다. 위젯은 56개에서 58개가 됐다. Prod는 TPS 필터가 없어 변경하지 않는다.

저장 전 AWS 소스가 복구 JSON과 같음을 해시로 확인했고, 저장 후 새로고침해 다시 읽은 소스와 복구 JSON이 같음을 확인했다.

## 2026-11-03 후속 결정: P95·P99 그래프의 일기 생성을 오른쪽 축으로 분리한다

최근 2주 Dev에서 일기 생성 요청이 최대 약 120,000ms까지 찍혀 일반 API 선이 바닥에 붙었다. Dev와 Prod 모두 일반 API는 왼쪽, 일기 생성은 오른쪽 축을 쓴다. 지표와 통계는 바꾸지 않았다. 저장 전 AWS 소스가 복구 JSON과 같음을 해시로 확인했고, 저장 후 다시 읽은 소스가 복구 JSON과 같음을 확인했다.
