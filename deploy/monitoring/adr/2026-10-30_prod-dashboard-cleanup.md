# ADR: Prod 대시보드에서 서비스 상태와 실패 원인을 순서대로 확인한다

- 날짜: 2026-10-30
- 상태: 결정 완료. 대시보드에 적용했으며, API 경로별 지표의 실제 수신은 확인 대기
- 대상: 서울 리전의 `DASHBOARD-harudle-prod`
- 범위: RDS에서 EC2 PostgreSQL로 전환한 뒤 진행한 Prod 대시보드 정리
- 이전 기록: [10월 22일 Prod 배치](2026-10-22_cloudwatch-prod-dashboard-layout.md), [10월 29일 EC2 PostgreSQL 모니터링](2026-10-29_ec2-postgresql-monitoring.md)

## 배경

기존 대시보드는 중복 그래프가 있고, API 응답 시간과 요청 수를 한 그래프에 겹쳐 보여 읽기 어려웠다. 일부 그래프는 값을 변환한 뒤에도 원본 단위를 표시했다. 로그 검색 결과가 비어 있어도 실제 오류가 없는지, 검색 조건이 맞지 않는지 구분하기 어려웠다.

Prod에서는 서비스에 문제가 있는지 먼저 확인하고, 문제가 발생한 시간과 작업을 찾은 뒤 서버 자원과 로그로 원인을 확인하기로 했다. Dev는 부하 테스트와 개발 확인에 쓰므로 같은 구성을 일괄 적용하지 않는다. 아래 결정은 Prod 기준이며, 앞서 두 환경에 적용한 변경은 이전 기록에 남긴다.

## 1. 확인 순서와 맨 위 항목

다음 순서로 배치한다.

1. 맨 위 상태 항목 6개
2. 서비스 오류와 알림
3. API 속도와 요청 수
4. 일기 생성과 외부 API
5. DB 연결과 데이터 저장 공간
6. DB EC2 자원과 EBS
7. 앱 EC2 자원
8. Java 메모리
9. 상세 로그

맨 위 항목의 이름과 의미를 다음과 같이 정한다. 제목에는 `요약:`을 붙이지 않는다.

| 이름 | 확인하는 내용 |
| --- | --- |
| 백엔드 5xx 비율 (선택 기간) | 선택한 시간 전체의 백엔드 5xx 응답 수를 전체 백엔드 응답 수로 나눈 비율 |
| 일반 API P95 (ms) | 최근 표시 구간의 일반 API P95 응답 시간 |
| 생성 실패 | 선택한 시간 전체에 DB 저장이 확정된 생성 실패 건수 |
| 최근 DB 연결 대기 최댓값 | 최근 표시 구간에서 DB 연결을 기다린 요청 수의 최댓값 |
| DB 데이터 여유 공간 (GiB) | DB 서버의 `/srv/harudle/db-data` 파일 시스템에 남은 공간 |
| DB 백업 상태 (1 정상, 0 주의) | 최근 확인에서 24시간 안의 성공 백업을 찾았는지 여부 |

백엔드 5xx 비율에는 Nginx에서 연결 실패로 발생한 502와 504가 포함되지 않는다. 요청이 없을 때는 정상 0으로 채우지 않는다. DB 연결 대기 카드도 선택한 시간 전체의 최댓값으로 해석하지 않는다.

## 2. API는 느린 경로와 요청량을 나누어 본다

전체 API, 일반 API, 일기 생성 API의 평균과 P95 및 P99를 겹쳐 보던 구성을 경로별 P95로 바꾼다. 요청 수는 응답 시간 그래프에서 분리한다.

- 일반 API는 선택한 시간 안에서 구간별 P95의 최댓값이 높은 경로 5개를 표시한다.
- 일기 생성 API는 요청이 있는 경로를 모두 표시한다.
- API RPS는 초당 처리가 끝난 요청 수를 별도 그래프로 표시한다. 실패 응답도 포함한다.
- 작업별 TPS는 Prod에서 제거한다. 요청량은 RPS에서 보고, 생성 성공 여부는 DB 최종 확정 수에서 확인한다.

API 응답 시간과 RPS는 API 완료 로그를 기준으로 하며 자동 상태 확인과 지표 수집 요청은 제외한다. 기존 백엔드 HTTP 응답 수에는 상태 확인 요청이 포함되므로, 두 그래프의 건수가 같아야 하는 것은 아니다.

로그의 `apiRoute`는 `GET:/api/v1/feeds/{feedId}`처럼 HTTP 방식과 Spring 경로 패턴을 사용한다. 실제 사용자 ID나 원본 요청 주소를 지표 이름으로 사용하지 않는다. 경로를 찾지 못하면 `<unmatched>`로 묶는다. 일반 API의 표시를 5개로 제한해도 수집되는 경로별 지표 수가 줄어드는 것은 아니다.

경로별 지표가 수신되면 범례의 `${PROP('Dim.ApiRoute')}`는 해당 API 경로를 표시한다. 10월 30일 확인에서는 두 경로별 그래프가 비어 있었다. 코드 변경과 화면 구성이 끝난 것만으로 수집 완료로 판단하지 않고, 배포 후 실제 요청과 지표 수신을 확인한다.

## 3. 중복되거나 역할이 불분명한 그래프를 제거한다

| 제거한 항목 | 결정 이유와 대신 확인할 위치 |
| --- | --- |
| 별도의 5xx 비율 그래프 | 적은 요청을 기준값 미달로 0 처리하면 오류가 없는 것으로 오해할 수 있다. 맨 위 비율과 HTTP 응답 수 그래프를 유지한다. |
| 작업별 TPS | 생성 작업의 결과와 처리량을 바로 이해하기 어렵다. RPS와 DB 최종 확정 수를 사용한다. |
| 생성 실행 수 | 실행 수만으로 DB 최종 성공을 판단할 수 없다. 생성 시간과 최종 확정 결과를 함께 본다. |
| Gemini 관측 토큰 | 기본 운영 화면의 상태 판단에 우선하지 않는다. 화면에서 제거하며 수집 설정은 유지한다. |
| DB 연결 풀의 별도 대기 요청 최댓값 그래프 | 대기 요청과 시간 초과를 함께 보여주는 그래프와 겹친다. 맨 위 최근 값과 상세 통합 그래프를 유지한다. |
| External Failure Trend | 실패 수만으로 어디서 실패했는지 알기 어렵다. 외부 실패 상세 표를 넓혀 원인을 바로 확인한다. |

일기 생성 구역에는 생성 실행 평균 시간과 정리 및 Gemini 요청 실패 그래프를 나란히 둔다. 평균 시간은 구간별 실행 시간 합을 실행 수로 나눈 값이며, 실행이 없는 구간은 비워 둔다. `returned`는 실행기가 예외 없이 반환된 경우이고, DB 최종 성공을 뜻하지 않는다. `threw`는 실행 중 예외가 발생한 경우다.

## 4. 수집 주기와 표시 단위를 구분한다

대시보드의 `periodOverride`는 `auto`로 설정한다. 조회 시간 범위는 화면에서 선택하며, 이를 바꾼다고 원본 수집 주기가 바뀌지는 않는다. 제거한 로그 추이 그래프의 고정 5분 집계를 다시 추가하지 않는다.

| 지표 | 계산과 표시 |
| --- | --- |
| API 응답 시간 | 밀리초로 수집한 값을 ms로 표시 |
| API RPS | 구간 요청 수를 구간 초 수로 나누고 세로축을 `요청/초`로 표시 |
| 생성 실행 평균 시간 | 원본 초 값을 사용하고 세로축을 `초`로 표시 |
| DB 연결 획득 시간 | 원본 초 값에 1,000을 곱하고 세로축을 `밀리초 (ms)`로 표시 |
| DB 여유 공간 | 바이트를 1,073,741,824로 나누고 GiB로 표시 |
| EC2 네트워크 | 구간 바이트 합계를 1,000,000으로 나누고 `전송량 (MB, 구간 합계)`로 표시 |
| Java 힙과 RSS | 바이트를 1,048,576으로 나누고 `메모리 (MiB)`로 표시 |
| EBS 지연과 대기 길이 | 지연은 왼쪽 ms 축, 평균 대기 길이는 오른쪽 개수 축으로 분리 |

변환한 값에는 CloudWatch의 원본 자동 단위 표시를 끄고 단위를 직접 적는다. 네트워크는 초당 속도가 아니다. 수신은 파란색, 송신은 주황색으로 구분한다. RSS는 Java 프로세스가 실제 RAM에서 사용하는 양이며 힙 밖의 메모리도 포함한다.

## 5. 앱과 DB 서버 자원을 분리해서 유지한다

DB와 앱은 별도 EC2이므로 CPU, 메모리와 상태 검사를 각각 확인한다. 같은 지표의 숫자 카드와 상세 그래프는 최근 상태와 시간별 변화를 확인하는 역할이 달라 유지한다.

- DB 첫 행은 CPU 카드 6칸, 여유 메모리 카드 6칸, CPU 그래프 12칸으로 배치한다. 높이는 모두 6칸이다.
- 앱 첫 행은 CPU, 여유 메모리, Swap 사용률, 루트 디스크 사용률 카드를 각각 너비 6칸과 높이 4칸으로 배치한다.
- CPU 크레딧과 네트워크는 보조 진단 지표로 유지한다.
- DB 데이터 디스크와 루트 디스크의 여유 공간은 따로 확인한다.

서버와 EBS 대상은 [targets.json](../targets.json)에 기록한다. 앱 연결 대기 0이나 EC2 상태 검사 0을 PostgreSQL 직접 접속 성공으로 해석하지 않는다.

## 6. 백업은 매일 한 번 확인한다

기존 DB 백업은 매일 한국 시간 오전 4시에 실행한다. 별도의 `harudle-db-backup-monitor.timer`는 오전 5시에 한 번 백업 정보를 읽는다. 백업 일정과 DB 실행 설정은 바꾸지 않는다.

- `BackupWithin24Hours`: 확인 시점에 최근 24시간 안의 성공 백업이 있으면 1이다. 없거나 정보를 읽지 못하면 0이다.
- `BackupInfoCheckSuccess`: 백업 정보를 읽는 작업 자체의 성공 여부를 별도로 표시한다.
- 맨 위 백업 카드는 최근 24시간의 확인 결과를 표시한다. 표본이 없을 때 1로 채우지 않는다.

따라서 카드에서 0은 `실패` 대신 `주의`로 표시한다. 오전 5시에도 백업 중이면 완료 후 별도 확인이 필요하다. 이 감시는 실제 복원 가능 여부를 보장하지 않는다. 백업 실패 및 누락 알림과 WAL 전송 감시는 이번에 추가하지 않았다.

## 7. 상세 로그에서 실패한 작업을 확인한다

`Gemini & S3 Failures`는 상세 로그 구역의 첫 행 전체 너비 24칸을 사용한다. 발생 시간, 제공자, 작업, 실패 유형, 응답 코드와 추적 ID 등을 확인한다. 10월 30일에는 Gemini 스토리보드 생성의 `RATE_LIMIT`, 응답 코드 `429`가 표시되는 것을 확인했다.

OAuth는 현재 로그가 메시지 안에 `event=oauth_login_failure` 형태로 기록되는 경우도 읽는다. 제공자와 실패 이유를 추출하며, 구조화된 `event` 필드가 있는 로그도 함께 지원한다. 앱 로거 변경이나 재배포 없이 검색 조건을 수정했다.

Nginx 검색은 502와 504 응답 및 실제 오류 등급의 upstream 또는 시간 초과 로그만 표시한다. 정상 JSON 요청에 있는 `upstreamConnectSeconds` 같은 항목 이름만으로 오류로 분류하지 않는다. 응답 로그와 연결 오류 로그는 같은 요청에서 각각 남을 수 있으므로 로그 건수를 실패 요청 수로 해석하지 않는다.

백엔드 내부 오류 표와 최근 백엔드 오류 표는 유지한다. 결과가 비어 있으면 조회 시간과 검색 조건 및 로그 형식을 확인하며, 빈 표만으로 오류가 없다고 단정하지 않는다.

## 적용과 남은 확인

AWS 대시보드에 저장해야 같은 계정과 리전의 팀원에게 같은 화면이 보인다. 저장소 변경이나 앱 배포만으로 대시보드가 바뀌지는 않는다. 재생성할 때는 [준비 스크립트](../prepare_dashboard.py)와 [운영 안내](../README.md)를 사용하고, 최신 AWS 원본과 차이를 비교한다.

10월 30일 점검에서 전체 위젯은 54개였다. 지표 38개, 안내 10개, 로그 표 5개, 경보 위젯 1개이며 겹침은 없었다. 경보 위젯에는 기존 경보 19개가 연결돼 있었다. 마지막 이름 변경까지 저장 후 새로고침으로 확인했고, 준비 스크립트 관련 테스트 20개가 통과했다. 이 개수는 당시 화면의 확인값이며 새 지표 추가를 금지하는 기준은 아니다.

이번 화면 정리로 기존 경보의 기준과 알림 연결은 바꾸지 않았다. 정리 실패 3종과 Gemini 요청 실패의 기존 경보는 유지한다. 이미지 대체 실패 경보는 R2 경로 활성화와 실제 로그 확인 후 별도로 설정한다. 경보가 OK여도 이전 실패가 해결되었다는 뜻은 아니다.

남은 확인은 다음과 같다.

- API 경로별 로깅 코드 배포 후 일반 상위 5개와 일기 생성 전체 경로의 실제 지표 수신
- PostgreSQL 직접 접속과 전체 연결 수, WAL 전송 상태 등 아직 수집하지 않는 항목의 별도 설계
- 백업 복원 시험과 경보의 실제 알림 발송 시험

화면에서 지표를 제거한 것과 원본 수집을 중단한 것은 구분한다. Prod에만 결정한 배치와 표시 변경을 Dev에 일괄 적용하지 않는다.

## 2026-11-02 후속 결정: 콘솔에서 완성한 Prod 배치를 보존한다

현재 콘솔에는 R2 백업 상태 카드가 추가되어 위젯이 55개다. 이 원본을 기존 준비 스크립트에 넣으면 상단 P95 카드가 빠지고 생성 실패 카드가 하나 더 생겼다. R2 카드도 다른 구역으로 이동했다. 상단 카드를 원본 대신 상세 지표에서 재생성하고, 새 카드를 기존 배치 규칙으로 다시 배치했기 때문이다.

기본 상태 항목이 갖춰지고 전체 위젯의 위치와 크기가 있는 Prod 원본은 콘솔 배치를 기준으로 유지하기로 했다. 이 경우 스크립트는 관측 위젯을 자동으로 추가하지 않고, 기존 카드와 새로 추가한 카드의 위치와 크기를 보존한다. 단위와 로그 검색 조건 보정은 유지한다. 아직 구성이 갖춰지지 않은 원본의 초기 배치 기능과 Dev 처리 방식은 유지한다.

준비 스크립트는 콘솔 수정에 필수인 도구가 아니다. 콘솔에서 직접 수정할 수 있으며, 스크립트는 최신 설정을 파일로 검토하거나 다시 적용할 때 선택해서 사용한다. 콘솔에서 편집한 뒤에는 최신 JSON을 다시 가져오고 생성 결과를 비교한다.

11월 2일 콘솔 소스를 읽기 전용으로 복사해 검증했다. 수정 후 위젯 55개의 순서, 종류, 위치와 크기가 원본과 같고 반복 실행 결과도 같았다. P95와 R2 카드는 유지되고 생성 실패 카드가 중복되지 않았다. 두 행의 상태 카드와 콘솔에서 추가한 카드 및 안내를 보존하는 회귀 테스트를 추가했으며 모니터링 테스트 82개가 통과했다. 이번에는 AWS 설정과 서버를 변경하거나 Git 커밋을 만들지 않았다.

## 2026-11-02 후속 결정: Prod 정상 구성을 JSON으로 보관한다

잘못 바뀐 배치나 계산식을 복구할 수 있도록 [dashboards/prod.json](../dashboards/prod.json)에 현재 Prod 구성을 보관한다. 준비 스크립트는 입력 JSON을 기준으로 동작하므로, 스크립트만으로 과거 배치를 복구할 수는 없다. 정상 원본을 별도로 남기고 복구할 때는 그 JSON을 콘솔에 직접 적용한다.

콘솔을 새로고침한 뒤 저장된 소스를 읽기 전용으로 가져왔다. 위젯 55개를 포함한 전체 설정이 보관 파일과 같은지 확인했다. 실제 측정 데이터는 포함하지 않으며, 경보 자체나 수집 설정을 복구하는 파일도 아니다. 복구 순서는 운영 안내에 기록했다. 이번에는 Prod 파일만 추가했으며 AWS에 다시 적용하거나 Git 커밋을 만들지 않았다.

## 2026-11-03 후속 결정: Prod에도 P99 그래프를 둔다

경로별 P95만으로는 상위 5% 안의 지연을 확인할 수 없어, 일반 API와 일기 생성의 P95와 P99를 한 그래프로 표시한다. [Dev 정리 결정](2026-10-30_dev-dashboard-corrections.md)과 같은 그래프이며 기존 `ApiResponseTimeMs`의 통계만 사용하므로 수집 설정과 로그 필터는 바꾸지 않는다. RPS 오른쪽 빈칸에 두어 다른 위젯의 위치는 그대로다.

요청이 적은 구간의 P99는 최댓값에 가까워 한 건만 느려도 튈 수 있다. 원인을 찾을 때 참고하며 경보 기준으로 쓰지 않는다.

저장 직전 AWS 소스가 복구 JSON과 같음을 해시로 확인하고, 저장 후 새로고침해 다시 읽은 소스와 [dashboards/prod.json](../dashboards/prod.json)이 같은지 확인했다. 위젯은 55개에서 56개가 됐다. 준비 스크립트는 완성된 Prod 배치에 그래프를 자동으로 추가하지 않고, 구성이 갖춰지지 않은 원본에만 추가한다.
