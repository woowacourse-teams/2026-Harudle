# 백엔드 작업 지침

이 파일은 `backend/` 전체에 적용한다. 테스트를 추가하거나 수정할 때는
아래 규칙을 먼저 읽는다. 배경과 실행 옵션은 [README의 테스트 절](README.md#테스트)을 따른다.

## 테스트 작성 전 확인

1. 검증할 동작과 필요한 범위를 정한다. Spring이나 DB가 필요 없는 로직은
   단위 테스트로 검증한다. 모든 테스트를 통합 테스트로 만들지 않는다.
2. 같은 종류의 기존 테스트와 `src/test/java/com/harudle/support/`의 공통 설정을
   읽는다. 오래된 테스트의 클래스별 컨테이너 선언을 그대로 복사하지 않는다.
3. 아래 기준으로 공통 설정을 선택한다. 필요한 별도 설정이 있으면 그 이유를
   유지한다. 실행 시간을 줄이려고 테스트의 전제를 바꾸지 않는다.

## 테스트 종류별 공통 설정

- 일반 서비스 통합 테스트는 `ServiceIntegrationTestSupport`를 상속한다.
  이 클래스의 Spring 설정, JWT mock과 `DiaryGenerationWorker` mock을
  중복 선언하지 않는다. 실제 작업 처리기를 검증하는 테스트는 해당 mock이
  목적에 맞지 않으므로 기존 전용 설정을 확인한다.
- 실제 Bean을 사용하는 MockMvc 통합 테스트는 `@MockMvcIntegrationTest`를
  사용한다. 컨트롤러만 별도로 검증하는 테스트에 일괄 적용하지 않는다.
- 그 밖의 Spring 기반 DB 테스트는 `@Import(TestcontainersConfiguration.class)`로
  공통 PostgreSQL 컨테이너 설정을 사용한다.
- 카테고리 서비스의 JPA 테스트는 같은 패키지의 `CategoryJpaTestConfiguration`과
  기존 테스트를 확인한다. 같은 서비스 등록 설정을 테스트마다 새로 만들지 않는다.
- 고정 Clock, 추가 mock, spy, 프로필과 속성이 필요한 테스트는 그 설정을 보존한다.
  새 설정을 추가하기 전에는 기존 공통 설정으로 해결할 수 있는지 확인한다.
- 차단과 관리자 조치 등 전용 DB 지원 클래스를 사용하는 기존 테스트는 해당
  지원 클래스의 사용 조건을 확인한다. 이번 일반 통합 테스트 규칙을 이유로
  전용 DB 설정을 일괄 교체하지 않는다.

## 컨테이너와 Spring 실행 환경의 재사용

[PR #381](https://github.com/woowacourse-teams/2026-Harudle/pull/381)의
컨테이너 관리 방식을 유지한다. Spring 컨텍스트는 테스트에 필요한 객체와 설정을
담은 실행 환경이다. 설정이 같은 테스트는 이 환경과 DB 컨테이너를 함께 재사용한다.
컨테이너는 전체 테스트에 하나가 아니라 Spring 컨텍스트마다 만들어진다.

- 일반 Spring 통합 테스트에 클래스별 `@Container`, 별도 PostgreSQL 컨테이너,
  직접 작성한 `start()`와 `stop()` 코드를 추가하지 않는다. Spring이 컨테이너의
  시작과 종료를 관리하게 한다. DB가 먼저 종료되고 재사용되는 DB 연결이 남는
  문제를 다시 만들지 않는다.
- 테스트별 `@MockitoBean`, `@Import`, 프로필과 속성의 차이는 별도 실행 환경을
  만들 수 있다. 같은 목적의 설정은 공통 설정을 재사용하되, 필요한 차이를
  없애서 강제로 같은 환경을 사용하게 하지 않는다.
- `Flyway.clean()`이나 이전 스키마를 검증하는 테스트는 별도 컨테이너를 사용한다.
  일반 통합 테스트와 DB를 공유하지 않는다.
- 테스트가 실패한다는 이유만으로 `@DirtiesContext`를 추가하지 않는다.
  먼저 데이터 정리 누락과 공유 객체의 설정 변경을 확인한다. 실행 환경을 다시
  만들어야 하는 동작을 검증한다면 그 이유를 테스트에 명시한다.

## 공유 DB와 실행 상태 정리

- 테스트가 만든 데이터는 트랜잭션 롤백이나 명시적인 삭제로 정리한다.
  다른 테스트가 먼저 실행되어야 성공하는 테스트를 만들지 않는다.
- 별도 스레드, 별도 트랜잭션이나 HTTP 요청에서 커밋한 데이터가 테스트의
  트랜잭션 롤백으로 지워진다고 가정하지 않는다. 직접 정리할 범위를 확인한다.
- 동시성 테스트는 성공과 실패 모두에서 작업을 종료하고 종료를 기다린 뒤
  데이터를 삭제한다. 외래 키가 있으면 참조하는 데이터부터 삭제한다.
- 공유 DB 전체를 비우거나 공통 초기 데이터를 임의로 삭제하지 않는다.
  공통 데이터를 바꾸는 테스트는 종료 시 원래 상태로 복원한다.
- 공유 Bean과 mock의 상태가 다음 테스트에 남지 않게 한다. 테스트가 바꾼
  전역 상태나 설정은 복원한다.

## MockMvc와 CSRF

- 같은 Spring 실행 환경을 공유하는 MockMvc 테스트에서 `.with(csrf())`를
  사용하지 않는다. 이 도구는 공유 보안 필터의 토큰 저장 방식을 바꿔
  쿠키 기반 테스트에 영향을 줄 수 있다.
- 기존 `GuestSessionControllerTest`처럼 CSRF 발급 경로에서 쿠키를 받은 뒤
  요청에 쿠키와 `X-XSRF-TOKEN` 헤더를 전달하는 방식을 참고한다.
  토큰 누락이나 불일치를 검증하는 테스트는 그 조건을 유지한다.
- 테스트를 통과시키려고 보안 필터나 CSRF 검사를 끄지 않는다.

## 검증과 결과 보고

1. DB 테스트를 실행하기 전에 `docker info`로 Docker 엔진 상태를 확인한다.
   Docker 없이 건너뛰는 테스트와 Docker가 반드시 필요한 테스트를 구분한다.
2. `backend/`에서 변경한 테스트와 같은 실행 환경을 공유하는 기존 테스트를
   함께 실행한다. 한 클래스의 성공만으로 테스트 간 간섭이 없다고 판단하지 않는다.
3. 공통 설정을 바꿨다면 `IntegrationTestContextConfigurationTest`를 실행하고,
   영향을 받는 통합 테스트도 실행한다. 이 테스트는 설정의 동일성을 확인하므로
   실제 DB 정리와 컨테이너 종료까지 검증했다고 보고하지 않는다.
4. 새 테스트가 기존 공유 그룹에 속해야 한다면 위 설정 검사에 포함할지 확인한다.
   별도 설정이 필요한 테스트는 그 차이가 유지되는지도 확인한다.
5. 공통 지원 클래스나 컨테이너 관리 방식을 바꿨다면 전체 백엔드 테스트를 실행한다.
   실행 범위, 실패와 건너뛴 항목을 결과에 적는다. 실행하지 못한 테스트를
   통과했다고 보고하지 않는다.

로컬 메모리가 부족하면 README에 있는 `-PtestContextCacheMaxSize=4` 옵션을
사용할 수 있다. 로컬 실행 문제를 해결하려고 CI 기본값이나 공통 테스트 설정을
임의로 바꾸지 않는다.
