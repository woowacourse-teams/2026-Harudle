# 2026-08-25 관리자 API 권한을 DB의 현재 역할로 검증

- 작성일: 2026-08-25
- 작성자: 이산
- 결정 대상: 관리자 권한의 기준과 관리자 API 인가 책임의 위치

## 배경

관리자 대시보드는 사용자 정보와 최근 생성 상태를 조회하고, 사용자의 일일 생성 사용량을 복구하거나 초기화한다. 일반 사용자에게
노출되면 안 되는 정보와 데이터 변경 기능을 제공하므로 일반 API 인증과 별도로 관리자 권한을 검증해야 한다.

하루들 API는 서비스가 발급한 Access Token JWT의 subject에 사용자 UUID를 저장한다. 사용자 역할은 `users.role`에 `USER` 또는
`ADMIN`으로 저장하며, 최초 관리자는 운영 DB에서 UUID를 확인한 뒤 수동으로 지정한다. 역할을 JWT에 포함하거나, Controller 또는
Service마다 관리자 검증을 호출하는 방식도 가능하다.

관리자 권한을 어디의 정보로 판단할지, 역할 변경을 언제 반영할지, 어느 계층에서 관리자 API 전체를 보호할지 결정해야 한다.

## 결정 요인

- DB에서 관리자 역할을 회수하면 가능한 한 즉시 접근을 차단해야 한다.
- 탈퇴한 사용자는 DB에 `ADMIN` 역할이 남아 있어도 접근할 수 없어야 한다.
- 관리자 API를 추가할 때 권한 검증을 빠뜨리지 않아야 한다.
- Controller와 Service에 같은 권한 검증 코드를 반복하지 않아야 한다.
- 관리자임을 확실하게 확인할 수 없는 경우 접근을 허용하지 않아야 한다.
- 관리자 API의 호출량은 일반 사용자 API보다 적다.

## 고려한 대안

### 대안 1: JWT에 역할을 포함하고 `hasRole`로 검증

로그인 또는 Access Token 재발급 시 DB의 역할을 JWT claim에 포함하고 Spring Security가 해당 claim을 권한으로 변환한다.

장점은 다음과 같다.

- 관리자 API 요청마다 사용자 역할을 조회하지 않아도 된다.
- Spring Security의 `hasRole("ADMIN")`과 표준 권한 변환 방식을 사용할 수 있다.
- 요청 시점의 권한 검증 코드가 단순하다.

단점은 다음과 같다.

- DB에서 `ADMIN`을 `USER`로 변경해도 기존 Access Token이 만료될 때까지 관리자 권한이 유지될 수 있다.
- JWT의 역할과 DB의 현재 역할이 일시적으로 다를 수 있다.
- 즉시 권한 회수를 보장하려면 토큰 폐기 목록, 짧은 만료 시간 또는 별도 DB 검증이 다시 필요하다.

### 대안 2: Controller 또는 Service에서 관리자 여부를 직접 검증

각 관리자 Controller 또는 Service가 인증 사용자 UUID를 얻어 DB 역할을 확인한다.

장점은 다음과 같다.

- 각 기능에서 필요한 권한 정책을 명시적으로 표현할 수 있다.
- Spring Security의 커스텀 인가 API를 이해하지 않아도 된다.
- 기능별로 서로 다른 권한 검증을 추가하기 쉽다.

단점은 다음과 같다.

- 관리자 API마다 같은 검증 코드가 반복된다.
- 새로운 API에서 검증 호출을 빠뜨릴 수 있다.
- 인증과 인가 책임이 Controller 또는 비즈니스 Service에 섞인다.
- API 실행 전에 공통으로 차단하기 어렵다.

### 대안 3: Spring Security에서 요청마다 DB의 현재 역할을 검증

`AuthorizationManager`가 Access Token의 subject에서 사용자 UUID를 얻고 DB에서 현재 사용자 상태와 역할을 확인한다.
`/api/v1/admin/**` 경로 전체에 이 검증을 적용한다.

장점은 다음과 같다.

- DB에서 역할을 변경하면 다음 관리자 API 요청부터 반영된다.
- 탈퇴 상태와 현재 역할을 같은 DB 조회 결과로 검증할 수 있다.
- 관리자 API 경로 전체를 한 곳에서 보호한다.
- Controller와 Service는 관리자 권한 검증을 반복하지 않는다.
- 향후 관리자 API를 추가해도 같은 경로 아래에 있으면 자동으로 보호된다.

단점은 다음과 같다.

- 관리자 API 요청마다 사용자 DB 조회가 한 번 추가된다.
- DB 장애가 발생하면 관리자 API 권한도 확인할 수 없다.
- Spring Security의 `AuthorizationManager` 계약과 필터 체인 순서를 이해해야 한다.
- 역할이 필요한 일반 API가 늘어나면 권한 조회 전략을 다시 설계할 수 있다.

## 결정

대안 3을 선택한다.

관리자 권한의 단일 기준은 `users.role`의 현재 값으로 한다. Access Token은 사용자를 식별하기 위한 UUID만 제공하며 관리자 역할을
JWT claim에 포함하지 않는다.

`AdminAuthorizationManager`는 관리자 API 요청마다 다음 순서로 권한을 검증한다.

```text
Access Token 검증
→ Authentication의 사용자 UUID 파싱
→ DB에서 현재 사용자 조회
→ 탈퇴 여부 확인
→ 현재 role 확인
→ 활성 ADMIN이면 허용
```

권한 검증은 `SecurityFilterChain`에서 `/api/v1/admin/**` 경로 전체에 적용한다. 일반 `/api/v1/**` 인증 규칙보다 관리자 규칙을
먼저 선언해 관리자 API가 단순 인증만으로 허용되지 않게 한다.

인증 정보 없음, UUID 파싱 실패, 사용자 없음, 탈퇴 사용자 또는 `USER` 역할처럼 활성 관리자임을 확실하게 확인할 수 없는 모든
경우에는 접근을 거부한다. DB 조회 중 예외가 발생해도 요청을 허용하지 않는 fail-closed 방향을 유지한다.

```text
활성 사용자 + ADMIN
→ 접근 허용

그 외 모든 경우
→ 접근 거부
```

## 긍정적 결과

- 운영 DB에서 관리자 역할을 회수하면 다음 관리자 API 요청부터 반영된다.
- 탈퇴한 관리자를 별도의 토큰 폐기 처리 없이 관리자 API에서 차단한다.
- 관리자 권한의 기준이 DB 한 곳에 유지된다.
- Controller와 Service가 인증 및 관리자 역할 검증 책임을 갖지 않는다.
- `/api/v1/admin/**` 아래에 추가되는 API는 같은 권한 정책으로 보호된다.
- JWT claim과 DB 역할의 불일치 문제를 만들지 않는다.

## 부정적 결과와 트레이드오프

- 관리자 API 요청마다 사용자 DB 조회가 추가된다.
- DB가 응답하지 않으면 관리자 API도 사용할 수 없다.
- 권한 검증 코드가 Spring Security의 `AuthorizationManager` 인터페이스에 의존한다.
- 관리자 권한이 여러 단계로 세분화되면 하나의 `ADMIN` 역할과 경로 규칙만으로는 부족할 수 있다.
- 관리자 API를 `/api/v1/admin/**` 밖에 만들면 현재 규칙의 보호를 받지 못한다.

관리자 API 호출량이 적고 사용자 데이터 변경 기능을 보호하는 것이 조회 비용보다 중요하므로 요청별 DB 조회를 감수한다.

## 구현 및 검증 조건

- [ ] 기존 사용자와 신규 사용자의 기본 역할은 `USER`다.
- [ ] 관리자 역할은 사용자 UUID를 확인한 뒤 운영 DB에서 수동으로 부여한다.
- [ ] 유효한 Access Token의 subject를 사용자 UUID로 파싱한다.
- [ ] 활성 `ADMIN` 사용자만 `/api/v1/admin/**`에 접근할 수 있다.
- [ ] 일반 사용자는 관리자 API 요청에서 `403 Forbidden`을 받는다.
- [ ] Access Token이 없는 사용자는 `401 Unauthorized`를 받는다.
- [ ] 탈퇴한 `ADMIN` 사용자는 관리자 API에 접근할 수 없다.
- [ ] DB에서 `ADMIN`을 `USER`로 변경하면 다음 관리자 API 요청부터 차단된다.
- [ ] 관리자 API 경로 규칙은 일반 인증 API 규칙보다 먼저 적용된다.
- [ ] 사용자 조회 실패나 잘못된 principal 값은 접근 허용으로 이어지지 않는다.

## 재검토 조건

다음 조건 중 하나가 발생하면 관리자 권한 검증 방식을 다시 검토한다.

- 관리자 API 호출량이 증가해 요청별 사용자 조회가 성능 문제로 확인됨
- `ADMIN` 외에 읽기 전용 관리자, 운영 관리자 등 여러 권한 단계가 필요해짐
- 서비스가 여러 인스턴스 또는 별도 관리자 서비스로 분리됨
- 관리자 권한 회수 지연을 허용하고 JWT 기반 무조회 검증이 더 중요해짐
- 사용자 역할 및 권한을 외부 Identity Provider에서 관리하게 됨
- 관리자 API가 `/api/v1/admin/**` 이외의 별도 보안 영역으로 분리됨
