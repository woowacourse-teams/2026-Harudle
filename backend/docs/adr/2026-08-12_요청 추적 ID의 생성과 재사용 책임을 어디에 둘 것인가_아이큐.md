# 2026-08-12 요청 단위 Trace ID 생성과 재사용

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 공통 오류 응답과 로그의 Trace ID 생성 및 재사용 전략

## 배경

서버는 동시에 많은 요청을 처리하므로 발생 시각이나 HTTP 상태만으로 특정 오류의 로그를 찾기 어렵다. 그렇다고 오류 응답에 내부
예외와 stack trace를 노출하면 구현 정보와 민감한 데이터가 외부에 드러날 수 있다.

클라이언트에는 안전한 공통 오류 정보와 불투명한 trace ID만 제공하고, 개발자는 그 값을 로그 검색에 사용해야 한다. 이때 요청 처리
중 여러 계층에서 서로 다른 trace ID를 만들면 로그와 오류 응답을 연결할 수 없다. 하나의 요청에서 생성된 값을 필터, 예외 처리기와
Problem Details 생성 과정이 동일하게 사용하도록 생성 및 재사용 책임을 결정해야 한다.

## 결정 요인

- 하나의 HTTP 요청에는 하나의 trace ID만 사용해야 한다.
- 로그 컨텍스트와 오류 응답의 trace ID가 같아야 한다.
- 내부 예외 정보나 stack trace를 클라이언트에 노출하지 않아야 한다.
- 요청 처리가 끝나면 스레드 로컬 로그 컨텍스트를 반드시 정리해야 한다.
- 난수 생성 때문에 테스트 결과가 비결정적이지 않아야 한다.
- trace ID 생성과 재사용 정책이 여러 오류 처리 코드에 중복되지 않아야 한다.

## 고려한 대안

### 대안 1: 오류 응답을 만들 때마다 trace ID 생성

각 예외 처리기 또는 응답 작성기가 필요한 시점에 새로운 값을 생성한다.

장점은 다음과 같다.

- 오류 응답 코드만 수정하면 된다.
- 성공 요청에는 trace ID 생성 비용이 들지 않는다.
- 별도 요청 컨텍스트 객체가 필요하지 않다.

단점은 다음과 같다.

- 오류가 발생하기 전의 로그에는 같은 식별자가 없다.
- 여러 오류 처리 경로가 서로 다른 값을 만들 수 있다.
- 로그와 클라이언트가 전달한 trace ID를 연결하기 어렵다.
- 난수 생성 코드가 여러 위치에 중복된다.

### 대안 2: 클라이언트가 보낸 식별자를 그대로 신뢰

요청 헤더의 식별자를 로그와 오류 응답에 사용한다.

장점은 다음과 같다.

- 프론트엔드부터 백엔드까지 동일한 값으로 요청을 연결할 수 있다.
- 서버가 별도 값을 생성하지 않아도 된다.
- 여러 외부 시스템을 거치는 요청을 추적하기 쉽다.

단점은 다음과 같다.

- 임의로 길거나 중복된 값이 로그에 유입될 수 있다.
- 검증하지 않은 사용자 입력을 로그 식별자로 신뢰하게 된다.
- 헤더가 없는 요청을 위한 별도 생성 정책이 여전히 필요하다.
- 향후 분산 추적 표준을 도입할 때 현재의 임의 계약과 충돌할 수 있다.

### 대안 3: 서버가 요청마다 생성하고 RequestTraceId가 재사용

서버가 요청 초기에 trace ID를 만들고 request attribute에 보관한다. 이후 필요한 모든 코드가 `RequestTraceId`를 통해 같은 값을
조회한다.

장점은 다음과 같다.

- 요청마다 하나의 서버 관리 식별자를 보장한다.
- 필터의 MDC와 Problem Details가 동일한 값을 사용할 수 있다.
- 생성 및 재사용 정책이 한 객체에 응집된다.
- 생성기를 주입하면 테스트에서 고정된 값을 사용할 수 있다.
- 클라이언트 입력을 로그 식별자로 직접 신뢰하지 않는다.

단점은 다음과 같다.

- 모든 요청에서 식별자를 생성하고 요청 속성에 저장한다.
- request attribute 이름과 생명주기를 서버 코드가 관리해야 한다.
- MDC는 스레드 로컬 기반이므로 요청 종료 시 정리가 필요하다.
- 비동기 작업으로 컨텍스트를 넘기려면 별도의 전파 전략이 필요하다.

## 결정

대안 3을 선택한다.

`TraceIdFilter`는 요청 초기에 `RequestTraceId.getOrCreate`를 호출하고 반환된 값을 MDC의 `traceId`에 넣는다. 필터 체인이 끝나면
`finally`에서 MDC 값을 제거한다. `ProblemDetailFactory`도 같은 `RequestTraceId`를 사용하므로 오류 응답의 `traceId`는 요청 로그
컨텍스트와 동일하다.

```text
HTTP 요청
→ RequestTraceId가 서버 trace ID 생성 및 request attribute 저장
→ TraceIdFilter가 같은 값을 MDC에 등록
→ 요청 처리와 로그 기록
→ Problem Details가 같은 값을 응답에 포함
→ TraceIdFilter가 MDC 정리
```

실제 난수 생성은 `TraceIdGenerator` 포트로 분리하고 구성 경계에서 UUID 기반 구현을 주입한다. 테스트에서는 고정 값을 반환하는
생성기를 주입해 생성 횟수와 재사용 여부를 검증한다.

현재는 외부 요청 헤더의 값을 trace ID로 채택하지 않는다. 향후 여러 서비스 간 분산 추적이 필요하면 W3C Trace Context 같은 표준과
신뢰 경계를 별도로 결정한다.

## 긍정적 결과

- 같은 요청의 로그와 Problem Details를 하나의 trace ID로 검색할 수 있다.
- 클라이언트에 내부 stack trace를 노출하지 않고 장애 문의에 필요한 연결 정보를 제공한다.
- 여러 예외 처리 경로가 같은 요청 식별자를 재사용한다.
- 난수 생성과 요청별 보관 책임이 분리되어 테스트가 결정적이다.
- MDC를 요청 종료 시 정리해 스레드 재사용으로 인한 식별자 누출을 막는다.

## 부정적 결과와 트레이드오프

- 애플리케이션 로그 출력 설정이 MDC의 `traceId`를 포함해야 실제 로그 검색에 사용할 수 있다.
- 비동기 실행이나 다른 서비스 호출에는 request attribute와 MDC가 자동으로 전파되지 않는다.
- 서버가 생성한 ID이므로 프론트엔드에서 이미 사용 중인 요청 ID와 자동으로 연결되지 않는다.
- trace ID는 오류 원인을 설명하지 않으므로 로그 보관과 검색 체계가 함께 운영되어야 한다.

현재 범위는 단일 백엔드 요청의 오류 응답과 로그를 연결하는 것이다. 분산 추적이 필요해질 때 표준 trace context와 관측성 도구를
도입하되, 요청마다 하나의 식별자를 생성하고 모든 오류 경로가 재사용한다는 원칙은 유지한다.
