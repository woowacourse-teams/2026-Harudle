# 2026-09-30 내부 생성 이력 코드는 세분화하고 사용자 API 오류 코드는 기존대로 반환

- 상태: 채택
- 작성일: 2026-09-30
- 작성자: 이산
- 결정 대상: 내부 생성 이력 코드와 사용자 API 오류 코드의 분리

## 배경

현재 생성 이력에는 서로 다른 실패 원인이 `AI_PROVIDER_ERROR`로 뭉쳐 기록될 수 있다. 원인 분석과 복구 정책 결정을 위해 내부 기록은 더 구체적이어야 한다. 반면 사용자에게 반환하는 API 오류 코드는 세부 원인을 모두 드러낼 필요가 없다.

## 결정

생성 이력에 저장하는 `GenerationErrorCode`는 확인 가능한 실패 원인에 따라 세분화한다. 예를 들어 429, `MAX_TOKENS`, JSON 처리 실패는 내부 이력에서 서로 다른 코드로 구분한다. 분류할 수 없는 그 밖의 AI 제공자 오류에는 기존 `AI_PROVIDER_ERROR`를 사용할 수 있다.

사용자 API 응답에 사용하는 `ErrorType`은 현재 계약을 유지한다. 내부 코드가 구체적으로 바뀌어도 사용자에게는 기존의 넓은 오류 코드를 반환한다. 예를 들면 다음과 같다.

| 저장되는 내부 `GenerationErrorCode` | 사용자 API `ErrorType` |
| --- | --- |
| `AI_OUTPUT_TRUNCATED` | `AI_PROVIDER_ERROR` |
| `AI_RESPONSE_PROCESSING_ERROR` | `AI_PROVIDER_ERROR` |
| `GENERATION_INTERNAL_ERROR` | `INTERNAL_SERVER_ERROR` |

즉, `AI_OUTPUT_TRUNCATED` 같은 코드는 생성 이력에만 구체적으로 저장하며 새로운 사용자 API 오류 코드로 추가하지 않는다. 기존 `AI_PROVIDER_TIMEOUT`, `IMAGE_STORAGE_ERROR`, `GENERATION_INTERRUPTED`의 API 코드는 유지한다.

## 이유

- 내부 실패 원인을 구분해 집계하고, 원인별 복구·운영 대응을 결정할 수 있다.
- 사용자 API 코드는 기존대로 유지해 프론트엔드 계약을 바꾸지 않고 내부 진단 정보도 불필요하게 노출하지 않는다.

## 결과

- `GenerationErrorCode`는 내부 생성 이력의 분류이고, `ErrorType`은 사용자 API 응답의 분류다. 두 코드는 같은 목적의 목록이 아니다.
- 내부 코드에서 API 코드로 변환하는 매핑을 테스트한다.
- 세부 내부 코드 목록과 각 오류의 분류 기준은 실패 원인 분류 결정에서 확정한다.
