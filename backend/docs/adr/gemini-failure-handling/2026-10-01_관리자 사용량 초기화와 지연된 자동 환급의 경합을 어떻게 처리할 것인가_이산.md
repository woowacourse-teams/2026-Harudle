# 2026-10-01 관리자 사용량 초기화와 지연된 자동 환급의 경합을 어떻게 처리할 것인가 - 이산

- 상태: 채택
- 작성일: 2026-10-01
- 작성자: 이산
- 결정 대상: 관리자 사용량 초기화 후 이전 생성의 지연된 실패 환급이 발생할 때의 처리 방식

## 배경

`daily_generation_usage`는 사용자와 날짜별 합계(`used_count`)를 저장한다. 관리자 초기화는 합계를 0으로 만들고, 생성 실패 환급은 저장된 `usage_date`의 합계를 1 줄인다. 합계만으로는 현재 사용량이 어느 생성 요청에서 비롯됐는지 구분할 수 없다.

다음 순서에서는 초기화 뒤 시작한 B의 사용량을 A의 늦은 환급이 대신 차감할 수 있다.

```text
A 시작: used_count 0 → 1, 상태 PROCESSING
관리자 초기화: used_count → 0
B 시작: used_count 0 → 1
A 실패 확정: 환급 쿼리가 used_count 1 → 0
```

이 경합이 발생하려면 다음 세 조건이 같은 사용자와 같은 `usage_date`에서 모두 겹쳐야 한다.

1. A의 사용량이 차감된 뒤에도 A가 `PROCESSING` 상태이고, 관리자가 해당 날짜의 사용량을 초기화한다.
2. 초기화 후 같은 사용자가 같은 날짜에 새 생성 B를 시작해 해당 사용량 합계가 다시 1 이상이 된다.
3. 그 후 A가 실패로 확정되어 자동 환급이 실행된다.

관리자 초기화만 발생하거나, 초기화 후 B의 사용량이 생기기 전에 A의 환급이 실행되는 경우에는 B의 사용량을 잘못 차감하는 문제가 발생하지 않는다.

환급 쿼리는 `used_count`가 0보다 작아지지 않도록 조건을 둔다. 따라서 초기화 뒤 다른 생성이 없다면 A의 늦은 환급은 0에서 아무것도 차감하지 않는다. 문제는 초기화 후 새 사용량이 생긴 경우, 그 사용량이 A의 차감분인지 B의 차감분인지 구분할 수 없다는 점이다.

관리자 초기화와 한도 변경은 같은 사용자 행 잠금을 사용하므로, 두 관리자 작업이 서로 동시에 값을 덮어쓰는 것을 막는다. 하지만 생성 시작과 실패 환급은 그 사용자 행 잠금을 사용하지 않고, 날짜별 사용량 합계를 직접 갱신한다. 따라서 기존 잠금은 관리자 작업끼리는 순서를 정해도, 초기화와 생성·실패 환급이 겹치는 상황까지 막지는 못한다. 사용량이 생성별 기록이 아닌 합계라서, 늦은 환급이 어떤 생성의 차감분을 되돌리는지도 구분할 수 없다.

## 고려한 대안

### 대안 1: 현재 동작을 유지하고 드문 사용량 오차를 수용

관리자 초기화와 생성 실패 환급의 추가 동기화나 저장 구조 변경은 하지 않는다. 환급은 기존대로 `PROCESSING`에서 `FAILED`로 처음 전이할 때 실행하고, 사용량이 0 아래로 내려가지 않도록 한다.

장점:

- 코드와 데이터베이스 변경이 없다.
- 관리자 초기화가 처리 중 생성 때문에 거절되거나 지연되지 않는다.
- 자동 실패 환급으로 관리자가 수동 초기화에 개입할 필요가 줄어들 것으로 기대한다.

단점:

- 조건이 겹치면 초기화 뒤 사용량이 실제보다 작게 기록될 수 있다.
- 그 결과 해당 사용자에게 의도하지 않은 추가 생성 기회가 생길 수 있다. 이는 해당 사용자에게는 이득으로 느껴질 수 있지만, 서비스는 추가 Gemini 호출 및 이미지 저장 비용을 부담할 수 있다.
- 일일 한도 준수와 사용자 간 형평성, 사용량 통계의 정확성이 낮아질 수 있다.

### 대안 2: 처리 중 생성이 있으면 초기화를 거절

초기화 대상 사용자에게 `PROCESSING` 생성이 있으면 관리자 요청을 거절하고, 생성이 끝난 뒤 다시 시도하도록 안내한다. 생성 선점과 초기화가 동일한 사용자 잠금으로 직렬화되어야 한다. 상태를 단순 조회한 뒤 초기화하는 것만으로는 조회와 갱신 사이에 새 생성이 시작되는 경합을 막지 못한다.

장점:

- 생성별 사용량 날짜 컬럼 외에 새 데이터를 추가하지 않고 경합을 예방할 수 있다.
- 처리 중인 요청과 초기화의 우선순위가 명확해진다.

단점:

- 관리자가 생성 완료 또는 실패 확정까지 기다려야 할 수 있다.
- 생성 선점 경로도 같은 잠금 규칙을 사용하도록 변경하고 테스트해야 한다.

### 대안 3: 초기화 버전(epoch)을 저장

초기화할 때 사용량 버전을 올리고, 생성 시작 시 그 버전을 생성 기록에 저장한다. 실패 환급은 생성 당시 버전과 현재 버전이 같을 때만 허용한다.

장점:

- 처리 중 생성이 있어도 초기화를 허용하면서 이전 생성의 늦은 환급이 새 사용량을 차감하지 않게 할 수 있다.

단점:

- 생성 기록과 사용량 데이터에 버전 정보 및 마이그레이션이 필요하다.
- 초기화 전 시작해 초기화 후 성공한 생성의 사용량을 어떻게 취급할지 정책을 추가로 정해야 한다.

## 결정

대안 1을 선택한다. 현재의 초기화와 환급 동작을 유지하고, `PROCESSING` 중 초기화를 거절하는 보호 로직이나 초기화 버전은 추가하지 않는다.

이 경합은 위 세 조건이 같은 사용자와 같은 사용량 날짜에서 모두 충족되어야 한다. 생성 실패 자동 복구가 도입되면 실패 보상을 위한 관리자 수동 개입이 줄어들 것으로 예상하므로, 이 경합이 발생할 기회도 제한적이라고 판단한다. 다만 발생 빈도를 계측한 자료는 없다. 경합이 발생하면 해당 사용자는 의도보다 한 번 더 생성할 수 있다. 이는 해당 사용자에게는 이득으로 느껴질 수 있지만, 서비스는 추가 생성 비용과 사용자 간 한도 형평성 및 사용량 통계의 정확성 저하를 감수한다. 현재는 이 잔여 위험을 별도 잠금이나 스키마 변경으로 제거하는 비용보다 낮게 평가한다.

## 결과

- 환급 조건에 따라 `used_count`가 0 아래로 내려가지는 않는다.
- 초기화 후 `used_count`가 0인 상태에서 이전 생성의 실패 환급이 와도, 0보다 작아지지 않도록 하는 조건에 따라 사용량은 0으로 유지된다.
- 초기화 후 새 사용량이 생긴 다음 이전 생성의 환급이 오면, 새 생성의 사용량이 대신 차감될 수 있다.
- 경합이 발생하면 의도하지 않은 추가 생성이 가능하며, 서비스 비용 및 사용량 통계 오차를 감수한다.
- 이 결정은 경합을 기술적으로 제거한 것이 아니라, 낮은 발생 가능성과 제한된 영향 범위를 근거로 현재는 수용한 것이다.

## 재검토 조건

- 관리자 초기화가 잦아지거나, 이 경합으로 사용량 오차가 실제 확인되는 경우
- 일일 생성 한도를 엄격한 비용·형평성 기준으로 보장해야 하는 경우
- 추가 생성으로 인한 비용이나 사용량 통계 오차가 감수 가능한 수준을 넘는 경우
