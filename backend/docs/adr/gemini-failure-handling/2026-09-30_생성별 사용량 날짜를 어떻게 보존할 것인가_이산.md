# 2026-09-30 생성별 사용량 날짜를 어떻게 보존할 것인가 - 이산

- 상태: 채택
- 작성일: 2026-09-30
- 작성자: 이산
- 결정 대상: 최종 실패한 생성의 사용량을 원래 차감 날짜에 복구하기 위해 생성별 사용량 날짜를 보존하는 방식

## 배경

일일 생성 사용량은 `daily_generation_usage`에서 `(user_id, usage_date)`별 합계로 관리한다. 차감 시 `GenerationUsageService`가 `LocalDate.now(serviceClock)`으로 날짜를 정해 해당 행의 `used_count`를 증가시킨다.

하지만 이 날짜는 개별 `DiaryGeneration`에 연결되어 저장되지 않는다. 생성 실패가 스케줄러에 의해 나중에 확정되면, 해당 생성이 어느 날짜의 사용량을 증가시켰는지 알 수 없어 원래 날짜에 정확히 복구하기 어렵다.

별도 ADR에서는 최종 실패한 생성의 횟수를 처음 차감한 날짜에 복구하고, 비회원 1회 체험 복구는 별도 논의하기로 했다. 이 ADR은 그 날짜를 생성 기록과 연결해 보존하는 방법을 비교한다.

## 결정 기준

- 차감 시 실제 사용한 날짜를 실패 기록과 정확히 연결한다.
- 실패 확정이 자정을 넘겨도 원래 날짜의 사용량을 복구한다.
- 날짜 계산을 `Clock`으로 제어해 테스트할 수 있다.
- 비회원의 별도 체험 정책과 기존 `PROCESSING` 기록의 배포 전환을 고려한다.
- 날짜의 의미가 코드와 데이터베이스에서 명확해야 한다.
- 정책 배포 전에 생성된 기록에는 사용량 복구 정책을 소급 적용하지 않는다.

## 고려한 대안

### 대안 1: `DiaryGeneration`에 `usage_date` 컬럼 추가

새 생성 요청을 선점할 때 `LocalDate.now(serviceClock)`을 한 번만 계산한다. 그 날짜를 `DiaryGeneration.usage_date`에 저장하고, 같은 날짜를 사용량 증가 쿼리에도 전달한다. 최종 실패 시에는 생성 기록의 `usage_date`를 읽어 해당 사용량 행을 복구한다.

`daily_generation_usage`는 생성별 내역이 아니라 사용자와 날짜별 합계다. 따라서 복구 시 `usage_date`만으로 사용자를 찾는 것이 아니다. 실패한 `DiaryGeneration`의 `diary_id`로 `Diary.user_id`를 확인하고, 두 값을 `(user_id, usage_date)`로 사용해 집계 행의 `used_count`를 1 줄인다.

```text
실패한 DiaryGeneration.diary_id ──→ Diary.user_id
실패한 DiaryGeneration.usage_date ─┘
                 ↓
daily_generation_usage의 (user_id, usage_date) 행을 찾아 used_count 감소
```

장점은 다음과 같다.

- 실제 차감에 사용한 날짜가 생성 기록에 명시적으로 남는다.
- 실패 확정 시점이나 서버 시간대에 영향받지 않고 원래 날짜를 복구한다.
- `Clock.fixed`로 차감과 복구 날짜 테스트를 결정적으로 작성할 수 있다.
- `created_at`의 기술적 의미를 사용량 정책에 겸용하지 않는다.

단점과 고려사항은 다음과 같다.

- `diary_generations`에 날짜 컬럼을 추가하는 Flyway migration이 필요하다.
- `DiaryGeneration`은 회원과 비회원 생성에서 함께 사용된다. 비회원은 `daily_generation_usage`에서 차감하지 않으므로, 비회원 행에는 `usage_date`를 비워 두거나 비회원 날짜의 의미를 별도로 정의해야 한다. 비회원 체험 복구 정책이 미정인 동안에는 회원 생성에만 값을 채우는 nullable 컬럼이 자연스럽다.
- 배포 전에 존재하는 생성 기록은 상태와 관계없이 backfill하지 않고 `usage_date`를 비워 둔다. 따라서 배포 전 시작된 `PROCESSING` 생성이 배포 후 실패하더라도 복구 대상이 아니다. 이는 과거 기록에 새 정책을 소급 적용하지 않기 위한 경계다.
- 구버전 애플리케이션 인스턴스가 남아 있는 동안 생성된 기록도 `usage_date`가 비어 있을 수 있다. 새 버전의 모든 인스턴스 배포가 끝난 뒤 생성된 회원 요청부터 복구 대상이 된다.

### 대안 2: 기존 `DiaryGeneration.created_at`에서 날짜 계산

`created_at`을 차감 날짜의 기준으로 사용하고, 실패 시 같은 시각을 서비스 시간대 날짜로 변환해 복구한다. 정확성을 보장하려면 생성 시각을 `serviceClock`에서 한 번 얻어 저장하고, 차감 날짜도 그 시각에서 계산해야 한다.

장점은 다음과 같다.

- 데이터베이스 컬럼 추가와 migration을 피할 수 있다.
- 이미 저장된 생성 시각을 이용해 지연된 복구 날짜를 재현할 수 있다.

단점과 고려사항은 다음과 같다.

- 현재 `created_at`은 `@CreationTimestamp`로 관리되어 `serviceClock`과 직접 연결되어 있지 않다. 이를 재사용하려면 생성 시각 관리 방식과 테스트를 변경해야 한다.
- 생성 시각이 사용량 날짜라는 두 번째 의미를 갖게 되어, 기술적 생성 시각과 업무상 차감 날짜가 결합된다.
- 기존 방식처럼 차감은 별도의 `LocalDate.now(clock)`으로 계산하면서 복구만 `created_at`에서 계산하면 두 시각이 자정을 사이에 둘 때 다른 날짜가 될 수 있다.

### 대안 3: 실패 확정 시점의 오늘 날짜로 복구

구현은 단순하지만 생성이 다음 날 `FAILED`로 확정되면 다음 날 사용량을 변경한다. 원래 차감한 날짜에 복구한다는 기존 결정과 다르므로 선택하지 않는다.

## 결정

`diary_generations`에 nullable `usage_date DATE` 컬럼을 추가한다. 회원 생성 요청을 선점할 때 `LocalDate.now(serviceClock)`을 한 번만 계산해 생성 기록에 저장하고, 같은 날짜를 사용량 차감에도 전달한다. 생성 기록 저장과 사용량 차감은 같은 트랜잭션에서 처리한다.

비회원 생성은 일일 사용량 집계에서 차감하지 않으므로 `usage_date`를 비워 둔다. 비회원 1회 체험 복구는 별도 정책이 정해질 때까지 이 결정의 범위에서 제외한다.

최종 실패 시 저장된 `usage_date`와 생성 소유자를 사용해 원래 날짜의 사용량을 복구한다. 복구는 `PROCESSING`에서 `FAILED`로 처음 전이할 때만 같은 트랜잭션에서 실행해 중복 복구를 막는다. 성공한 생성은 복구하지 않는다.

배포 전에 존재하는 기록은 상태와 관계없이 backfill하지 않고 과거 실패 건의 사용량도 환급하지 않는다. 따라서 배포 전에 시작된 생성이 배포 후 실패하더라도 복구하지 않는다. 새 버전의 모든 애플리케이션 인스턴스가 배포된 뒤 생성된 회원 요청부터 복구 대상이다.

## 이유

`created_at`을 사용량 날짜로 재해석하지 않고 실제 차감 날짜를 명시적으로 보존할 수 있다. 또한 기존 생성 기록은 날짜가 불확실하므로 소급 보정하지 않아 잘못된 날짜 복구와 과거 사용량의 중복 환급을 피한다.

## 결과

- `diary_generations`에 nullable 날짜 컬럼을 추가하는 Flyway migration이 필요하다. 기존 행은 null로 유지한다.
- 새 회원 생성은 `usage_date`를 저장하며, 비회원과 기존 기록은 null일 수 있다. 컬럼은 nullable로 두되 새 회원 생성에서 값이 채워지는 것은 애플리케이션 규칙으로 보장한다.
- 구버전 인스턴스가 남아 있는 동안 생성된 기록은 `usage_date`가 비어 있을 수 있으므로, 모든 인스턴스가 새 버전으로 전환된 뒤부터 새 복구 정책이 완전히 적용된다.

## 재검토 조건

- 비회원 1회 체험의 사용량 복구 정책이 정해지는 경우
- 생성 사용량의 기준 날짜나 서비스 시간대가 변경되는 경우
