# 2026-10-01 Gemini 요청 실패의 하위 예외 타입을 로그에 기록할 것인가

- 상태: 제안 (코드 변경 검토 중)
- 작성일: 2026-10-01
- 결정 대상: Gemini 공급자 호출 실패의 진단 로그

## 배경

스토리보드 응답을 받은 뒤 JSON 파싱에 실패한 경우에는 `finishReason`, 토큰 사용량과 `maxOutputTokens`를 기록한다. 예를 들어 `finishReason=MAX_TOKENS`라면 출력 한도에 도달했는지 확인할 수 있다.

반면 `models.generateContent(...)` 호출 중 예외가 발생하면 `GenerateContentResponse`를 얻지 못한다. 이 경로의 로그에는 `exceptionType=GenAiIOException`, `failureType=PROVIDER_ERROR`가 남지만 `finishReason`은 없다. 기존 로그만으로는 SDK 예외 안에 어떤 종류의 하위 예외가 있는지 구분하기 어렵다. 따라서 이 실패를 출력 토큰 한도 문제로 단정하거나 요청 시간 제한을 늘릴 근거가 부족하다.

## 결정

Gemini 공급자 실패를 `WARN`으로 기록할 때 기존 필드 뒤에 최하위 원인 예외의 단순 클래스명인 `rootCauseType`을 추가한다. 스토리보드 생성과 이미지 생성의 Gemini 요청 실패에 적용한다. 하위 예외가 없으면 바깥 예외의 클래스명을 기록한다.

기존 `failureType`, `exceptionType`과 로그 수준은 유지한다. S3 로그와 Gemini 응답 처리 실패 로그의 형식은 변경하지 않는다. 예외 메시지, 원인 체인, 요청·응답 본문은 기록하지 않는다.

## 이유

`GenAiIOException`만으로는 연결·시간 제한 등 내부 실패의 예외 종류를 구분할 수 없다. 하위 예외의 클래스명은 원문 메시지나 응답 내용을 노출하지 않으면서 후속 조사에 필요한 단서를 제공한다. 공급자 응답을 받지 못한 경로에 `finishReason`을 추가하는 것은 불가능하므로, 이미 있는 예외 원인 정보를 활용한다.

## 한계와 후속 확인

- `rootCauseType`은 진단 단서이며 단독으로 장애 원인을 확정하지 않는다.
- SDK 예외에 하위 원인이 없으면 `rootCauseType=GenAiIOException`으로 기록되어 새 정보가 없을 수 있다. 실제 운영 로그를 보고 추가 진단 정보가 필요한지 판단한다.
- 배포 후 `operation=storyboard_generation`, `failureType=PROVIDER_ERROR` 로그의 `rootCauseType` 분포를 확인한다. 관측된 원인에 따라 연결 설정, 시간 제한 또는 재시도 정책을 별도로 검토한다.
