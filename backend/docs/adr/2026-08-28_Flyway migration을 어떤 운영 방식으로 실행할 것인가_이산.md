# 2026-08-28 Flyway migration을 어떤 운영 방식으로 실행할 것인가

- 작성일: 2026-08-28
- 작성자: 이산
- 결정 대상: `diary_generations` 인덱스 추가와 `daily_generation_usage` 제약조건 변경 migration의 운영 실행 방식

## 문제

Flyway migration은 애플리케이션이 시작할 때 자동으로 실행된다. 현재 migration에는 다음과 같은 데이터베이스 변경이 포함되어 있다.

- `V9`: `diary_generations` 테이블에 일반 인덱스를 추가한다.
- `V10`: `daily_generation_usage`의 기존 데이터를 보정하고 생성량 체크 제약조건을 변경한다.

현재 데이터 규모에서는 두 작업이 오래 걸릴 가능성이 낮다. 다만 일반 인덱스 생성과 테이블 제약조건 변경은 실행 중 테이블 잠금을 획득할 수 있으므로,
데이터가 증가하거나 기존 트랜잭션이 오래 실행 중인 운영 환경에서는 요청이 대기할 수 있다.

## 결정

현재는 Flyway의 기본 트랜잭션 실행 구조와 `V9`, `V10`의 SQL을 유지한다.

- migration은 배포 시 점검시간에 실행하는 것을 기본 운영 정책으로 삼는다.
- 점검시간 없이 실행해야 하는 경우에도 migration을 별도 작업으로 복잡하게 분리하지 않고 실행할 수 있다.
- 실행 전 대상 테이블의 규모와 오래 열린 트랜잭션을 확인하고, 실행 중에는 migration 시간과 요청 대기 여부를 확인한다.
- 대규모 테이블에 새로운 인덱스를 추가해야 할 때는 별도 검토를 거쳐 `CREATE INDEX CONCURRENTLY`와 같은 온라인 방식을 사용한다.
- 이미 운영 데이터베이스에서 실행된 migration 파일은 수정하지 않는다. 실행 방식 변경이 필요하면 새로운 versioned migration이나 배포 단계에서 처리한다.

## 고려한 대안

### 대안 1: 모든 인덱스와 제약조건 변경을 온라인 방식으로 실행

인덱스는 `CREATE INDEX CONCURRENTLY`로 만들고, 체크 제약조건은 `NOT VALID`로 추가한 뒤 별도로 검증한다.

장점은 운영 중 쓰기 요청이 장시간 대기할 가능성을 낮출 수 있다는 점이다.

단점은 인덱스 migration을 Flyway 트랜잭션 밖에서 실행해야 하고, 실패한 인덱스 정리와 배포 순서를 별도로 관리해야 한다는 점이다.
현재 데이터 규모와 배포 구조에서는 얻는 이점보다 운영 복잡성이 크다.

### 대안 2: Flyway migration을 애플리케이션 시작과 분리

배포 파이프라인에서 migration을 먼저 실행하고, 완료된 뒤 애플리케이션을 시작한다.

장점은 migration 실행 시점, 잠금 상태와 실패 복구를 운영자가 통제하기 쉽다는 점이다.

단점은 배포 파이프라인과 실행 절차를 함께 변경해야 하며, 애플리케이션 시작 시 자동으로 스키마를 최신화하는 현재의 단순한 흐름을 잃는다는 점이다.

### 대안 3: 현재 방식을 유지하고 점검시간에 실행

기존 migration을 그대로 두고 트래픽이 낮은 시간에 실행한다.

장점은 Flyway의 트랜잭션 원자성과 현재 배포 구조를 유지하면서 구현·운영 복잡성을 늘리지 않는다는 점이다.

단점은 점검시간을 지키지 않으면 migration 중 요청이 대기할 가능성을 완전히 없앨 수 없다는 점이다.

## 이유

현재 서비스의 데이터 규모와 트래픽을 고려하면 `V9`, `V10`이 장시간 실행될 가능성은 낮다. 지금 온라인 migration을 도입하면 트랜잭션 경계,
실패한 concurrent index 정리, 배포 순서까지 함께 관리해야 하므로 문제의 규모에 비해 복잡성이 커진다.

점검시간 실행을 기본으로 하되 실행 전 상태를 확인하면 현재의 단순한 구조를 유지하면서 운영 위험을 관리할 수 있다. 데이터 규모나 트래픽이 증가하면
그 시점의 새 migration부터 온라인 방식을 적용한다.

## 결과

- `V9`, `V10` migration의 SQL과 Flyway 자동 실행 구조를 유지한다.
- 배포 시 점검시간 실행이 권장된다.
- 점검시간 없이 실행할 수는 있지만, 테이블 규모와 장기 트랜잭션에 따라 요청 대기가 발생할 수 있다.
- 향후 대규모 인덱스 추가 시에는 migration별 온라인 실행 방식과 배포 파이프라인 분리를 재검토한다.

## 재검토 조건

- `diary_generations`의 데이터 규모가 크게 증가하는 경우
- migration 실행이 수초 이상 지속되거나 운영 요청 대기가 관찰되는 경우
- 무중단 배포가 필수 요구사항이 되는 경우
- migration 실패 시 애플리케이션을 시작할 수 없는 현재 구조가 운영상 문제가 되는 경우
