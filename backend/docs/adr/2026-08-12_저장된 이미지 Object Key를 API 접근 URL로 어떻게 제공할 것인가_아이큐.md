# 2026-08-12 Object Key를 저장하고 응답 시점에 임시 접근 URL 발급

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 영속 이미지 식별자와 클라이언트 접근 URL의 경계

## 배경

생성된 이미지는 객체 저장소에 보관되고 DB의 생성 기록에는 이미지 위치를 연결해야 한다. 클라이언트는 Object Key가 아니라 HTTP로
접근할 수 있는 URL이 필요하다. 비공개 버킷의 presigned URL은 만료되므로 URL 자체를 DB에 저장하면 저장 직후에는 유효해도 나중에
조회할 때 만료될 수 있다.

Object Key를 그대로 프론트엔드에 보내면 클라이언트가 bucket, prefix와 서명 방식 같은 저장소 세부 정책을 알아야 한다. 저장소가
변경되거나 접근 정책이 바뀔 때 API 클라이언트까지 함께 수정된다. 영속 식별자와 일시적인 접근 자격을 어느 계층에서 변환할지
결정해야 한다.

## 결정 요인

- DB에 저장한 이미지 참조는 URL 만료와 무관하게 안정적이어야 한다.
- 비공개 저장소의 bucket과 Object Key를 클라이언트에 직접 노출하지 않아야 한다.
- S3 presign 같은 구체 구현이 일기 조회 서비스에 결합되지 않아야 한다.
- URL 만료 시각을 API 응답에서 명시할 수 있어야 한다.
- 저장소 구현을 교체해도 도메인과 조회 계약의 변경을 최소화해야 한다.
- URL 발급 어댑터가 없을 때 잘못된 주소를 반환하지 않아야 한다.

## 고려한 대안

### 대안 1: 이미지 접근 URL을 DB에 저장

장점은 다음과 같다.

- 조회할 때 URL 발급 호출이 필요하지 않다.
- 응답 조립이 단순하다.
- 공개 URL을 영구적으로 사용하는 저장소에서는 바로 접근할 수 있다.

단점은 다음과 같다.

- presigned URL이 만료되면 DB 값이 무효해진다.
- URL 갱신 때마다 영속 데이터를 수정해야 한다.
- bucket, CDN과 서명 정책 변경이 기존 데이터에 남는다.
- 영속 식별자와 일시적인 접근 자격이 혼합된다.

### 대안 2: Object Key를 클라이언트에 반환하고 프론트엔드가 URL 구성

장점은 다음과 같다.

- 백엔드가 URL을 발급하지 않아도 된다.
- DB 값을 그대로 응답할 수 있다.
- 공개 버킷에서는 구현이 단순하다.

단점은 다음과 같다.

- 저장소 구조와 접근 정책이 프론트엔드에 노출된다.
- 비공개 객체의 서명을 클라이언트가 안전하게 만들 수 없다.
- 저장소 변경 시 모든 클라이언트를 수정해야 한다.
- Object Key가 내부 구현 정보이자 공격 표면이 된다.

### 대안 3: Object Key만 저장하고 응답 시 URL 발급

장점은 다음과 같다.

- DB 참조는 URL 만료와 무관하다.
- 클라이언트는 저장소 구현을 알지 않고 완성된 URL만 사용한다.
- URL 발급을 `ImageUrlProvider` 포트 뒤에 숨길 수 있다.
- 상세 응답에 URL 만료 시각을 함께 제공할 수 있다.
- 저장소나 CDN을 바꿔도 포트 구현만 교체할 수 있다.

단점은 다음과 같다.

- 조회할 때마다 URL 발급 비용이 발생한다.
- 목록 항목이 많으면 여러 URL을 발급해야 한다.
- URL 발급 어댑터가 없으면 완성된 이미지 조회를 제공할 수 없다.
- 클라이언트는 URL 만료 후 API를 다시 호출해야 한다.

## 결정

대안 3을 선택한다.

DB의 `comic_generations.image_object_key`에는 안정적인 Object Key만 저장한다. 일기 애플리케이션 서비스도 Object Key를 결과로
전달하고, 프레젠테이션의 `DiaryResponseAssembler`가 응답을 만들 때 `ImageUrlProvider`를 호출해 임시 접근 URL로 변환한다.

```text
DB imageObjectKey
→ DiaryQueryService 결과
→ DiaryResponseAssembler
→ ImageUrlProvider.createAccessUrl
→ 임시 URL과 만료 시각
```

상세 응답에는 `imageUrl`과 `imageUrlExpiresAt`을 함께 제공한다. 월간 응답에는 썸네일 URL을 제공하되 만료 후에는 월간 API를 다시
조회해 새 URL을 받는다.

`ImageUrlProvider`의 실제 구현 선택은 구성 경계에서 수행한다. 어댑터가 구성되지 않았을 때 Object Key나 가짜 URL을 대신 노출하지
않고 명시적인 저장소 오류를 반환한다.

## 긍정적 결과

- 저장된 이미지 참조가 presigned URL 만료에 영향받지 않는다.
- S3 bucket, prefix와 서명 방식이 도메인 및 프론트엔드에 노출되지 않는다.
- 이미지 접근 정책 변경을 URL 제공 어댑터 안에 제한할 수 있다.
- 상세 응답 사용자는 URL의 유효 기간을 알 수 있다.
- 비공개 객체에 필요한 일시적 접근 권한을 요청 시점에 발급한다.

## 부정적 결과와 트레이드오프

- 월간 조회마다 각 이미지의 접근 URL을 발급하는 비용이 생긴다.
- 목록이 커지면 URL 발급의 배치 처리나 캐싱이 필요할 수 있다.
- 월간 썸네일 응답에는 만료 시각이 없어 프론트엔드가 만료를 선제적으로 판단할 수 없다.
- 실제 `ImageUrlProvider`가 구성되지 않으면 성공한 생성 결과 조회가 503으로 실패한다.
- 이미 발급된 URL은 일기를 삭제해도 저장소가 정한 만료 시각까지 유효할 수 있다.

현재 월간 범위는 최대 한 달이고 이미지 접근 보안이 URL 발급 비용보다 중요하다. 성능 문제가 확인되면 Object Key를 노출하지 않는
범위에서 배치 presign, 짧은 캐시 또는 CDN signed URL을 검토한다.
