# 2026-08-11 AI 생성 사용량 판단 책임을 Diary에 배치

- 작성일: 2026-08-11
- 작성자: 캐모
- 결정 대상: Diary와 Generation 사이의 생성 사용량 판단 책임

## 배경

사용자가 일기를 AI 만화로 생성하려면 일기 내용과 사용자 정보뿐 아니라 일일 생성 한도와 현재 사용량을 확인해야 한다.
DB에는 사용자와 날짜별 생성 사용량을 관리할 수 있는 정보가 있으며, 실제 만화 생성은 Generation 서비스가 담당한다.

Generation이 사용량을 직접 확인하면 생성 기능을 호출하는 모든 경로에서 한도 검증을 강제할 수 있다. 반면 사용량은 AI나 S3
호출 방법이 아니라 사용자가 해당 일기를 지금 생성할 수 있는지 판단하는 비즈니스 정책이다. 이 정책에는 사용자, 일기 날짜,
일기 상태와 향후 구독 등급 같은 Diary 주변 정보가 함께 필요할 수 있다.

Generation은 다른 도메인에서 요청받아 재사용될 수 있어야 하므로 사용량 판단을 Diary와 Generation 중 어디에 둘지 결정해야 한다.

## 결정 요인

- 사용량 제한을 사용자와 일기에 대한 비즈니스 정책과 함께 판단할 수 있어야 한다.
- Generation은 AI 제공자와 저장소를 이용한 실제 생성 흐름에 집중해야 한다.
- 사용량 정책이 바뀌어도 AI 생성 서비스와 어댑터에 미치는 영향이 작아야 한다.
- 사용량 검증을 빠뜨리고 Generation을 직접 호출하는 경로를 통제할 수 있어야 한다.
- 사용량 차감과 생성 작업 시작 사이의 정합성을 관리할 수 있어야 한다.
- 다른 호출자가 Generation 기능을 재사용할 가능성을 고려해야 한다.

## 고려한 대안

### 대안 1: Generation이 사용량을 확인하고 차감

```text
Diary
→ GenerateComicService
→ 사용량 확인 및 차감
→ AI 생성 실행
```

장점은 다음과 같다.

- Generation을 호출하는 모든 경로에 사용량 제한이 동일하게 적용된다.
- 생성 실행과 사용량 처리를 한 서비스에서 확인할 수 있다.
- 호출자가 사용량 검증을 빠뜨릴 가능성이 작다.

단점은 다음과 같다.

- Generation이 사용자 정책과 일기 상태를 알아야 한다.
- AI 생성 흐름과 사용량 정책이라는 서로 다른 변경 이유가 한 서비스에 결합된다.
- 사용량 정책 변경이 Generation 서비스와 테스트에 영향을 준다.
- 다른 도메인이 자체 정책으로 Generation을 재사용하기 어렵다.
- Generation이 Diary 또는 사용자 관련 저장소에 추가로 의존하게 된다.

### 대안 2: Diary가 사용량을 판단한 후 Generation을 호출

```text
Diary 요청 처리
→ 일기와 사용량 정책 검증
→ 사용량 처리
→ GenerateComicService 호출
→ AI 생성 실행
```

장점은 다음과 같다.

- 사용자와 일기에 대한 정책을 Diary 흐름에서 함께 판단할 수 있다.
- Generation은 생성 실행과 상태 저장에만 집중한다.
- 사용량 정책과 AI·S3 어댑터 변경이 서로 영향을 덜 준다.
- 다른 도메인은 자신의 정책을 적용한 후 Generation을 재사용할 수 있다.

단점은 다음과 같다.

- Generation을 직접 호출하면 사용량 검증을 우회할 수 있다.
- 호출자가 사용량 확인과 차감을 반드시 수행해야 한다.
- 사용량 차감 후 생성 작업 시작에 실패하는 부분 실패를 Diary에서 처리해야 한다.
- 여러 호출 경로가 생기면 사용량 정책이 중복될 수 있다.

### 대안 3: 별도의 Usage 서비스가 사용량을 전담

```text
Diary
→ GenerationUsageService
→ GenerateComicService
```

장점은 다음과 같다.

- 사용량 정책을 Diary와 Generation에서 분리할 수 있다.
- 여러 생성 기능이 동일한 사용량 정책을 공유하기 쉽다.
- 사용량 관련 테스트와 변경을 한 곳에 모을 수 있다.

단점은 다음과 같다.

- 현재 하나의 AI 만화 생성 흐름을 위해 별도 서비스와 계약이 추가된다.
- Diary가 사용량 서비스와 Generation 서비스를 함께 조합해야 한다.
- 사용량 차감과 생성 작업 시작 사이의 정합성 문제는 여전히 남는다.
- 향후 공유 요구가 확정되지 않은 상태에서 추상화가 먼저 만들어질 수 있다.

## 결정

대안 2를 선택한다.

이유는 다음과 같다.

- 사용량은 AI 생성 방법이 아니라 사용자와 일기의 생성 가능 여부를 판단하는 정책이다.
- Diary는 사용자, 일기 날짜와 일기 상태를 이미 알고 있으므로 사용량을 판단하기 적절하다.
- Generation은 요청받은 만화 생성 작업을 실행하고 성공·실패 상태를 저장하는 역할에 집중해야 한다.
- 현재는 사용량 정책을 공유할 다른 생성 기능이 없으므로 별도 Usage 서비스를 도입하지 않는다.

Diary의 요청 처리 흐름이 사용량을 확인하고 필요한 처리를 마친 후 `GenerateComicService`를 호출한다. Generation은
`GenerateComicCommand`의 사용자 ID와 일기 날짜를 요청 지문 생성에 사용할 수 있지만, 사용량 한도를 조회하거나 생성 가능 여부를
판단하지 않는다.

```text
Diary API 또는 애플리케이션 서비스
→ 일기 조회 및 권한 확인
→ 일일 생성 사용량 판단
→ GenerateComicService.generate(command)
```

Generation 패키지에는 사용량 Repository, 사용량 차감 로직과 Diary 요청 Controller를 추가하지 않는다.

## 긍정적 결과

- Diary의 사용자 정책과 Generation의 생성 실행 책임이 분리된다.
- 생성 한도나 사용량 차감 정책이 바뀌어도 AI 생성 서비스와 어댑터를 변경하지 않아도 된다.
- Generation 서비스는 스토리보드, 이미지 생성과 상태 저장 흐름에 집중할 수 있다.
- 다른 도메인이 자신의 정책을 적용한 후 Generation 기능을 재사용할 수 있다.
- Generation 테스트에서 사용자 사용량 저장소를 함께 설정할 필요가 없다.

## 부정적 결과와 트레이드오프

- `GenerateComicService`를 직접 호출하는 코드가 생기면 사용량 검증을 우회할 수 있다.
- Diary 요청 흐름이 사용량 확인, 차감과 Generation 호출 순서를 책임져야 한다.
- 사용량 차감 후 Generation의 원자적 선점이나 외부 호출이 실패하는 부분 실패를 별도로 처리해야 한다.
- 생성 실패 시 사용량을 복구할지 유지할지에 대한 정책이 Diary에 필요하다.
- 향후 여러 도메인이 같은 사용량 정책을 공유하면 검증 로직이 중복될 수 있다.

현재 사용량은 일기 생성 가능 여부를 판단하기 위한 정책이며 Generation을 사용하는 공식 진입점은 Diary가 될 예정이다. 따라서
직접 호출 우회 가능성은 패키지 의존성과 애플리케이션 조립을 통해 통제하고, 정책 공유 필요성이 생기면 별도 Usage 서비스 도입을
다시 검토한다.
