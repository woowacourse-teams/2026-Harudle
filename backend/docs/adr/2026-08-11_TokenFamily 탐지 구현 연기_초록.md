## 배경

하루들은 카카오 OAuth 로그인이 완료된 뒤 서비스가 자체 Access Token과 Refresh Token을 발급한다.
Access Token은 짧은 수명의 JWT로 발급하고, Refresh Token은 무작위 값으로 생성한다. 브라우저는
Refresh Token 원본을 HttpOnly Cookie로 보관하고, 서버는 원본 대신 SHA-256 해시만 저장한다.

현재 `refresh_tokens` 테이블은 사용자, 토큰 해시, 만료 시각, 폐기 시각을 저장한다. 따라서 사용된 Refresh
Token을 폐기하고 새로운 Refresh Token을 발급하는 Rotation은 구현할 수 있다.

하지만 현재 스키마에는 토큰 간 관계를 나타내는 `family_id` 또는 부모 & 자식 식별자가 없다. 공격자가 탈취한
Refresh Token을 정상 사용자보다 먼저 사용한 경우, 이후 기존 토큰의 재사용은 확인할 수 있지만 공격자에게
발급된 후속 토큰을 찾아 같은 로그인 세션 전체를 폐기할 수는 없다.

MVP에서는 제한된 사용자 규모와 권한 범위 안에서 로그인 및 토큰 재발급의 기본 흐름을 우선 완성해야 한다.
Token Family 도입은 데이터베이스 변경 자체보다 동시 Refresh 요청, 재사용 오탐, 트랜잭션 커밋 경계까지
함께 설계하고 검증해야 하므로 현재 범위에서 분리한다.

## 결정

MVP 인증에서는 Refresh Token Rotation을 구현한다.

- Refresh 요청이 성공하면 사용한 Refresh Token을 즉시 폐기한다.
- 새로운 Refresh Token을 발급하고 원본은 Cookie, 해시는 데이터베이스에 저장한다.
- 폐기되거나 만료된 Refresh Token은 거절한다.
- Token Family를 이용한 후속 토큰 추적과 같은 로그인 세션 전체 폐기는 MVP 범위에서 제외한다.

따라서 MVP 완료는 안전한 단일 토큰 Rotation과 재사용 거절까지를 의미한다. 탈취 토큰 재사용 시 후속 토큰까지
폐기하는 replay containment는 포함하지 않으며, 이를 운영 수준의 최종 보안 구현으로 간주하지 않는다.

## 검토한 대안

### Rotation 없이 하나의 Refresh Token을 만료 시까지 재사용

구현은 단순하지만 토큰이 탈취되면 만료 시점까지 반복 사용할 수 있다. 사용된 토큰을 폐기할 수 없으므로 채택하지
않는다.

### MVP에서 Token Family까지 구현

폐기된 토큰의 재사용을 발견하면 같은 로그인 세션의 활성 토큰을 모두 폐기할 수 있다. 보안상 가장 강한
대안이지만, 정상적인 동시 Refresh 요청도 탈취 재사용으로 판단할 수 있어 프론트엔드 single-flight, 서버의 행 잠금,
트랜잭션 커밋 경계와 통합 테스트가 함께 필요하다.
MVP 일정을 고려해 후속 작업으로 연기한다.

### Refresh Token을 발급하지 않고 Access Token 만료 시 다시 로그인

토큰 관리 범위는 줄어들지만 Access Token이 만료될 때마다 사용자가 카카오 로그인을 반복해야 한다.
MVP의 사용자 경험에 부합하지 않아 채택하지 않는다.

## 결과

- 현재 V1 스키마를 유지하면서 OAuth 로그인과 토큰 재발급 흐름을 완성할 수 있다.
- 하나의 Refresh Token은 한 번만 사용할 수 있으며, 사용 후 즉시 폐기된다.
- 원본 Refresh Token을 데이터베이스에 저장하지 않아 데이터베이스 유출 시 위험을 줄인다.
- Token Family에 필요한 동시성 및 재사용 탐지 정책을 별도 범위에서 충분히 검증할 수 있다.

## 트레이드 오프

- 공격자가 탈취한 Refresh Token을 정상 사용자보다 먼저 사용하면 공격자에게 후속 Refresh Token이 발급될 수 있다.
- 이후 정상 사용자가 기존 토큰을 제출해 재사용 사실이 드러나더라도 현재 스키마만으로 공격자의 후속 토큰을 찾아
  폐기할 수 없다.
- 계정 탈취가 발생하면 사용자의 일기 조회·삭제, 생성 횟수 소모, 공유 링크 생성 등 서비스 권한이 악용될 수 있다.
- 이 위험은 MVP 기간에 한해 수용하며, 공개 서비스 확대 전에 결정을 재검토한다.

## 재검토 조건

다음 조건 중 하나가 발생하면 Token Family 도입을 다시 검토한다.

- 정식 서비스 출시
- 결제 또는 관리자 권한 기능 도입
- Refresh Token 유효기간 연장
- 다중 기기 로그인과 로그인 세션 관리 기능 도입
- 사용자 또는 트래픽 규모 증가
- 보안 감사, 침해 사고 또는 Refresh Token 재사용 징후 발생
