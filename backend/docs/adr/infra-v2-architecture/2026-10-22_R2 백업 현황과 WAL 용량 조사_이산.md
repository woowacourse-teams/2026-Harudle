## 기존 백업이 처리하는 범위

현재 코드는 S3의 생성 이미지 원본을 R2로 복사한다.
DB 전체와 WAL을 보관하는 기능은 아니다.

- 원본 PNG, JPG와 WebP를 대상으로 한다. 다시 만들 수 있는 상세 이미지와 썸네일은 제외한다.
- 이미 백업한 원본도 다시 읽어 MIME, 크기와 SHA-256이 같은지 확인한다.
- 매 실행마다 운영 대상 전체를 순회한다. 새로 생긴 파일만 확인하는 방식은 아니다.
- 기존 백업을 덮어쓰거나 삭제하지 않는다.
- 자동 실행은 기본적으로 꺼져 있다. 운영 환경에서 별도로 켜야 한다.
- 운영 환경 변수의 원문은 확인하지 않았다. 후속 조회에서 10월 14일부터 22일까지의 실제 배치 완료 로그를 확인했다.

코드와 운영 절차는 [R2 저장소 설정](../../r2-storage-configuration.md), [이미지 백업 스케줄러](../../image-backup-scheduler.md), [수동 복구](../../image-recovery.md), [이미지 대체 조회](../../image-url-fallback.md)에 있다.
`ImageBackupScheduler`와 `ImageBackupService`, `application.yml`의 기본값도 함께 확인했다.

10월 16일부터 22일까지의 완료 기록에는 작업 예외가 없다.
다만 당시 실패한 8개를 각각 후속 성공 기록과 연결한 것은 아니므로, 8개 모두 복구됐다고 단정하지 않는다.
10월 22일 00:10:41 완료가 조회 시점의 최신 기록이다. 이후 추가 완료 기록은 조회되지 않았다.
다음 정기 실행인 10월 23일 00시는 아직 지나지 않았다.

## 현재 RDS의 WAL 수치

CloudWatch에서 `harudle-db`와 `harudle-dev-db`의 `TransactionLogsGeneration`을 조회했다.
2026-10-22 저녁 기준 최근 1주 범위에서 5분 평균값을 사용했다.
이 지표의 단위는 바이트/초다. [AWS 지표 정의](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-metrics.html)

| RDS 인스턴스 | 범위 내 평균 생성률 | 하루 환산값 |
| --- | --- | --- |
| Prod `harudle-db` | 약 225,329B/초 | 약 19.47GB/일 |
| Dev `harudle-dev-db` | 약 224,616B/초 | 약 19.41GB/일 |

하루 환산값은 화면 평균에 86,400초를 곱한 참고값이다.
CSV 원본을 받아 하루별 합계를 계산한 결과는 아니다.
또한 이 값은 압축한 R2 업로드 크기가 아니며, 새 EC2에서도 같다고 볼 수 없다.

Prod에는 DBeaver의 읽기 전용 연결로 통계 SELECT도 실행했다.

| 항목 | 2026-10-22 19:15 KST 확인값 |
| --- | --- |
| 조회한 DB | `harudle_prod` |
| 해당 DB 크기 | 25,015,999바이트, 약 23.86MiB |
| WAL 파일 한 개 크기 | 64MiB |
| `archive_timeout` | 5분 |
| `wal_compression` | `zstd` |
| `pg_stat_wal.wal_bytes` | 366,891,559바이트 |
| 위 통계의 초기화 시각 | 2026-02-24 06:13:41 KST |

DB 크기는 해당 DB 하나의 값이다. PostgreSQL 전체 물리 백업 크기를 뜻하지 않는다.
`wal_bytes`도 현재 디스크 점유량이 아니라 통계 초기화 이후의 누적 변경 기록량이다.
초기화 시각이 현재 서비스 운영 구간보다 오래됐으므로 이 누적값을 최근 하루 사용량으로 쓰지 않는다.
Dev 전용 RDS에는 SQL을 직접 실행하지 않았다. DBeaver의 기존 Dev 연결은 Prod RDS의 별도 DB를 가리켜 이번 Dev 통계로 사용하지 않았다.

## WAL 수치를 그대로 저장 비용으로 계산하면 안 되는 이유

WAL은 정해진 크기의 파일로 보관된다. 파일이 다 차기 전에 전환해도 보관할 파일 크기는 유지된다.
현재 Prod의 64MiB 파일이 5분마다 전환된다고 계산하면 약 19.33GB/일이다.
CloudWatch 하루 환산값과 비슷하므로 파일 전환의 영향이 클 가능성이 있다.
이는 설정과 숫자를 비교한 해석이며, 전체 원인을 측정으로 확정한 것은 아니다.
[PostgreSQL WAL 보관 설명](https://www.postgresql.org/docs/18/continuous-archiving.html)

직접 설치하는 PostgreSQL의 기본 WAL 파일 크기는 보통 16MiB다. 실제 생성한 DB에서 다시 확인한다.
짧은 주기로 전환할수록 보관 파일 수가 늘 수 있다. 반대로 전송을 늦추면 5분 데이터 유실 목표를 지키기 어려워질 수 있다.

`wal_compression=zstd`는 WAL 안의 전체 페이지 이미지 압축 설정이다.
S3와 R2에 올리는 파일 전체의 압축 설정과는 다르다.
pgBackRest 같은 도구는 백업 파일 압축을 별도로 제공하지만, 실제 압축률은 아직 측정하지 않았다.
[PostgreSQL WAL 설정](https://www.postgresql.org/docs/18/runtime-config-wal.html), [pgBackRest 압축 설정](https://pgbackrest.org/configuration.html#section-general/option-compress-type)

## 비용과 보관 기간을 정하기 전에 할 일

1. Dev에 이관할 PostgreSQL과 백업 도구를 준비한다. 현재 RDS의 데이터 디렉터리를 직접 읽을 수 있다고 가정하지 않는다.
2. 평상시와 부하 테스트 때 `pg_stat_wal.wal_bytes`를 시작과 끝에 조회한다. 초기화 시각이 같을 때만 차이를 계산한다.
3. 전체 백업 1개의 압축 후 크기와 하루 동안 외부에 보관한 WAL의 압축 후 합계를 측정한다.
4. 각 저장소에서 실제 복원하고, 다운로드와 WAL 적용 시간을 포함해 4시간 목표를 시험한다.
5. 이미지 증가량도 포함해 7일, 14일과 30일 보관안을 비교한 뒤 보관 기간을 결정한다.

저장 용량은 대략 보관하는 전체 및 차등 백업의 합계에 필요한 WAL의 합계를 더해 계산한다.
R2에는 기존 이미지 용량도 함께 반영한다. 백업 간 의존 관계 때문에 가장 오래된 백업을 복원하는 데 필요한 WAL까지 남겨야 한다.
pgBackRest의 `retention-full=2`는 기본적으로 전체 백업 두 개를 뜻한다. 두 주를 보장하는 값이 아니다.
[pgBackRest 보관 설정](https://pgbackrest.org/configuration.html#section-repository/option-repo-retention-full)

R2 Standard의 무료 제공량은 월 10GB-month, Class A 100만 회, Class B 1,000만 회다.
현재 크기 2.83GB와 월평균 저장량은 다르다. 무료 제공량은 이미지와 새 DB 백업을 합쳐 계산한다.
저장 초과분은 GB-month당 0.015달러이며 요청 비용과 AWS에서 보내는 전송 비용은 별도다.

## 이번 조사에서 확정하지 않은 것

- DB 백업의 실제 압축률, 하루 업로드 크기와 보관 기간
- 새 DB 백업용 버킷, 접근 권한과 삭제 방지 설정
- 운영 환경 변수 원문, 이번 조회에서 나오지 않은 과거 실행 이력과 S3 원본 부재 항목의 복구 가능 여부
- RDS 통계와 새 EC2 PostgreSQL 통계가 얼마나 다른지
- 두 저장소의 월 비용과 실제 복구 시간

DB나 저장소 설정 변경, 객체 쓰기와 삭제, 복원 작업은 실행하지 않았다.
