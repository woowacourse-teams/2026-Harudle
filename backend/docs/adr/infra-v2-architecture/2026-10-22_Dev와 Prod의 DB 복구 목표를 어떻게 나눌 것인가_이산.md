# 2026-10-22 Dev와 Prod의 DB 복구 목표를 어떻게 나눌 것인가

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 서버 적용 및 복구 시험 전
- 결정 대상: DB EC2 또는 데이터 볼륨을 잃었을 때 허용할 데이터 유실과 서비스 중단 시간

## 배경

Dev와 Prod는 PostgreSQL을 별도 EC2에서 운영할 계획이다.
서버가 멈추거나 데이터 볼륨을 잃으면 DB를 다시 실행하거나 백업을 복원해야 한다.
이때 얼마나 많은 데이터를 잃어도 되는지, 얼마나 빨리 복구해야 하는지 먼저 정한다.

Prod는 실제 사용자 데이터를 보관한다. Dev는 개발과 부하 테스트에 사용하므로
Prod보다 데이터 유실을 더 많이 허용한다. 장애 시 복구 대응은 Prod를 우선한다.

- RPO는 허용할 데이터 유실 시간이다. 24시간이면 장애 직전 최대 24시간의 기록을 잃을 수 있다.
- RTO는 서비스 중단부터 정상 복구까지 허용할 시간이다. RPO와 별도로 정한다.

## 결정 요인

- Prod의 사용자 데이터와 서비스 복구를 우선한다.
- Dev는 최근 테스트 기록의 일부를 잃는 것을 허용한다.
- EC2 총 네 대 운영 조건을 지키고 별도 대기 DB 비용을 추가하지 않는다.
- 복구 목표에 맞춰 백업 주기와 복원 절차를 정한다.
- 결정한 목표와 시험으로 확인한 실제 복구 시간을 구분한다.

## 고려한 대안

### 대안 1: Dev에도 Prod와 같은 목표 적용

두 환경 모두 데이터 유실 최대 5분, 서비스 복구 4시간 이내를 목표로 한다.

장점은 다음과 같다.

- Dev의 최근 테스트 기록도 짧은 범위 안에서 보호할 수 있다.
- 두 환경의 복구 구성을 비슷하게 운영할 수 있다.

단점은 다음과 같다.

- 중요도가 낮은 Dev에도 빠른 복구를 위한 자원과 운영 작업이 필요하다.
- 두 환경 모두 짧은 주기로 변경 기록을 보관하고 실제 복원 시간을 검증해야 한다.

### 대안 2: Dev의 데이터 유실을 최대 24시간까지 허용

Prod는 데이터 유실 최대 5분과 서비스 복구 4시간 이내를 목표로 하고, Dev는 최대 24시간의 데이터 유실과 다음 근무일 이내 복구를 허용한다.

장점은 다음과 같다.

- Dev에 Prod와 같은 복구 대응 수준을 요구하지 않고 운영 우선순위를 나눌 수 있다.
- 사용자 데이터가 있는 Prod의 복구 준비에 더 집중할 수 있다.

단점은 다음과 같다.

- Dev의 최근 테스트 기록과 설정 데이터가 최대 24시간만큼 사라질 수 있다.
- 사라진 데이터를 다시 만들거나 테스트를 다시 실행해야 할 수 있다.

## 결정

대안 2를 채택한다.
EC2는 Dev 앱, Dev DB, Prod 앱, Prod DB의 네 대로 운영한다. 별도 대기 DB는 두지 않는다.

| 환경 | 허용할 데이터 유실 시간 | 서비스 복구 시간 |
| --- | --- | --- |
| Prod | 최대 5분 | 중단 후 4시간 이내 |
| Dev | 최대 24시간 | 중단 후 다음 근무일 이내 |

이 수치는 설계와 운영의 목표다. 아직 시험으로 확인한 결과나 복구 시간을 보장하는 약속은 아니다.
Prod의 4시간에는 서비스 중단부터 장애 발견과 담당자 대응, 서버 준비, 데이터 복원과 앱 확인까지 포함한다.

Prod의 복구 완료는 DB 접속뿐 아니라 로그인과 일기 작성 등 주요 앱 기능이 정상인 시점으로 본다.
Dev의 24시간은 데이터를 얼마나 잃어도 되는지에 대한 결정이다.
Dev의 복구 완료 시간은 중단 후 다음 근무일 이내로 정한다.
다음 근무일까지 Dev를 쓰는 개발과 부하 테스트가 지연될 수 있다는 점을 받아들인다.

Prod는 외부 저장소에 보관한 백업과 WAL로 복원하는 방식을 먼저 설계한다.
WAL은 PostgreSQL의 데이터 변경 기록이다. 전체 백업에 이후 변경 기록을 적용해 데이터를 복원할 수 있다.
데이터 유실 5분 목표를 위해서는 실제 WAL 보관 지연과 실패를 감시해야 한다.
이 구성으로 4시간 안에 복구되는지는 아직 확인하지 않았다.
백업 도구는 pgBackRest, 저장소는 S3로 정했다. 물리 백업과 필요한 WAL을 보관한다.
백업 일정과 증분 방식은 [일간 물리 백업 ADR](<2026-10-22_Dev와 Prod의 일간 물리 백업을 증분 방식으로 만드는 이유_이산.md>)에 따른다.
두 환경의 WAL 파일 전환 간격은 1분이며 Prod 보관 기간은 30일로 정했다.
Dev 보관 기간과 복원 명령은 후속 설계에서 정한다.

백업 상태는 실행 예약 여부가 아니라 실제로 복구할 수 있는 마지막 데이터 시각으로 확인한다.
하루 한 번 실행하도록 예약해도 백업이 실패하거나 늦어지면 24시간 목표를 넘을 수 있다.
백업 일정이 같아도 Dev의 유실 목표는 최대 24시간으로 유지한다.
실패 경보와 대응 절차는 이 여유를 고려해 정한다.

이 목표는 DB EC2 또는 데이터 볼륨 손실을 대상으로 한다.
AWS 계정 전체나 서울 리전 장애, 삭제 실수를 뒤늦게 발견한 경우의 복구 목표는 별도로 정한다.

## 긍정적 결과

- Dev와 Prod의 중요도에 맞춰 복구 준비 수준을 나눌 수 있다.
- 백업과 장애 전환을 설계할 때 판단할 기준이 생긴다.
- Dev의 24시간을 복구 완료 시간으로 잘못 해석하는 일을 줄일 수 있다.

## 부정적 결과와 트레이드오프

- Dev에서는 최근 테스트 결과를 잃고 다시 작업해야 할 수 있다.
- Dev가 중단되면 다음 근무일까지 개발과 부하 테스트가 지연될 수 있다.
- 대기 DB가 없으므로 백업을 복원하는 동안 Prod 서비스가 중단될 수 있다.
- 4시간 목표 달성 여부는 데이터 크기, WAL 양, 서버 준비와 백업 다운로드 시간에 따라 달라진다.
- EC2를 추가하지 않아도 백업 저장소와 전송 비용은 발생할 수 있다.

## 후속 결정과 재검토 조건

- Dev를 다음 근무일 이내에 복구할 수 있도록 담당자, 근무일 기준과 복원 절차를 정한다.
- 백업은 S3에 보관하고 주간 전체 백업과 일간 증분 백업을 사용한다. 서버 재구축과 복원 절차를 정한다.
- Prod 보관 기간은 30일로 정했다. Dev 보관 기간과 실패 경보를 정한다.
- Dev에 다시 만들기 어려운 데이터가 늘면 24시간 기준을 재검토한다.
- 시험에서 목표를 넘으면 네 대 운영 조건 안에서 설정과 복원 절차를 개선하고, 그래도 어렵다면 복구 목표를 다시 논의한다.

## 구현과 검증

목표만 결정한 상태다. 새 EC2 구성과 백업 작업은 아직 적용하지 않았다.
복원 시험에서 마지막으로 복구한 데이터 시각과 주요 앱 기능 복구 시각을 기록한다.
서비스 중단부터 경보 확인, 서버 준비, 백업 다운로드, WAL 적용과 앱 기능 확인까지 모두 측정한다.
측정 결과를 이 목표와 비교한 뒤 달성 여부를 판단한다.
