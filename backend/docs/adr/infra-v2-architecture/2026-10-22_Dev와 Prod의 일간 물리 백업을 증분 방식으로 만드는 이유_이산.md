# 2026-10-22 Dev와 Prod의 일간 물리 백업을 증분 방식으로 만드는 이유

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 서버 적용 및 복원 시험 전
- 결정 대상: Dev와 Prod PostgreSQL의 일간 물리 백업 방식

## 배경

처음에는 매일 전체 물리 백업을 만들기로 했지만, 30일 보관 시 반복 저장되는 용량을 줄이기로 했다.
하루 한 번 백업하는 일정은 유지하되, 평소에는 직전 백업 이후 변경된 부분을 저장한다.
전체 백업은 주 1회 새로 만들어 증분 백업의 기준을 갱신한다.
전체 백업과 변경분 백업은 모두 물리 백업이다. WAL 보관은 별도로 계속 수행한다.

## 결정 요인

- 매일 전체 백업을 새로 저장하는 대신 변경분을 보관한다.
- t4g.small의 백업 부하와 S3 저장량을 줄이는 방향으로 설계한다.
- 복원에 필요한 백업 사이의 의존 관계와 WAL은 pgBackRest로 관리한다.
- Dev에서도 같은 백업 방식을 적용해 실제 부하를 확인한다.

## 고려한 대안

### 대안 1: 매일 전체 백업

장점은 선택한 전체 백업이 이전 백업에 의존하지 않는다는 점이다.
단점은 매일 전체 데이터를 반복해 저장하고 전송한다는 점이다.

### 대안 2: 매일 차등 백업

장점은 마지막 전체 백업 이후 변경된 파일만 저장하고, 복원에 필요한 백업 의존 관계가 증분보다 단순하다는 점이다.
단점은 같은 파일이 여러 날에 걸쳐 변경되면 각 차등 백업에 다시 포함될 수 있다는 점이다.

### 대안 3: 매일 증분 백업

장점은 직전 성공한 백업 이후 변경된 파일을 저장하므로 차등보다 반복 저장을 줄일 수 있다는 점이다.
단점은 복원하려는 증분 백업뿐 아니라 그 백업이 의존하는 이전 백업들도 정상이어야 한다는 점이다.

## 결정

대안 3을 채택한다. Dev와 Prod 모두 주 1회 전체 물리 백업을 만들고, 나머지 6일은 하루 한 번 증분 백업을 만든다.

1. 처음에는 전체 물리 백업을 만들어 복원의 기준을 준비한다.
2. 전체 백업은 주 1회 pgBackRest의 `--type=full`로 실행한다.
3. 나머지 6일은 하루 한 번 `--type=incr`로 증분 백업한다.
4. 두 환경 모두 한국 시간 일요일 04:00에 전체 백업하고, 월요일부터 토요일까지 04:00에 증분 백업한다. 일요일에는 정기 증분 백업을 중복 예약하지 않는다.
5. WAL 보관은 계속 수행하며 두 환경의 `archive_timeout`은 1분으로 유지한다.
6. Prod는 최근 30일의 특정 시점 복구에 필요한 전체 백업, 증분 백업과 WAL을 함께 보관한다.

기본 증분 백업은 변경된 파일을 저장한다. 변경된 행만 저장하는 방식은 아니다.
파일 내부의 변경된 부분만 저장하는 블록 증분 기능의 사용 여부는 아직 정하지 않았다.
증분 백업은 마지막 성공 백업을 기준으로 하므로, 하루 실패했다고 무조건 복원 연결이 끊기는 것은 아니다.
다만 그만큼 백업 간격과 다음 증분 작업의 범위가 늘 수 있다.
Prod와 Dev의 기존 복구 목표는 유지한다. Dev 보관 기간은 7일로 정했다.

### 실행 일정

| 작업 | Dev와 Prod 공통 일정 | 시간대 |
| --- | --- | --- |
| 전체 물리 백업 | 매주 일요일 04:00 | Asia/Seoul |
| 증분 물리 백업 | 매주 월요일부터 토요일까지 04:00 | Asia/Seoul |
| WAL 보관 | 계속 수행, 파일 전환 기준 1분 | 백업 일정과 별개 |

사용자 요청이 적을 것으로 예상되는 새벽 시간을 초기 일정으로 선택했다.
시간대별 실제 이용량으로 최저 이용 시간임을 확인한 결과는 아니다.
기존 이미지용 R2 백업은 확인한 운영 로그에서 한국 시간 00시경 시작했다. DB 백업의 초기 시작 시각은 이 작업과도 간격을 두었다.
실제 작업 시간이 길어지면 겹칠 수 있으므로 실행 이력으로 확인한다.
예약 설정에 한국 시간 기준을 명시하고, 실행 로그에서도 한국 시간 04:00에 시작하는지 확인한다.

## 긍정적 결과

- 매일 전체 백업을 반복 저장하는 대신 변경분 중심으로 보관할 수 있다.
- Dev와 Prod에서 같은 방식의 백업 부하를 시험할 수 있다.

## 부정적 결과와 트레이드오프

- 필요한 이전 백업이 없거나 손상되면 그 자료에 의존하는 증분 백업도 복원하지 못할 수 있다.
- 백업은 변경 여부를 확인하는 작업도 수행하므로 DB 디스크 읽기와 CPU 부담이 없어지는 것은 아니다.
- WAL 발생량과 보관량은 증분 백업을 선택하는 것만으로 줄어들지 않는다.
- 보관 범위의 복원 시작점과 백업 의존 관계 때문에 30일보다 오래된 자료가 추가로 필요할 수 있다.

## 후속 결정과 재검토 조건

- 실행 예약 도구를 정하고, 한국 시간 기준과 중복 실행 방지 방법을 설정한다.
- 기존 예약 작업이나 배포와 겹쳐 DB 성능이 나빠지면 실행 시간을 재검토한다.
- 백업과 WAL 압축은 두 환경 모두 Zstandard 수준 1로 정했다. Dev 보관 기간은 7일로 정했다. 블록 증분 사용 여부를 정한다.
- 보관 정리는 pgBackRest에 맡기고, 복원에 필요한 백업과 WAL을 임의로 삭제하지 않는다.
- 증분 자료를 포함한 복원이 4시간을 넘거나 백업 부하가 크면 전체 백업 주기와 방식을 재검토한다.

## 구현과 검증

백업 방식과 실행 일정을 결정했다. 서버 설정과 실행 예약은 아직 적용하지 않았다.
실제 실행 요일과 시간대, 백업 종료 상태와 실패 알림을 확인한다.
Dev에서 전체 백업과 증분 백업, WAL 전송 중 DB 응답 시간과 CPU, 디스크 사용량을 기록한다.
전체 백업과 여러 날의 증분 백업을 바탕으로 복원한 뒤, 추가 WAL을 적용해 시험 데이터를 확인한다.
백업 하루 실패 후 다음 증분 백업과 복원이 가능한지, 보관 정리 후에도 필요한 자료가 유지되는지 확인한다.
시험은 원본 DB를 덮어쓰지 않도록 격리된 환경에서 수행한다.
