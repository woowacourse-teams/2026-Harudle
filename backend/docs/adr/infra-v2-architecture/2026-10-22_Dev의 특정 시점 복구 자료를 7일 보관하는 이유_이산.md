# 2026-10-22 Dev의 특정 시점 복구 자료를 7일 보관하는 이유

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 서버 적용 및 복원 시험 전
- 결정 대상: Dev의 물리 백업과 WAL 보관 범위

## 배경

Prod는 최근 30일의 특정 시점 복구 자료를 보관한다.
Dev는 개발과 부하 테스트에 사용하므로, 같은 기간을 보관하기보다 저장량을 줄이기로 했다.
백업 작업 자체의 부하를 시험할 수 있도록 백업 일정, WAL 간격과 압축은 Prod와 맞춘다.

## 결정 요인

- Dev의 백업과 WAL 저장량을 줄인다.
- 최근 일주일의 개발과 테스트 상태를 복구할 수 있도록 준비한다.
- 부하 테스트에 필요한 백업 실행 조건은 Prod와 맞춘다.

## 고려한 대안

### 대안 1: Prod와 같은 30일

장점은 더 오래전 Dev 상태까지 복구할 수 있고, 보관 기간도 같게 운영할 수 있다는 점이다.
단점은 중요도가 낮은 Dev 자료를 더 오래 저장하고 비용을 부담한다는 점이다.

### 대안 2: 7일

장점은 최근 일주일 복구를 준비하면서 30일 보관보다 저장량을 줄일 수 있다는 점이다.
단점은 일주일보다 늦게 발견한 잘못된 변경 이전의 자료가 이미 정리됐을 수 있다는 점이다.

## 결정

대안 2를 채택한다. Dev는 최근 7일 안의 원하는 시점으로 복구하는 것을 보관 목표로 정한다.

- 이 범위를 복구하는 데 필요한 전체 백업, 증분 백업과 연속된 WAL을 함께 남긴다.
- 주 1회 전체 백업을 사용하므로, 7일 전의 복원 시작점이 되는 더 오래된 전체 백업이 필요할 수 있다.
- 필요한 백업 간 의존 관계를 유지하고, 정리는 pgBackRest 보관 규칙에 맡긴다.
- 생성 후 7일이 지난 S3 객체를 일괄 삭제하는 규칙으로 구현하지 않는다.
- 전체 백업은 한국 시간 일요일 04:00, 증분 백업은 월요일부터 토요일까지 04:00에 실행한다.
- WAL 파일 전환은 1분, 백업과 WAL 압축은 Zstandard 수준 1로 Prod와 같게 유지한다.

Dev의 데이터 유실 최대 24시간과 다음 근무일 이내 복구 목표는 유지한다.
7일은 과거 어느 시점까지 복구할지에 대한 범위이며, 데이터 유실 허용 시간이나 서비스 복구 시간과 다르다.

## 긍정적 결과

- Prod보다 짧게 보관해 Dev의 저장량과 비용을 줄일 수 있다.
- 실제 백업과 WAL 전송을 유지해 Dev에서 성능 영향을 시험할 수 있다.

## 부정적 결과와 트레이드오프

- 7일보다 오래된 특정 시점 복구는 초기 보관 목표에 포함하지 않는다.
- 복원 시작점과 증분 자료 때문에 실제 저장량이 정확히 7일치로 제한되지는 않는다.
- 보관 정리의 부하와 오래된 자료를 사용하는 복원 조건은 Prod와 다를 수 있다.

## 후속 결정과 재검토 조건

- Dev와 Prod 각각의 pgBackRest 보관 설정과 실제 비용을 확인한다.
- Dev에 다시 만들기 어려운 자료가 늘거나 문제를 늦게 발견하면 보관 기간을 재검토한다.

## 구현과 검증

보관 목표만 결정했다. 서버 설정과 삭제 작업은 아직 적용하지 않았다.
격리된 시험 저장소에서 정리 이후에도 최근 7일의 복원 시작점과 필요한 증분 백업, WAL이 남는지 확인한다.
보관 경계 시점의 복원을 시험하고 실제 저장량을 기록한다.
Prod의 30일 보관 검증은 별도로 수행한다.
