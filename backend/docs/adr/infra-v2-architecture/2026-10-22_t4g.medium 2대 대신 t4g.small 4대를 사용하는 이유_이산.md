# 2026-10-22 t4g.medium 2대 대신 t4g.small 4대를 사용하는 이유

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 서버 적용 및 부하 테스트 전
- 결정 대상: RDS를 EC2의 PostgreSQL로 옮길 때 앱과 DB를 배치하는 방법

## 배경

처음에는 Dev와 Prod에 `t4g.medium`을 한 대씩 두려고 했다.
각 EC2 안에서 Spring Boot, 프론트엔드와 PostgreSQL을 Docker 컨테이너로 실행하는 방식이다.
서버 수가 적고, 한 환경에서 4GiB 메모리를 나누어 쓸 수 있다.

하지만 EC2를 재시작하거나 교체하면 앱과 DB가 함께 멈춘다.
앱의 CPU와 메모리 사용이 늘어도 같은 서버의 DB에 영향을 줄 수 있다.
우리는 앱 작업 때문에 DB까지 중단되는 일을 줄이는 것을 더 중요하게 봤다.

앱 컨테이너 하나가 멈췄다고 DB 컨테이너도 반드시 멈추는 것은 아니다.
배포 대상을 나누면 앱만 교체할 수 있다. 그래도 EC2 자체의 중단과 서버 자원 부족은 함께 겪는다.
이번 결정은 이 위험을 줄이기 위한 것이다.

## 결정 요인

- 앱 EC2를 재시작하거나 교체해도 DB EC2는 계속 실행할 수 있어야 한다.
- 앱과 DB가 같은 서버의 CPU와 메모리를 두고 경쟁하는 일을 줄여야 한다.
- 앱과 DB 중 자원이 부족한 서버만 크기를 바꿀 수 있어야 한다.
- Dev와 Prod의 기본 구성을 맞춰 부하 테스트 조건의 차이를 줄여야 한다.
- 서버 수가 늘어나는 관리 부담과 Node.js 추가 시 메모리 부족 가능성을 감당할 수 있어야 한다.

## 고려한 대안

### 대안 1: t4g.medium 2대에 앱과 DB를 함께 배치

Dev와 Prod에 EC2를 한 대씩 두고 앱과 PostgreSQL을 함께 실행한다.

장점은 다음과 같다.

- 관리할 OS와 에이전트가 두 벌이다.
- 환경마다 4GiB 메모리를 앱과 DB의 사용량에 따라 나누어 쓸 수 있다.
- 앱과 DB가 같은 서버에서 통신하므로 서버 사이의 연결 설정이 줄어든다.
- OS용 디스크가 두 개여서 네 대 구성보다 중복 저장 공간이 적다.

단점은 다음과 같다.

- EC2를 재시작하거나 교체하면 앱과 DB가 함께 멈춘다.
- 앱과 DB가 같은 EC2의 CPU, 메모리와 디스크 처리 성능을 나누어 쓴다.
- 앱과 DB 중 한쪽만 자원이 부족해도 같은 EC2의 크기를 바꿔야 한다.

### 대안 2: t4g.small 4대에 앱과 DB를 나누어 배치

Dev와 Prod에 앱 EC2와 PostgreSQL EC2를 한 대씩 둔다.

장점은 다음과 같다.

- 앱 EC2를 재시작하거나 교체할 때 DB EC2를 함께 멈추지 않아도 된다.
- 앱이 사용하는 메모리와 CPU를 DB 서버 자원과 분리할 수 있다.
- 앱과 DB 중 자원이 부족한 서버만 크기를 바꿀 수 있다.

단점은 다음과 같다.

- 관리할 OS와 에이전트가 네 벌로 늘어난다.
- 서버마다 2GiB로 나뉘므로 다른 서버에 남는 메모리를 사용할 수 없다.
- 서버 사이의 DB 주소, 보안 그룹과 네트워크 경로를 설정해야 한다.
- OS용 디스크가 늘어난다. IP 구성과 통신 경로에 따라서도 비용이 달라진다.

`t4g.small`은 2 vCPU와 2GiB 메모리, `t4g.medium`은 2 vCPU와 4GiB 메모리를 제공한다.
두 구성의 전체 메모리는 8GiB로 같다. 다만 네 대 구성은 OS와 에이전트도 네 벌 실행한다.
메모리 총합이 같아도 앱이 실제 사용할 수 있는 메모리까지 같은 것은 아니다.
CPU도 네 대 구성에서는 서버별로 나뉘며, T4g의 CPU 크레딧 상태를 함께 확인해야 한다.
사양은 [AWS T4g 안내](https://aws.amazon.com/ec2/instance-types/t4/)를 기준으로 한다.

이 결정은 전체 요금이 같다는 계산에 근거하지 않는다.
디스크, IP, 백업 저장소와 가용 영역 사이의 통신을 포함한 비용은 실제 배치가 정해진 뒤 계산한다.

## 결정

대안 2를 채택한다. Dev와 Prod에 앱용 EC2와 DB용 EC2를 각각 둔다.
네 대 모두 `t4g.small`로 시작하고 상시 실행한다.
추가 EC2 비용을 들이지 않도록 총 네 대 안에서 운영한다. 별도 대기 DB는 두지 않는다.

서버 수를 줄이는 것보다 앱 서버 작업이 DB 중단으로 이어지는 일을 줄이는 것을 우선한다.
Node.js 전용 서버는 처음부터 추가하지 않고, 앱 서버에서 함께 실행한 결과를 보고 결정한다.

| 환경 | 앱 서버 | DB 서버 |
| --- | --- | --- |
| Dev | t4g.small 1대 | t4g.small 1대, PostgreSQL |
| Prod | t4g.small 1대 | t4g.small 1대, PostgreSQL |

1. 앱 서버에는 Spring Boot와 프론트엔드 컨테이너를 배포한다. SSR을 위한 Node.js도 먼저 이곳에서 실행한다.
2. DB 서버에는 PostgreSQL과 백업에 필요한 도구를 둔다. DB 데이터는 EBS 볼륨에 보관한다.
3. 앱은 같은 환경의 DB에 사설 IP로 접속한다. DB의 5432 포트는 해당 앱 보안 그룹에서만 접근하도록 제한한다. 관리 접속 방법은 보안 ADR에서 따로 정한다.
4. CodeDeploy의 앱 배포는 앱 서버만 대상으로 한다. DB 서버의 컨테이너와 데이터 볼륨은 앱 배포 작업에 포함하지 않는다.
5. 앱 서버와 DB 서버의 CPU, 메모리, 디스크와 중단 상태를 각각 확인한다. 연결 수와 느린 쿼리 등 앱이 DB에 주는 부하도 확인한다.

DB를 다른 EC2에 두므로 같은 Docker 네트워크의 서비스 이름만으로 연결할 수 없다.
DB 주소, 보안 그룹과 네트워크 경로를 별도로 설정해야 한다.
또한 Dev와 Prod의 사양을 맞춰도 데이터 양과 동시 요청 수가 다르면 부하 테스트 결과는 달라질 수 있다.

## 긍정적 결과

- 앱 EC2의 재시작과 교체를 DB EC2의 중단 없이 진행할 수 있다.
- 앱 서버의 메모리 부족이 DB 서버의 메모리를 직접 차지하지 않는다.
- 앱과 DB의 자원 사용량을 각각 확인하고 필요한 서버만 확장할 수 있다.
- 앱 배포 대상에서 DB 서버와 데이터 볼륨을 분리할 수 있다.

## 부정적 결과와 트레이드오프

- 서버가 네 대로 늘어 OS 업데이트, 접근 권한과 경보를 각각 관리해야 한다.
- 전체 메모리는 같아도 OS와 에이전트가 더 많은 메모리를 사용한다. 서버 사이에 남는 메모리를 공유할 수도 없다.
- 앱이 많은 쿼리를 보내거나 연결을 오래 점유하면 분리한 DB에도 부하가 생긴다.
- DB EC2가 멈추면 해당 환경의 앱도 DB를 쓰는 기능을 제공할 수 없다.
- RDS를 없애면 PostgreSQL 업데이트, 백업, 복원과 장애 대응을 우리가 맡아야 한다.

## 후속 결정과 재검토 조건

### Node.js를 함께 실행할 때 메모리가 부족한 경우

앱 서버의 2GiB 메모리로 Spring Boot와 Node.js를 함께 운영할 수 있는지는 아직 확인하지 않았다.
현재 배포 설정의 백엔드 메모리 상한은 `1200m`이고, 프론트엔드는 정적 파일을 제공하는 Nginx다.
이 값만으로 Node.js까지 충분하다고 판단하지 않는다.
SSR 적용 후 평시와 부하 테스트에서 실제 메모리 사용량, 응답 시간과 메모리 부족에 따른 종료를 확인한다.
부족하면 네 대 안에서 메모리 설정과 서버별 규격을 조정하는 안을 먼저 검토한다.
기존에 검토했던 Node.js용 `t4g.micro` 추가안은 현재 네 대 운영 조건에 포함하지 않는다.

### Prod 복구 목표를 검증하는 경우

**이 4대 구성은 DB 장애 때 자동으로 대체할 서버가 없는 기본 구성이다.**
추가 EC2 비용을 들여 대기 DB를 운영하지 않는다.
Prod의 데이터 유실 최대 5분, 서비스 복구 4시간은 목표로 유지한다.
외부에 보관한 백업과 WAL로 DB를 복원하는 절차를 준비하고 실제 복원 시험으로 시간을 확인한다.
복원 중에는 DB를 사용하는 서비스가 중단된다. 시험 전에는 4시간 안에 복구할 수 있다고 보장하지 않는다.
목표를 넘으면 네 대 운영 조건 안에서 복원 절차와 백업 구성을 개선하고, 그래도 어렵다면 복구 목표를 다시 논의한다.

백업 보관 기간은 [Prod 30일 보관 ADR](<2026-10-22_Prod의 특정 시점 복구 자료를 30일 보관하는 이유_이산.md>)에 따르며 Dev 기간은 미정이다.
DB 보안과 복원 절차는 후속 ADR에서 정한다.
운영 부담이나 전체 비용이 감당하기 어렵다면 RDS 유지안도 다시 비교한다.

## 구현과 검증

이 문서는 서버 배치에 대한 결정이다. 현재 배포 설정은 앱 EC2와 RDS를 사용하는 구성이며,
EC2 PostgreSQL 구성과 SSR용 Node.js는 아직 적용하지 않았다.

적용할 때는 다음을 확인한다.

- 앱 배포와 앱 EC2 재시작 중에도 DB EC2가 계속 실행되는지 확인한다.
- 같은 환경의 앱 서버만 DB 포트에 접근할 수 있는지 확인한다.
- Node.js를 함께 실행하고 평시와 부하 테스트에서 CPU, 메모리, 응답 시간과 종료 기록을 확인한다.
- Dev와 Prod의 데이터 양, 동시 요청 수와 CPU 크레딧 상태를 기록해 테스트 결과를 비교한다.
