# 2026-10-22 Dev와 Prod의 WAL 파일 전환 간격을 1분으로 맞추는 이유

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 서버 적용 및 검증 전
- 결정 대상: Dev와 Prod PostgreSQL의 WAL 파일 전환 간격

## 배경

Prod는 데이터 유실 최대 5분을 목표로 한다.
Dev에서도 같은 WAL 보관 설정으로 부하 테스트해, Prod에서 발생할 수 있는 자원 경합과 전송 지연을 확인한다.
pgBackRest로 물리 백업과 WAL을 S3에 보관하기로 했다.
WAL은 데이터 변경 기록이며, PostgreSQL은 마무리된 WAL 파일을 보관 작업에 넘긴다.
변경이 적으면 파일이 다 찰 때까지 오래 걸릴 수 있으므로 시간 기준도 정한다.

## 결정 요인

- 파일 전환 이후의 압축과 전송 시간을 고려해 5분 목표에 여유를 둔다.
- PostgreSQL 공식 안내와 공개 운영 도구에서 사용하는 값을 출발점으로 삼는다.
- Dev와 Prod의 WAL 파일 전환 간격을 맞춰 부하 테스트의 환경 차이를 줄인다.
- t4g.small의 실제 부하와 S3에 보관한 용량은 적용 후 확인한다.

## 고려한 대안

### 대안 1: 4분

장점은 변경이 적을 때 1분보다 WAL 파일 수를 줄일 수 있다는 점이다.
단점은 유실 5분 목표에서 압축과 전송 대기, 업로드에 남는 시간이 약 1분이라는 점이다.

### 대안 2: 1분

장점은 공식 문서에서 보통 합리적이라고 설명하는 값이며, 전송 지연에 더 여유를 둘 수 있다는 점이다.
단점은 덜 찬 파일을 자주 마무리하므로 압축 전 보관량과 전송 횟수가 늘 수 있다는 점이다.
압축 후 S3 저장량과 CPU 부담은 실제 데이터에 따라 달라진다.

## 결정

대안 2를 채택한다. Dev와 Prod PostgreSQL에 `archive_timeout = '60s'`를 설정하는 방향으로 설계한다.

- WAL 파일이 가득 차면 1분을 기다리지 않고 보관 작업에 넘긴다.
- 파일이 덜 차도 DB 활동이 있는 상태에서 전환 간격에 도달하면 파일을 마무리한다.
- 마무리된 WAL은 pgBackRest를 통해 S3에 보관한다. 1분마다 전체 DB 백업을 실행하는 것은 아니다.
- Dev에서도 WAL을 실제 S3로 전송한다. 저장 경로는 Prod와 구분하고 인증은 [저장소 ADR](<2026-10-22_DB 백업을 S3와 R2에 함께 보관할 것인가_이산.md>)에 따라 기존 EC2 IAM Role 방식을 사용한다. 환경별 IAM 역할 분리는 이번에 추가하지 않는다.
- 압축은 두 환경 모두 Zstandard 수준 1로 맞춘다. 전송 작업 수와 WAL 파일 크기도 같은 기준으로 적용하되 구체적인 값은 후속 설계에서 정한다.
- 두 환경은 주 1회 전체 백업을 실행하고 나머지 6일은 하루 한 번 증분 백업한다. Prod 보관 기간은 30일로 정했다. 백업은 한국 시간 일요일 04:00에 전체, 월요일부터 토요일까지 04:00에 증분으로 실행한다. Dev 보관 기간은 7일로 정했다.

Dev의 복구 목표는 데이터 유실 최대 24시간과 다음 근무일 이내 복구로 유지한다.
WAL 간격을 맞추는 것은 부하 테스트 조건에 대한 결정이며, Dev의 복구 목표를 5분으로 바꾸는 것은 아니다.

이 설정은 S3 업로드가 1분 안에 끝난다는 뜻이 아니다.
pgBackRest의 `archive-timeout`은 WAL 도착을 기다리는 제한 시간이며, 이번 PostgreSQL 설정과 다르다.
유실 5분 목표는 필요한 WAL이 실제 S3에 저장되기까지의 지연을 포함해 확인한다.

## 긍정적 결과

- 변경이 적어도 파일이 다 찰 때까지 기다리는 시간을 줄일 수 있다.
- 4분안보다 전송 지연에 대응할 시간 여유를 확보할 수 있다.
- Dev에서 WAL 보관을 포함한 DB 성능을 확인할 수 있다.

## 부정적 결과와 트레이드오프

- 변경량에 비해 파일 수가 많아지고 압축과 전송 작업이 늘 수 있다.
- 공식 안내에 있는 값이어도 t4g.small에서 부하가 없다고 보장되지는 않는다.
- S3 전송이 실패하거나 지연되면 유실 5분 목표를 넘을 수 있고, 로컬 WAL도 쌓일 수 있다.

## 후속 결정과 재검토 조건

- 압축은 Zstandard 수준 1로 정했다. 백업 작업 수와 CPU 우선순위를 정한다.
- [WAL 지연과 DB 디스크 부족 알림](<2026-10-23_DB 연결과 백업 및 저장 공간 문제를 알리는 이유_이산.md>)을 적용한다. WAL 지연 3분은 주의, 5분은 긴급으로 기존 Discord에 알린다.
- DB 응답 시간이 나빠지거나 전송이 계속 밀리면 작업 설정과 전환 간격을 다시 검토한다.
- 보관 기간은 Prod 30일과 Dev 7일로 정했다. 실행 예약 도구와 실제 보관 설정값은 구현할 때 준비하고 검증한다.

## 구현과 검증

설정값만 결정했다. 서버에는 아직 적용하지 않았다.
Dev에 두 환경의 공통 1분 설정을 먼저 적용하고, 실제 S3 전송을 켠 상태로 검증한다.
DB 응답 시간과 함께 디스크 처리량, CPU 크레딧, 전송 대기량도 확인한다.
데이터 양과 요청 패턴, EBS 성능이 다르면 결과도 달라지므로 시험 조건을 기록한다.
WAL 파일이 빨리 차는 부하에서는 1분보다 자주 전환될 수 있으므로 평시와 높은 부하를 모두 확인한다.
평시와 부하 테스트에서 DB 응답 시간, CPU 사용량, WAL 보관 지연과 압축 후 업로드 용량을 기록한다.
S3의 물리 백업과 WAL로 복원하고, 복구 가능한 마지막 데이터 시각을 확인한다.
