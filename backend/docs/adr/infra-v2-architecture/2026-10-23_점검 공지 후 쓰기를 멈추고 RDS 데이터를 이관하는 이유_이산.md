# 2026-10-23 점검 공지 후 쓰기를 멈추고 RDS 데이터를 이관하는 이유

- 작성일: 2026-10-23
- 작성자: 이산
- 상태: 채택, 이관 및 전환 검증 전
- 결정 대상: RDS PostgreSQL에서 EC2 PostgreSQL로 데이터를 옮기는 방식

## 배경

RDS의 데이터를 새 EC2 PostgreSQL로 옮겨야 한다.
덤프를 만든 뒤에도 기존 DB에 쓰기가 계속되면 그 변경은 새 DB에 포함되지 않는다.
점검 공지를 띄우고 쓰기를 멈춘 상태에서 최종 데이터를 옮긴다.

## 결정 요인

- 최종 덤프 이후 기존 DB에 새 데이터가 쌓이지 않게 한다.
- 복제와 동시 쓰기 구성을 추가하지 않고 전환 절차를 단순하게 유지한다.
- 사용자에게 점검을 알리고 실패 시 대응할 기준을 준비한다.

## 고려한 대안

### 대안 1: 계속 복제하며 짧은 전환 시간만 확보

장점은 서비스 중단 시간을 줄일 수 있다는 점이다.
단점은 복제 설정과 지연 확인, 쓰기 전환 절차를 추가로 관리해야 한다는 점이다.

### 대안 2: 점검 공지 후 쓰기를 멈추고 최종 덤프 이관

장점은 옮길 데이터의 기준을 맞추고 검증과 전환 순서를 단순하게 관리한다는 점이다.
단점은 덤프와 복원, 검증하는 동안 사용자가 쓰기 기능을 사용할 수 없다는 점이다.

## 결정

대안 2를 채택한다. 먼저 Dev에서 이관을 연습한 뒤 Prod에 적용한다.

| 순서 | 작업 |
| --- | --- |
| 1 | 점검 일정과 이용 제한을 사전 안내하고 작업 중 점검 공지를 표시한다. |
| 2 | 새 쓰기 요청을 차단한다. 진행 중인 일기 생성과 대기 작업을 안전하게 마무리하고 예약 작업 등 다른 DB 쓰기도 멈춘다. |
| 3 | 기존 DB에 더 이상 쓰기가 없는지 확인한 뒤 최종 pg_dump를 만든다. |
| 4 | 새 DB에 pg_restore하고 기존 앱 계정과 객체 소유권, Flyway 이력을 맞춘다. |
| 5 | 앱 접속 대상을 새 DB로 바꾸고 데이터, TLS, Flyway와 주요 앱 기능을 확인한다. |
| 6 | 새 DB의 WAL 전송과 기준 전체 백업, 별도 복원 시험이 정상인지 확인한다. |
| 7 | 쓰기를 재개하고 정상 동작을 확인한 뒤 점검 공지를 해제한다. |

공지 표시만으로 쓰기가 차단됐다고 보지 않는다. 서버에서도 쓰기를 막고 진행 중인 작업과 열린 트랜잭션을 확인한다.
Dev 연습에서 필요한 중단 시간과 이관 명령을 측정한 뒤 실제 점검 시간과 담당자를 정한다.
점검 중 조회 기능도 제한될 수 있으므로 공지에 실제 이용 제한을 적는다.
이관 검증은 가능하면 같은 앱 버전을 기준으로 진행하고 별도 기능 변경을 함께 섞지 않는다.

### 전환 실패와 기존 RDS 보존

실제 사용자 쓰기를 재개하기 전 검증에 실패하면 기존 RDS를 이용하도록 되돌린다.
새 DB에 실제 사용자 쓰기를 재개한 뒤에는 기존 RDS가 최신 상태가 아니므로 주소만 바꿔 되돌리지 않는다.
이때는 쓰기를 다시 멈추고 새 DB 복구 또는 새 데이터를 보존하는 재이관 절차를 판단한다.

기존 RDS는 전환 즉시 삭제하지 않는다. 새 서비스 동작과 백업 복원을 확인한 뒤 삭제 시점과 최종 스냅샷 보관을 정한다.
RDS를 남겨두는 기간에는 기존 리소스 비용이 겹칠 수 있다.

## 긍정적 결과

- 쓰기를 멈춘 시점의 데이터를 기준으로 이관할 수 있다.
- 사용자에게 중단을 안내하고 검증 뒤에 서비스를 다시 연다.

## 부정적 결과와 트레이드오프

- 점검 중 사용자가 일기를 저장하거나 수정할 수 없다.
- 실제 중단 시간은 덤프, 복원, 백업과 검증 시간에 따라 달라진다.
- 쓰기 재개 후의 복귀에는 새 데이터 보존을 위한 추가 작업이 필요하다.

## 후속 결정과 재검토 조건

- Dev 이관 연습 뒤 점검 일정, 담당자, 공지 문구와 실제 명령을 준비한다.
- 진행 중인 작업의 종료와 쓰기 차단 및 재개 방법을 점검한다.
- 주요 데이터 비교 항목, 기능 확인과 복원 시험의 성공 기준을 실행 절차에 적는다.
- 전환 뒤 관찰 기간과 기존 RDS 삭제 시점은 검증 결과를 보고 정한다.

## 구현과 검증

이관 방식을 결정했다. 공지 게시, 서비스 중단, 데이터 이관과 RDS 삭제는 아직 실행하지 않았다.
Dev에서 덤프와 복원, 소유권과 Flyway 검증, TLS 연결 및 기능 확인을 수행한다.
쓰기 재개 전 기존 RDS로 되돌리는 절차도 연습한다.
최종 덤프 이후 기존 DB에 쓰기가 들어가지 않는지 확인하고 실제 단계별 시간을 기록한다.
