# 2026-10-23 DB 연결과 백업 및 저장 공간 문제를 알리는 이유

- 작성일: 2026-10-23
- 작성자: 이산
- 상태: 채택, 서버 적용 전
- 결정 대상: Dev와 Prod의 EC2 PostgreSQL 연결 상태, 백업과 저장 공간 경보

## 배경

WAL의 S3 전송이 밀리면 최근 데이터를 복구하지 못할 수 있고, 로컬 디스크에도 WAL이 쌓인다.
DB 데이터와 로그가 늘어도 디스크가 찰 수 있다. 공간이 완전히 차기 전에 알림을 받아 대응한다.
DB가 멈춘 경우와 백업이 실패하거나 실행되지 않은 경우도 확인해야 한다.

## 결정 요인

- DB 연결 불가와 정상 백업 부재를 발견한다.
- WAL 보관 문제를 디스크가 차기 전에 발견한다.
- 데이터, WAL과 로그 등 원인에 관계없이 실제 디스크 여유를 확인한다.

## 고려한 대안

### 대안 1: 디스크 부족만 알림

장점은 수집할 항목이 적다는 점이다.
단점은 공간에 여유가 있어도 WAL이 S3에 보관되지 않는 문제를 늦게 발견할 수 있다는 점이다.

### 대안 2: DB 연결, 백업, WAL과 디스크를 각각 확인

장점은 DB 중단과 백업 부재, 전송 지연과 공간 부족을 각각 발견할 수 있다는 점이다.
단점은 항목별 확인 방법과 경보 기준을 설정해야 한다는 점이다.

## 결정

대안 2를 채택한다. Dev와 Prod에 다음 네 알림을 준비한다.

| 알림 | 확인할 상황 |
| --- | --- |
| DB 연결 불가 | 앱에서 DB에 접속할 수 없는 경우 |
| 백업 실패 또는 누락 | 백업 명령이 실패하거나 예정된 정상 백업이 없는 경우 |
| WAL 전송 지연 | S3에 보관해야 할 WAL이 전송되지 않고 밀리는 경우 |
| DB 디스크 부족 | DB 데이터, WAL 또는 로그가 사용하는 디스크의 여유 공간이 부족한 경우 |

DB가 꽉 차는 상황은 DB 디스크 부족 알림에 포함한다. 같은 알림을 별도로 중복 생성하지 않는다.
기존 CloudWatch 수집과 알림 구성을 우선 활용하고, 기존 Discord 경로로 알린다.
Dev와 Prod 모두 아래 기준을 적용한다.

| 항목 | 확정 기준 | 이유 |
| --- | --- | --- |
| DB 연결 불가 | 연결 실패가 1분 지속되면 알림 | 짧은 재연결 오류와 구분하면서 중단을 빨리 발견한다. |
| 백업 명령 실패 | 실패 확인 후 다음 점검 때 알림 | 완료 기한까지 기다릴 이유가 없다. |
| 백업 완료 기한 | 매일 04:00 KST 실행, 06:00 KST까지 예정 종류의 정상 백업이 없으면 알림 | 실행 누락과 지나치게 오래 걸리는 작업을 함께 발견한다. 2시간은 초기 여유이며 실측값이 아니다. |
| WAL 전송 지연 | 보관하지 못한 최근 데이터의 시간이 3분에 이르면 주의, 5분에 이르면 긴급 알림 | Prod의 데이터 유실 목표 5분에 맞춘 기준이다. 추가로 5분을 더 기다리지 않는다. |
| 디스크 부족 | 사용률 80% 이상이 5분 지속되면 주의, 90% 이상은 다음 점검 때 긴급 알림 | 별도 대기 DB가 없어 기본 예시보다 먼저 대응할 시간을 확보한다. |

백업은 실패 로그뿐 아니라 마지막 정상 완료 시각과 백업 종류도 확인한다.
일요일 전체 백업이 빠지고 증분만 성공한 상황도 구분한다.

## 긍정적 결과

- DB 중단과 백업 부재를 알림으로 확인할 수 있다.
- 디스크가 가득 차 DB가 중단되기 전에 대응할 수 있다.
- 디스크 여유와 별개로 WAL 보관 지연을 확인할 수 있다.

## 부정적 결과와 트레이드오프

- 알림은 공간 확장이나 전송 오류 수정을 자동으로 수행하지 않는다.
- 기준이 너무 느슨하면 늦게 발견하고, 너무 엄격하면 불필요한 알림이 늘 수 있다.

## 후속 결정과 재검토 조건

- 실제 백업 소요 시간과 디스크 증가 속도를 측정한 뒤 기준을 재검토한다.
- 알림 대응 담당자를 정한다.
- DB 데이터, WAL과 로그가 실제 저장되는 경로를 확인한다. 현재 앱 서버의 루트 디스크 수집만으로 새 DB 디스크를 감시한다고 보지 않는다.
- DB 변경이 없어 전송할 WAL이 없는 상태를 전송 지연으로 잘못 판단하지 않도록 한다.

## 구현과 검증

알림 대상, Discord 전달 경로와 발송 기준을 결정했다. 지표와 경보는 아직 설정하지 않았다.
DB 연결 상태 확인과 간단한 쿼리 확인을 구분해 점검 방법을 정한다.
DB EC2 자체가 멈춰 점검 지표가 오지 않는 상황도 정상으로 처리하지 않도록 설계한다.
격리된 환경에서 DB 연결 불가, 백업 실패와 예약 누락을 재현해 알림을 확인한다.
격리된 시험 환경에서 WAL 전송 지연과 디스크 경보 조건을 재현하고 알림 도착을 확인한다.
운영 DB의 디스크를 실제로 가득 채우는 시험은 하지 않는다.

## 경보 기준 선정 근거

2026-10-23 조사와 합의를 기준으로 정했다. 공개 설정을 참고하고 우리 복구 목표에 맞춰 기준을 정했다.

- Prometheus PostgreSQL 공개 경보 예시는 연결 실패가 1분 지속되면 알린다.
- Prometheus Node Exporter 기본 설정은 디스크 여유 5%와 3% 경보 외에, 증가 추세로 24시간 또는 4시간 안에 공간이 찰지도 확인한다. 사용률 80%와 90%가 모든 서비스의 공통 기준인 것은 아니다.
- Barman은 마지막 백업과 WAL의 허용 경과 시간을 운영자가 정하도록 한다. 기본으로 정해진 공통 시간은 없다.

WAL 지연은 마지막 전송 시각만으로 계산하지 않는다. 변경이 없는 DB와 미전송 WAL이 있는 DB를 구분한다.
WAL 생성부터 S3 보관까지 걸린 시간을 확인해야 하며, 완성된 WAL의 전송 대기 시간만 재면 파일 전환 전의 시간이 빠진다.
점검 간격과 알림 전달 지연만큼 실제 알림은 늦을 수 있다. 5분 경보가 데이터 유실 5분 이내를 보장하지는 않는다.
디스크는 사용률과 남은 실제 공간을 함께 확인하고, WAL 증가 속도를 측정한 후 기준을 조정한다.

### 백업 소요 시간과 완료 기한

pgBackRest 공식 문서는 모든 DB에 적용할 정상 소요 시간을 정하지 않는다.
백업에는 파일 복사뿐 아니라 시작 전 체크포인트와 필요한 WAL의 보관 완료를 기다리는 시간도 든다.
실제 소요 시간은 DB 전체 크기, 변경량, CPU, 디스크, 파일 수와 S3 전송 성능에 따라 달라진다.

단순 계산으로 20GiB를 초당 10MiB로 처리하면 약 34분, 초당 20MiB면 약 17분이다.
이는 처리 속도를 가정한 계산이며 t4g.small의 측정 결과가 아니다. 추가 대기 시간도 포함하지 않는다.
현재 조회했던 약 24MiB는 Prod DB 하나의 크기다. 물리 백업 대상 전체 크기와 같다고 보지 않는다.

처음에는 전체와 증분 모두 2시간을 완료 기한으로 정한다. 이 시간은 백업 강제 종료 시간이 아니다.
초기 전체 백업과 첫 주의 증분 백업에서 시작과 완료 시각을 기록하고, 부하가 있는 경우도 확인한 뒤 기한을 조정한다.
백업 완료 기한과 장애 후 서비스 복구 목표 4시간은 별개다.

기존 Discord 전달 코드는 허용된 경보 이름만 전송한다. 구현 시 새 DB 경보를 허용 목록에 추가하고 실제 도착을 확인한다.
