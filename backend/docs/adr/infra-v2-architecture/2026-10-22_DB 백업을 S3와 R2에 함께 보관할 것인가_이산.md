# 2026-10-22 DB 백업을 S3와 R2에 함께 보관할 것인가

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 백업 설정 및 복원 시험 전
- 결정 대상: Dev와 Prod PostgreSQL의 외부 백업 저장소

## 배경

PostgreSQL을 실행하는 EC2의 디스크를 잃어도 데이터를 복원할 수 있어야 한다.
그래서 DB 서버 밖에 백업을 보관한다.

과거 S3 이미지 유실 경험이 있고, 현재 이미지 파일의 백업에는 R2를 사용하고 있다.
DB도 두 저장소에 보관하는 안을 검토했지만, 먼저 S3에서 백업과 복원이 동작하도록 준비하기로 했다.
기존 이미지 백업은 PostgreSQL의 데이터까지 백업하는 작업이 아니므로 DB 백업을 따로 설정해야 한다.

## 결정 요인

- DB 서버의 데이터 볼륨을 잃어도 백업을 가져올 수 있어야 한다.
- 초기에는 S3의 백업 생성, 실패 감지와 실제 복원을 먼저 확인해야 한다.
- 백업용 EC2를 추가하지 않고 기존 네 대 구성 안에서 실행해야 한다.
- 운영 작업과 비용이 확인된 뒤 R2를 두 번째 저장소로 추가할 수 있어야 한다.

## 고려한 대안

### 대안 1: S3에만 보관

장점은 다음과 같다.

- 백업 저장소와 접근 권한을 AWS에서 관리할 수 있다.
- 백업 성공 여부와 복원을 한 저장소에 대해 확인하면 된다.

단점은 다음과 같다.

- S3 백업이 삭제되거나 AWS 계정에 접근하지 못하면 다른 저장소의 사본이 없다.
- 과거 S3 유실 경험을 고려한 별도 사본을 갖추지 못한다.

### 대안 2: R2에만 보관

장점은 다음과 같다.

- 기존 R2 운영 경험을 활용할 수 있다.
- AWS 밖에 DB 백업을 보관할 수 있다.

단점은 다음과 같다.

- R2 백업이 삭제되거나 접근에 문제가 생기면 다른 저장소의 사본이 없다.
- 기존 이미지 백업과 별도로 DB 백업을 설정하고 복원 가능 여부를 확인해야 한다.

### 대안 3: S3와 R2에 각각 보관

장점은 다음과 같다.

- 한쪽 저장소의 사본을 사용할 수 없어도 다른 쪽으로 복원할 수 있다.
- AWS 안과 밖에 DB 백업을 나누어 보관할 수 있다.

단점은 다음과 같다.

- 두 저장소의 저장 비용과 접근 권한을 관리해야 한다.
- 백업과 전송의 성공 여부를 저장소별로 확인해야 한다.
- 두 저장소에서 복원 시험을 각각 실행해야 한다.

## 결정

대안 1을 초기 구성으로 채택한다. Dev와 Prod의 DB 백업은 S3부터 시작하고 R2 도입은 연기한다.

1. pgBackRest로 S3에 DB 물리 백업과 복원에 필요한 WAL을 보관한다.
2. Dev와 Prod의 백업을 구분해 저장한다. 정확한 버킷과 저장 경로는 설정 단계에서 정한다.
3. 백업 실패와 WAL 보관 지연을 확인할 경보를 준비한다.
4. 백업 작업은 기존 DB EC2에서 실행한다. 별도 백업 서버나 대기 DB를 추가하지 않는다.
5. S3만 사용한 실제 복원 시험으로 데이터와 앱 기능, 복구 시간을 확인한다.

기존 이미지용 R2 백업은 DB 백업과 별개로 유지한다. 이번 결정으로 이미지 백업을 끄거나 삭제하지 않는다.
DB 백업의 R2 도입 시점과 범위는 S3 운영 결과를 보고 다시 정한다.

## 긍정적 결과

- 초기에는 한 저장소의 백업 성공 여부와 복원 절차에 집중할 수 있다.
- DB 서버의 디스크와 별개로 백업을 보관할 수 있다.
- EC2 네 대 운영 조건을 지키면서 외부 백업을 준비할 수 있다.

## 부정적 결과와 트레이드오프

- 백업 저장과 전송에 드는 비용은 EC2 실행 비용과 별도로 계산해야 한다.
- S3 백업이 삭제되거나 AWS 계정에 접근하지 못하면 초기 구성에는 AWS 밖의 DB 사본이 없다.
- S3 접근 권한과 삭제 방지 정책을 설계해야 한다. 기존 이미지용 R2 사본으로 DB를 복원할 수는 없다.
- S3를 선택한 것만으로 Prod 데이터 유실 5분과 서비스 복구 4시간 목표를 달성한 것은 아니다.

## 후속 결정과 재검토 조건

- 백업 방식과 일정은 [일간 물리 백업 ADR](<2026-10-22_Dev와 Prod의 일간 물리 백업을 증분 방식으로 만드는 이유_이산.md>), WAL 간격은 [WAL ADR](<2026-10-22_Dev와 Prod의 WAL 파일 전환 간격을 1분으로 맞추는 이유_이산.md>)에 따른다.
- Prod 보관 기간은 30일로 정했다. Dev 보관 기간은 7일로 정했다.
- S3 실패 경보, 접근 권한과 삭제 방지 정책을 정한다.
- S3에서 실제 복원과 운영 상태를 확인한 뒤 DB 백업의 R2 추가 시점과 목표를 정한다.
- 실제 데이터 크기와 전송량을 확인해 비용이 부담되면 보관 기간과 백업 구성을 다시 검토한다.

## 구현과 검증

저장소는 S3, 도구는 pgBackRest로 결정했다. DB 백업 작업과 접근 권한은 아직 설정하지 않았다.
현재 R2와 RDS 수치는 [백업 현황과 WAL 용량 조사](<2026-10-22_R2 백업 현황과 WAL 용량 조사_이산.md>)에 기록했다.
Prod 보관 기간은 30일로 정했다. 현재 RDS 지표를 비용으로 바로 환산하지 않고, 압축 후 업로드 용량으로 실제 보관 비용을 확인한다.
시험 환경에서 S3만 사용한 복원을 실행한다. DB 백업의 R2 설정은 이번 초기 적용에 포함하지 않는다.
복원한 데이터와 앱 기능을 확인하고, 복구할 수 있는 마지막 데이터 시각과 걸린 시간을 기록한다.
