# 2026-10-22 EC2 PostgreSQL 백업 도구로 pgBackRest를 사용하는 이유

- 작성일: 2026-10-22
- 작성자: 이산
- 상태: 채택, 백업 설정 및 복원 시험 전
- 결정 대상: Dev와 Prod의 EC2 PostgreSQL 백업 도구

## 배경

RDS 대신 EC2에서 PostgreSQL을 직접 운영한다. 자동 백업과 복원도 우리가 준비해야 한다.
DB 백업 저장소는 우선 S3로 정했다. 기존 이미지용 R2 백업에는 DB 백업이 포함되지 않는다.

전체 백업은 백업 시점의 DB 상태를 보관한다.
WAL은 이후의 데이터 변경 기록이다. 필요한 WAL이 이어져 있어야 백업 이후 시점까지 복원할 수 있다.
전체 백업과 WAL을 함께 관리하고, 실패를 확인할 수 있는 도구가 필요하다.

## 결정 요인

- Prod의 데이터 유실 최대 5분과 복구 4시간 목표를 시험할 수 있어야 한다.
- 백업 실패와 WAL 전송 문제를 로그와 명령 결과로 확인할 수 있어야 한다.
- 백업 생성, 보관 기간에 따른 정리와 복원을 일관된 절차로 운영해야 한다.
- Dev와 Prod의 기존 DB EC2에서 실행하고, 별도 EC2를 추가하지 않아야 한다.

## 고려한 대안

### 대안 1: pg_dump 중심으로 운영

장점은 DB 내용을 내보내고 가져오는 절차가 단순하고, RDS 데이터 이관에도 사용할 수 있다는 점이다.
단점은 덤프만으로 백업 이후의 변경 기록을 적용하는 특정 시점 복구를 할 수 없다는 점이다.
데이터 유실 5분 목표에 맞추려면 다른 백업 방식이 필요하다.

### 대안 2: WAL-G 사용

장점은 전체 백업과 WAL의 저장 및 복원을 지원하고, S3에 보관할 수 있다는 점이다.
단점은 우리 팀이 해당 명령과 설정을 익히고, 실패 감지와 복원 절차를 별도로 검증해야 한다는 점이다.
이 검증 부담은 pgBackRest에도 있다. 두 도구의 장애율을 직접 비교한 결과는 없다.

### 대안 3: pgBackRest 사용

장점은 백업과 WAL 보관, 복원과 오래된 백업 정리를 한 도구로 관리할 수 있다는 점이다.
`check`로 설정과 WAL 보관 동작을 점검하고, `info`로 백업 정보를 확인할 수 있다.
명령 결과와 로그를 실패 경보에 연결할 수 있다.
단점은 PostgreSQL의 WAL 설정, S3 권한과 실행 예약을 직접 준비해야 한다는 점이다.
설정 점검만으로 실제 복원을 보장할 수 없으므로 복원 시험도 필요하다.

## 결정

대안 3인 pgBackRest를 사용한다. Dev와 Prod 모두 같은 도구로 운영한다.

1. 각 DB EC2에서 pgBackRest를 실행한다. 추가 백업 서버나 대기 DB는 두지 않는다.
2. DB의 물리 백업과 복원에 필요한 WAL을 S3에 보관한다. 환경별 백업은 구분한다.
3. [DB와 백업 경보 ADR](<2026-10-23_DB 연결과 백업 및 저장 공간 문제를 알리는 이유_이산.md>)에 따라 DB 연결 불가, 백업 실패 및 누락, WAL 전송 지연과 디스크 부족을 알린다.
4. S3 백업을 내려받아 복원하고, 데이터와 앱 동작을 확인한다.
5. DB 백업의 R2 저장은 추후 검토한다.
6. Dev와 Prod의 백업과 WAL은 Zstandard 수준 1로 압축한다.

선정 이유는 팀이 백업 상태와 오류를 확인하고 복원 절차를 관리하기에 적합하다고 판단했기 때문이다.
WAL-G보다 장애가 적거나 더 안정적이라고 실험으로 입증한 결정은 아니다.
논리 백업인 `pg_dump`의 정기 실행은 초기 구성에 포함하지 않는다.
RDS에서 EC2로 데이터를 이관할 때 `pg_dump`를 사용하는 것과는 별개다.
pgBackRest를 선택해도 WAL은 계속 필요하다. pgBackRest가 그 WAL의 보관과 복원을 관리한다.

## 긍정적 결과

- Dev와 Prod에서 같은 명령과 운영 절차를 사용할 수 있다.
- 백업과 WAL을 함께 관리하며, 특정 시점 복구를 준비할 수 있다.
- 백업 상태 확인과 실패 원인 조사를 위한 기준을 정할 수 있다.

## 부정적 결과와 트레이드오프

- 실행 예약과 경보는 직접 구성해야 한다. 도구 설치만으로 자동 운영이 완성되지는 않는다.
- 백업 중 DB EC2의 CPU, 메모리와 디스크를 사용한다. 앱은 별도 EC2에 있지만 DB 응답 지연이 앱에도 영향을 줄 수 있어 함께 확인한다.
- 필요한 WAL이 없으면 원하는 시점까지 복원할 수 없다.
- Prod의 복구 목표는 아직 검증 전이다. 도구 선택만으로 달성됐다고 보지 않는다.

## 후속 결정과 재검토 조건

- Dev와 Prod 모두 주 1회 전체 백업을 실행하고 나머지 6일은 하루 한 번 증분 백업한다.
- Prod는 최근 30일의 특정 시점 복구 자료를 보관한다. 백업은 한국 시간 일요일 04:00에 전체, 월요일부터 토요일까지 04:00에 증분으로 실행한다. Dev 보관 기간은 7일로 정했다.
- Dev와 Prod의 WAL 파일 전환 간격은 동일하게 1분으로 정했다. 전송 지연 경보는 DB와 백업 경보 ADR에 따른다.
- 기존 공용 S3에서 DB 백업도 Dev와 Prod 경로로 나누고, 기존 EC2 IAM Role 인증 방식을 따른다. 실제 권한을 확인하고 삭제 방지 설정을 정한다.
- ARM64 환경의 설치 버전, 컨테이너 구성과 실행 예약 방법을 정한다.
- 복원 시간이 목표를 넘거나 백업 부하가 크면 주기와 자원 배분을 다시 검토한다.

## 구현과 검증

도구, 저장소, 일정과 압축 및 보관 정책을 결정했다. 서버 설치, S3 설정과 복원 시험은 아직 실행하지 않았다.
정기 복원 시험은 [월간 복원 시험 ADR](<2026-10-23_월 1회 Prod 백업으로 복원 시험을 하는 이유_이산.md>)에 따른다.
먼저 Dev에서 전체 백업과 WAL 보관을 준비한다.
설정을 점검하고, 백업 이후 만든 시험 데이터를 특정 시점 복원으로 확인한다.
원본 DB를 덮어쓰지 않도록 별도 데이터 경로와 격리된 실행 환경에서 시험한다.
추가 상시 EC2는 두지 않는다. 시험 자원과 Prod 적용 절차는 구현 단계에서 정한다.
백업 크기, WAL 업로드 크기와 복원 시간을 기록한 뒤 Prod 목표 달성 여부를 판단한다.
