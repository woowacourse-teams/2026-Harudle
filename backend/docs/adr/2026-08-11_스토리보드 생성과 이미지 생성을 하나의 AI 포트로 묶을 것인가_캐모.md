# 2026-08-11 스토리보드 생성과 이미지 생성 포트 분리

- 작성일: 2026-08-11
- 작성자: 캐모
- 결정 대상: Generation 서비스의 AI 생성 포트 구성

## 배경

일기 기반 만화 생성은 한 번의 작업처럼 보이지만 실제로는 다음 두 단계로 이루어진다.

1. 일기와 스토리보드 프롬프트로 구조화된 스토리보드를 생성한다.
2. 스토리보드, 이미지 스타일 프롬프트와 기준 이미지로 최종 만화 이미지를 생성한다.

두 단계 모두 Gemini를 호출하므로 하나의 AI 포트와 어댑터가 전체 과정을 담당하게 만들 수 있다. 이 경우 서비스는 최종
이미지만 전달받으면 되므로 호출 구조가 단순해진다.

하지만 스토리보드는 이미지 생성을 위한 임시 문자열이 아니다. 제목, 등장인물 연속성, 패널별 장면, 감정, 캡션과 소품을 가진
도메인 객체이며 생성 결과와 함께 DB에 저장된다. 스토리보드 생성 응답은 구조화된 JSON 규칙과 도메인 검증을 통과해야 하고,
이미지 생성은 기준 이미지와 `MediaType`을 포함한 멀티모달 요청을 사용한다.

두 단계는 입력, 출력, 검증 규칙과 실패 조건이 서로 다르므로 하나의 AI 포트로 묶을지 별도 포트로 분리할지 결정해야 한다.

## 결정 요인

- 스토리보드를 독립적인 도메인 결과로 검증하고 저장할 수 있어야 한다.
- 스토리보드 모델과 이미지 모델을 서로 독립적으로 변경할 수 있어야 한다.
- 단계마다 다른 프롬프트와 요청·응답 형식을 표현할 수 있어야 한다.
- 어느 단계에서 실패했는지 식별하고 테스트할 수 있어야 한다.
- AI 제공자가 변경되더라도 Generation 서비스의 생성 흐름은 유지되어야 한다.
- 인터페이스와 오케스트레이션 복잡도가 불필요하게 커지지 않아야 한다.

## 고려한 대안

### 대안 1: 하나의 AI 포트가 전체 생성 과정을 수행

```java
public interface ComicGenerator {

    ComicGenerationOutput generate(ComicGenerationRequest request);
}
```

장점은 다음과 같다.

- 서비스가 한 번의 메서드만 호출하므로 생성 흐름이 단순하다.
- 인터페이스와 요청 객체의 수가 적다.
- 하나의 어댑터 안에서 provider 전용 객체를 바로 다음 호출에 사용할 수 있다.

단점은 다음과 같다.

- 스토리보드 생성과 이미지 생성의 책임이 한 구현체에 결합된다.
- 두 단계가 같은 AI 제공자와 모델을 사용해야 하는 구조로 굳어질 수 있다.
- 중간 스토리보드의 검증과 저장 시점이 어댑터 내부로 숨겨진다.
- 단계별 오류 처리와 단위 테스트가 어려워진다.
- 어댑터가 외부 API 변환뿐 아니라 애플리케이션 생성 순서까지 소유하게 된다.

### 대안 2: 하나의 인터페이스에 두 생성 메서드를 배치

```java
public interface ComicGenerator {

    Storyboard generateStoryboard(StoryboardGenerationRequest request);

    GeneratedImage generateImage(ComicImageGenerationRequest request);
}
```

장점은 다음과 같다.

- 생성 단계는 구분하면서 서비스의 의존성 수를 줄일 수 있다.
- 동일한 AI 클라이언트와 공통 설정을 한 구현체에서 공유하기 쉽다.

단점은 다음과 같다.

- 텍스트 생성과 이미지 생성 기능이 하나의 구현체에 묶인다.
- 한 단계만 다른 제공자로 교체하기 어렵다.
- 인터페이스가 서로 다른 변경 이유를 가진 두 기능을 함께 노출한다.
- 이미지 생성만 필요한 테스트도 스토리보드 생성 기능을 가진 구현체에 의존한다.

### 대안 3: 스토리보드 생성과 이미지 생성을 별도 포트로 분리

```java
public interface StoryboardGenerator {

    Storyboard generate(StoryboardGenerationRequest request);
}
```

```java
public interface ComicImageGenerator {

    GeneratedImage generate(ComicImageGenerationRequest request);
}
```

장점은 다음과 같다.

- 각 포트가 하나의 생성 단계와 변경 이유만 가진다.
- 단계마다 다른 모델, 제공자, 프롬프트와 요청 형식을 사용할 수 있다.
- 스토리보드를 도메인 객체로 검증한 후 이미지 생성에 전달할 수 있다.
- 각 어댑터와 실패 조건을 독립적으로 테스트할 수 있다.
- 애플리케이션 생성 순서를 `GenerateComicService`에서 명확하게 확인할 수 있다.

단점은 다음과 같다.

- 인터페이스와 요청 객체의 수가 늘어난다.
- 서비스가 두 생성 단계의 호출 순서를 직접 조합해야 한다.
- 두 구현체가 같은 AI 클라이언트를 사용하면 설정과 예외 변환 코드가 중복될 수 있다.
- 중간 단계가 추가되면서 단계별 실패 상태를 관리해야 한다.

## 결정

대안 3을 선택한다.

이유는 다음과 같다.

- 스토리보드는 최종 이미지와 별도로 검증하고 저장해야 하는 도메인 결과다.
- 스토리보드 생성과 이미지 생성은 입력, 출력과 실패 조건이 명확히 다르다.
- 두 단계에서 사용할 AI 모델과 제공자는 독립적으로 변경될 가능성이 있다.
- 포트가 늘어나는 비용보다 단계별 교체 가능성과 테스트 용이성이 더 중요하다.

`GenerateComicService`가 생성 순서를 조합한다.

```text
일기와 스토리보드 프롬프트
→ StoryboardGenerator
→ Storyboard
→ 기준 이미지 조회
→ ComicImageGenerator
→ GeneratedImage
→ 이미지 저장
```

두 Gemini 어댑터가 같은 SDK 클라이언트와 설정을 사용하더라도 포트 구현체는 분리한다. 공통 클라이언트와 예외 변환은
configuration이나 작은 공통 객체로 공유할 수 있지만, 스토리보드와 이미지 생성 책임을 하나의 어댑터로 합치지는 않는다.

## 긍정적 결과

- 스토리보드 생성 결과를 이미지 생성 전에 도메인 규칙으로 검증할 수 있다.
- 생성된 스토리보드를 `ComicGeneration`에 저장하고 장애 조사에 활용할 수 있다.
- 스토리보드와 이미지 생성 모델을 독립적으로 교체할 수 있다.
- 단계별 프롬프트와 provider 응답 형식이 서로 영향을 덜 받는다.
- 스토리보드 JSON 파싱 오류와 이미지 응답 오류를 독립적으로 검증할 수 있다.
- 외부 어댑터는 한 단계의 요청·응답 변환에 집중하고 서비스가 애플리케이션 흐름을 소유한다.

## 부정적 결과와 트레이드오프

- `StoryboardGenerator`, `ComicImageGenerator`와 각각의 요청 객체를 관리해야 한다.
- `GenerateComicService`가 생성 순서와 중간 결과 전달을 담당하므로 오케스트레이션 코드가 늘어난다.
- 동일한 AI 제공자를 사용할 경우 클라이언트 설정과 오류 변환의 공통화가 필요하다.
- 스토리보드 생성은 성공했지만 이미지 생성이 실패하는 부분 성공 상태가 발생할 수 있다.
- 한 번의 외부 호출로 전체 결과를 생성하는 제공자가 등장하더라도 현재 서비스 흐름에 맞게 두 단계로 적응시켜야 한다.

현재 Generation은 스토리보드를 저장하고 단계별 오류 코드를 관리한다. 따라서 추가되는 인터페이스 수보다 도메인 결과의
명확성과 각 단계의 독립성이 더 중요하다고 판단한다.
