# 2026-08-12 정규화 요청의 SHA-256 지문으로 멱등성 키 재사용 검증

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: Idempotency-Key 재사용 시 요청 동일성 판정과 기존 결과 재현 정책

## 배경

AI 생성은 처리 시간이 길고 비용이 발생한다. 클라이언트가 응답을 받기 전에 연결이 끊기면 같은 요청을 재전송할 수 있는데, 서버가
이를 새로운 요청으로 처리하면 AI를 중복 호출하고 일일 사용량도 다시 차감한다.

클라이언트가 제공하는 `Idempotency-Key`를 요청 식별자로 사용할 수 있지만 키만 같다고 모든 요청을 동일하게 취급하면 실수로 같은
키에 다른 날짜나 본문을 보낸 요청이 이전 결과를 받게 된다. 반대로 원본 HTTP 요청 전체를 저장하면 전송 형식과 헤더 차이까지
비교 대상이 되고 민감한 원문 저장 범위가 늘어난다. 의미상 같은 일기 생성 요청을 안정적으로 판정하는 방법을 결정해야 한다.

## 결정 요인

- 네트워크 재시도에서 AI 재호출과 사용량 중복 차감을 막아야 한다.
- 같은 키를 다른 의미의 요청에 사용하면 기존 결과를 반환하지 않아야 한다.
- 공백 정규화 등 도메인상 동일한 본문은 같은 요청으로 판정해야 한다.
- 요청 원문 전체를 멱등성 비교 목적으로 중복 저장하지 않아야 한다.
- 동시 요청에서도 한 요청만 키를 선점해야 한다.
- 성공, 처리 중과 실패 상태마다 재요청 응답이 명확해야 한다.

## 고려한 대안

### 대안 1: Idempotency-Key만 같으면 동일 요청으로 간주

장점은 다음과 같다.

- 구현과 조회가 가장 단순하다.
- 추가 지문 컬럼과 해시 계산이 필요하지 않다.
- Stripe 등 외부 API에서 익숙한 키 기반 모델과 유사하다.

단점은 다음과 같다.

- 같은 키에 다른 날짜나 본문을 보내도 이전 결과를 반환한다.
- 클라이언트의 키 재사용 버그를 탐지하기 어렵다.
- 다른 사용자가 우연히 같은 키를 사용했을 때 요청 의미를 구분할 수 없다.
- 잘못된 성공 응답이 데이터 오염으로 이어질 수 있다.

### 대안 2: 요청 JSON 또는 모든 HTTP 요소를 저장해 비교

장점은 다음과 같다.

- 원본 요청을 그대로 재현하고 비교할 수 있다.
- 해시 충돌을 고려하지 않아도 된다.
- 장애 조사에서 당시 요청 형식을 확인할 수 있다.

단점은 다음과 같다.

- JSON 필드 순서와 공백처럼 의미 없는 차이가 요청 충돌을 만들 수 있다.
- 인증 헤더 등 비교하면 안 되는 요소를 분리해야 한다.
- 일기 원문을 멱등성 용도로 중복 저장한다.
- 요청 스키마가 바뀔 때 과거 데이터 비교가 복잡하다.

### 대안 3: 정규화된 의미 필드의 버전 지문을 저장

사용자 ID, 일기 날짜와 정규화된 본문을 canonical 문자열로 만들고 SHA-256 해시를 저장한다.

장점은 다음과 같다.

- 의미상 동일한 요청을 전송 표현과 분리해 판정한다.
- 같은 키의 다른 사용자, 날짜 또는 본문을 충돌로 차단한다.
- 원문을 별도 멱등성 컬럼에 중복 저장하지 않는다.
- 고정 길이 지문으로 DB 비교와 제약이 단순하다.
- 버전 prefix로 향후 canonical 규칙 변경 가능성을 남긴다.

단점은 다음과 같다.

- canonical 필드와 정규화 순서를 계약으로 유지해야 한다.
- 해시만 보고 어떤 원본 필드가 달랐는지 알 수 없다.
- 버전이 바뀌면 과거 지문과의 호환 전략이 필요하다.
- SHA-256 충돌 가능성은 극히 낮지만 이론적으로 0은 아니다.

## 결정

대안 3을 선택한다.

`CreateDiaryCommand`에서 일기 본문을 도메인 규칙으로 정규화하고 다음 UTF-8 canonical 문자열을 SHA-256으로 해시한다.

```text
v1\n{userId}\n{diaryDate}\n{normalizedSourceText}
```

소문자 64자리 지문을 생성 작업과 함께 저장한다. `Idempotency-Key`는 UUID 형식의 전역 생성 요청 식별자로 사용하고 DB unique
constraint로 한 작업만 선점한다. 사용자 ID가 지문에 포함되므로 다른 사용자가 같은 키를 사용해도 기존 결과를 받지 않고
`IDEMPOTENCY_KEY_CONFLICT`가 된다. 올바르게 생성된 UUID의 우연한 충돌 가능성은 충분히 낮다고 판단한다.

같은 키와 같은 지문의 재요청은 저장 상태에 따라 처리한다.

```text
SUCCEEDED
→ AI 재호출과 추가 차감 없이 기존 결과 반환

PROCESSING + 제한 시간 이내
→ 409 GENERATION_IN_PROGRESS

PROCESSING + 제한 시간 초과
→ FAILED / GENERATION_INTERRUPTED 전환 후 저장된 실패 반환

FAILED
→ AI 재호출과 추가 차감 없이 저장된 실패 반환

같은 키 + 다른 지문
→ 409 IDEMPOTENCY_KEY_CONFLICT
```

동시에 같은 신규 키를 요청하면 DB unique constraint의 패자가 트랜잭션을 롤백한 뒤 기존 행을 다시 조회한다. 사용량은 신규 키를
성공적으로 선점한 트랜잭션에서만 증가한다.

## 긍정적 결과

- 응답 유실에 따른 재요청이 AI 생성과 사용량을 중복 실행하지 않는다.
- 같은 키에 다른 본문을 보내는 클라이언트 오류를 명시적으로 탐지한다.
- 일기 원문을 멱등성 판정 목적으로 추가 저장하지 않는다.
- 성공과 실패 결과를 재현해 클라이언트 재시도 동작이 안정적이다.
- 사용자 ID를 지문에 포함해 다른 사용자의 결과가 노출되지 않는다.

## 부정적 결과와 트레이드오프

- canonical 규칙을 변경하면 같은 의미의 과거 요청이 다른 지문이 될 수 있다.
- 현재 DB에는 지문 버전 컬럼이 없고 해시 안에만 `v1`이 반영돼 있어 지문 자체만으로 버전을 판독할 수 없다.
- 멱등성 키가 전역 unique이므로 다른 사용자의 동일 UUID도 충돌하며, 사용자별 key scope가 필요해지면 스키마를 변경해야 한다.
- 처리 제한 시간이 지난 작업은 같은 키 재요청에서만 중단 상태로 전환된다.
- 실패 작업을 실제로 다시 실행하려면 새로운 키를 사용하고 사용량을 새로 차감해야 한다.

canonical 규칙을 변경할 때는 기존 `v1` 지문 비교 경로를 유지하거나 별도 버전 컬럼을 추가한다. 멱등성 키를 UUID가 아닌 짧거나
예측 가능한 값으로 허용하게 되면 전역 unique 정책도 사용자별 unique 정책으로 다시 검토한다.
