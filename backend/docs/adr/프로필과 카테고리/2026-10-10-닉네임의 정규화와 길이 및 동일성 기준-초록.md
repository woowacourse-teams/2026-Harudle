# 닉네임의 정규화와 길이 및 동일성 기준

- 작성일: 2026-10-10
- 작성자: 초록
- 상태: 채택

## 배경

앞뒤 공백이나 Unicode 표현이 다른 입력을 그대로 저장하면 같은 닉네임이 별개의 값으로 취급될 수 있다. 길이 검사도 DB의 1~10자 제약과 일치해야 한다.

## 검토한 대안

| 방식 | 장점 | 감수할 점 |
| --- | --- | --- |
| 입력 그대로 저장하고 `length()`로 검사 | 구현이 단순하다. | Unicode 표현 차이가 남고, UTF-16 길이가 DB의 문자 수와 다를 수 있다. |
| 앞뒤 공백 제거, NFC 정규화 후 code point로 검사 | 저장 형태를 맞추고 기존 DB 제약과 같은 기준을 사용한다. | 원래 입력 형태가 일부 바뀌며, 조합된 이모지의 보이는 글자 수와는 다를 수 있다. |
| 앞뒤·연속 공백 거부, NFC 정규화 후 code point로 검사 | 입력 오류를 사용자에게 알리고 유효한 중간 공백 한 칸을 보존한다. | 사용자가 앞뒤·연속 공백을 직접 수정해야 하며, 조합된 이모지의 보이는 글자 수와는 다를 수 있다. |

## 결정

- `null`, 빈 값과 공백만 있는 값을 거부하고, 탭·줄바꿈 및 앞뒤·연속 공백 검증 -> NFC 정규화 -> code point 기준 1~10자 검사 -> 허용 문자 검사를 적용한다. 문자 범위는 별도 ADR `닉네임 이모지와 특수문자 금지`에 따른다.
- 검증 전 입력 대신 정규화한 결과를 저장하고, 중복 판정도 저장된 값을 기준으로 한다.
- 중간의 일반 공백은 연속되지 않는 경우 허용하고 길이에 포함한다. 수동 변경에 형용사·명사 조합 규칙을 강제하지 않는다.
- 앞뒤 공백은 자동으로 제거하지 않고 `닉네임 앞뒤의 공백을 제거해 주세요.`라는 검증 오류로 거부한다. 중간에 일반 공백이 두 칸 이상 연속되면 `닉네임에는 공백을 연속으로 사용할 수 없습니다.`라는 검증 오류로 거부하며, 한 칸으로 자동 변환하지 않는다.
- 탭(`\t`)과 줄바꿈(`\n`, `\r`, `\r\n`)은 입력의 앞뒤 또는 중간 어느 위치에 있어도 거부한다.
- 닉네임 검증 오류는 `InvalidNicknameException`으로 구분하고 공통 예외 처리기에서 HTTP 400, `VALIDATION_ERROR`, `errors[].field=nickname`, 구체적인 `errors[].reason`으로 전달한다. 실제 닉네임 변경 API와 화면 연결은 해당 단계에서 구현한다.

## 결과와 재검토 조건

`"재미있는 하루"`는 유효한 값으로 저장한다. `"  재미있는 하루  "`와 `"재미있는  하루"`는 각각 앞뒤 공백과 연속 공백의 수정 안내 오류로 거부한다. 입력의 공백을 자동으로 제거하거나 줄여 저장하지 않으며, 중복 판정은 검증과 NFC 정규화를 통과한 저장 값을 기준으로 한다.
