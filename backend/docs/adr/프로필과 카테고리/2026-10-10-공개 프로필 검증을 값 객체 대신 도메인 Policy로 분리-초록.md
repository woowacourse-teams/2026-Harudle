# 공개 프로필 검증을 값 객체 대신 도메인 Policy로 분리

- 작성일: 2026-10-10
- 작성자: 초록
- 상태: 채택

## 배경

신규 가입, 랜덤 닉네임 생성, 닉네임 변경에 같은 규칙이 필요하다. 기존 JPA 매핑과 공개 프로필 미배정 상태도 유지해야 한다.

## 검토한 대안

| 방식 | 장점 | 감수할 점 |
| --- | --- | --- |
| DTO, 서비스에서 검증 | 요청 처리 흐름에서 구현하기 쉽다. | 내부 배정 등 다른 경로에서 검증을 빠뜨리거나 다르게 적용할 수 있다. |
| 닉네임, 이미지 코드 값 객체 | 타입 자체에 규칙을 담아 잘못된 값의 사용을 줄인다. | JPA 매핑과 미배정 상태 처리까지 설계해야 한다. |
| `String`, `Short` 필드와 도메인 Policy | 기존 컬럼 매핑을 유지하며 검증을 재사용한다. | 필드 타입만으로 유효성을 보장하지 못하므로 변경 경로에서 Policy 호출을 보장해야 한다. |

## 결정

- `User`는 `String nickname`, `Short profileImageCode`를 저장하고 도메인 메서드에서 Policy를 호출한다.
- 최초 배정은 두 값을 검증하고, 닉네임 변경은 닉네임만 검증한다. 랜덤 생성기도 같은 닉네임 규칙을 사용하도록 한다.
- 다른 회원과의 중복은 Policy가 아니라 DB UNIQUE 제약과 서비스의 충돌 처리로 보장한다.

## 결과와 재검토 조건

현재는 값 객체의 타입 보장보다 기존 매핑 유지와 검증 재사용을 우선한다. 검증 호출 누락이 반복되거나 닉네임 자체의 동작이 늘어나면 값 객체 도입을 재검토한다.
