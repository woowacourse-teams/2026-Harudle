# 2026-08-12 생성 흐름을 선점·외부 실행·완료 단계로 분리

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 일기 및 4컷 동기 생성 흐름의 데이터베이스 트랜잭션 경계

## 배경

일기 생성 요청은 일기와 생성 작업을 저장하고 일일 사용량을 차감한 뒤, 외부 AI API를 여러 번 호출하고 이미지를 객체 저장소에
업로드한다. 데이터베이스 변경은 서로 정합성을 가져야 하지만 AI와 객체 저장소 호출은 느리고 네트워크 실패 가능성이 있다.

외부 호출이 끝날 때까지 하나의 DB 트랜잭션을 유지하면 커넥션과 행 잠금을 오랫동안 점유한다. 반대로 DB 상태를 남기지 않고 외부
호출부터 실행하면 같은 요청의 중복 실행과 사용량 초과를 막기 어렵다. 현재 API는 생성이 끝난 결과를 같은 HTTP 응답으로 반환하는
동기 계약이므로, 동기 응답을 유지하면서 DB 자원을 오래 점유하지 않는 경계를 결정해야 한다.

## 결정 요인

- 일기, 생성 작업과 사용량 선점은 함께 성공하거나 함께 롤백되어야 한다.
- 같은 멱등 요청이 AI를 중복 호출하거나 사용량을 중복 차감하지 않아야 한다.
- 외부 AI와 객체 저장소 호출 동안 DB 커넥션 및 행 잠금을 점유하지 않아야 한다.
- 성공과 실패 상태의 동시 갱신에서 먼저 확정된 결과를 덮어쓰지 않아야 한다.
- 현재 프론트엔드의 동기 생성 응답 계약을 유지해야 한다.
- 프로세스 중단과 부분 실패를 복구할 수 있는 상태를 DB에 남겨야 한다.

## 고려한 대안

### 대안 1: 외부 호출까지 하나의 DB 트랜잭션으로 처리

```text
트랜잭션 시작
→ 일기·사용량 저장
→ AI 호출
→ 이미지 저장
→ 생성 완료 저장
→ 커밋
```

장점은 다음과 같다.

- 애플리케이션 코드에서 하나의 성공 및 실패 경계로 보인다.
- 외부 호출이 예외를 던지면 DB 변경을 함께 롤백할 수 있다.
- 중간 상태를 별도로 설계하지 않아도 된다.

단점은 다음과 같다.

- 외부 호출 시간 동안 DB 커넥션과 잠금을 점유한다.
- DB 롤백으로 이미 실행된 AI 호출이나 업로드를 되돌릴 수 없다.
- 동시 요청의 대기 시간이 외부 API 지연만큼 길어진다.
- 트랜잭션 제한 시간과 외부 HTTP 제한 시간이 강하게 결합된다.

### 대안 2: 비동기 큐와 Outbox로 생성 실행

```text
트랜잭션에서 일기·사용량·Outbox 저장
→ 202 Accepted
→ Worker가 AI 및 저장소 호출
→ 상태 조회 또는 알림
```

장점은 다음과 같다.

- HTTP 요청 시간과 외부 생성 시간을 분리한다.
- 재시도, 처리량 제어와 장애 복구를 작업 큐에서 관리할 수 있다.
- 긴 외부 처리에도 API 서버 스레드를 점유하지 않는다.
- Outbox로 DB 상태와 작업 발행의 정합성을 보장할 수 있다.

단점은 다음과 같다.

- 현재 동기 성공 응답 계약을 202 및 상태 조회 방식으로 변경해야 한다.
- 큐, Worker, Outbox 발행기와 운영 모니터링이 추가된다.
- 사용자에게 완료를 전달할 polling, SSE 또는 알림 계약이 필요하다.
- 현재 MVP 범위보다 운영 구성과 실패 상태가 크게 늘어난다.

### 대안 3: 선점·외부 실행·완료 트랜잭션을 분리

```text
짧은 선점 트랜잭션
→ 외부 호출을 트랜잭션 밖에서 동기 실행
→ 짧은 완료 또는 실패 트랜잭션
```

장점은 다음과 같다.

- 일기, `PROCESSING` 생성과 사용량을 원자적으로 선점한다.
- 외부 호출 중 DB 커넥션과 잠금을 점유하지 않는다.
- 현재 동기 HTTP 응답 계약을 유지한다.
- 완료 및 실패 갱신만 짧은 잠금 트랜잭션으로 직렬화할 수 있다.
- 프로세스가 중단되어도 `PROCESSING` 기록을 복구 근거로 사용할 수 있다.

단점은 다음과 같다.

- 선점 후 외부 호출 실패라는 부분 실패를 명시적으로 처리해야 한다.
- 프로세스가 종료되면 `PROCESSING` 작업이 남을 수 있다.
- 업로드 후 완료 커밋 전 실패하면 고아 이미지 정리 정책이 필요하다.
- 동기 요청이므로 외부 처리 시간 동안 HTTP 연결과 서버 스레드는 유지된다.

## 결정

대안 3을 선택한다.

첫 번째 트랜잭션에서 다음 작업을 하나의 선점 단위로 처리한다.

```text
Idempotency-Key 잠금 또는 신규 선점
→ 일기 저장
→ PROCESSING 생성 작업 저장
→ 오늘 사용량 원자적 증가
→ 커밋
```

선점이 커밋된 뒤 `DiaryCreationService`가 트랜잭션 없이 스토리보드 생성, 이미지 생성과 객체 저장소 호출을 동기 실행한다. 성공하면
생성 행을 비관적 잠금으로 조회하는 별도 트랜잭션에서 `SUCCEEDED`로 변경한다. 실패하면 별도 트랜잭션에서 `FAILED`와 일기 soft
delete를 함께 저장한다.

완료 시점에는 `PROCESSING` 상태만 변경할 수 있다. 이미 실패 또는 성공으로 확정된 상태를 늦게 도착한 외부 결과가 덮어쓰지 않는다.

현재는 같은 멱등성 키가 다시 요청됐을 때 처리 제한 시간을 넘긴 `PROCESSING`을 `GENERATION_INTERRUPTED`로 전환한다. 주기적인
복구 작업은 아직 구현하지 않으며, 재요청 없이 남는 작업이 운영상 문제가 되면 별도 스케줄러 또는 비동기 작업 구조를 도입한다.

### 기존 사용량 책임 ADR과의 관계

2026-08-11의 `AI 만화 생성 사용량을 Diary와 Generation 중 어디에서 판단할 것인가` ADR이 정한 핵심 원칙을 유지한다. 사용량
가능 여부와 차감 순서는 `DiaryCreationTransactionService`가 결정하고, 실제 외부 생성을 수행하는 `ComicGenerationExecutor`는
사용량 저장소와 서비스에 의존하지 않는다.

다만 현재 스택에서 조회 API와 함께 먼저 도입된 사용량 타입 및 저장소가 물리적으로 `generation` 패키지에 있는 점은 기존 ADR의
패키지 배치 문구와 다르다. 이 ADR은 그 차이를 묵시적으로 대체하지 않는다. 최신 `develop-backend`를 최종 통합하기 전에 사용량
코드를 Diary 또는 독립된 Usage 컨텍스트로 이동할지, 기존 ADR의 패키지 경계를 팀 합의로 수정할지 결정해야 한다.

## 긍정적 결과

- 일기, 생성 선점과 사용량 증가의 DB 정합성이 한 트랜잭션으로 보장된다.
- 외부 AI 및 객체 저장소 지연이 DB 커넥션과 행 잠금 점유 시간에 포함되지 않는다.
- 멱등 재요청이 기존 상태를 보고 AI 중복 호출과 추가 차감을 피할 수 있다.
- 성공과 실패 갱신이 짧은 트랜잭션과 행 잠금으로 직렬화된다.
- 현재 프론트엔드의 동기 생성 응답을 유지한다.

## 부정적 결과와 트레이드오프

- 선점 이후 실패해도 외부 자원을 시도했으므로 사용량을 복구하지 않는다.
- 프로세스 강제 종료 시 `PROCESSING` 행이나 업로드 이미지가 남을 수 있다.
- 현재 stale 복구는 같은 멱등성 키의 재요청에 의존한다.
- 외부 호출 시간 동안 HTTP 연결과 애플리케이션 실행 스레드는 계속 점유된다.
- 완료 트랜잭션의 결과가 불명확한 경우 DB 재조회와 보수적인 이미지 정리가 필요하다.

동시 생성량, 외부 API의 429 또는 타임아웃이 증가하면 동기 계약을 유지하는 비용이 커진다. 이 지표가 운영 한계를 넘으면 Outbox와
작업 큐를 사용하는 비동기 방식으로 전환하는 결정을 다시 검토한다.
