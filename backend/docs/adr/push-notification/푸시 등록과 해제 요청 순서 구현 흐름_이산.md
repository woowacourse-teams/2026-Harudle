# 푸시 등록과 해제 요청 순서 구현 흐름

이 문서는 [등록과 해제 요청 순서 ADR](2026-10-15_푸시%20등록과%20해제%20요청의%20순서%20보장_이산.md)을 코드에 어떻게 적용했는지 설명한다. 백엔드 구현은 끝났고, 프론트엔드 연결은 남아 있다.

## 왜 바꿨나

사용자가 알림을 켰다가 바로 끄면 등록 요청 `PUT`과 해제 요청 `DELETE`가 겹칠 수 있다. 예전에는 등록이 아직 없을 때 `DELETE`가 아무것도 저장하지 않았다. 그래서 `DELETE`가 먼저 끝난 뒤 늦은 `PUT`이 도착하면 알림이 다시 켜질 수 있었다.

## 지금 백엔드는 어떻게 처리하나

1. 브라우저는 로그인 세션과 `deviceId`에 대한 `stateVersion`을 요청에 보낸다. 처음 값은 `0`이다.
2. 서버는 `push_registration_states`에 현재 번호와 알림을 켰는지 저장한다. 등록이 아직 없어도 해제 기록을 남긴다.
3. 서버는 받은 번호가 현재 번호와 같으면 요청을 처리하고 번호를 1 올린다. 번호가 오래됐으면 등록을 바꾸지 않고 `409 STALE_PUSH_STATE`와 현재 번호를 반환한다.
4. 등록을 해제할 때는 그 등록의 미발송 작업도 같은 DB 트랜잭션에서 취소한다. 같은 요청을 다시 보내면 번호를 또 올리지 않는다.

새 테이블은 Flyway `V26`에서 만든다. 기존 활성 등록 중 로그인 세션이 있는 등록은 `stateVersion=1`, 알림 켜짐 상태로 옮긴다. 기존 `push_registrations.version`은 FID 변경 순서를 확인하는 값이다. 새 `stateVersion`은 등록과 해제 요청의 처리 순서를 확인하는 값이다.

| 먼저 끝난 요청 | 뒤늦은 요청 | 서버 결과 |
| --- | --- | --- |
| `DELETE`, 번호 `0` | 옛 `PUT`, 번호 `0` | 해제 상태를 유지하고 `PUT`에 `409`를 반환한다. |
| `PUT`, 번호 `0` | 옛 `DELETE`, 번호 `0` | 등록을 유지하고 `DELETE`에 `409`를 반환한다. 사용자가 여전히 끄기를 원하면 현재 번호 `1`로 다시 해제해야 한다. |

서버는 두 요청이 처리된 순서를 기록한다. 하지만 `409` 이후 사용자가 지금 켜기를 원하는지 끄기를 원하는지는 브라우저가 확인해야 한다.

## 바뀐 API

- `PUT /api/v1/me/push-registrations/{deviceId}`: 본문에 `fid`와 `stateVersion`을 보낸다. FID 변경이면 `registrationId`와 기존 등록의 `version`도 보낸다. 성공하면 `id`, `version`, 새 `stateVersion`을 받는다.
- `DELETE /api/v1/me/push-registrations/{deviceId}?stateVersion=값`: 성공하면 `204`를 받는다. 새 번호는 `Push-State-Version` 응답 헤더에 있다.
- 번호가 오래되면 `409 STALE_PUSH_STATE`를 받는다. 응답의 `currentStateVersion`과 `enabled`로 서버의 현재 상태를 확인한다.

## 확인한 것

DB 테스트는 `DELETE`가 먼저 끝나는 경우, `PUT`이 먼저 끝나는 경우, 실제 동시 요청, 같은 요청의 반복, 다시 켜기와 미발송 작업 취소를 확인한다. API 테스트는 필수 번호와 `409` 응답을 확인한다. 마이그레이션 테스트는 기존 등록을 새 상태 테이블로 옮기는지 확인한다.

## 추가로 해야 할 일

1. 프론트엔드에서 현재 로그인과 `deviceId`에 맞는 `stateVersion`을 저장하고, 모든 등록 및 해제 요청에 넣는다. 성공 응답의 새 번호도 저장한다.
2. 프론트엔드에서 `409 STALE_PUSH_STATE`를 받으면 사용자의 **현재** 알림 선택을 확인한다. 끄기 상태라면 현재 번호로 `DELETE`를 다시 보낸다. 켜기 상태라면 최신 FID와 현재 번호로 `PUT`을 다시 보낸다. 오래된 요청을 그대로 반복하지 않는다.
3. 프론트엔드 테스트에서 두 요청이 겹칠 때 최종 선택이 유지되는지 확인한다. 로그아웃할 때 해당 로그인의 저장 값도 지운다.
4. 노션의 푸시 등록 API 명세를 현재 코드와 대조한다. `stateVersion`, 새 성공 응답, `DELETE`의 요청 번호와 응답 헤더, `409 STALE_PUSH_STATE`가 빠져 있으면 반영한다.
5. 프론트엔드를 연결한 뒤 실제 브라우저에서 등록, 해제, 다시 켜기, FCM 수신을 확인한다. 확인 순서는 [프론트엔드 연결과 검증 계획](피드%20푸시%20프론트엔드%20연결과%20검증%20계획_이산.md)에 적었다.
