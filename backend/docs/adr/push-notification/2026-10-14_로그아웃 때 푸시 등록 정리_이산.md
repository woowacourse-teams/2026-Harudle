# 로그아웃 때 푸시 등록은 어떻게 정리되는가

로그아웃한 곳으로 새 피드 알림을 계속 보내지 않기 위해, 서버는 **로그아웃한 로그인 세션에 속한 푸시 등록을 해제**한다. 같은 사용자가 다른 곳에서 로그인한 상태라면 그쪽 등록은 유지한다.

## 현재 서버가 하는 일

1. 로그아웃 요청의 쿠키에서 Refresh Token을 읽고, 그 토큰의 세션 ID를 찾는다.
2. `auth_sessions`에 세션 종료 시각을 저장하고, 같은 세션의 유효한 Refresh Token을 폐기한다.
3. 같은 세션의 `push_registrations`를 해제한다.
4. 그 등록에 연결된 `PENDING`, `PROCESSING` 발송 작업을 `CANCELLED`로 바꾼다.

이 변경은 하나의 DB 트랜잭션에서 처리한다. 중간에 저장이 실패하면 로그아웃 정리 전체를 되돌린다. 이미 `SENT`인 작업은 바꾸지 않는다. FCM이 이미 수락한 알림도 회수할 수 없다.

예를 들어 A가 크롬과 휴대폰에 각각 로그인했다면 세션이 두 개다. 크롬에서 로그아웃할 때는 크롬 세션의 토큰, 푸시 등록, 미발송 작업만 정리한다. 휴대폰 세션은 유지한다.

## 함께 들어온 요청은 어떻게 처리하는가

Refresh Token 갱신과 로그아웃이 겹치면 두 요청이 같은 세션을 잠근 뒤 처리한다. 로그아웃이 끝난 뒤에는 그 세션에서 새 유효 토큰이 남지 않는다. 쿠키의 토큰이 이미 갱신되어 폐기됐더라도 세션 ID가 있으면 해당 세션을 종료한다.

쿠키에 토큰이 없으면 서버는 종료할 세션을 알 수 없다. 이때는 쿠키를 지우고 응답한다. 세션 ID가 없는 기존 토큰은 그 토큰만 폐기한다.

## 확인한 내용과 남은 작업

테스트에서 로그아웃한 세션만 정리되는지, 미발송 작업이 취소되는지, 이미 전송된 작업이 유지되는지, 토큰 갱신과 로그아웃이 겹쳐도 유효 토큰이 남지 않는지 확인했다.

**이 작업만으로 로그인 중인 곳에만 푸시를 보내는 기능이 완성되지는 않는다.** 푸시 등록 API가 Access Token의 세션 ID를 등록에 연결하고, 발송 워커가 FCM에 보내기 직전 세션 상태를 확인하는 작업이 남아 있다.
