# 2026-10-11 FCM 발송 대상을 FID로 등록

- 작성일: 2026-10-11
- 작성자: 이산
- 결정 대상: 웹 푸시의 기기 등록 및 FCM 발송 대상

## 배경

처음에는 FCM 등록 토큰으로 피드 푸시를 구현하려 했고, 피드 테크스펙과 `push_registrations` 스키마도 이를 기준으로 작성했다. 이후 Firebase가 웹의 `getToken()`을 폐기 예정으로 표시하고 새 등록에는 Firebase Installation ID(FID)를 권장한다는 점을 확인해, 구현 전에 FID 방식으로 결정을 바꿨다. 토큰 방식의 제거일은 발표되지 않았으며 현재 두 방식 모두 지원된다. [웹 시작 가이드](https://firebase.google.com/docs/cloud-messaging/web/get-started), [등록 관리 가이드](https://firebase.google.com/docs/cloud-messaging/manage-tokens)

## 결정

- 새 피드 푸시는 웹에서 `register()`와 `onRegistered()`로 받은 FID를 서버에 등록하고, 백엔드는 FID를 대상으로 발송한다.
- 기존 `deviceId`는 하루들이 관리하는 기기 등록 식별자로 유지한다. FID는 해당 등록의 발송 대상 값이며 변경될 수 있으므로, 변경 통지를 받으면 서버의 값을 갱신한다.
- A의 세션과 푸시 등록이 유효할 때 B가 A의 `deviceId`로 직접 PUT하면 `409`를 반환하고 A의 등록을 유지한다.
- 하나의 FID가 다른 활성 기기 등록에 연결되어 있으면 기본적으로 `409`로 거절하고 기존 등록을 유지한다. 같은 유효 세션에서 `deviceId`만 바뀌었거나 기존 세션이 만료·해제됐음을 확인한 경우에는 기존 등록과 미발송 작업을 정리한 뒤 새 기기로 등록한다.
- `deviceId`는 브라우저·PWA 저장 환경별로 클라이언트가 생성해 유지하는 UUID다. 이 값만으로 다른 계정의 등록을 해제할 수 없다.
- 로그인 직후 해당 환경에서 푸시 수신 여부를 안내한다. 사용자가 받기를 선택하면 브라우저 권한을 요청하고 FID를 등록한다. 로그인만으로 자동 등록하지 않는다.
- 로그아웃이나 푸시 해제 시 해당 계정의 기기 연결과 아직 발송하지 않은 작업을 해제·취소한다.

## 이유

FID 방식은 Firebase가 새 구현에 권장하며, `onRegistered()`로 등록 및 FID 변경을 서버에 반영할 수 있다. 토큰 방식으로 새로 구현하면 향후 API 제거 시 등록·발송 계약을 다시 바꿔야 한다. [웹 시작 가이드](https://firebase.google.com/docs/cloud-messaging/web/get-started), [Java Admin SDK 릴리스 노트](https://firebase.google.com/support/release-notes/admin/java)

다른 계정이 `deviceId`만 알아도 유효한 푸시 등록을 끊을 수 있는 상황을 막는다. 세션이 해제되거나 만료된 등록은 새 계정을 막지 않아야 한다.

### 계정 전환과 세션 만료

1. **A가 로그아웃 → B가 푸시 등록:** A의 세션과 해당 환경의 푸시 등록을 해제하고 미발송 작업을 취소한다. B의 등록은 성공한다.
2. **A가 로그인 중 → B가 정상 화면에서 로그인:** 먼저 A가 로그아웃하므로 1번과 같다. 정상 계정 전환에서는 `409`가 나지 않는다.
3. **A의 세션 만료 → B가 로그인:** 로그인 자체가 A의 작업을 정리하지는 않는다. B의 푸시 등록 요청에서 A 세션의 무효 상태를 확인하고, **A의 푸시 등록과 미발송 작업만** 정리한 뒤 B를 등록한다. 발송 워커도 FCM 호출 전에 세션 유효성을 확인하고, 무효하면 해당 작업을 취소한다.

예를 들어 A가 크롬에서 로그아웃하지 않아 세션과 푸시 등록이 유효한 상태다. B가 같은 맥의 사파리에서 로그인해 자기 `deviceId`로 등록하면 성공한다. 그러나 B가 A의 `deviceId`를 별도로 알아내 그 값으로 직접 PUT하면 `409`이고 A의 등록은 유지된다. 크롬과 사파리의 저장소는 분리되므로 B가 A의 `deviceId`를 자동으로 알지는 못한다.

Access Token 만료만으로 세션이 만료된 것은 아니다. 갱신 가능한 로그인 상태는 유효하다. 세션 만료를 알리는 별도 요청이나 정리 워커는 필수가 아니며, 등록 요청과 발송 워커가 필요한 시점에 확인한다. 이미 FCM이 수락한 알림은 회수할 수 없다.

## 결과

- 피드 개발 테크스펙의 등록 및 해제 경로를 `/me/push-registrations/{deviceId}`로, 등록 요청을 `{fid}`로 바꿨다. 프론트는 수신을 선택한 계정의 `onRegistered()`에서 받은 FID를 등록한다.
- `V23` 마이그레이션은 `recipient_kind`의 기본값과 `CHECK` 허용 값을 `FID`로 바꾼다. 실제 FID는 기존 `recipient_value`에 저장한다. 다른 발송 방식을 도입하면 새 마이그레이션으로 허용 값을 확장한다.
- 기존 토큰 행은 FID로 변환할 수 없으므로, 남아 있으면 마이그레이션을 실패시켜 별도로 처리한다.
- 로그인 세션과의 연결은 [별도 ADR](2026-10-11_푸시%20등록을%20로그인%20세션에%20연결_이산.md)에 따른다. `V24`는 세션 테이블과 연결 컬럼을 추가하며, 등록·로그아웃 동작은 후속 코드에서 구현한다.
