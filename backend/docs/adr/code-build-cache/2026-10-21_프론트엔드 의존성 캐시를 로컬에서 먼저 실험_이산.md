# 프론트엔드 의존성 캐시를 로컬에서 먼저 실험

- 작성일: 2026-10-21
- 작성자: 이산
- 결정 대상: CodeBuild 프론트엔드 지속 캐시 도입 여부

이 문서는 캐시 도입 전 실험 기록이다. 후속 구현안은 [프론트엔드 PR 검사와 이미지 재사용](2026-10-21_프론트엔드%20PR%20검사와%20이미지%20재사용_이산.md)을 따른다.

## 배경

기존 AWS 실행 10건에서 프론트엔드 구간은 1분 30초에서 1분 42초였다. 이 구간에는 의존성 설치, `pnpm check`, Docker 이미지 생성과 내보내기가 함께 들어 있다. #400은 백엔드 Gradle 캐시를 바꿨지만 프론트엔드의 지속 캐시는 추가하지 않았다. CodeBuild가 새 빌드 호스트를 사용하면 Docker의 이전 의존성 설치 레이어를 재사용할 수 없다.

## 실험

ARM64 로컬 Docker 29.4.0에서 실험 당시 프론트엔드 Dockerfile의 `builder` 단계까지 빌드했다. 이 실험은 Docker 이미지 내보내기와 AWS S3 전송을 포함하지 않는다.

다음으로 임시 Dockerfile에서 `pnpm install --frozen-lockfile` 직후를 `dependencies` 단계로 나눴다. 이 단계만 Buildx 로컬 캐시로 내보낸 뒤 새 Buildx 빌더에서 캐시를 가져와 `builder` 단계를 빌드했다. 임시 Dockerfile과 캐시는 저장소에 적용하지 않았다.

| 확인 항목 | 로컬 결과 |
| --- | --- |
| 캐시가 없는 `pnpm install` | 22.2초 |
| 캐시가 없는 `pnpm check` | 21.9초 |
| 의존성 단계 캐시 내보내기 | 10.9초 |
| 내보낸 캐시 크기 | 231MB |
| 새 빌더에서 캐시 복원 후 `pnpm install` | 실행 생략, `CACHED` 확인 |
| 새 빌더에서 캐시 복원 후 `pnpm check` | 22.7초, 정상 실행 |

추가로 당시 Dockerfile을 캐시 없이 최종 이미지 tar까지 만든 로컬 실행은 전체 47초였다. 이 실행에서 `pnpm install`은 19.6초, `pnpm check`는 19.9초, 이미지 내보내기는 0.8초였다. tar 크기는 41MB였다. 기존 AWS 기록의 프론트엔드 구간 약 1분 38초와 차이가 있지만, 로컬 장비와 CodeBuild의 성능과 네트워크가 달라 원인을 이 숫자만으로 정할 수 없다.

## 결정

이 실험 시점에는 프론트엔드 지속 캐시를 CodeBuild에 추가하지 않기로 했다. 설치 단계에서 줄일 수 있는 시간은 로컬 첫 실행 기준 약 22초다. 반면 캐시를 내보내는 데 약 11초가 걸렸고, CodeBuild에서는 231MB 캐시의 S3 업로드와 다운로드 시간도 더해진다. 이 실험만으로 전체 CodeBuild 시간이 줄어든다고 판단할 수 없었다. 당시에는 `pnpm check`를 그대로 실행하기로 했다.

## 실험 당시의 다음 확인 계획

1. #400과 구간별 시간 로그가 `stage`에 반영된 뒤, 새 방식의 프론트엔드 시간과 전체 CodeBuild 시간을 여러 번 기록한다.
2. Docker 상세 로그에서 `pnpm install`, `pnpm check`, 이미지 내보내기 중 시간이 큰 작업을 확인한다.
3. 의존성 설치가 계속 큰 비중을 차지하면 별도 AWS 실행에서 캐시 복원과 저장을 포함한 전체 시간을 비교한다. 캐시 적용 후 전체 시간이 줄어들 때만 유지한다.

로컬 결과는 AWS의 S3 전송 속도나 빌드 호스트 성능을 대신하지 않는다.

## 다른 대안

| 방법 | 기대할 수 있는 효과 | 검토 결과와 남은 확인 사항 |
| --- | --- | --- |
| 변경 없는 프론트엔드 이미지 재사용 | 백엔드만 바뀐 배포에서 프론트엔드 빌드 전체를 생략할 수 있다. | 팀과 논의한 후속 방식은 PR에서 `pnpm check`를 실행하고, CodeBuild에서는 새 이미지가 필요할 때 `pnpm build`를 실행한다. 입력이 같으면 CodeBuild의 S3 캐시에서 압축 이미지를 가져오는 구현안을 작성했다. GitHub Actions 캐시에는 이미지를 저장하지 않는다. AWS 실행 확인은 아직 필요하다. |
| 의존성 설치 레이어를 외부 캐시에 저장 | 같은 의존성을 다시 설치하지 않는다. | 로컬 후보 캐시가 231MB다. AWS에서 전송과 저장까지 포함한 전체 시간을 비교해야 한다. Docker는 [외부 캐시](https://docs.docker.com/build/cache/backends/)를 지원한다. |
| 백엔드와 프론트엔드 이미지를 동시에 빌드 | 순서대로 빌드하는 시간을 겹칠 수 있다. | 현재 CodeBuild ARM Small은 2 vCPU와 4GiB다. 순차 빌드에서도 CPU 사용률이 60%를 넘은 실행이 있어 지금은 적용하지 않는다. 추후 CodeBuild 빌드 환경의 CPU와 메모리를 늘릴 때 다시 검토한다. 배포 서버 EC2의 용량 변경과는 별개다. |
| CodeBuild 크기를 ARM Medium으로 변경 | CPU나 메모리가 부족하다면 백엔드와 프론트엔드 작업이 모두 빨라질 수 있다. | ARM Medium은 4 vCPU와 8GiB지만 비용이 늘어난다. 순차 빌드 두 건의 사용률을 아래에 기록했다. 크기 변경은 아직 결정하지 않았다. |
| CodeBuild 로컬 Docker 레이어 캐시 | 같은 빌드 호스트를 다시 쓰면 레이어를 빠르게 재사용할 수 있다. | [로컬 캐시](https://docs.aws.amazon.com/codebuild/latest/userguide/caching-local.html)는 다른 호스트에서 사용할 수 없다. 실험 당시 프로젝트는 백엔드용 S3 캐시를 사용했고 Docker는 별도 Buildx 빌더를 만들었다. 후속 구현안은 로컬 Docker 레이어 캐시 대신 CodeBuild S3 캐시에 완성 이미지를 저장한다. |
| `pnpm fetch`나 pnpm 저장소 캐시 | 패키지 다운로드를 재사용할 수 있다. | 현재 Dockerfile은 이미 패키지 목록을 소스 코드보다 먼저 복사한다. 빌드 호스트가 바뀌는 환경에서는 [pnpm 안내](https://pnpm.io/docker)처럼 캐시 저장소가 실제로 유지되는지 확인해야 한다. 설치 전체가 로컬에서 약 20초라 우선순위가 낮다. |
| Webpack 파일 캐시 | 소스 빌드의 일부 작업을 재사용할 수 있다. | 로컬 Webpack 빌드는 약 4초였다. [Webpack 파일 캐시](https://webpack.js.org/configuration/cache/)를 저장하고 전송하는 비용보다 이득이 큰지 먼저 확인해야 한다. |

이 실험에서 가장 큰 절감 가능성은 프론트엔드가 바뀌지 않은 배포에서 이미지를 재사용하는 방법이었다. 이후 PR에서 `pnpm check`를 실행하고 CodeBuild에서 새 이미지의 배포용 빌드만 실행하는 방식을 팀과 논의했다. 이미지 재사용 구현안은 별도 ADR에 기록했으며 AWS 실행 확인은 아직 필요하다.

## CodeBuild 자원 사용률 확인

2026-10-20 AWS CodeBuild 실행 두 건의 CloudWatch 지표를 확인했다. 표의 최대값은 선택한 시간 범위에서 1분 구간의 `Average` 지표 중 가장 큰 값이다. 순간 최고 사용률은 아니다.

| 실행 | CPU 사용률 최대 | 메모리 사용률 최대 | 메모리 사용량 최대 |
| --- | ---: | ---: | ---: |
| #118, dev 배포 | 61.2% | 44.8% | 1.66GB |
| #119, prod 배포 | 63.3% | 34.9% | 1.30GB |

두 실행은 각각 백엔드 이미지를 만든 다음 프론트엔드 이미지를 만들었다. 각 실행의 CPU 사용률이 60%를 넘었으므로, 현재 CodeBuild 환경에서 두 이미지 빌드를 병렬로 실행하는 변경은 보류한다. 추후 CodeBuild 빌드 환경의 CPU와 메모리를 늘린다면, 같은 코드로 순차 실행과 병렬 실행의 전체 시간과 최대 메모리 사용량을 비교해 다시 결정한다. 배포 대상 EC2의 용량을 늘려도 CodeBuild 빌드 환경의 용량은 바뀌지 않는다. 로컬 Webpack 빌드는 약 4초라 별도 최적화 대상으로 삼지 않는다.
