# 프론트엔드 PR 검사와 이미지 재사용

- 작성일: 2026-10-21
- 작성자: 이산
- 상태: PR 검사와 CodeBuild 빌드 역할을 팀과 논의함. 이미지 재사용은 AWS 실행 확인 전
- 결정 대상: 프론트엔드 검사 위치와 CodeBuild 이미지 재사용

## 배경

기존 `dev` 대상 PR에서는 프론트엔드 타입 검사, 린트, 테스트를 실행한다. 형식 검사와 배포용 빌드는 빠져 있다. CodeBuild는 배포할 프론트엔드 이미지를 매번 새로 만들면서 `pnpm check`를 실행한다. 이전 AWS 기록에서 이 프론트엔드 구간은 보통 1분 30초에서 1분 42초였다.

백엔드는 PR에서 테스트하고 CodeBuild에서는 JAR를 만들 때 테스트를 제외한다. 팀과 논의한 프론트엔드 방식도 PR에서 검사하고 CodeBuild에서는 배포 파일을 만든다.

## 결정

1. 프론트엔드 PR에서는 `pnpm check`를 실행한다. 이 명령은 타입 검사, 린트, 형식 검사, Jest 테스트, 배포용 빌드를 차례로 실행한다. Jest에는 기존 CI의 `--ci --runInBand` 옵션을 유지한다.
2. 새 프론트엔드 이미지가 필요할 때 CodeBuild의 Dockerfile에서 `pnpm build`로 배포 파일을 만든다. 타입 검사, 린트, 형식 검사, 테스트를 다시 실행하지 않는다.
3. 프론트엔드 이미지 입력이 이전에 저장한 입력과 같으면 CodeBuild 프로젝트의 S3 캐시에서 압축 이미지를 가져와 재사용한다. 다르면 `pnpm build`를 실행해 새 이미지를 만든다. 변경된 파일만 골라 검사하는 방식은 사용하지 않는다.

이 방식은 모든 프론트엔드 변경이 PR 검사를 거쳐야 안전하다. 현재 워크플로는 `dev`, `main`, `develop-frontend` 대상 PR에서 프론트엔드 검사를 실행하고, `develop-backend` 대상 PR에서는 실행하지 않는다. `stage`를 대상으로 하는 PR 검사와 배포 브랜치 직접 push 검사는 정의되어 있지 않다. 이 경로로 프론트엔드 변경을 넣을 수 있다면 별도 검사 방법이 필요하다.

## 이미지 재사용 방법

GitHub Actions의 pnpm 캐시는 PR 검사의 의존성 설치에 사용한다. Docker 이미지는 이 캐시에 저장하지 않는다. CodeBuild가 재사용할 압축 이미지는 별도의 CodeBuild S3 캐시에 저장한다.

CodeBuild는 프론트엔드 파일 내용, PostHog 빌드 인자, 빌드 설정과 스크립트, Dockerfile의 두 베이스 이미지 원본을 묶어 지문을 만든다. S3 캐시에서 가져온 지문이 같고, 압축 이미지의 체크섬, gzip 형식, Docker 태그와 ARM64 설정이 맞을 때만 재사용한다. 이때 `pnpm build`와 로컬 프론트엔드 캐시 교체는 실행하지 않는다.

캐시가 없거나 검증에 실패하면 새 이미지를 만든다. 배포 파일을 확인하고 빌드 전후 입력 지문이 같으면 기존 캐시의 지문과 체크섬이 같아도 새 이미지를 로컬 캐시 경로에 저장한다. 입력이 달라졌다면 저장하지 않는다. 캐시를 교체할 때는 기존 지문을 지우고 새 이미지와 체크섬을 옮긴 뒤 새 지문을 마지막에 저장한다. 교체 중 실패해 지문이 없으면 다음 실행에서 그 캐시를 재사용하지 않는다. 이번 배포는 검증한 이미지로 계속한다. S3 업로드는 CodeBuild가 담당한다.

현재 `.dockerignore` 내용이 바뀌면 캐시 재사용을 멈춘다. 파일 제외 규칙과 지문 계산 범위를 함께 수정해야 잘못된 이미지를 재사용하지 않는다. CodeBuild S3 캐시를 쓰지 않는 프로젝트에서는 매번 새 이미지를 만든다. 캐시 경로에는 이미지 한 개만 보관하므로 dev와 prod의 프론트엔드 입력이 번갈아 달라지면 재사용하지 못할 수 있다.

## 이유

PR에서 전체 검사를 하면 형식 오류와 배포용 빌드 오류를 병합 전에 발견할 수 있다. CodeBuild에서는 같은 검사를 반복하는 대신 필요한 배포 파일을 만든다. 프론트엔드 파일과 빌드 인자, 베이스 이미지가 같으면 이미지 생성, 의존성 설치, Webpack 빌드를 모두 생략할 수 있다. 이때 CodeBuild S3 캐시에 저장된 완성 이미지를 다시 사용한다.

## 결과와 확인할 점

1. `stage`나 `main`으로 가는 프론트엔드 변경이 반드시 PR 검사를 거치는지 팀의 병합 규칙을 확인한다.
2. 변경을 `stage`에 반영한 뒤, 프론트엔드 변경이 없는 두 번째 CodeBuild 실행에서 `frontend_image_reused=true`를 확인한다. 프론트엔드 변경과 PostHog 인자 변경 시에는 `false`를 확인한다.
3. 변경 전후 CodeBuild 전체 시간에 S3 캐시 다운로드와 업로드 시간까지 포함해 비교한다. 캐시 전송 때문에 전체 시간이 줄지 않으면 재사용 방식을 다시 검토한다.

로컬 코드만 작성한 상태이며 실제 AWS 캐시 복원과 시간 절감은 아직 확인하지 못했다.
