# 2026-10-11 피드는 소프트 삭제하고 연결 데이터는 공개 조회에서 제외

- 상태: 채택
- 작성일: 2026-10-11
- 작성자: 캐모
- 결정 대상: 피드 삭제 방식과 댓글·좋아요·인앱 알림·푸시 발송 작업의 수명 주기

## 배경

피드는 개인 일기의 생성 이미지를 공개하는 게시물이다. 피드 삭제 시 개인 일기와 원본 이미지는 유지하고, 개인 일기 삭제 시에는 연결된 피드도 같은 트랜잭션에서 삭제해야 한다.

삭제된 피드는 공개 목록과 상세에서 제외하고, 연결 댓글·좋아요와 인앱 알림도 조회에서 숨겨야 한다. 아직 보내지 않은 새 글 푸시는 취소해야 한다. 피드 삭제 후 같은 일기를 다시 게시할 수 있으며, 재게시에는 새로운 피드 ID와 게시 시각을 사용한다.

현재 스키마에는 `feeds.deleted_at`과 활성 피드에만 적용하는 일기별 유니크 인덱스가 있다. 댓글·좋아요·인앱 알림·푸시 Outbox는 피드를 참조하며, 피드를 물리 삭제하면 `ON DELETE CASCADE`로 함께 삭제된다. 이 연쇄 삭제는 원본 일기나 객체 저장소 이미지로 전파되지 않는다.

기존 `FeedLifecycle` 계약은 연결 피드에 삭제 시각을 기록하도록 정의되어 있다. `FeedPushOutbox` 계약은 대기·처리 중인 작업을 취소 상태로 바꾸도록 정의되어 있다. 기존 인터페이스의 메서드와 입력·반환 타입을 유지하면서 삭제 정책을 결정한다.

## 결정 요인

- 삭제 후 피드와 연결 반응이 공개 조회에 노출되지 않아야 한다.
- 피드만 삭제하면 개인 일기와 원본 이미지를 계속 사용할 수 있어야 한다.
- 피드 삭제와 미발송 푸시 취소는 함께 커밋하거나 롤백해야 한다.
- 게시·삭제·재게시와 발송·취소 상태를 운영 중 확인할 수 있어야 한다.
- 기존 피드 생명주기와 푸시 포트 계약을 유지해야 한다.
- 삭제 데이터가 쌓이는 비용과 후속 파기 정책을 고려해야 한다.

## 고려한 대안

### 대안 1: 피드를 하드 삭제

피드 행을 물리 삭제하고 현재 FK의 연쇄 삭제로 댓글·좋아요·인앱 알림·푸시 Outbox도 제거한다.

장점은 다음과 같다.

- 삭제된 피드와 연결 데이터가 DB에 남지 않는다.
- 해당 피드의 삭제 여부를 공개 조회에서 별도로 확인할 필요가 없다.
- 별도 보관·정리 작업을 줄일 수 있다.
- 원본 일기와 이미지를 유지하면서 새 피드 ID로 재게시할 수 있다.

단점은 다음과 같다.

- 현재 FK 설정에서는 이미 발송·실패·취소된 푸시 작업의 이력도 함께 사라진다.
- 삭제 시각 기록과 취소 상태 전환을 전제로 한 기존 계약 설명을 조정해야 한다.
- 댓글·좋아요 등 연결 행이 많으면 삭제 트랜잭션의 작업량이 커진다.
- 피드와 연결 데이터의 과거 상태를 조사할 수 없게 된다.

### 대안 2: 피드를 소프트 삭제하고 연결 데이터를 조회에서 제외

피드의 `deleted_at`을 기록하고 연결 댓글·좋아요·인앱 알림 행은 유지한다. 조회와 쓰기에서는 활성 피드 조건을 확인하고, 미발송 푸시 작업은 취소 상태로 전환한다.

장점은 다음과 같다.

- 기존 삭제 시각 기록과 푸시 취소 계약을 그대로 적용할 수 있다.
- 피드 삭제 이력과 푸시 발송·실패·취소 상태를 보존할 수 있다.
- 댓글·좋아요 전체를 삭제하는 작업 없이 공개 접근을 차단할 수 있다.
- 활성 피드에만 적용하는 유니크 인덱스를 이용해 재게시할 수 있다.

단점은 다음과 같다.

- 공개 조회와 연결 데이터 조회에서 활성 피드 조건을 일관되게 적용해야 한다.
- 피드와 연결 데이터가 계속 쌓이므로 보관 기간과 실제 파기 정책이 필요하다.
- 조회에서 숨기는 것과 데이터를 물리적으로 제거하는 시점이 달라진다.

## 결정

대안 2를 채택한다. 피드는 소프트 삭제하고 연결 데이터를 공개 조회에서 제외한다.

### 피드와 원본 데이터

- 작성자의 피드 삭제 요청은 피드 행을 잠근 뒤 소유권을 확인하고 `Feed` 도메인을 통해 `deletedAt`을 기록한다.
- 이미 삭제된 피드의 삭제 시각은 다시 변경하지 않는다.
- 피드 삭제 시 개인 일기, 생성 기록과 원본 이미지 객체는 유지한다.
- 피드 삭제가 생성 사용량을 복구하지 않는다.
- 개인 일기 삭제에 연결된 피드 삭제도 같은 정책과 트랜잭션을 사용한다.

### 댓글·좋아요·인앱 알림

- 피드 삭제 시 연결 댓글·좋아요·인앱 알림을 일괄 물리 삭제하지 않는다.
- 피드 목록·상세, 댓글 목록과 좋아요 조회는 삭제된 피드를 제외한다.
- 댓글·좋아요의 쓰기 작업은 잠근 피드의 활성 여부를 확인하고 삭제된 피드에 대한 작업을 거부한다.
- 인앱 알림 목록과 전체 미읽음 수는 모두 삭제된 피드를 제외한다. 목록만 숨기고 미읽음 수에는 남는 상태를 허용하지 않는다.
- 삭제된 피드의 반응 수를 일괄 감소시키거나 0으로 초기화하지 않는다. 기존 피드와 반응 데이터는 같은 피드 ID에 남는다.

### 푸시 취소와 트랜잭션

- 피드 상태 변경과 `FeedPushOutbox.cancelUnsentByFeed(feedId)` 호출은 같은 DB 트랜잭션에서 수행한다.
- `PENDING`과 `PROCESSING` 작업은 `CANCELLED`로 바꾸고 잠금 정보와 `sent_at`을 비운다.
- 이미 `SENT`인 작업의 발송 이력은 유지한다.
- 취소 저장이 실패하면 피드 삭제도 롤백한다.
- 푸시 워커는 삭제된 피드의 작업을 발송하지 않도록 확인하며, 이미 외부로 전송 중인 메시지는 회수할 수 없다.

```text
피드 행 잠금
→ 작성자 소유권 확인
→ Feed.deletedAt 기록
→ 대기·처리 중인 푸시 작업 취소
→ 같은 트랜잭션으로 커밋
```

### 재게시와 개인 일기 조회

- 삭제된 피드의 ID를 재사용하거나 삭제 상태를 되돌려 재게시하지 않는다.
- 같은 일기를 새 피드 ID와 새 게시 시각으로 게시한다. 좋아요·댓글 수는 0에서 시작하고 새 게시 이벤트를 예약한다.
- 이전 피드의 댓글·좋아요·알림은 이전 피드 ID에 연결된 상태로 유지되어 새 게시물에 합쳐지지 않는다.
- 개인 일기 상세의 `publishedFeedId`는 피드 삭제 후 null, 재게시 후 새 피드 ID를 반환한다.

### 구현 책임

| 영역 | 책임 |
| --- | --- |
| `Feed` 도메인 | 삭제 상태와 삭제 시각 관리 |
| 피드 서비스 | 소유권 검증, 트랜잭션 흐름과 푸시 취소 호출 |
| 피드 Repository | 피드 조회·잠금·영속화 |
| `FeedLifecycle` 구현 | 호출자의 일기 삭제 트랜잭션에서 연결 피드 삭제와 푸시 취소. 연결이 없거나 이미 삭제됐으면 아무것도 하지 않음 |
| 댓글·좋아요·알림 영역 | 조회·쓰기와 미읽음 수에 활성 피드 조건 적용 |
| 푸시 영역 | 미발송 작업 취소 저장과 워커의 발송 대상 확인 |

기존 포트의 메서드와 타입은 변경하지 않는다. 피드 서비스가 댓글·좋아요·알림 테이블을 직접 정리하는 책임을 갖지 않는다.

## 긍정적 결과

- 원본 일기와 이미지를 유지하면서 공개 게시를 취소할 수 있다.
- 피드 삭제와 미발송 푸시 취소가 함께 성공하거나 함께 롤백된다.
- 게시·삭제·재게시와 푸시 처리 상태를 확인할 DB 기록이 남는다.
- 기존 스키마와 생명주기 포트를 유지하면서 삭제 기능을 연결할 수 있다.
- 재게시한 피드에 이전 게시물의 반응이 다시 노출되지 않는다.

## 부정적 결과와 트레이드오프

- 활성 피드 조건을 빠뜨린 조회는 삭제된 연결 데이터를 노출할 수 있으므로 각 담당 영역의 조회와 쓰기를 함께 검증해야 한다.
- 삭제된 피드와 반응·알림·푸시 행의 저장 비용이 남는다.
- 소프트 삭제는 사용자 복구 기능이나 영구 보관을 의미하지 않는다.
- 이미 발급된 이미지 접근 URL은 만료 전까지 유효할 수 있다. 피드 삭제 후에도 원본 이미지는 개인 일기에서 사용한다.

## 후속 결정과 재검토 조건

이번 결정에서 보관 기간이나 정리 배치의 실행 주기를 확정하지 않는다. 실제 파기 작업은 보관 기간, 연결 데이터의 삭제 범위와 푸시 이력 보존 방식이 정해진 뒤 별도로 설계한다. 피드 데이터의 물리 정리가 원본 일기 이미지 삭제로 이어지지 않도록 이미지 수명 주기는 일기·생성 영역의 정책에 따른다.

다음 경우 삭제 정책을 재검토한다.

- 삭제 데이터의 보관 기간과 실제 파기 요구사항이 확정되는 경우
- 삭제 데이터의 규모와 저장 비용이 운영 부담이 되는 경우
- 푸시 이력을 별도 저장소로 분리해 피드 하드 삭제의 영향을 줄일 수 있는 경우
- 게시물 복구 기능이 요구되어 재게시와 복구의 구분이 필요한 경우

4번 피드 삭제 구현과 5번 개인 일기 삭제 연동에서 이 결정을 적용한다. 검증 대상은 삭제 후 공개 조회와 반응 쓰기 차단, 미읽음 수 제외, 원본 유지, 재게시, 푸시 취소 실패 시 롤백이다.
