# 2026-08-12 PostgreSQL 원자적 UPSERT로 일일 생성 사용량 증가

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 일일 생성 사용량 증가의 동시성 제어와 영속성 구현 방식

## 배경

사용자는 서비스가 정한 날짜를 기준으로 하루에 정해진 횟수만큼 AI 이미지를 생성할 수 있다.
`daily_generation_usage`는 `(user_id, usage_date)`를 기본 키로 사용하고, 현재 사용량과 일일 한도를 함께 저장한다.

일반적인 JPA 조회, 계산, 저장 방식으로 사용량을 증가시키면 다음과 같은 흐름이 된다.

```text
사용량 조회
→ Java에서 현재 값에 1을 더함
→ 변경된 사용량 저장
```

같은 사용자가 동시에 여러 요청을 보내면 각 트랜잭션이 동일한 현재 값을 읽을 수 있다. 두 요청이 모두 같은 값을 저장하면 실제 요청
수보다 사용량이 적게 기록되는 lost update가 발생하고, 일일 생성 한도를 초과할 수 있다.

사용량 행이 아직 없는 첫 요청에는 행 생성이 필요하고, 이미 행이 있으면 한도 확인과 증가를 함께 수행해야 한다. 이 작업을 어떤
영속성 방식으로 구현할지 결정해야 한다.

## 결정 요인

- 같은 사용자의 동시 요청에서도 사용량이 유실되지 않아야 한다.
- 사용량 생성, 한도 검사와 증가 사이에 다른 요청이 끼어들 수 없어야 한다.
- 일일 한도를 초과한 요청은 사용량을 변경하지 않아야 한다.
- 사용량 행이 없는 첫 요청과 이후 요청을 하나의 일관된 흐름으로 처리해야 한다.
- 팀에서 합의한 JPA 영속성 기술을 유지해야 한다.
- 특정 데이터베이스에 종속된 구현은 인프라스트럭처 경계 안에 격리해야 한다.

## 고려한 대안

### 대안 1: 일반 JPA 조회 후 엔티티 값을 증가시켜 저장

```text
SELECT
→ Java에서 사용량 및 한도 확인
→ INSERT 또는 UPDATE
```

장점은 다음과 같다.

- JPQL과 JPA 엔티티 변경 감지만으로 구현할 수 있다.
- 데이터베이스 전용 SQL에 의존하지 않는다.
- 코드 흐름이 익숙하고 단순해 보인다.

단점은 다음과 같다.

- 조회와 저장 사이에 다른 트랜잭션이 끼어들 수 있다.
- 동시 요청에서 lost update가 발생할 수 있다.
- 행이 없는 첫 요청이 동시에 들어오면 기본 키 충돌을 별도로 처리해야 한다.
- 애플리케이션에서 수행한 한도 검사 결과가 저장 시점까지 유효하다고 보장할 수 없다.

### 대안 2: JPA 잠금으로 조회 후 증가

비관적 잠금 또는 낙관적 잠금을 적용해 사용량을 조회하고 증가한다.

장점은 다음과 같다.

- JPA가 제공하는 잠금 API를 사용할 수 있다.
- 기존 행에 대한 동시 수정을 직렬화하거나 충돌을 감지할 수 있다.
- 데이터베이스 전용 UPSERT 문법을 직접 작성하지 않아도 된다.

단점은 다음과 같다.

- 아직 존재하지 않는 첫 사용량 행은 행 잠금만으로 보호하기 어렵다.
- 낙관적 잠금은 충돌 시 재시도 정책이 추가로 필요하다.
- 비관적 잠금은 조회, 조건 검사와 저장이 여러 단계로 남는다.
- 잠금 범위와 순서를 잘못 관리하면 대기 시간이나 교착 상태가 증가할 수 있다.

### 대안 3: EntityManager로 PostgreSQL 원자적 UPSERT 실행

PostgreSQL의 `INSERT ... ON CONFLICT ... DO UPDATE ... WHERE ... RETURNING`을 한 SQL로 실행한다.

```sql
INSERT INTO daily_generation_usage (...)
VALUES (...)
ON CONFLICT (user_id, usage_date)
DO UPDATE
   SET used_count = daily_generation_usage.used_count + EXCLUDED.used_count
 WHERE daily_generation_usage.used_count < daily_generation_usage.limit_count
RETURNING used_count, limit_count;
```

장점은 다음과 같다.

- 행 생성, 한도 검사와 증가를 데이터베이스의 한 문장 안에서 수행한다.
- 충돌한 행에 대한 PostgreSQL의 동시성 제어 안에서 사용량을 증가시킨다.
- 한도에 도달하면 업데이트와 `RETURNING` 결과가 모두 발생하지 않는다.
- 별도의 `JdbcTemplate`을 도입하지 않고 JPA의 `EntityManager`로 실행할 수 있다.

단점은 다음과 같다.

- PostgreSQL 전용 SQL에 의존한다.
- JPQL만 사용하는 저장소보다 쿼리 동작을 이해하기 어렵다.
- 반환된 컬럼을 도메인 객체로 명시적으로 매핑해야 한다.
- 실제 PostgreSQL을 사용한 동시성 테스트가 필요하다.

## 결정

대안 3을 선택한다.

`JpaGenerationUsageRepository`가 `EntityManager`로 PostgreSQL 원자적 UPSERT를 실행한다. 사용량 행이 없으면 기본 사용량으로
생성하고, 이미 있으면 저장된 한도보다 사용량이 작은 경우에만 1을 증가시킨다. 쿼리의 `RETURNING` 결과가 비어 있으면 한도에
도달한 것으로 해석한다.

```text
INSERT 성공
→ 증가된 사용량 반환

기본 키 충돌 + 한도 미도달
→ 기존 행 사용량 증가
→ 증가된 사용량 반환

기본 키 충돌 + 한도 도달
→ 변경 없음
→ 빈 결과 반환
```

네이티브 SQL은 Generation의 인프라스트럭처 어댑터 내부에만 둔다. 애플리케이션과 도메인 계층은 PostgreSQL 문법을 알지 않고
`GenerationUsageRepository.tryIncrementWithinLimit` 계약만 사용한다.

## 긍정적 결과

- 동시에 요청해도 각 성공 요청의 사용량이 정확히 한 번 반영된다.
- 데이터베이스가 한도 검사와 증가를 함께 수행해 일일 한도 우회를 막는다.
- 첫 요청의 행 생성과 이후 요청의 증가가 하나의 쿼리로 처리된다.
- JPA를 기본 영속성 기술로 유지하면서 PostgreSQL이 필요한 부분만 `EntityManager`로 실행한다.
- 데이터베이스 전용 구현이 영속성 어댑터 밖으로 전파되지 않는다.

## 부정적 결과와 트레이드오프

- PostgreSQL이 아닌 데이터베이스로 변경하면 해당 어댑터를 다시 구현해야 한다.
- JPQL과 달리 컴파일 시점에 쿼리 문법과 컬럼 매핑을 검증할 수 없다.
- 쿼리의 `WHERE`와 `RETURNING` 의미를 모르면 빈 결과의 정책을 이해하기 어렵다.
- H2 같은 대체 데이터베이스만으로는 실제 동시성 동작을 충분히 검증할 수 없다.

현재 운영 데이터베이스가 PostgreSQL로 정해져 있고 생성 비용과 직접 연결된 한도 정확성이 이식성보다 중요하다. 따라서
PostgreSQL 결합을 어댑터 내부에 제한하고, 실제 PostgreSQL 기반 테스트로 원자성과 한도 동작을 검증한다.
