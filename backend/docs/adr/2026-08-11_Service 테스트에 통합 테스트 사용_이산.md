# Service 테스트에 통합 테스트 사용

서비스 계층은 여러 객체와 Repository를 조합하여 하나의 비즈니스 흐름을 수행한다.

Service만 격리하여 테스트하려면 Mock이나 Fake를 사용해야 한다. 이 경우 실제 협력 객체의 동작을 테스트 코드에서 다시 정의해야 한다.

Mock을 사용하면 객체 사이의 호출 방식이나 횟수를 검증할 수 있지만, 테스트가 Service의 내부 구현에 결합될 수 있다. 기능의 결과가 같더라도 내부 구현을 변경하면 테스트 코드가 깨질 수 있다.

Fake를 사용하면 실제 Repository와 유사하게 테스트할 수 있지만, 실제 JPA Repository와 PostgreSQL의 동작과는 차이가 있다. 따라서 다음 내용을 정확하게 검증하기 어렵다.

- JPA 엔티티 매핑
- 실제 조회 쿼리와 연관관계
- 데이터베이스 고유 제약 조건
- 트랜잭션과 동시 요청

결국 실제 Repository의 동작까지 확인하려면 Service와 Repository를 함께 사용하는 통합 테스트가 필요하다.

따라서 Service의 주요 협력 흐름은 Mock이나 Fake를 사용하는 격리 테스트 대신 실제 Service와 Repository를 사용한 통합 테스트로 검증한다. 데이터베이스는 Testcontainers로 PostgreSQL을 실행하여 운영 환경과의 차이를 줄인다.

공유 링크 Service에서는 다음 흐름을 통합 테스트로 확인한다.

- 성공한 생성 결과에 공유 링크가 없으면 새 링크를 생성한다.
- 공유 링크가 이미 존재하면 기존 링크를 반환한다.
- 생성 상태가 `PROCESSING` 또는 `FAILED`이면 공유 링크를 생성하지 않는다.
- 다른 사용자의 그림일기이거나 삭제된 그림일기이면 공유 링크를 생성하지 않는다.
- 하나의 생성 결과에는 하나의 공유 링크만 저장된다.

도메인의 핵심 규칙과 실패 케이스는 단위 테스트로 검증한다. 복잡한 쿼리나 데이터 정합성을 별도로 보호해야 하는 경우에는 Repository 테스트를 추가하고 작성 이유를 PR에 남긴다. Controller를 통한 주요 사용자 시나리오는 인수 테스트로 검증한다.

Mock과 Fake의 사용을 모두 금지하는 것은 아니다. 외부 API, 이미지 저장소, 시간처럼 테스트 환경에서 직접 사용하기 어렵거나 결과를 통제해야 하는 대상에는 테스트 대역을 사용할 수 있다. 다만 애플리케이션 내부의 Service와 Repository 협력은 가능한 한 실제 구현으로 검증한다.
