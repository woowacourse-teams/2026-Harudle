# 2026-08-28 관리자 생성 가능 횟수 복구 요청의 멱등성을 어떻게 보장할 것인가

- 작성일: 2026-08-28
- 작성자: 이산
- 결정 대상: `PATCH /api/v1/admin/users/{userId}/generation-usage/restore`의 재시도 처리

## 배경

복구 API는 `used_count`에서 요청 수량을 차감하는 상대적 변경이다. 관리자가 요청을 성공시켰지만 네트워크
타임아웃으로 응답을 받지 못하면 같은 요청을 재전송할 수 있다. 이때 `Idempotency-Key`가 없으면 같은 복구가
두 번 적용된다.

사용자 행 잠금과 조건부 차감은 동시 요청의 순서와 음수 사용량을 제어하지만, 순차적으로 도착한 동일 요청을
구분하지는 못한다.

## 고려한 대안

### 대안 1: 복구 전용 멱등성 기록과 `Idempotency-Key` 사용

복구 요청마다 사용자 ID, 복구 수량, 처리 상태와 최초 결과를 별도 테이블에 저장한다. 같은 키의 재요청은
저장된 결과를 반환하고, 다른 요청에 같은 키를 사용하면 충돌로 거절한다.

장점은 다음과 같다.

- 응답 유실에 따른 중복 차감을 데이터베이스에서 방지한다.
- 여러 애플리케이션 인스턴스와 재시작 상황에서도 동작한다.
- 최초 응답 결과를 그대로 재현할 수 있다.

단점은 다음과 같다.

- 전용 테이블과 마이그레이션이 필요하다.
- 멱등성 기록의 보존 기간과 정리 정책을 운영해야 한다.
- 같은 키를 다른 수량으로 재사용하면 충돌하므로 새 키가 필요하다.

### 대안 2: 모든 API가 공유하는 범용 멱등성 테이블

작업 종류와 요청 지문, 상태, 응답 본문을 범용 테이블에 저장한다.

장점은 관리자 초기화나 다른 변경 작업에도 재사용할 수 있다는 점이다.

단점은 응답 직렬화, 작업별 상태와 오류 처리, 보존 정책을 범용화해야 하므로 이번 복구 기능보다 구현 범위가
크고 도메인 규칙이 흐려진다.

### 대안 3: 작업 ID를 URL에 포함한 `PUT` API로 변경

복구 작업 ID를 리소스 식별자로 사용해 같은 작업 ID의 `PUT` 요청을 멱등적으로 처리한다.

장점은 작업 리소스가 API에 명시되고 감사 이력으로 확장하기 쉽다는 점이다.

단점은 기존 `PATCH` 계약과 클라이언트 호출 방식을 변경해야 하며, 결국 작업 상태를 저장할 테이블도 필요하다.

## 결정

대안 1을 선택한다.

- 복구 API는 UUID 형식의 `Idempotency-Key`를 필수로 받는다.
- 멱등성 키는 `admin_generation_usage_restores`의 기본 키로 사용한다.
- 같은 키의 요청 동일성은 `user_id`와 `restore_count`로 판단한다.
- 기록 상태는 `PROCESSING`, `SUCCEEDED`, `CONFLICT`로 관리한다.
- 성공한 복구의 `usage_date`, `used_count`, `limit_count`를 저장해 최초 응답을 재현한다.
- 사용량 부족 등으로 복구에 실패한 결과도 `CONFLICT`로 저장해 같은 키의 재시도에서 같은 결과를 반환한다.

처리 순서는 다음과 같다.

1. 대상 사용자 행을 `PESSIMISTIC_WRITE`로 잠근다.
2. `INSERT ... ON CONFLICT DO NOTHING`으로 멱등성 기록을 선점한다.
3. 기록을 잠그고 사용자 ID와 복구 수량이 같은지 확인한다.
4. 이미 성공한 기록이면 저장된 사용량을 반환한다.
5. 새 기록이면 조건부 원자 차감을 실행하고 결과를 기록한다.
6. 복구 충돌이면 충돌 상태를 저장하고 같은 예외를 반환한다.

사용자 행, 멱등성 기록, 사용량 행의 접근 순서를 고정해 기존 생성·한도 변경·초기화와의 잠금 순서도 일관되게
유지한다. 복구 충돌 기록을 커밋하기 위해 해당 도메인 예외는 트랜잭션을 롤백하지 않도록 처리한다.

## 결과

- 네트워크 재시도로 같은 복구 요청이 두 번 차감되지 않는다.
- 동시 요청에서도 하나의 멱등성 기록만 선점한다.
- 같은 키에 다른 사용자나 수량을 보내면 `IDEMPOTENCY_KEY_CONFLICT`를 반환한다.
- 최초 성공 응답의 사용량 스냅샷을 재시도에서도 동일하게 반환한다.
- 멱등성 기록이 계속 쌓이므로 향후 보존 기간과 정리 작업을 별도로 결정해야 한다.
- 성공 후 사용량이 다른 관리자 작업으로 변경되어도 재시도에는 최초 결과가 반환된다. 이는 재시도 일관성을 위한
  의도된 동작이다.

## 재검토 조건

- 복구 기록을 관리자 감사 로그로 확장해야 하는 경우
- 멱등성 기록의 자동 만료·정리 정책이 필요한 경우
- 초기화나 한도 변경에도 동일한 멱등성 작업 모델을 적용해야 하는 경우
