# 2026-08-27 관리자 조회 결과와 조회 Repository를 어떤 패키지에 둘 것인가

- 작성일: 2026-08-27
- 작성자: 이산
- 결정 대상: 관리자 조회 계층의 패키지 책임

## 결정

관리자 모듈의 조회 Repository와 조회 결과 모델을 분리한다.

- `admin/repository`: Spring Data repository 인터페이스와 `@Query` 기반 조회 쿼리
- `admin/query`: 검색·상세 조회 결과, projection, 페이지 모델
- `admin/presentation/dto`: HTTP 요청·응답 DTO
- 별도 `admin/infrastructure` 구현체는 단순 조회에 두지 않는다. 사용자 정의 Repository 구현이 필요한 경우에만 추가한다.

## 이유

`repository` 패키지에 Repository 인터페이스와 여러 조회용 record가 섞이면 저장소 접근 책임과 조회 결과 표현이 구분되지 않는다. 조회 record를 `query`에 두면 API DTO나 도메인 모델과도 명확히 분리할 수 있다.

현재 관리자 조회는 조건과 반환 형태가 정해져 있으므로 쿼리를 `@Query`에 JPQL로 명시한다. `@Query`를 사용하면 엔티티 조인, 검색 조건, 정렬, projection을 Repository 메서드에서 한눈에 확인할 수 있어 `EntityManager`로 `createQuery`, 파라미터 바인딩, 결과 매핑, 페이징을 직접 작성하는 방식보다 조회 흐름의 가독성이 좋다. Spring Data가 `Page`와 `countQuery` 처리도 담당하므로 조회 구현의 반복 코드도 줄어든다.

## 결과

새로운 관리자 조회 API의 `@Query` Repository는 `admin/repository`에 추가하고, 내부 결과 모델은 `admin/query`에 추가한다. 외부 응답 형식은 `admin/presentation/dto`에서 관리한다. 현재 `AdminUserQueryRepository`와 `AdminGenerationHistoryQueryRepository`가 이 구조를 따른다.

생성 사용량 증가·복구·초기화·한도 변경처럼 원자적인 네이티브 SQL이 필요한 연산은 조회와 성격이 다르므로 기존처럼 `generation/infrastructure`에서 관리한다.

## 재검토 조건

- 관리자 조회 기능이 별도 read model 또는 CQRS 구조로 확장되는 경우
- 조회 조건이 동적으로 크게 늘어 `@Query`의 가독성이 떨어지는 경우
- 관리자 모듈 외에도 동일한 조회 계층 패키지 규칙을 적용해야 하는 경우
