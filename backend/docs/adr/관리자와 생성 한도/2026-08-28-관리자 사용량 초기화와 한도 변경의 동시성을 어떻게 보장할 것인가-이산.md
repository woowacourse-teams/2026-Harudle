# 2026-08-28 관리자 사용량 초기화와 한도 변경의 동시성을 어떻게 보장할 것인가

- 작성일: 2026-08-28
- 작성자: 이산
- 결정 대상: 관리자의 오늘 생성 사용량 초기화와 사용자별 생성 한도 변경

## 문제

오늘 사용량 초기화는 사용자 행에서 읽은 현재 한도를 오늘 사용량 스냅샷에 기록한다. 한도 변경과 초기화가 동시에 실행되면,
초기화가 이전 한도를 읽은 뒤 한도 변경이 커밋되고 초기화가 이전 값을 다시 기록할 수 있다.

예를 들어 사용자 한도가 `5`이고 오늘 사용량이 `used_count = 5`, `limit_count = 5`인 상태에서 다음 순서가 가능하다.

```text
T1: 초기화가 사용자 한도 5를 읽음
T2: 사용자 한도와 오늘 스냅샷을 3으로 변경하고 커밋
T1: 읽어 둔 5를 오늘 스냅샷에 기록하고 커밋
```

그러면 `users.daily_generation_limit = 3`인데 `daily_generation_usage.limit_count = 5`가 되어 새 한도보다 많이 생성할 수 있다.

## 결정

초기화와 한도 변경 모두 같은 사용자 행에 `PESSIMISTIC_WRITE` 잠금을 획득한 뒤 작업을 수행한다.

- `UserRepository.findByIdForUpdate`가 사용자 행을 `PESSIMISTIC_WRITE`로 조회한다.
- `AdminGenerationUsageService.reset`은 잠금을 획득한 뒤 현재 한도를 읽고 오늘 사용량을 초기화한다.
- `AdminGenerationUsageService.changeLimit`은 잠금을 획득한 뒤 사용자 한도와 오늘 스냅샷을 변경한다.
- 관련 흐름의 잠금 순서는 `users` 행을 먼저 잠근 뒤 `daily_generation_usage` 행을 갱신하는 순서로 통일한다.
- 잠금은 트랜잭션이 커밋되거나 롤백될 때까지 유지한다.

## 고려한 대안

### 대안 1: 사용자 행의 비관적 잠금

같은 사용자의 작업을 데이터베이스 행 잠금으로 직렬화한다.

장점은 다음과 같다.

- 여러 애플리케이션 인스턴스가 실행되어도 데이터베이스가 동시성을 제어한다.
- 현재 서비스·도메인 흐름을 유지하면서 변경 범위를 작게 가져갈 수 있다.
- 사용자별 잠금이므로 서로 다른 사용자의 요청은 계속 병렬로 처리된다.

단점은 다음과 같다.

- 같은 사용자의 동시 요청 중 하나는 먼저 실행 중인 트랜잭션이 끝날 때까지 대기한다.
- 트랜잭션이 길어지거나 잠금 순서가 일관되지 않으면 대기 시간과 데드락 가능성이 커진다.
- 잠금 조회를 위해 데이터베이스 왕복이 추가된다.

### 대안 2: 초기화와 한도 변경을 하나의 데이터베이스 전용 SQL로 처리

사용자 한도와 오늘 사용량 스냅샷을 PostgreSQL의 CTE 또는 단일 갱신 문으로 함께 변경한다.

장점은 데이터베이스 안에서 변경 범위를 더 직접적으로 표현할 수 있고, 애플리케이션의 중간 상태를 줄일 수 있다는 점이다.

단점은 PostgreSQL 문법과 반환값 매핑에 강하게 결합되며, 사용량 행이 없는 초기화와 기존 JPA 변경 감지 흐름까지 함께 재설계해야 한다는 점이다.
또한 한도 변경 경로와 동일한 잠금 순서를 별도로 보장해야 한다.

### 대안 3: 낙관적 잠금과 충돌 시 재시도

사용자 버전 또는 현재 한도를 함께 비교해 충돌을 감지하고, 실패하면 다시 읽어 재시도한다.

장점은 충돌이 없는 경우 잠금 대기가 없다는 점이다.

단점은 초기화가 사용자를 직접 변경하지 않으므로 별도의 기대값 비교가 필요하고, 재시도 횟수·실패 응답·스냅샷 갱신 정책이 복잡해진다.

## 이유

이 기능은 사용자별 한도와 오늘 사용량 스냅샷의 정합성이 핵심이다. 같은 사용자에 대한 관리자 변경 요청은 빈도가 높지 않고 트랜잭션도 짧으므로,
충돌 시 짧게 대기하는 대신 오래된 한도가 저장되는 것을 막는 비관적 잠금이 요구사항과 현재 구조에 가장 잘 맞는다.

잠금 순서를 `users → daily_generation_usage`로 고정하면 사용량 최초 생성, 한도 변경, 사용량 초기화가 동일한 방향으로 자원을 획득하므로
교착 상태 가능성도 줄일 수 있다.

## 결과

- 초기화가 한도 변경 전의 값을 다시 저장하는 lost update를 방지한다.
- 초기화와 한도 변경이 동시에 요청되어도 사용자 한도와 오늘 스냅샷이 일치한다.
- 서로 다른 사용자의 요청에는 불필요한 전역 잠금을 적용하지 않는다.
- 같은 사용자의 동시 요청은 첫 번째 트랜잭션의 커밋까지 대기할 수 있다.

## 재검토 조건

- 한 사용자에 대한 관리자 작업이 긴 외부 호출이나 대량 처리로 확장되는 경우
- 여러 사용자의 행을 한 트랜잭션에서 동시에 변경해야 하는 요구사항이 생기는 경우
- PostgreSQL 의존성을 줄이거나 다른 데이터베이스를 지원해야 하는 경우
