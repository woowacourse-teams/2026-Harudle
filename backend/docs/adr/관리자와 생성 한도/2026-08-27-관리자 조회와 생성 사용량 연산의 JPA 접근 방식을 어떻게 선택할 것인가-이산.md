# 관리자 조회와 생성 사용량 연산의 JPA 접근 방식을 어떻게 선택할 것인가

- 상태: 채택
- 작성자: 이산
- 결정 대상: 관리자 조회와 생성 사용량 변경 저장소

## 결정

- 관리자 사용자·생성 이력 조회는 Spring Data `@Query`로 JPQL을 실행한다.
- 생성 사용량의 증가·복구·초기화·한도 변경은 `EntityManager`로 네이티브 SQL을 실행한다.
- `EntityManager`는 네이티브 원자 연산이 필요한 인프라 구현체에서만 직접 사용하고, 서비스에는 노출하지 않는다.
- 현재는 Querydsl을 도입하지 않고, 관리자 조회 조건이 더 복잡해질 때 도입을 재검토한다.

## 이유

### 관리자 조회

관리자 사용자 조회는 이름·사용자 ID 검색, 게스트 제외, OAuth 마지막 로그인 시각, 오늘 사용량과 한도 조인, DTO 프로젝션, 정렬, 페이징과 전체 개수 조회를 함께 처리한다.

생성 이력 조회도 사용자·상태·기간 필터를 선택적으로 조합하고, 생성 이력·일기·사용자 조인, DTO 프로젝션, 정렬, 페이징과 `countQuery`가 필요하다. 사용자 상세 조회는 사용자 정보와 최근 생성 5개를 별도로 조회해 하나의 결과로 조합한다.

현재 필터와 조회 방식은 한정적이므로 JPQL을 `@Query`에 명시하는 편이 흐름을 직접 확인하기 쉽다. Spring Data가 파라미터 바인딩과 `Page` 처리를 담당하므로, `EntityManager`의 쿼리 생성·파라미터 설정·페이징 코드를 반복하지 않아도 된다. Querydsl의 Q 클래스 생성과 annotation processing 설정을 추가하지 않아도 되는 점도 고려했다.

### 생성 사용량 변경

생성 사용량 변경은 단순 CRUD가 아니라 다음 조건을 하나의 원자 연산 흐름으로 처리해야 한다.

- 첫 생성 요청이면 오늘 사용량 행을 만들고 사용자별 현재 한도를 함께 기록한다.
- 기존 행은 한도 미만일 때만 증가시켜 동시 요청에서도 초과 사용이 발생하지 않게 한다.
- 복구는 현재 사용량이 복구 횟수 이상일 때만 차감한다.
- 초기화는 기존 행이 있을 때만 사용량을 0으로 변경한다.
- 한도 변경 시 이미 사용한 횟수보다 작은 한도를 저장하지 않도록 `max(used_count, 새 한도)`를 적용한다.
- 변경된 사용량과 한도를 즉시 반환한다.

이 과정에는 PostgreSQL의 `ON CONFLICT`, 조건부 `UPDATE`, `RETURNING` 같은 네이티브 기능이 필요하다. JPQL은 이를 충분히 표현하기 어렵고, Querydsl JPA를 사용해도 네이티브 SQL 연산 자체가 없어지지 않는다.

## 대안

- 모든 조회를 `EntityManager`로 처리할 수 있지만, 쿼리 생성과 파라미터 바인딩, 페이징을 직접 관리해야 한다.
- 모든 조회를 Querydsl로 처리할 수 있지만, 현재 범위에서는 설정과 생성 코드 관리 비용이 크다. 또한 사용량 변경의 네이티브 SQL 문제는 해결하지 못한다.
- `JdbcTemplate`으로 사용량 쿼리를 실행할 수도 있지만, 기존 JPA 기반 저장소에 별도 데이터 접근 방식을 추가하게 된다.

## 결과

관리자 조회는 `@Query`로 읽기 쿼리를 명시하고, 사용량 변경에만 `EntityManager` 네이티브 쿼리를 제한적으로 사용한다. `@Query`도 내부적으로는 EntityManager를 사용하지만, 애플리케이션 코드에서 직접 쿼리 생성과 파라미터 바인딩을 관리하지 않는다는 차이가 있다.

관리자 조회 필터가 늘어나거나 동적 쿼리의 가독성이 떨어지면 Querydsl 도입을 재검토한다.
