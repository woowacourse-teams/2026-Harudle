## 배경과 보호 목표

현재 일기 입력은 최대 300 Unicode code point이며 `diaries.source_text`에 저장된다.
서버는 본인 상세 조회와 이미지 생성에 원문을 다시 사용한다. 일기 원문으로 검색·정렬하거나
DB에서 문자열 연산을 수행하는 요구는 없다. 회원·게스트 생성은 같은 저장 경로를 쓴다.
여기서 논리 덤프는 SQL 조회 등으로 DB의 행과 값을 파일로 내보낸 결과를 뜻한다.
디스크 자체를 암호화해도 정상 조회로 내보낸 파일에 평문이 담기면 그 파일은 따로 보호해야 한다.

이번 결정의 목표는 **애플리케이션 키가 없는 DB 조회 권한 또는 논리 덤프의 유출만으로
신규 일기 입력 원문을 직접 읽거나 짧은 후보를 지문으로 확인하지 못하게 하는 것**이다.
다른 일기·사용자 행에서 가져온 암호문과 손상된 암호문도 정상 원문으로 처리하지 않아야 한다.

애플리케이션은 생성과 응답을 위해 원문을 볼 수 있어야 하므로 종단간 암호화는 선택하지 않는다.
앱 프로세스·호스트·키가 함께 탈취된 경우, 인증 우회, 같은 행의 과거 암호문 재생·삭제,
날짜 등 다른 DB 열의 위변조를 이 기능 하나로 막는다고 주장하지 않는다.
제목·스토리보드·생성 이미지 같은 파생 콘텐츠와 공개 피드는 별도 데이터다. 이를 통해
내용을 추론할 수 있는 문제까지 해결한 **일기 전체의 기밀성 보장**은 아니다.

기존 평문과 과거 SHA 지문·백업은 #423 전환 전까지 남는다. 이 ADR의 신규 데이터 보호
목표와 전체 운영 DB의 전환 완료는 구분한다.

## 용어와 흐름을 먼저 이해하기

구현은 다음 세 흐름으로 나누어 읽으면 된다.

1. **새 일기 저장:** 입력을 검증하고 비밀 키로 암호화한다. 암호문 바이트를 Base64 문자열로 바꿔
   DB에 저장하며, 사용한 키를 나중에 찾을 수 있도록 키 ID도 기록한다. 요청 지문도 비밀 키로 보호해 저장한다.
2. **본인 일기 조회:** 로그인한 요청자와 일기 소유자가 같은지 먼저 확인한다. 그다음 저장된 키 ID로
   키를 찾고, 암호문이 해당 일기·사용자와 맞는지 검증하면서 복호화해 응답한다.
3. **생성 재시도:** 멱등성 키로 기존 생성 요청을 찾는다. 요청 내용으로 보호된 지문을 다시 계산해
   저장된 값과 비교한다. 내용이 같으면 기존 결과나 상태를 사용하고, 다르면 같은 요청의 재시도로 받지 않는다.

멱등성 키는 **어떤 요청인지 찾는 식별자**, 지문은 **요청 내용이 같은지 확인하는 검증값**이다.
암호화·복호화의 변조 검증과 API 소유권 확인도 각각 수행한다. 이 구분을 기준으로 세부 용어를 읽으면 된다.

## 결정 기준

1. 원문 복원이 가능하고, 암호문과 소유자/일기 식별자의 일치 여부를 검증할 수 있어야 한다.
2. DB에 복호화 키를 전달하지 않고 저장소 접근 권한과 키 접근 권한을 분리한다.
3. 기존 Java 21·JPA·PostgreSQL과 생성 트랜잭션에 통합할 수 있어야 한다.
4. 추가 외부 통신·인프라 권한을 필수로 늘리지 않되 키 보관·교체·복구 책임을 명시한다.
5. 버전·키 ID로 기존 데이터 호환과 향후 전환을 구분한다. 암호화 실패를 평문으로 우회하지 않는다.

비교는 **보호 경계, 암호 알고리즘, 키 관리, 저장 표현**의 네 가지 결정으로 나눈다.
Base64·KMS·AES-GCM을 같은 역할의 경쟁 제품으로 취급하지 않는다.

## 1. 보호 경계

| 대안 | 얻는 점 | 우리 요구와의 차이 및 비용 | 결정 |
| --- | --- | --- | --- |
| 원문에 Base64만 적용 | 문자열로 표현·복원하기 쉬움 | 키 없이 바로 복원할 수 있어 DB 유출 시 기밀성·변조 탐지를 제공하지 않음 | 보호 수단으로 제외 |
| 단방향 해시만 저장 | 원문 자체를 보관하지 않음 | 본인 조회·AI 생성용 원문 복원이 불가능하고 짧은 입력은 후보 검증 가능 | 원문 저장 수단으로 제외 |
| RDS/디스크 저장 암호화 | 저장 매체·물리 백업 보호를 인프라에서 제공 | 정상 SQL 조회와 논리 덤프에서 반환되는 값을 보호하는 경계가 아님. 실제 RDS 활성 상태는 별도 확인 대상 | 앱 암호화를 보완하는 별도 계층 |
| PostgreSQL `pgcrypto` | SQL에서 암복호화, DB와 기능 통합 | 평문·키가 DB 서버 처리 경계를 통과하며 DB/시스템 관리자를 신뢰해야 함. SQL·확장 기능에 키 수명주기가 결합됨 | 이번 목표에는 앱 경계 선택 |
| 애플리케이션 필드 암호화 | DB에는 암호문만 전달, 키를 DB 밖에 보관, 필요한 경로만 복호화 | 앱·키가 함께 탈취되면 보호 불가. 앱이 키와 데이터 형식을 관리해야 함 | 채택 |
| 클라이언트 종단간 암호화 | 서버도 원문을 보지 않음 | 현재 서버 AI 생성·다중 기기 조회·키 복구 제품 흐름을 다시 설계해야 함 | 현재 제품 요구와 맞지 않음 |

Base64는 인코딩 규약이다. 암호문을 저장할 때 사용할 수는 있지만 원문에 적용하는 것만으로
보호가 되지는 않는다. [RFC 4648](https://www.rfc-editor.org/rfc/rfc4648.html#section-12)
암호화는 비밀 키가 있어야 원문으로 복원할 수 있게 값을 바꾸고, Base64는 바이트를 일반 문자열로
옮겨 적는다. 이번 저장 순서는 `원문 → AES-GCM 암호문 바이트 → Base64 문자열`이다.
DB에서 Base64를 되돌려도 암호문 바이트만 얻으며, 원문을 읽으려면 여전히 비밀 키가 필요하다.

`pgcrypto`의 신뢰 경계는 PostgreSQL이 직접 명시한다. 앱에서 키를 분리하려는 이번 목표에는
앱 암호화가 더 맞는다. [PostgreSQL 보안 제한](https://www.postgresql.org/docs/current/pgcrypto.html#PGCRYPTO-SECURITY-LIMITATIONS)
RDS 저장 암호화의 범위는 [AWS RDS 암호화 문서](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Overview.Encryption.html)를 참고한다.

## 2. 애플리케이션 암호 알고리즘

`AES-256-GCM`에서 **AES**는 비밀 키로 데이터를 암호화하는 알고리즘이고, **256**은 키의
길이인 256비트, 즉 32바이트를 뜻한다. **GCM**은 AES를 사용해 암호화와 변조 검증을 함께
수행하는 운용 방식이다. 따라서 AES-128과 AES-256의 비교는 키 길이의 선택이고,
CBC와 GCM의 비교는 AES를 어떤 방식으로 사용할지의 선택이다.

**AEAD**는 원문을 숨기는 동시에 암호문과 추가 데이터의 변조를 검증하는 암호화 방식을 가리킨다.
AES-GCM과 ChaCha20-Poly1305가 여기에 해당한다. 여기서 인증은 암호화할 때의 키·데이터와
복호화할 때의 키·데이터가 맞는지 검증한다는 뜻이며, API 요청자의 로그인·접근 권한 확인은 별도로 한다.

| 대안 | 필요한 구성 | 장점 | 감수할 점과 판단 |
| --- | --- | --- | --- |
| AES-CBC 단독 | IV·패딩 | 가역적 암호화 | 인증이 없어 암호문 변조를 신뢰성 있게 거절할 요구에 부족하므로 제외 |
| AES-CBC + HMAC | 독립 키, Encrypt-then-MAC, IV·메타데이터 인증, 인증 후 복호화 | 올바르게 조합하면 기밀성·무결성 충족 | 키·패딩·인증 순서·인증 범위를 직접 조합할 책임이 증가. 기존 CBC 데이터와의 호환 요구가 없어 선택할 이점이 적음 |
| AES-GCM | AES 키, 매번 새로운 nonce, 인증 tag, AAD | 암호화와 인증을 한 AEAD API에서 처리. 일기·소유자 정보를 AAD로 연결 가능 | nonce 재사용에 취약. 난수·키별 사용량과 교체 정책이 필요. 이번 구현에 채택 |
| ChaCha20-Poly1305 | 32바이트 키, 새로운 nonce, tag, AAD | 같은 기밀성·인증 요구를 충족하고 Java 21에서도 지원. 적합한 대안 | nonce 관리가 여전히 필요. 실제 서버에서 성능 우위를 측정한 근거가 없어 알고리즘 교체의 이득을 주장하지 않음 |

AES-GCM과 ChaCha20-Poly1305 모두 현재 요구에 맞는다. AES-GCM이 더 유명하다거나
ChaCha가 Java에서 불가능하다는 이유로 고르지 않는다. 결정은 **AEAD로 직접 조합할 오류
지점을 줄이고, 현재 JDK의 `Cipher` API만으로 추가 라이브러리나 네트워크 없이 기존
트랜잭션을 유지할 수 있다는 조건을 충족하는 AES-GCM을 이번 저장 형식 v1로 고정**하는 것이다.
이 조건에서는 ChaCha도 유효하므로 AES만이 유일한 정답이라는 결론은 아니다.

EC2 ARM64의 실제 암호화 가속 상태와 두 알고리즘의 성능은 측정하지 않았다. 따라서
“AES가 더 빠르다”는 주장을 채택 근거로 쓰지 않는다. 300자 입력에 대해 성능 문제가
관측되거나 실행 환경이 바뀌면 같은 워크로드로 둘을 측정하고 형식 v2를 검토한다.
검토에서는 코드의 호환성·키 관리 비용도 함께 비교한다.

AES-128-GCM도 보안 요구를 충족할 수 있다. AES-256-GCM을 선택한 것은 이번 키링을
장기 보관 일기의 키 탐색 공격에 대한 여유를 확보하는 32바이트 규격으로 고정하기 위해서다.
두 규격의 키 생성·주입·보존 절차는 같으며 AES-128이 안전하지 않아서 제외한 것은 아니다.
256비트의 추가 연산 비용은 있을 수 있지만 현재 입력 길이에서 서비스 병목이라고 측정한
근거는 없다. 실제 병목이 되면 성능을 측정한 뒤 재검토한다.

근거: [GCM 규격](https://csrc.nist.gov/pubs/sp/800/38/d/final),
[JDK Cipher의 nonce·AAD 계약](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/javax/crypto/Cipher.html),
[JDK 지원 알고리즘](https://docs.oracle.com/en/java/javase/21/security/oracle-providers.html),
[ChaCha20-Poly1305](https://www.rfc-editor.org/rfc/rfc8439.html).

## 3. 키 관리

**키링**은 `키 ID → 실제 비밀 키`의 목록이다. 키 ID는 `primary`, `k202611`처럼 어떤 키를
사용했는지 찾는 이름이며 공개되어도 되는 정보다. 실제 32바이트 키는 비밀로 보관한다.
활성 키는 새 일기를 쓸 때 사용하고, 기존 일기를 읽을 때는 암호문에 기록된 키 ID로 당시 키를 찾는다.
이렇게 구키와 신키를 함께 보관하면 새 쓰기를 신키로 바꾼 뒤에도 이전 일기를 읽을 수 있다.

| 대안 | 얻는 점 | 비용과 제한 | 결정 |
| --- | --- | --- | --- |
| 환경별 로컬 키링 | 암복호화 외부 호출 없음, 현재 배포의 보안 환경 변수로 주입 가능, 키 ID로 구/신 키 병행 | 장기 키가 앱 메모리에 존재. 접근 통제·백업·회전·폐기를 팀이 담당. 환경 단위 키 노출의 영향이 큼 | 이번 구현에서 채택 |
| KMS 직접 암복호화 | 관리형 키 접근 제어·감사, 장기 마스터 키를 앱 밖에 보관 | API 네트워크·권한·비용·할당량·장애에 일기 읽기/쓰기가 의존 | 도입 필요성이 확인되면 재검토 |
| KMS envelope encryption | 데이터는 로컬 암호화, 데이터 키를 KMS로 감싸 장기 키 관리 개선 | 암호화된 데이터 키 보관·복호화 호출·캐시 수명/폐기·장애 정책 필요. 캐시하면 매 행마다 호출할 필요는 없으나 설계 책임 증가 | 운영 요구 확대 시 우선 검토할 전환 방향 |

현재 300 code point 원문의 UTF-8 최대 길이는 1,200바이트다. KMS 직접 암호화의
4,096바이트 한도 안이므로 입력 크기 때문에 KMS를 제외하는 것은 잘못된 설명이다.
이번에는 키 관리 서비스의 권한·감사·장애 운영을 필수로 추가할 요구가 아직 확인되지 않았고,
새 외부 의존성 없이 저장 보호를 적용하는 범위를 선택한다. KMS 비용이 비싸다고 단정하지 않으며
실제 도입 판단에는 호출량·캐시 정책·사용 가능한 IAM 권한과 복구 절차를 확인해야 한다.

감사 가능한 복호화 접근, 서버 `.env`의 장기 키 제거, 여러 인스턴스·서비스 간 키 통제가
필요해지면 KMS envelope 방식을 다시 검토한다. KMS를 사용해도 탈취된 앱이 기존 IAM 권한으로
복호화를 호출하는 문제까지 자동으로 해결하지는 못한다.
[KMS Encrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Encrypt.html),
[KMS envelope encryption](https://docs.aws.amazon.com/kms/latest/developerguide/kms-cryptography.html#enveloping)

## 4. 저장 표현과 호환 경계

`source_text_version=0`은 기존 평문, `1`은 AES-256-GCM으로 명시한다. 문자열 prefix로
평문 여부를 추측하지 않는다. 새 쓰기는 항상 `1`이며 알 수 없는 버전과 복호화 실패에는
평문 fallback을 제공하지 않는다.
다만 전환 중 버전 `0`이 허용되므로 DB 쓰기 권한을 가진 공격자가 버전까지 `0`으로 낮추는
변조는 막지 못한다. #423에서 전환 완료를 검증한 뒤 기존 평문 읽기 경로도 닫아야 한다.

암호문은 `keyId:Base64(nonce[12] + ciphertext + tag[16])`로 `TEXT`에 저장한다.
Base64는 이 단계의 바이너리 직렬화이며 암호화는 그 전에 이미 끝난다. `BYTEA`를 쓰면
Base64의 약 33% 크기 증가를 피할 수 있으나, 기존 문자열 기반 엔티티·projection과 평문
호환 경로를 함께 변경해야 한다. 최대 저장 길이 1,705자에서 이 변경을 필수로 만들 이득은
확인되지 않아 이번에는 TEXT를 유지한다. 대량 저장 비용이 문제가 되면 BYTEA를 재검토한다.

96비트 nonce는 암호화마다 `SecureRandom`으로 만들고 tag는 128비트를 사용한다.
키 ID·목적·버전·일기 ID·사용자 ID를 AAD로 인증한다. 버전은 알고리즘 교체용,
키 ID는 같은 알고리즘 내 키 교체용이다. 키 ID 내용을 바꾸거나 구키를 지우는 방식으로
회전하지 않는다. 키별 2^32회 암호화에 접근하도록 운용하지 않으며 그 전에 키를 전환한다.
현재 코드에는 호출량 기반 자동 회전·상한 강제는 없으므로 운영 관리 책임이다.

각 값의 역할은 다음과 같다. nonce와 tag는 암호문과 함께 저장해도 되며, AAD는 저장된 일기의
식별자 등으로 다시 만든다. 이 값들이 공개된다는 이유로 비밀 키를 DB에 저장해도 되는 것은 아니다.

| 용어 | 이번 구현에서 하는 일 |
| --- | --- |
| nonce(논스) | 같은 키로 암호화할 때 중복되면 안 되는 12바이트 값. 매번 보안 난수로 만들어 같은 원문도 서로 다른 암호문이 되게 한다. 재사용은 GCM의 보안을 해치므로 키별 사용량도 관리한다. |
| tag(인증 태그) | 암호화 시 GCM이 만드는 16바이트 검증값. 복호화할 때 키·nonce·암호문·AAD에 맞는지 확인하고, 검증이 실패하면 원문을 반환하지 않는다. |
| AAD(추가 인증 데이터) | 암호화해 숨기지는 않지만 tag로 함께 검증하는 데이터. 이 구현에서는 목적·버전·키 ID·일기 ID·사용자 ID를 묶어 암호문의 사용 위치를 제한한다. |

예를 들어 A 사용자의 일기 1을 암호화할 때는 A의 사용자 ID와 일기 1의 ID가 AAD에 들어간다.
누군가 nonce와 tag를 포함한 암호문 전체를 B 사용자의 일기 2에 복사해도, 앱은 조회한 행에 맞춰
B의 사용자 ID와 일기 2의 ID로 AAD를 만든다. 암호화할 때와 다른 AAD이므로 tag 검증이 실패한다.
원래 행에서 키·nonce·암호문·AAD를 그대로 다시 사용하는 과거 값 재생까지 막는 것은 아니다.

**소유권 확인을 먼저 하는 이유**도 별개다. A가 B의 일기 상세를 요청했다면 서버가 요청자와
일기 소유자를 비교해 거절해야 한다. GCM은 해당 행의 암호문이 올바른지만 확인하므로,
접근 권한 없이 복호화한 뒤 응답해도 되는지까지 판단해 주지는 않는다. 본인 요청임을 확인한 뒤
복호화하면 타인의 요청으로 불필요하게 키를 사용하거나 손상된 원문을 처리하는 일도 줄어든다.

JPA converter의 자동 복호화도 선택하지 않는다. 본인 상세와 생성 재요청의 권한 확인 뒤
명시적으로 복호화하면 공개·관리자·목록·삭제 경로에서 불필요한 원문 처리를 줄일 수 있다.
부담은 엔티티와 projection 양쪽에 저장 버전을 전달하고 실제 DB 테스트를 유지해야 한다는 점이다.

여기서 **JPA converter**는 DB 값과 Java 필드 값을 읽고 쓸 때 자동으로 변환하는 기능이다.
여기에 복호화를 넣으면 엔티티를 읽는 시점에 권한 확인 전부터 원문을 만들 수 있다.
**projection**은 조회에 필요한 필드만 골라 받는 객체로, 목록처럼 전체 엔티티가 필요 없는 조회에서
사용한다. 현재 `DiarySnapshot`도 이 조회 결과를 받는다. 원문이 필요한 조회 결과에는 암호문과
버전을 함께 전달하고, 서비스에서 권한 확인 후 명시적으로 복호화한다. 이 구조가 조회 성능을
얼마나 개선했는지는 측정하지 않았으며, 여기서는 복호화가 일어나는 위치를 분명히 하는 것이 목적이다.

## 원문 지문도 함께 보호한다

**멱등성 키**는 클라이언트가 재시도할 때도 같은 요청을 가리키도록 보내는 식별자다.
같은 키로 다시 요청하면 일기 생성이나 사용량 차감을 반복하지 않는다. **요청 지문**은 사용자·날짜·
원문 등 요청 내용으로 계산하는 검증값이다. 같은 멱등성 키에 다른 내용을 보내면 기존 요청과
다르다는 것을 알아내 거절하는 데 사용한다. 키는 어떤 요청인지를 찾고, 지문은 내용이 같은지 확인한다.

기존 지문은 `v1`, 사용자 ID, 일기 날짜, 원문을 줄바꿈으로 이어 붙여 계산한 SHA-256 값이다.
**SHA-256**은 입력을 일정한 길이의 해시값으로 바꾸며 같은 입력에는 같은 결과를 만든다.
저장된 해시를 일반적으로 원문으로 복원할 수는 없지만, 후보를 알고 있으면 그 후보의 해시와 대조할 수 있다.

예를 들어 원문이 `오늘도 피곤했다`일 것으로 예상한다면 DB에서 읽은 사용자·날짜와 이 후보를
같은 규칙으로 해시해 저장된 지문과 비교할 수 있다. 값이 같으면 그 후보가 실제 입력인지 확인할 수 있다.
임의의 긴 원문을 쉽게 역산한다는 뜻은 아니지만, 짧거나 흔한 문장은 후보를 시도할 여지가 크다.
원문 열만 암호화하고 이 값을 계속 신규 저장하면 목표에 빈틈이 남는다. 공개 salt를 추가해도
공격자가 그 salt까지 읽어 후보 계산에 넣을 수 있으므로 이 검증 경로는 남는다.

신규 버전 `1`에는 위 SHA 결과를 그대로 저장하지 않고 HMAC-SHA256으로 보호한 64자리
hex를 저장한다. 암호화 키에서 고정된 별도 목적의 HMAC으로 지문용 subkey를 파생하고,
독립 목적·키 ID·일기 ID·사용자 ID·요청 SHA를 인증한다. 데이터 암호화와 지문 인증에
같은 원시 키를 직접 재사용하지 않는다. 재요청은 저장된 암호문의 키 ID로 검증하므로 활성 키
변경 뒤에도 기존 요청을 재현할 수 있다. [HMAC 규격](https://www.rfc-editor.org/rfc/rfc2104.html)

**HMAC**은 비밀 키와 메시지로 계산하는 검증값이다. 공격자가 `오늘도 피곤했다`의 SHA 값을
만들어도, 저장된 지문과 비교할 HMAC 결과는 지문용 키 없이는 계산할 수 없다. 신규 경로에서는
중간 SHA를 요청 처리 중 계산하고 최종 HMAC 결과를 DB에 저장하므로, DB만 읽은 공격자가
그 SHA를 직접 대조하는 경로를 없앤다. HMAC은 원문 조회용 암호문을 대신하지 않으며,
원문은 AES-GCM으로 복호화하고 HMAC은 요청이 같은지 확인하는 데 사용한다.

**별도 목적의 파생 키(subkey)**는 설정된 루트 키로부터 지문 작업에 쓸 키를 따로 계산한 값이다.
이번 구현은 고정 문자열 `harudle.diary.request-fingerprint.key:v1`을 목적 구분값으로 사용한다.
그 결과로 만든 키를 지문 HMAC에 사용하고, 지문 메시지에도 별도 목적 문자열과 일기·사용자 정보를
넣는다. 암호화와 지문 검증이 서로 다른 용도임을 코드와 입력 형식에서 구분하되,
두 키를 각각 생성해 설정·교체하는 운영 부담은 추가하지 않는 선택이다.

별도 무작위 HMAC 키를 관리하면 키 접근 권한을 더 세밀하게 분리할 수 있지만, 키링 두 개의
보존·교체·복구 관계를 관리해야 한다. 현재 같은 앱에서 두 연산을 수행하므로 별도 키 운영을
추가하는 대신 목적이 다른 subkey를 파생한다. 환경 루트 키가 유출되면 두 보호가 함께 무너지는
한계는 남으며, 역할별 권한 분리가 필요해지면 별도 키와 KMS 관리를 재검토한다.

기존 버전 `0`은 현재 SHA 계약을 유지한다. #423에서는 원문·저장 버전·지문을 한
트랜잭션으로 전환해야 한다. 서로 다른 상태가 되면 기존 멱등 재요청이 충돌하기 때문이다.
향후 원문을 다른 키로 재암호화할 때도 지문 재계산이 필요하다. 과거 SHA가 남은 백업의
보존기간까지 관리해야 기존 데이터의 후보 검증 위험을 제거할 수 있다.

원문과 지문을 같은 트랜잭션으로 바꾸는 것 외에 진행 중 생성과의 경쟁도 통제해야 한다.
실행기는 generation 지문을 읽은 뒤 일기를 따로 읽으므로 전환 시점이 겹치면 이전 지문과
새 암호문을 혼합해 정상 요청을 거부할 수 있다. #423/재암호화는 생성 중단·대기,
`PROCESSING` 행 제외 후 재처리 또는 일관된 조회/잠금 중 하나를 계약으로 정해야 한다.
키 추가·활성 키 변경만 하는 현재 운영은 기존 행을 수정하지 않아 이 경쟁을 만들지 않는다.

## 결과와 검증 기준

채택하는 조합은 **애플리케이션 AES-256-GCM + 환경별 키링 + 암호문 Base64/TEXT 직렬화**다.
선정 근거는 원문 복원·기밀성·변조 감지·DB와 키의 분리·현재 실행/배포 흐름의 유지다.
추가 키 관리 서비스 없이 시작하는 대신 키 보관·교체·복구 책임과 앱 호스트 침해의 한계를 감수한다.

검증에는 신규 암호문·보호된 지문 저장, 동일 원문의 비결정적 암호화, 변조·다른 행·다른 사용자·
키 오류 거절, 키 전환 뒤 재요청, 기존 평문 혼재, 권한 확인 우선순위, 실패 롤백,
로그·예외의 원문/키 비노출이 포함된다. 운영 키 준비·배포 검증과 기존 데이터 전환을
테스트 통과만으로 완료 처리하지 않는다.
