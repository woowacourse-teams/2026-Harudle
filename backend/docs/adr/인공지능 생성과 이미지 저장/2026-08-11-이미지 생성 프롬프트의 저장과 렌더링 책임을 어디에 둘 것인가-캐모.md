# 2026-08-11 이미지 생성 프롬프트 저장과 렌더링 책임 분리

- 작성일: 2026-08-11
- 작성자: 캐모
- 결정 대상: Generation 이미지 생성 프롬프트의 저장 위치와 동적 렌더링 책임

## 배경

일기 기반 이미지 생성은 저장된 프롬프트 문자열 하나를 Gemini에 그대로 전달하는 과정이 아니다. 스토리보드 생성과 이미지
생성에 서로 다른 프롬프트가 필요하며, 이미지 생성 요청에는 스토리보드의 동적 데이터와 기준 이미지도 함께 전달해야 한다.

이번 구현에 참고로 사용한 생성 프로그램에서는 다음 프롬프트와 예시가 포함되어 있었다.

- `01-storyboard-generation-prompt.txt`: 일기를 네 개 패널의 스토리보드로 변환하는 지시문
- `02-image-style-prompt.txt`: 최종 이미지의 그림체, 구성과 금지 요소를 정의하는 지시문
- `04-example-story-prompt.txt`: 생성된 스토리보드를 이미지 모델에 전달할 이야기 프롬프트의 예시
- `05-reference-style-asset.png`: 최종 이미지의 기준 그림체로 사용하는 참조 이미지

`01`과 `02`는 운영 중 문장을 조정하거나 새로운 버전으로 교체할 수 있는 프롬프트다. 반면 `04`는 독립적인 원본
프롬프트가 아니라 `Storyboard`의 제목, 등장인물 연속성, 패널별 장면, 감정, 소품과 캡션을 일정한 형식으로 직렬화한 결과다.

최종 이미지 요청은 개념적으로 다음과 같이 구성된다.

```text
참조 이미지 전용 지시문
→ 참조 이미지
→ [Final Task]
→ 이미지 스타일 프롬프트
→ Storyboard로부터 렌더링한 이야기 프롬프트
```

모든 내용을 DB에 저장하면 동적 패널 값을 치환할 템플릿 기능이 필요하다. 반대로 모든 문장을 Java 코드에 두면 그림체나 품질
지시문을 조정할 때마다 애플리케이션을 다시 배포해야 한다. 따라서 프롬프트의 저장 책임과 동적 렌더링 책임을 어디에서
나눌지 결정해야 한다.

## 결정 요인

- 스토리보드와 이미지 스타일 프롬프트를 배포 없이 새로운 버전으로 등록할 수 있어야 한다.
- `Storyboard`의 필드를 타입 안전하게 이미지 요청 형식으로 변환할 수 있어야 한다.
- DB 문자열의 placeholder 오타와 누락을 운영 요청 전에 방지할 수 있어야 한다.
- 원본 Python 구현의 프롬프트 조립 순서와 이야기 프롬프트 형식을 유지할 수 있어야 한다.
- Gemini 전용 출력 형식과 역할 정보가 Generation 도메인에 불필요하게 유출되지 않아야 한다.
- 최종 프롬프트가 의도하지 않게 변경되는 것을 테스트로 확인할 수 있어야 한다.
- 프롬프트를 조정하는 유연성과 생성 결과의 재현 가능성을 함께 고려해야 한다.

## 고려한 대안

### 대안 1: 최종 프롬프트 전체를 DB 템플릿으로 관리

DB에 다음과 같은 placeholder를 포함한 템플릿을 저장한다.

```text
Panel 1:
Scene: {{panels[0].scene}}
Caption: {{panels[0].caption}}
```

장점은 다음과 같다.

- 문장, 라벨과 패널 출력 순서를 배포 없이 변경할 수 있다.
- 프롬프트 운영자가 최종 요청 형식을 한곳에서 확인할 수 있다.
- 스타일 프롬프트와 이야기 프롬프트를 동일한 버전 정책으로 관리할 수 있다.
- 모델별 프롬프트 실험을 빠르게 수행할 수 있다.

단점은 다음과 같다.

- 별도의 템플릿 문법, 치환기와 검증 기능이 필요하다.
- placeholder 이름의 오타와 필수 값 누락을 컴파일 시점에 발견할 수 없다.
- `Storyboard` 구조가 변경되면 기존 DB 템플릿과의 호환성을 관리해야 한다.
- 잘못된 템플릿이 등록되면 실제 생성 요청 시점에야 실패할 수 있다.
- 반복문, 조건부 소품 출력과 캡션 목록 같은 동적 형식을 템플릿 문법으로 표현해야 한다.

### 대안 2: 모든 프롬프트와 조립 형식을 Java 코드로 관리

스토리보드 생성 지시문, 이미지 스타일 지시문, 참조 이미지 지시문과 이야기 프롬프트 문장을 모두 코드 상수나 Renderer에
작성한다.

장점은 다음과 같다.

- `Storyboard` 필드를 타입 안전하게 사용할 수 있다.
- 프롬프트 변경이 코드 리뷰와 배포 이력에 함께 남는다.
- 템플릿 파싱이나 placeholder 검증이 필요하지 않다.
- Renderer와 도메인 구조를 같은 변경 단위로 수정할 수 있다.

단점은 다음과 같다.

- 그림체나 품질 지시문 한 문장을 변경해도 코드 배포가 필요하다.
- 프롬프트 실험과 이전 버전 복구 속도가 느려진다.
- 생성 작업이 어떤 스타일 프롬프트 버전을 사용했는지 DB 관계로 추적하기 어렵다.
- 긴 프롬프트가 Java 코드에 포함되어 생성 흐름과 요청 변환 로직의 가독성을 떨어뜨릴 수 있다.

### 대안 3: 변경 가능한 지시문은 DB에 저장하고 구조 결합 부분은 코드에서 렌더링

DB의 `GenerationPrompt`에는 다음 값을 저장한다.

- `storyboardPromptText`: 일기에서 스토리보드를 생성하는 지시문
- `imageStylePromptText`: 최종 이미지의 스타일, 품질과 금지 요소를 정의하는 지시문
- `imageAssetObjectKey`: 기준 이미지의 S3 Object Key

코드는 다음 형식을 담당한다.

- 스토리보드 프롬프트와 일기 원문 사이의 구분자
- Gemini structured output의 JSON Schema와 provider 응답 DTO
- 참조 이미지가 그림체 기준임을 설명하는 별도 멀티모달 part
- `[Final Task]` 구분자와 멀티모달 parts 조립 순서
- `Storyboard`를 패널 위치, 이야기 역할, 장면, 감정, 소품과 캡션 형식으로 변환하는 Renderer
- 캡션을 정확히 한 번씩 출력하도록 강조하는 최종 이야기 확인 형식

장점은 다음과 같다.

- 자주 조정할 스타일과 스토리보드 지시문을 배포 없이 새로운 DB 행으로 등록할 수 있다.
- 생성 작업이 참조하는 `GenerationPrompt` ID를 통해 사용한 DB 프롬프트 버전을 추적할 수 있다.
- `Storyboard` 필드를 별도 템플릿 엔진 없이 타입 안전하게 직렬화할 수 있다.
- 원본 Python의 `render_story_prompt()` 출력 형식을 코드와 테스트로 보호할 수 있다.
- Provider 전용 라벨과 요청 순서를 어댑터 내부에 유지할 수 있다.

단점은 다음과 같다.

- 최종 프롬프트 전체가 DB와 코드에 나뉘어 한곳에서 보이지 않는다.
- Renderer의 고정 문장을 변경하려면 코드 배포가 필요하다.
- DB 프롬프트와 배포된 Renderer 사이의 호환성을 함께 관리해야 한다.
- DB에는 프롬프트 ID가 남지만 Renderer 코드 버전은 생성 기록에 직접 저장되지 않는다.
- 패널 역할과 순서가 Schema, Mapper와 Renderer에 각각 표현될 수 있다.

## 결정

대안 3을 선택한다.

변경 가능성이 높은 스토리보드 및 이미지 스타일 지시문은 `GenerationPrompt`에 저장한다. `Storyboard` 구조에 결합된 이야기
프롬프트와 Gemini 멀티모달 요청 형식은 코드가 생성한다.

스토리보드 요청은 다음과 같이 조립한다.

```text
{storyboardPromptText}

[SOURCE DIARY — preserve its meaning]
{diaryText}
```

이미지 요청의 parts 순서는 다음과 같다.

```text
1. 참조 이미지 전용 지시문
2. 참조 이미지 bytes와 MediaType
3. [Final Task] + imageStylePromptText + Renderer 결과
```

Renderer는 `Storyboard`를 다음과 같은 고정된 직렬화 형식으로 변환한다.

```text
SELECTED STORY
SOURCE AND ADAPTATION RULE
CAST AND CONTINUITY
Panel + position + story role
Scene
Characters and action
Visible emotion
Sparse symbolic props
Caption
FINAL STORY CHECK
```

`Panel`, `Scene`, `Caption`, 패널 위치와 이야기 역할은 독립적인 운영 프롬프트가 아니라 동적 데이터를 Gemini에 전달하는
직렬화 형식으로 판단해 코드에 둔다. 반복 사용되는 패널 헤더, 위치와 이야기 역할만 상수로 두며, 한 번만 사용하는 프롬프트
문장은 출력 흐름을 읽기 쉽도록 Renderer 메서드 안에 유지한다.

Gemini 응답의 `storyRole`은 `setup`, `action`, `escalation`, `resolution` 순서를 검증하기 위한 provider 전용 필드로
유지한다. `StoryPanel`에는 저장하지 않으며 이미지 Renderer는 도메인이 보장하는 1번부터 4번까지의 패널 순서로 이야기 역할을
결정한다. 패널 개수, 번호, 캡션과 소품 같은 공통 규칙은 Mapper에서 중복 검증하지 않고 Domain에 맡긴다.

## 긍정적 결과

- 스토리보드와 이미지 스타일 프롬프트를 새로운 `GenerationPrompt`로 등록해 배포 없이 교체할 수 있다.
- 동적 Storyboard 렌더링에서 컴파일 타임 타입 검사를 활용할 수 있다.
- 별도의 템플릿 엔진과 placeholder 검증 기능을 도입하지 않아도 된다.
- Gemini structured output과 멀티모달 parts 순서를 어댑터에서 명시적으로 관리할 수 있다.
- Storyboard의 공통 불변식은 Domain에 모으고 provider 전용 형식은 어댑터에 유지할 수 있다.

## 부정적 결과와 트레이드오프

- 최종 요청 프롬프트를 확인하려면 DB의 프롬프트와 코드 Renderer를 함께 봐야 한다.
- 이야기 프롬프트의 고정 문장, 라벨이나 멀티모달 parts 순서를 바꾸려면 애플리케이션을 다시 배포해야 한다.
- `GenerationPrompt` ID만으로는 당시 사용한 Renderer 코드 버전까지 완전히 재현할 수 없다.
- 정확한 문자열을 비교하는 golden-file 테스트는 의도적인 문구 수정에도 실패하므로 테스트 리소스를 함께 갱신해야 한다.
- `storyRole`의 순서가 Schema, Mapper와 Renderer에 분산되어 변경 시 세 위치의 일관성을 확인해야 한다.
- 패널별 캡션과 최종 캡션 목록을 반복 전달하므로 프롬프트 토큰이 증가한다.
- 현재 Renderer는 정확히 네 개의 패널과 고정된 이야기 역할 순서에 결합되어 있어 다른 패널 수를 지원하려면 코드 변경이
  필요하다.

현재 MVP는 정확히 네 패널의 이미지 생성 형식을 사용하며 별도의 프롬프트 템플릿 관리 기능을 제공하지 않는다. 따라서 최종
프롬프트 전체를 운영 중 자유롭게 변경하는 것보다, 변경 가능한 지시문은 DB에서 관리하면서 동적 데이터 직렬화의 타입 안전성과
요청 형식의 안정성을 코드로 보장하는 것이 더 중요하다고 판단한다.
