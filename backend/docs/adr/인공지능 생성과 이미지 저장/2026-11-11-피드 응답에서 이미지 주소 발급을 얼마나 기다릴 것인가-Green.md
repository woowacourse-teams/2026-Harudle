# 피드 응답에서 이미지 주소 발급을 얼마나 기다릴 것인가

## 배경

사진마다 주소를 기다리면 캐시가 비어 있거나 발급이 지연될 때 대기가 누적된다. 동시에 여러 요청이 같은 사진을 기다리는 동안 각 요청이 새 서명을 시작하면 실행 자원도 더 많이 필요하다.

## 고려한 방법

- 사진별로 대기 한도를 두면 각 사진에 같은 기회를 주지만, 사진이 많은 응답에서는 총 대기가 늘어난다.
- 요청이 시간 초과될 때마다 새 서명을 시도하면 한 요청이 회복될 수 있지만, 지연 중인 같은 키의 작업이 중복된다.
- 피드 응답이 하나의 대기 예산을 공유하고 같은 키의 발급 결과를 함께 기다리면 응답과 작업 수를 제한할 수 있다. 앞선 조회가 오래 걸리면 뒤쪽 사진이 받을 수 있는 시간이 줄어든다.

## 결정과 이유

캐시가 적용된 피드 목록과 상세는 S3 존재 확인, R2 원본 조회, S3 서명 대기에 `S3_URL_CACHE_WAIT_TIMEOUT`을 응답마다 한 번 적용한다. 같은 서버에서 동일한 이미지 키의 발급이 진행 중이면 요청들은 같은 결과를 기다린다. 한 요청의 대기가 끝나도 이미 시작한 서명은 이어간다. 대기열에서 시작 기한을 넘긴 작업은 작업자가 꺼냈을 때 서명 없이 건너뛴다.

## 실제 동작과 결과

기본 1초는 검증용 초기 상한이다. 대기열 기한은 작업을 넣은 시점부터 같은 설정값으로 별도로 센다. 응답 예산이 끝나면 새 저장소 조회와 서명을 시작하지 않고, 이미 쓸 수 있는 주소는 반환한다. 이 상한이 제한하는 범위는 사진 주소를 준비하는 시간이다. 로컬에서 S3 확인에 300ms를 쓰면 R2 조회가 700ms를 받는 경우, 응답 시간 초과 뒤 같은 발급을 공유하는 경우, 오래된 대기 작업을 건너뛴 뒤 다시 발급하는 경우를 확인했다.
