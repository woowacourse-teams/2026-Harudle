# 우테코 캠퍼스에 회원 신원을 서명 토큰으로 알린다

## 결정 (Decision)

우리는 우테코 캠퍼스(`campus.harudle.com`)에 하루들 회원 신원을 알릴 때, 로그인한 회원에게 60초짜리 HS256 서명 토큰을 발급하고 캠퍼스가 그 서명을 직접 확인하게 한다. 하루들은 토큰을 저장하지 않고, 기존 코드와 DB를 바꾸지 않는다.

- 발급: `POST /api/v1/campus/link-tokens` (Bearer). 기존 `/api/v1/**` 인증 규칙과 약관 확인 필터를 그대로 따르고, 정지 여부와 닉네임을 확인한다.
- 토큰: `iss=harudle`, `aud=harudle-campus`, `sub=회원 ID`, `jti`, `iat`, `exp(60초)`, `nickname`, `picture`(만료되지 않는 기본 이미지만), `state`. 이메일 · 실명 · 하루들 토큰은 담지 않는다.
- 서명 키는 Access Token 키와 따로 둔다(`HARUDLE_CAMPUS_SIGNING_KEY_BASE64`). `JwtEncoder`, `SecretKey` 빈을 새로 만들지 않아 기존 인증 빈 주입에 영향이 없다.
- 돌아갈 주소(`HARUDLE_CAMPUS_REDIRECT_URI`)는 서버 설정으로만 정하고 HTTPS만 허용한다. 로컬 개발은 정확한 `localhost`와 `127.0.0.1`의 HTTP만 허용한다. 사용자 정보나 fragment가 있는 주소는 거절한다. 기능이 꺼져 있으면(`HARUDLE_CAMPUS_ENABLED`, 기본 false) API를 등록하지 않는다.
- 한 번만 쓰기(`jti`)와 state 확인, 캠퍼스 사용자 · 세션 저장은 캠퍼스가 자기 DB(Supabase)에서 한다.

## 근거 (Rationale)

- Refresh Token 쿠키는 `www.harudle.com` 전용이고 Access Token은 전체 권한을 가진다. 캠퍼스는 회원이 누구인지만 알면 된다.
- 연결 코드를 하루들 DB에 저장하고 캠퍼스 서버가 교환하는 방식도 검토했다. 표 · 교환 API · 정리 작업 · 보안 체인 변경이 필요해 기존 코드와 DB를 건드리게 되므로 기각했다.
- 캠퍼스 출처에 CORS를 열고 브라우저가 하루들 API를 직접 호출하는 방식은 전체 권한 토큰이 캠퍼스에 노출되고 Refresh Token 교체가 본 사이트와 충돌해 기각했다.

### 토큰을 한 번만 쓰게 하는 범위

캠퍼스는 서버 간 시각 차이를 고려해 `exp` 뒤 30초까지 여유를 둔다. 따라서 `jti` 사용 기록도
토큰의 만료 시각이 아니라 **캠퍼스가 토큰을 더 이상 받지 않는 시각**까지 보관한다.
검증과 기록 보관에 같은 종료 시각을 사용하고, 그 시각부터 토큰을 거절한다. 허용 구간 안에서
정리 작업이 실행돼도 같은 `jti`를 다시 사용할 수 없어야 한다. 동시 요청은 DB의 `jti` 기본 키로
하나만 성공하게 한다. 이 책임은 토큰을 발급하는 하루들이 아니라 소비하는 캠퍼스에 있다.
소비자 수정은 [캠퍼스 PR #23](https://github.com/Harudle/harudle-campus/pull/23)에서 관리하며,
이 연결 기능을 운영에서 켜기 전에 함께 반영한다.

### 인증 저장소는 Supabase를 유지한다

현재 캠퍼스는 한 EC2에서 동작하며, 새 워커를 준비한 뒤 이전 워커를 종료한다.
교체 중 두 워커가 함께 존재하므로 사용자, 세션과 토큰 사용 기록을 공유해야 한다.
같은 호스트의 워커라면 SQLite 파일을 공유할 수도 있다. 워커 수만으로 Supabase가 필수인 것은 아니다.

- **Supabase 유지:** 워커와 EC2를 교체해도 같은 외부 DB를 사용하므로 인증 파일 이전을 배포 절차에
  추가하지 않는다. 대신 외부 통신과 DB 장애에 의존하고, 서비스 키와 별도 DB의 백업을 관리해야 한다.
- **SQLite 도입:** 외부 인증 DB 호출과 별도 서비스 설정을 줄일 수 있다. 같은 EC2의 워커들은
  영구 파일을 공유할 수 있지만, 인증용 저장소 구현과 동시 쓰기 처리, DB와 WAL의 일관된 백업,
  EC2 교체 시 파일 복원을 직접 준비해야 한다. WAL은 아직 DB 파일에 합쳐지지 않은 변경을 보관하는 파일이다.

현재 미디어 SQLite의 지원 범위는 단일 EC2와 로컬 영구 디스크이며 디스크 유실 복구는 포함하지 않는다.
인증까지 이 디스크의 이전과 복구 절차에 묶지 않기 위해 Supabase를 유지한다. 이는 Supabase가
백업 책임을 없애 준다는 뜻은 아니다. 실제 요금제의 백업 범위와 서버 밖 보관, 복원 검증 결과는
운영 활성화 전에 별도로 확인한다. 현재 문서는 그 검증이 완료됐다고 기록하지 않는다.

## 결과 (Consequences)

- 하루들은 캠퍼스를 호출하지도, 캠퍼스에 호출받지도 않는다(단방향). 캠퍼스가 꺼져도 하루들에는 영향이 없다.
- 정지와 닉네임은 발급 시점의 값이다. 토큰을 받을 수 있는 동안(유효기간 60초와 캠퍼스의 시각 여유 30초) 값이 바뀌어도 토큰에는 반영되지 않는다. 연결 후 세션은 캠퍼스의 정책을 따른다.
- 캠퍼스는 회원 탈퇴를 알 수 없다. 캠퍼스는 마지막 로그인 후 90일이 지난 사용자 정보를 지운다.
- 서명 키를 캠퍼스와 나눠 가진다. 키가 새면 캠퍼스용 신원만 위조될 수 있고 하루들 API 권한에는 영향이 없다. 키를 바꿀 때는 두 서버를 함께 바꾼다.
- 개인정보처리방침에 "우테코 캠퍼스 로그인 연동"(회원 ID · 닉네임 · 프로필 사진)을 처리 목적으로 추가해야 한다.
