# 우테코 캠퍼스에 회원 신원을 서명 토큰으로 알린다

## 결정 (Decision)

우리는 우테코 캠퍼스(`campus.harudle.com`)에 하루들 회원 신원을 알릴 때, 로그인한 회원에게 60초짜리 HS256 서명 토큰을 발급하고 캠퍼스가 그 서명을 직접 확인하게 한다. 하루들은 토큰을 저장하지 않고, 기존 코드와 DB를 바꾸지 않는다.

- 발급: `POST /api/v1/campus/link-tokens` (Bearer). 기존 `/api/v1/**` 인증 규칙과 약관 확인 필터를 그대로 따르고, 정지 여부와 닉네임을 확인한다.
- 토큰: `iss=harudle`, `aud=harudle-campus`, `sub=회원 ID`, `jti`, `iat`, `exp(60초)`, `nickname`, `picture`(만료되지 않는 기본 이미지만), `state`. 이메일 · 실명 · 하루들 토큰은 담지 않는다.
- 서명 키는 Access Token 키와 따로 둔다(`HARUDLE_CAMPUS_SIGNING_KEY_BASE64`). `JwtEncoder`, `SecretKey` 빈을 새로 만들지 않아 기존 인증 빈 주입에 영향이 없다.
- 돌아갈 주소(`HARUDLE_CAMPUS_REDIRECT_URI`)는 서버 설정으로만 정한다. 기능이 꺼져 있으면(`HARUDLE_CAMPUS_ENABLED`, 기본 false) API를 등록하지 않는다.
- 한 번만 쓰기(`jti`)와 state 확인, 캠퍼스 사용자 · 세션 저장은 캠퍼스가 자기 DB(Supabase)에서 한다.

## 근거 (Rationale)

- Refresh Token 쿠키는 `www.harudle.com` 전용이고 Access Token은 전체 권한을 가진다. 캠퍼스는 회원이 누구인지만 알면 된다.
- 연결 코드를 하루들 DB에 저장하고 캠퍼스 서버가 교환하는 방식도 검토했다. 표 · 교환 API · 정리 작업 · 보안 체인 변경이 필요해 기존 코드와 DB를 건드리게 되므로 기각했다.
- 캠퍼스 출처에 CORS를 열고 브라우저가 하루들 API를 직접 호출하는 방식은 전체 권한 토큰이 캠퍼스에 노출되고 Refresh Token 교체가 본 사이트와 충돌해 기각했다.

## 상태 (Status)

- 제안됨 (Proposed)

## 결과 (Consequences)

- 하루들은 캠퍼스를 호출하지도, 캠퍼스에 호출받지도 않는다(단방향). 캠퍼스가 꺼져도 하루들에는 영향이 없다.
- 정지 · 닉네임 확인은 발급 시점에만 한다. 발급 후 60초 안의 변화는 반영하지 못한다.
- 캠퍼스는 회원 탈퇴를 알 수 없다. 캠퍼스는 마지막 로그인 후 90일이 지난 사용자 정보를 지운다.
- 서명 키를 캠퍼스와 나눠 가진다. 키가 새면 캠퍼스용 신원만 위조될 수 있고 하루들 API 권한에는 영향이 없다. 키를 바꿀 때는 두 서버를 함께 바꾼다.
- 개인정보처리방침에 "우테코 캠퍼스 로그인 연동"(회원 ID · 닉네임 · 프로필 사진)을 처리 목적으로 추가해야 한다.
