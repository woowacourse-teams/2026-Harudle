# 2026-08-26 관리자 API 기능과 생성 사용량 조정 방식을 어떻게 구성할 것인가

- 작성일: 2026-08-26
- 작성자: 하루들 팀
- 결정 대상: 관리자 API의 기능 범위, 생성 사용량 조정 API의 의미와 생성 이력 조회 방식

## 배경

관리자 대시보드는 사용자를 검색하고 상세 정보를 확인하며, 생성 실패 등으로 잘못 차감된 오늘의 생성 횟수를 운영자가 조정할 수 있어야 한다. 또한 전체 생성 이력을 조회해 실패 요청을 확인하고 사용자별 운영 대응을 수행할 수 있어야 한다.

관리자 기능을 추가하면서 다음 API 후보가 생겼다.

- 사용자의 기본 일일 생성 한도 변경
- 오늘 사용량 직접 설정
- 오늘 사용량 일부 복구
- 오늘 사용량 전체 초기화
- 최근 생성 이력 조회
- 전체 생성 이력 및 실패 이력 조회

오늘 사용량과 사용자별 지속 한도는 서로 다른 의미를 가지므로 API와 저장 모델에서도 구분해야 한다. 관리자 기능은 일반 사용자 API와 달리 개인정보와 사용량 변경 권한을 포함하므로 모든 요청에 현재 DB 권한을 확인한다.

## 결정 요인

- 사용자의 지속 한도와 오늘 사용량을 혼동하지 않아야 한다.
- 정상 생성 실패로 잘못 차감된 횟수를 일부 또는 전체 복구할 수 있어야 한다.
- 같은 목적의 API를 중복 제공하지 않으면서도 각 작업의 의도가 URL과 요청 형식에 드러나야 한다.
- 사용량 복구가 동시 요청에서 음수가 되거나 현재 상태보다 많이 복구되지 않아야 한다.
- 관리자 화면에서 전체 생성 이력과 실패 이력을 조회할 수 있어야 한다.
- 기존에 구현된 운영용 직접 설정 기능과의 호환성을 유지해야 한다.
- API가 추가되어도 관리자 권한 검증이 누락되지 않아야 한다.

## 고려한 대안

### 대안 1: 하나의 사용량 API에서 모든 변경을 처리

`PUT /api/v1/admin/users/{userId}/usage`에 최종 `usedCount`를 전달하고, `0`을 전달하면 초기화로 간주한다.

장점은 다음과 같다.

- API 수가 적다.
- 운영자가 원하는 최종 상태를 직접 지정할 수 있다.
- 사용량을 임의의 값으로 조정해야 하는 운영 대응에 유연하다.

단점은 다음과 같다.

- 일부 복구와 전체 초기화의 의도가 API에 드러나지 않는다.
- 요청 전후 상태를 계산해야 하므로 실수로 잘못된 사용량을 설정할 수 있다.
- 프런트엔드가 reset 버튼을 직접 설정 API에 연결하게 된다.
- 노션 명세의 restore/reset 계약과 달라진다.

### 대안 2: 작업 의미별 API를 분리하고 직접 설정 API도 유지

다음처럼 작업별 API를 분리한다.

```text
PATCH /api/v1/admin/users/{userId}/generation-usage/restore
PUT   /api/v1/admin/users/{userId}/generation-usage/reset
PUT   /api/v1/admin/users/{userId}/usage
```

`restore`는 현재 사용량에서 `count`만큼 원자적으로 차감한다. `reset`은 오늘 사용량을 0으로 만든다. `usage`는 운영자가 최종 `usedCount`를 직접 설정해야 하는 예외적인 운영용 기능으로 유지한다.

장점은 다음과 같다.

- API 경로만으로 작업 의도를 구분할 수 있다.
- 일반적인 복구와 초기화는 안전한 전용 계약을 사용한다.
- 직접 설정이 필요한 운영 대응의 유연성은 유지한다.
- 프런트엔드가 복구·초기화 버튼을 각 목적에 맞는 API에 연결할 수 있다.

단점은 다음과 같다.

- 사용량 변경 API가 세 개로 늘어난다.
- 직접 설정 API와 전용 API의 사용 목적을 문서와 운영 화면에서 구분해야 한다.
- 동일한 저장 로직을 여러 명령에서 공유하되 각 명령의 검증 규칙을 별도로 유지해야 한다.

### 대안 3: 직접 설정 API를 제거하고 전용 API만 제공

`restore`와 `reset`만 제공하고 `usage`를 제거한다.

장점은 API 의미가 가장 명확하고 잘못된 직접 조정을 줄일 수 있다는 점이다.

단점은 과거 사용량을 특정 값으로 맞춰야 하는 운영 대응을 표현하기 어렵고, 이미 제공 중인 운영 기능과의 호환성이 깨진다는 점이다.

### 대안 4: 최근 생성 이력만 사용자 상세 API에서 제공

전체 생성 이력 API를 추가하지 않고 사용자 상세 조회의 최근 5건만 사용한다.

장점은 API와 조회 쿼리가 단순하다.

단점은 전체 실패 이력 분석과 기간별 운영 대응이 불가능하다. 사용자가 많은 경우 상세 화면을 반복 조회해야 하며, 상태·기간 필터를 제공할 수 없다.

## 결정

대안 2와 대안 4의 반대 방향을 선택한다.

관리자 API는 기능별 의미를 분리하되 기존 운영용 직접 설정 API를 유지한다.

### 사용자와 사용량 API

```text
GET   /api/v1/admin/users
GET   /api/v1/admin/users/{userId}
PATCH /api/v1/admin/users/{userId}/generation-usage/restore
PUT   /api/v1/admin/users/{userId}/generation-usage/reset
PUT   /api/v1/admin/users/{userId}/usage
PUT   /api/v1/admin/users/{userId}/generation-limit
```

- `generation-limit`은 `users.daily_generation_limit`을 변경하는 지속 한도 조정이다.
- `usage`는 오늘의 `usedCount`를 최종값으로 직접 설정하는 운영용 조정이다.
- `restore`는 오늘의 `usedCount`를 `count`만큼 줄이는 일반적인 선택 복구다.
- `reset`은 오늘의 `usedCount`를 0으로 만드는 멱등 작업이다.
- 사용량 변경은 `daily_generation_usage`의 해당 날짜 스냅샷을 기준으로 처리한다.
- 지속 한도와 오늘 사용량 변경은 서로 독립적으로 처리한다.

`restore`는 다음 조건을 원자적인 DB 연산으로 검증하고 변경한다.

```text
usedCount >= count
→ usedCount = usedCount - count
```

현재 사용량보다 많은 복구 요청은 거부하며, 동시 요청에서도 사용량이 음수가 되지 않도록 한다. `reset`은 같은 요청을 여러 번 실행해도 결과가 같도록 처리한다.

### 생성 이력 API

```text
GET /api/v1/admin/generations
```

다음 필터를 지원한다.

- `userId`: 특정 사용자 이력
- `status`: `PROCESSING`, `SUCCEEDED`, `FAILED`
- `from`, `to`: `Asia/Seoul` 기준 날짜 범위
- `page`, `size`: 페이지네이션

실패 이력은 별도 API를 만들지 않고 `status=FAILED` 필터로 조회한다. 기본 정렬은 생성 요청 시각 내림차순이며, 응답에는 생성 사용자 정보와 실패 코드를 포함한다.

### 권한

모든 `/api/v1/admin/**` API는 기존 관리자 권한 ADR을 따른다. Access Token에서 사용자 UUID를 식별한 뒤 DB의 현재 역할과 탈퇴 여부를 확인하며, 활성 `ADMIN`만 허용한다.

## 긍정적 결과

- reset, restore, 직접 설정, 지속 한도의 의미가 API 계약에 드러난다.
- 운영자가 오류 차감 횟수를 일부 또는 전체 복구할 수 있다.
- 기존 직접 설정 API를 유지해 운영 대응의 유연성을 보존한다.
- 전체 생성 이력과 실패 이력을 기간·상태·사용자 기준으로 조회할 수 있다.
- 관리자 API를 `/api/v1/admin/**` 아래에 추가하면 공통 권한 검증을 적용받는다.
- 날짜별 사용량 스냅샷과 사용자별 지속 한도를 서로 다른 변경 대상으로 유지한다.

## 부정적 결과와 트레이드오프

- 사용량을 변경하는 API가 세 개이므로 프런트엔드와 운영 문서에서 용도를 명확히 구분해야 한다.
- 직접 설정 API는 강력한 운영 기능이므로 잘못된 값 입력에 대한 운영자 책임이 남는다.
- 전체 생성 이력 조회를 위한 조인과 페이지네이션 쿼리가 추가된다.
- 관리자 요청마다 DB에서 현재 역할을 확인하므로 일반 API보다 조회 비용이 높다.
- 감사 로그는 아직 기록하지 않으므로 누가 사용량을 변경했는지 추적할 수 없다.

## 구현 및 검증 조건

- [x] 활성 `ADMIN`만 관리자 API에 접근할 수 있다.
- [x] 사용자를 이름·이메일·UUID로 검색할 수 있다.
- [x] 사용자 상세 조회에서 오늘 사용량과 최근 생성 5건을 반환한다.
- [x] 선택 복구 API가 현재 사용량보다 많이 차감하지 않는다.
- [x] reset API가 오늘 사용량을 0으로 초기화한다.
- [x] 운영용 직접 설정 API가 오늘 사용량의 최종값을 변경한다.
- [x] 사용자별 지속 생성 한도를 변경할 수 있다.
- [x] 전체 생성 이력을 상태·사용자·기간으로 조회할 수 있다.
- [x] 생성 이력이 없을 때 404가 아닌 빈 페이지를 반환한다.
- [x] 관리자 통합 테스트와 전체 백엔드 테스트가 통과한다.

## 재검토 조건

- 관리자 작업 감사 로그가 요구됨
- 직접 설정 API를 제한하거나 제거해야 할 만큼 운영 실수가 발생함
- 역할이 `ADMIN` 외에 읽기 전용 관리자, 운영 관리자 등으로 세분화됨
- 생성 이력 조회량이 증가해 전용 검색 인덱스나 비동기 집계가 필요해짐
- 사용량 복구 정책이 생성 실패 상태와 자동으로 연동되어야 함
- 스트릭 보너스와 관리자 한도의 우선순위가 확정됨
