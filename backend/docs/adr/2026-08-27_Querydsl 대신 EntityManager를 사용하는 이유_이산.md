# Querydsl 대신 EntityManager를 사용하는 이유

- 상태: 채택
- 작성자: 이산

## 결정

- 관리자 사용자·생성 이력 조회는 Spring Data `@Query`로 JPQL을 실행한다.
- 생성 사용량의 증가·복구·초기화는 `EntityManager`를 통해 네이티브 SQL을 실행한다.
- `EntityManager`는 네이티브 원자 연산이 필요한 인프라 구현체에서만 직접 사용하고, 서비스에는 노출하지 않는다.
- 현재는 Querydsl을 도입하지 않고, 조회 조건이 더 복잡해질 때 도입을 재검토한다.

## 이유

관리자 조회는 동적 조건, 조인, DTO 프로젝션, 페이징과 카운트 쿼리가 필요하다. 현재 범위에서는 Querydsl 설정과 생성 코드 관리 비용을 추가하기보다, JPQL을 `@Query`에 명시하고 Spring Data가 파라미터 바인딩과 페이징을 처리하게 하는 편이 직관적이다.

생성 사용량 변경은 `ON CONFLICT`, 조건부 `UPDATE`, `RETURNING` 같은 PostgreSQL 원자 연산을 사용하므로 JPQL만으로 표현하기 어렵다. Querydsl JPA를 도입하더라도 이 네이티브 SQL 문제는 해결되지 않는다.

## 현재 필요한 연산의 복잡도

- 첫 생성 요청이면 오늘 사용량 행을 만들고, 사용자별 현재 한도를 함께 기록한다.
- 이미 행이 있으면 한도 미만일 때만 사용량을 증가시키며, 동시 요청에서도 초과 사용이 발생하지 않아야 한다.
- 복구는 현재 사용량이 복구 횟수 이상일 때만 차감하고, 초기화는 기존 행이 있을 때만 0으로 변경한다.
- 한도 변경 시 이미 사용한 횟수보다 작은 한도를 그대로 저장하지 않도록 `max(used_count, 새 한도)`를 적용한다.
- 각 원자 연산 후 사용량과 한도를 즉시 반환해야 하므로 변경과 결과 조회를 하나의 SQL 흐름으로 처리한다.

따라서 단순히 데이터를 저장하는 CRUD가 아니라, 조건부 삽입·수정과 동시성 제어, 변경 결과 반환을 함께 다루는 연산이다. 관리자 생성 이력 조회도 사용자·상태·기간 필터를 선택적으로 조합하고, 결과와 전체 개수를 별도로 계산해야 한다. 다만 조회 쿼리는 현재 필터 수가 제한적이므로 `@Query`만으로 관리할 수 있다.

## 결과

관리자 조회는 `@Query`로 직접 읽을 수 있게 하고, PostgreSQL 원자 연산만 `EntityManager` 네이티브 쿼리로 제한한다. 관리자 조회 조건이 늘어나거나 동적 쿼리의 가독성이 떨어지면 Querydsl 도입을 검토한다. `@Query`도 내부적으로는 EntityManager를 사용하지만, 애플리케이션 코드에서 직접 쿼리 생성과 파라미터 바인딩을 관리하지 않는다는 차이가 있다.
