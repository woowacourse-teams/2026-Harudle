# 2026-10-12 좋아요 반복 요청과 원인 행동별 알림 중복을 어떻게 처리할 것인가

- 상태: 채택
- 작성일: 2026-10-12
- 수정일: 2026-10-13
- 작성자: 아이큐
- 결정 대상: 좋아요 설정·취소의 멱등성, 재좋아요의 행동 ID와 인앱 알림 중복 방지

## 배경

네트워크 재시도나 연속 클릭으로 같은 좋아요 요청이 반복될 수 있다. 반복 요청을 새로운 좋아요로 처리하면 카운터와 알림이 중복 증가한다. 반면 좋아요를 취소한 뒤 다시 누르는 것은 새로 발생한 행동으로 구분해야 한다.

댓글과 좋아요의 알림은 같은 테이블을 사용한다. 알림의 원인을 알림 ID가 아닌 실제 댓글·좋아요 ID로 식별해야 같은 행동의 중복 기록을 막을 수 있다.

## 결정 요인

- 같은 상태를 요청하는 재시도가 반응 수와 알림을 추가로 변경하지 않아야 한다.
- 동시에 같은 회원이 좋아요를 눌러도 활성 좋아요는 하나여야 한다.
- 취소 후 재좋아요를 이전 행동과 구분해야 한다.
- 원인 행동을 삭제해도 DB 알림 이력을 보존할 수 있어야 한다.

## 고려한 대안

### 대안 1 하나의 토글 API 사용

버튼 동작과 쉽게 연결할 수 있지만, 같은 요청을 두 번 보내면 좋아요가 켜졌다 꺼진다. 클라이언트가 원하는 최종 상태와 재시도의 결과가 달라질 수 있어 채택하지 않는다.

### 대안 2 요청 전에 좋아요 존재 여부만 조회

반복 요청을 구분할 수 있지만, 두 요청이 동시에 미존재를 확인할 수 있다. 애플리케이션의 선행 조회만으로 중복을 막지 않고 DB 제약도 필요하다.

### 대안 3 상태 설정 API와 DB 유니크 제약 사용

PUT은 좋아요 상태, DELETE는 취소 상태를 요청한다. DB의 `UNIQUE (feed_id, user_id)`와 실제 변경 행 수를 기준으로 카운터·알림을 처리한다. 재시도 의미가 명확하고 동시 요청에도 제약을 유지할 수 있어 채택한다.

## 결정

### 좋아요 설정과 취소

- PUT은 `INSERT ... ON CONFLICT (feed_id, user_id) DO NOTHING`을 사용한다.
- 실제 삽입 성공 시에만 카운터 증가와 알림 기록을 수행한다. 이미 좋아요가 있으면 현재 상태와 수를 반환한다.
- DELETE는 좋아요 행을 물리 삭제한다. 실제 삭제 성공 시에만 카운터를 감소시키고, 이미 취소된 상태면 다시 감소시키지 않는다.
- 취소 후 PUT은 새 UUID를 가진 좋아요 행을 생성한다. 기존 좋아요 ID를 복구하거나 재사용하지 않는다.
- 동일 요청을 반복해도 상태 변경은 한 번이다. 다만 다른 회원의 반응이 있으면 응답의 전체 카운터 값은 달라질 수 있다.

댓글 POST에는 별도 멱등성 키를 도입하지 않는다. 같은 본문을 두 번 보내면 두 댓글이며 각각 다른 원인 행동 ID를 가진다. 좋아요의 멱등성 계약을 댓글 작성 전체에 확대하지 않는다.

### 알림 원인과 DB 제약

`source_action_id`에는 실제로 저장한 좋아요 또는 댓글 ID를 넣는다. API 요청으로 수신자 ID를 받지 않고, 서버 서비스가 잠근 피드의 작성자 ID를 수신자로 결정한다. 공통 반응 포트는 피드·원본 일기·피드 작성자의 활성 상태를 확인한 뒤 이 ID를 반환한다.

`UNIQUE (recipient_user_id, type, source_action_id)`와 같은 키의 `ON CONFLICT DO NOTHING`을 이용해 같은 행동의 알림 중복을 막는다. 기록 결과는 `CREATED`·`DUPLICATE`·`SELF_SKIPPED`로 구분하며, 자기 피드에 반응을 남겨도 반응 행과 카운터는 정상 반영한다.

`source_action_id`는 두 테이블의 ID를 담고 원인 삭제 후에도 보존하므로 일반 FK를 두지 않는다. 대신 반응 서비스가 저장한 실제 ID를 넘기는 호출 계약을 지킨다. 기록기는 필수 필드·자기 알림·중복을 확인하지만, 원인 행의 존재와 소유 관계 전체를 다시 조회하는 검증기는 아니다.

예를 들어 좋아요 L1의 기록기를 두 번 호출해도 같은 수신자·LIKE·L1의 알림은 하나다. 취소 후 생성한 L2는 다른 행동이므로 새 알림 N2를 저장한다. L1의 과거 알림 N1을 화면에 다시 보여주지 않는 규칙은 별도의 알림 노출 결정으로 처리한다.

## 긍정적 결과

- 반복·동시 PUT과 DELETE가 카운터를 중복 변경하지 않는다.
- 같은 원인 행동의 알림만 중복 제거하며, 실제 새 행동은 기록할 수 있다.
- 취소된 좋아요와 삭제된 댓글의 DB 알림 이력을 원인 ID와 함께 남길 수 있다.

## 부정적 결과와 트레이드오프

- FK가 없는 원인 ID의 의미적 정합성은 서비스 계약과 테스트에 의존한다. 유니크 제약만으로 잘못된 피드·행위자·원인 조합을 막지는 못한다.
- 취소·재좋아요가 반복되면 과거 알림 행은 DB에 누적된다. 화면에 하나만 보이는 것과 DB에 한 행만 남는 것은 다르다.
- 댓글 POST를 자동 재시도하면 중복 댓글이 생성될 수 있으므로 클라이언트가 좋아요 PUT과 같은 재시도 계약으로 취급하면 안 된다.

## 후속 결정과 재검토 조건

댓글 작성의 멱등 재시도가 필요해지거나 원인 관계를 DB로 강제해야 하면 별도 행동 테이블·종류별 FK·멱등성 키를 검토한다. 알림 종류 확장 시에는 원인 ID 규칙과 중복 키, 노출 조건을 함께 정해야 한다.
