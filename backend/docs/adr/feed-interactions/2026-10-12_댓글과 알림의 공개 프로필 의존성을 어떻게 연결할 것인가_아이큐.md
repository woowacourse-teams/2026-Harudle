# 2026-10-12 댓글과 알림의 공개 프로필 의존성을 어떻게 연결할 것인가

- 상태: 채택
- 작성일: 2026-10-12
- 수정일: 2026-10-13
- 작성자: 아이큐
- 결정 대상: 공개 작성자 정보의 조회 경계, 일괄 조회와 프로필 미연동 시 응답

## 배경

댓글과 알림에는 작성자 닉네임과 프로필 이미지가 필요하다. 각 기능이 User 엔티티를 직접 읽거나 임시 프로필을 만들면 닉네임 표시 규칙이 달라지고, 작성자별 추가 조회가 발생할 수 있다. 닉네임 변경이 기존 댓글과 알림에도 반영돼야 하므로 반응 행에 표시 정보를 복사해 고정하지 않는다.

프로필 기능은 별도 PR에서 구현한다. 댓글·알림 코드가 독립적으로 시작할 수 있어야 하지만, 프로필이 필요한 요청을 가짜 작성자 정보로 성공 처리해서는 안 된다.

## 결정 요인

- 작성자 정보를 공통 계약으로 읽고 User 저장 모델과 분리해야 한다.
- 반환 페이지의 작성자만 필요한 범위로 모아 한 번에 조회해야 한다.
- 프로필 미연동과 실제 탈퇴한 행위자를 구분해야 한다.
- 프로필이 필요 없는 삭제·읽음 요청까지 불필요하게 막지 않아야 한다.

## 고려한 대안

### 대안 1 각 기능이 User Repository를 직접 조회

즉시 구현할 수 있지만 회원 저장 모델과 표시 규칙에 각 서비스가 결합된다. 작성자별 호출을 사용하면 N+1 조회가 생길 수 있다.

### 대안 2 프로필 구현이 없을 때 임시 닉네임과 이미지 사용

응답을 계속 성공시킬 수 있지만 실제 사용자 정보가 아닌 데이터를 반환하고 연동 누락을 숨긴다. 운영용 fallback으로 채택하지 않는다.

### 대안 3 활성 프로필은 일괄 조회하고 확인된 탈퇴 작성자만 익명화

`PublicProfileReader.readAll(Set<UUID>)`를 사용하며 활성 회원의 필요한 정보가 누락되면 실패 처리한다. DB에서 탈퇴가 확인된 작성자는 프로필 없이 표시하므로 정상 탈퇴가 전체 목록 장애로 이어지지 않는다. 정상 탈퇴와 연동 누락을 구분할 수 있어 채택한다.

## 결정

### 인터페이스와 일괄 조회

`PublicProfileReader`는 회원 ID를 키로 하는 Map과 공개 정보만 담은 `Profile(id, nickname, profileImageUrl)`을 반환한다. 닉네임이 없을 때 기존 이름을 표시하는 규칙과 배정된 이미지 선택은 프로필 제공자의 책임이다.

목록에서는 실제 응답 페이지에 포함되는 회원 ID를 Set으로 모아 한 번 조회한다. `hasNext` 확인용 추가 행의 프로필은 조회하지 않는다. 닉네임과 이미지는 조회 시점의 제공자 응답을 사용한다.

댓글 목록의 SQL은 `users.deleted_at`을 읽어 `authorDeleted`를 반환한다. 이 값이 true인 작성자는 Reader 입력에서 제외하고, 활성 작성자 ID만 일괄 조회한다. Map에 ID가 없다는 이유만으로 탈퇴했다고 판단하지 않는다.

서비스는 필요한 ID의 프로필이 모두 있는지, ID가 맞는지, 닉네임이 비어 있지 않은지, 이미지 URI가 호스트를 가진 절대 HTTP·HTTPS URL인지 확인한다. Reader가 조회할 수 없는 회원을 Map에서 제외하는 것은 인터페이스 계약에 맞지만, 필요한 필수 프로필이 누락된 서비스 요청은 503으로 처리한다.

### 필요한 요청에서만 의존

생성자에는 `ObjectProvider<PublicProfileReader>`를 받는다. Bean이 없는 상태에서도 애플리케이션은 시작할 수 있지만, 작성자 정보가 필요한 요청의 성공을 보장하는 것은 아니다.

| 요청 | 프로필 처리 |
| --- | --- |
| 댓글 작성 | 작성자의 유효한 프로필이 필요. 없으면 503이며 댓글·카운터·알림을 저장하지 않음 |
| 활성 작성자가 있는 댓글 목록 | 활성 작성자의 프로필만 일괄 조회. 누락되면 503이며 확인된 탈퇴 작성자는 익명화 |
| 탈퇴 작성자만 있는 댓글 목록 | Reader 없이 댓글·페이지 유지, 작성자 익명화 |
| 빈 댓글 목록 | 프로필 조회 없이 빈 페이지 반환 |
| 댓글 삭제 | 프로필 조회 없음 |
| 활성 행위자가 있는 알림 페이지 | 해당 행위자의 프로필을 일괄 조회. 누락되면 503 |
| 빈 알림 페이지 또는 탈퇴 행위자만 있는 페이지 | 프로필 조회 없이 반환 |
| 알림 읽음 처리 | 프로필 조회 없음 |

댓글은 `503 COMMENT_UNAVAILABLE`, 알림은 `503 NOTIFICATION_UNAVAILABLE`로 미연동 상태를 알린다. 알림은 DB에서 탈퇴한 행위자를 구분해 `actor=null`로 표시하지만, 활성 행위자의 프로필 누락을 탈퇴로 간주하지 않는다.

탈퇴한 댓글 작성자는 `author={id:null, nickname:'탈퇴한 회원', profileImageUrl:null}`로 반환하고 `isMine=false`로 표시한다. 댓글 내용·내부 작성자 ID·댓글 수·커서는 유지하며, 프론트는 이미지 URL이 null일 때 기본 아이콘을 표시한다. 알림의 `actor=null`과는 응답 모양이 다르다.

이 보존 정책은 `users.deleted_at`을 설정하는 논리 탈퇴 기준이다. users 행을 물리 삭제하면 기존 댓글 FK의 `ON DELETE CASCADE`가 적용되므로 댓글 보존과 같다고 간주하지 않는다.

## 긍정적 결과

- 기능마다 닉네임과 이미지 표시 규칙을 별도로 구현하지 않는다.
- 현재 작성자 정보가 기존 댓글·알림에 반영되며 페이지 단위 일괄 조회로 중복 조회를 줄인다.
- 미연동 상태에서도 프로필이 필요 없는 요청은 사용할 수 있고, 필요한 요청은 실패 원인을 명시한다.

## 부정적 결과와 트레이드오프

- 활성 작성자의 프로필 누락 하나가 해당 페이지 전체의 503으로 이어질 수 있다. 확인된 탈퇴 작성자는 이 실패 조건에서 제외한다.
- 별도 구현을 연결하지 않으면 댓글 작성과 일부 목록을 정상 사용할 수 없다.
- 현재 댓글 작성의 프로필 조회는 피드 잠금 안에서 수행한다. 외부 호출 또는 느린 조회를 연결하면 쓰기 대기 시간이 늘어난다.
- 댓글·알림의 스냅샷 일관성은 제공자가 같은 DB·같은 트랜잭션에 참여할 때 적용된다. 외부 호출이나 별도 트랜잭션까지 같은 시점으로 만들지는 못한다.

## 후속 결정과 재검토 조건

프로필 Reader 구현을 연결할 때 같은 트랜잭션 참여, 조회 수, nickname fallback과 URL 계약을 검증한다. 프로필 유효성 검증을 제공자에게 통합하는 작업과 공통 회원 자격 조회 포트는 각 담당 영역의 반환·인증 계약을 맞출 때 정리한다. 프로필 공급자를 외부 서비스로 바꾸거나 부분 성공·캐시·회원 물리 삭제 후 댓글 보존이 필요해지면 가용성과 스냅샷 보장 수준을 다시 정한다.
