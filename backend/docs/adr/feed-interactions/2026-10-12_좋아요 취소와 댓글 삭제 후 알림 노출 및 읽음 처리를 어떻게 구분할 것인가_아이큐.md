# 2026-10-12 좋아요 취소와 댓글 삭제 후 알림 노출 및 읽음 처리를 어떻게 구분할 것인가

- 상태: 채택
- 작성일: 2026-10-12
- 수정일: 2026-10-13
- 작성자: 아이큐
- 결정 대상: 원인 행동 삭제 후 인앱 알림의 가시성, 미읽음 수와 클릭한 항목의 읽음 처리

## 배경

DB에 행동 이력을 남기는 것과 사용자에게 알림을 보여주는 것은 다른 정책이다. 좋아요 취소 후 재좋아요할 때 과거 알림까지 노출하면 같은 사람의 좋아요 알림이 누적된다. 댓글 삭제 후에는 댓글 내용이 아닌 댓글을 남겼다는 알림 이력을 유지하기로 한다.

삭제된 피드·원본 일기와 탈퇴한 피드 작성자의 알림은 목록과 미읽음 수에서 제외해야 한다. 이미 알림창에 떠 있던 항목을 클릭할 수 있으므로 읽음 API에도 같은 가시성 규칙이 필요하다.

## 결정 요인

- 취소·재좋아요 후 같은 행위자의 활성 좋아요 알림만 노출해야 한다.
- 목록·전체 미읽음 수·읽음 처리에 같은 조건을 적용해야 한다.
- 과거 알림의 원인 ID와 읽음 시각은 DB에 보존해야 한다.
- 알림창을 여는 것만으로 전체 읽음 처리하지 않아야 한다.

## 고려한 대안

### 대안 1 모든 원인 행동 삭제 후 알림을 계속 노출

저장 이력과 화면 노출이 같아 단순하지만, 좋아요 취소·재좋아요마다 과거 알림이 누적된다. 현재 원하는 사용자 경험에는 채택하지 않는다.

### 대안 2 취소 시 알림도 삭제하거나 동일 행을 재활용

노출할 알림만 남길 수 있다. 반면 취소 서비스가 알림 삭제·갱신을 담당해야 하고, 과거 읽음 시각을 지우거나 새 행동과 기존 알림의 연결을 바꾸게 된다. 기존 포트 변경 없이 적용하기 위해 채택하지 않는다.

### 대안 3 DB 이력을 유지하고 원인별 가시성을 조회에서 적용

취소 서비스와 기록 인터페이스는 유지하면서 LIKE의 실제 원인이 남았을 때만 조회한다. COMMENT는 원인 댓글의 존재 여부와 분리한다. 조회 조건이 늘어나지만 현재 구조와 표시 정책을 함께 만족해 채택한다.

## 결정

### 공통 가시성과 원인 행동

피드·원본 일기·피드 작성자가 모두 활성 상태인 알림만 노출한다. 반응한 회원의 탈퇴 여부와 피드 작성자의 탈퇴 여부는 구분한다. LIKE는 다음 세 조건을 만족하는 실제 `feed_likes` 행이 있어야 한다.

- 좋아요 ID가 `notifications.source_action_id`와 같다.
- 좋아요 피드 ID가 알림의 `feed_id`와 같다.
- 좋아요 회원 ID가 알림의 원래 `actor_user_id`와 같다.

현재 같은 사람이 해당 피드에 좋아요를 눌렀다는 조건만 확인하지 않는다. 새 좋아요가 과거 알림을 되살리지 않게 원인 ID까지 확인한다. 프로필 표시를 위한 nullable 행위자 값이 아닌 DB의 원래 행위자 ID를 비교한다.

이 조건을 목록, 전체 미읽음 수, 읽음 대상 조회와 읽음 UPDATE의 네 경로에 적용한다. COMMENT는 댓글 행이 삭제돼도 부모가 공개 상태이면 유지한다. 댓글 내용은 알림 응답에 담지 않는다.

| 행동 | DB 알림 이력 | 노출되는 알림 | 미읽음 수 |
| --- | --- | --- | --- |
| 좋아요 L1 생성 | N1 저장 | N1 | N1이 미읽음이면 1 |
| L1 취소 | N1 보존 | 없음 | 0 |
| 재좋아요 L2 생성 | N1과 N2 보존 | N2만 | N2가 미읽음이면 1 |
| 원인 댓글 삭제 | COMMENT 알림 보존 | 부모가 공개 상태이면 유지 | 읽음 여부에 따라 포함 |
| 피드 또는 원본 일기 소프트 삭제 | 알림 보존 | 없음 | 0 |
| 피드 작성자 논리 탈퇴 | 알림 보존 | 없음 | 0 |

다른 사람의 좋아요 알림까지 숨기지 않는다. 취소된 알림의 DB `read_at`은 보존하며, 재좋아요는 새 알림을 미읽음으로 생성한다. 이력 보존은 피드·수신자의 물리 삭제에 따른 FK 연쇄 삭제까지 막는 영구 보관 보장은 아니다.

### 탈퇴한 행위자

노출 조건을 만족하는 알림에서 탈퇴한 행위자는 `actor=null`과 탈퇴 안내 메시지를 반환한다. 피드 작성자가 아닌 반응 행위자만 논리 탈퇴하고 좋아요 행이 남으면 LIKE는 노출되고 프로필만 null이다. 물리 탈퇴로 좋아요가 FK 연쇄 삭제되면 LIKE는 숨긴다. COMMENT는 행위자가 물리 삭제돼도 부모와 피드 작성자가 공개 조건을 만족하면 유지한다.

### 클릭한 알림 읽음 처리

목록 조회는 읽음 상태를 바꾸지 않는다. `PATCH /api/v1/notifications/{notificationId}`에 실제 JSON boolean인 `read=true`를 요청해 해당 항목 하나만 읽는다. 읽음 취소와 전체 읽음 API는 제공하지 않는다. 문자열·숫자 자동 변환은 해당 필드의 역직렬화에서만 차단한다.

없는 알림, 삭제된 부모·탈퇴한 피드 작성자의 알림, 취소된 LIKE는 `404 NOTIFICATION_NOT_FOUND`다. 노출 가능한 타인 수신 알림은 403이다. 예전 LIKE 알림은 재좋아요 후에도 읽음 요청이 404다.

읽음 변경은 수신자·부모·피드 작성자·원인 조건을 가진 UPDATE와 `read_at = COALESCE(read_at, :readAt)`로 처리한다. 처음 성공한 NULL 갱신의 시각을 보존하며 반복·동시 요청은 그 값을 덮어쓰지 않는다. 먼저 도착한 HTTP 요청의 시각이나 여러 Clock 값의 최솟값을 보장하는 것은 아니다. 이미 읽은 정상 본인 알림도 반복 요청은 204다.

피드·좋아요 행을 추가로 잠그지 않는다. 취소·부모 삭제와 읽음 요청이 겹치면 요청의 DB 스냅샷에 따라 204 또는 404가 될 수 있다. 취소·삭제 커밋 뒤 시작한 새 목록·미읽음 수·읽음 요청에는 숨김·404를 적용한다. 성공 응답은 204이며 피드 이동 주소를 새로 반환하지 않는다. 클라이언트는 목록의 `feedId`로 이동하고 상세 조회의 404도 처리해야 한다.

## 긍정적 결과

- 취소·재좋아요 후 과거 LIKE를 되살리지 않고 새 알림 하나만 노출한다.
- 숨긴 알림이 미읽음 배지에만 남는 불일치를 방지한다.
- 기록 인터페이스와 원인 행동 저장 구조를 바꾸지 않고 기존 읽음 이력을 유지한다.

## 부정적 결과와 트레이드오프

- 조회에 원인 좋아요의 EXISTS 검사가 추가된다.
- 화면에서 숨긴 알림도 DB 저장 공간을 사용하므로 보관·정리 정책이 필요하다.
- 서로 다른 행을 조회하는 조건이 취소·읽음 요청을 완전히 직렬화하지는 않는다.
- COMMENT와 LIKE의 삭제 후 노출 정책이 다르므로 새 종류를 추가할 때 명시적인 규칙이 필요하다.

## 후속 결정과 재검토 조건

취소와 읽음의 엄격한 직렬화, 과거 알림 파기, 댓글 삭제 시 알림 제거 또는 새 알림 종류가 필요해지면 재검토한다. FCM 재푸시 간격·휴대폰 푸시 회수·특정 댓글로 이동하는 기능은 이 결정에 포함하지 않는다. 특정 외부 서비스의 내부 정책을 완전히 재현한다는 의미도 아니다.
