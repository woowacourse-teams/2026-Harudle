# 2026-10-12 반응 API의 공개 조회와 인증 및 CSRF 검증을 어떻게 분리할 것인가

- 상태: 채택
- 작성일: 2026-10-12
- 수정일: 2026-10-13
- 작성자: 아이큐
- 결정 대상: 댓글 공개 조회, 회원 전용 반응·알림 API와 해당 경로의 보안 필터 체인

## 배경

공개 피드 상세를 구성하는 댓글 목록은 로그인 없이 볼 수 있지만, 댓글 작성·삭제와 좋아요 변경은 회원만 사용할 수 있다. 인앱 알림은 특정 회원의 개인 정보이므로 조회와 읽음 모두 인증이 필요하다.

기존 API 전체의 보안을 한 번에 변경하면 OAuth 세션, Refresh Cookie와 다른 API에 영향을 줄 수 있다. 반응 변경은 기존 기능 명세의 Bearer와 CSRF 계약을 유지하고 프론트 요청을 맞추기로 결정했다. 이 요구를 관련 없는 모든 Bearer 변경 API로 확대하지 않는다.

## 결정 요인

- 공개 조회와 개인정보 조회 및 상태 변경을 구분해야 한다.
- 사용자 ID는 요청 본문이 아니라 검증된 인증 정보에서 가져와야 한다.
- 유효한 JWT와 실제 활성 OAuth 회원 자격을 구분해야 한다.
- 새 필터 체인이 기존 OAuth·쿠키 API와 미등록 경로 보호를 침범하지 않아야 한다.
- 기존 쿠키 API 보호를 유지하면서 실제 체인과 프론트 요청·Scalar 계약을 함께 맞춰야 한다.

## 고려한 대안

### 대안 1 기존 API 체인의 경로와 CSRF 정책을 함께 변경

체인 수와 공통 설정 중복을 줄일 수 있다. 반면 작은 기능 PR에서도 기존 모든 API의 인증·CSRF 동작을 함께 회귀 검증해야 한다. 현재 PR의 국소적 변경 방식으로는 채택하지 않는다.

### 대안 2 Bearer 반응 API에는 추가 CSRF를 요구하지 않음

추가 쿠키·헤더 계약 없이 기존 일반 Bearer API의 정책과 일치시킬 수 있다. 하지만 반응 API의 합의된 기능 명세를 바꾸게 되므로 채택하지 않는다. 기존 `CookieApiCsrfProtectionMatcher`의 쿠키 API 보호 범위는 그대로 유지한다.

### 대안 3 정확한 반응 경로별 체인에서 인증 후 CSRF 검증

회원 전용 반응 변경 요청에 Bearer와 CSRF를 모두 요구한다. 기존 경로의 동작을 유지하며 인증 실패와 CSRF 실패를 구분한다. 기존 명세를 유지하고 프론트 전송 계약을 맞추는 방식으로 채택하며, 모든 Bearer API에 CSRF가 필수라는 일반 원칙을 뜻하지는 않는다.

## 결정

### 공개 범위와 회원 확인

| 경로 | 공개 여부와 인증 계약 |
| --- | --- |
| GET `/api/v1/feeds/{feedId}/comments` | 익명 조회 허용. 인증된 조회자면 `isMine` 조립 |
| POST `/api/v1/feeds/{feedId}/comments` | 활성 OAuth 회원의 Bearer와 CSRF |
| DELETE `/api/v1/comments/{commentId}` | 활성 OAuth 회원의 Bearer와 CSRF, 댓글 작성자 권한 확인 |
| PUT·DELETE `/api/v1/feeds/{feedId}/like` | 활성 OAuth 회원의 Bearer와 CSRF |
| GET `/api/v1/notifications` | 활성 OAuth 회원의 Bearer |
| PATCH `/api/v1/notifications/{notificationId}` | 활성 OAuth 회원의 Bearer와 CSRF, 수신자 권한 확인 |

피드 목록·상세 자체의 공개 설정은 피드 영역의 책임이다. 이 문서가 카테고리·관리자·개인 일기 API를 추가로 공개하는 것은 아니다.

보호 API의 서비스는 `users.deleted_at IS NULL`과 OAuth 계정 존재 여부를 함께 확인한다. 유효한 JWT만으로 게스트를 회원 전용 기능에 허용하지 않는다. 서비스의 활성 회원 확인은 신규 요청 기준의 검사이며, 요청 중 탈퇴와 모든 반응 저장을 같은 회원 잠금으로 직렬화하는 것은 아니다.

공개 GET에서 Bearer를 생략하면 익명으로 조회한다. 잘못된 Bearer를 보낸 요청을 익명으로 자동 전환하지는 않는다. 댓글 응답의 `isMine`은 삭제 권한 검사를 대신하지 않는다.

### 필터 체인과 오류

댓글·좋아요·알림 체인은 정확한 HTTP 메서드와 경로에만 매칭하고 `STATELESS`를 사용한다. OAuth 세션을 보호 API의 인증 수단으로 사용하지 않는다.

기본 CSRF 필터를 비활성화한 뒤 `CsrfFilter`를 Bearer 인증 필터 뒤에 명시적으로 추가한다. 이는 CSRF 전체를 제거한 설정이 아니다. 변경 요청에서 인증이 성립했을 때 `XSRF-TOKEN` 쿠키와 `X-XSRF-TOKEN` 헤더를 확인한다.

미인증·잘못된 JWT는 401, 활성 회원의 인증 이후 CSRF 누락·불일치는 403이다. 유효한 JWT와 CSRF가 있어도 게스트·탈퇴 회원은 서비스에서 401로 거부한다. 대상 소유권과 가시성에 따른 403·404는 각 서비스에서 처리한다.

변경 요청의 실제 순서는 JWT 인증 → CSRF 검사 → 서비스의 활성 회원 검사다. 따라서 게스트·탈퇴 회원의 유효한 JWT 요청이라도 CSRF가 누락되면 서비스의 회원 검사에 도달하기 전에 403이 반환될 수 있다. JWT와 CSRF를 통과한 뒤의 회원 자격 오류와 구분한다.

댓글 응답은 조회자별 `isMine`이 달라지고 알림은 개인별 데이터이므로 `Cache-Control: no-store`로 반환한다. Scalar에는 기존 쿠키 변경 API, 좋아요 PUT·DELETE, 댓글 POST·DELETE, 알림 읽음 PATCH에만 실제 CSRF 요구를 반영한다. 보호 반응 API의 Bearer와 CSRF는 대체 인증 수단인 OR가 아니라 함께 필요한 AND 조건이다.

### 프론트 전송과 토큰 갱신

CSRF 쿠키의 Path가 `/api/v1`이므로 일반 화면에서 `document.cookie`를 읽는 방식에 의존하지 않는다. `GET /api/v1/auth/csrf`의 응답 token을 헤더에 넣고 브라우저가 함께 발급받은 쿠키를 요청에 포함하게 한다.

인증 복구 과정에서도 CSRF 토큰을 새로 발급받으므로, 변경 요청의 nonce 발급과 실제 전송을 함께 관리해야 한다. 같은 화면에서 병렬 요청이 서로의 쿠키를 바꾸지 않도록 발급·전송을 직렬화하고, 기존 refresh 단일 실행과 원래 요청의 401 재시도 1회 계약을 유지한다. 모든 탭 사이의 쿠키 경쟁까지 직렬화하는 것은 아니다.

프론트 수정은 `fix/feed-like-csrf-request`의 로컬 커밋으로 준비했으며 아직 병합·배포하지 않았다. 댓글·알림 화면의 요청 연동과 배포 환경에서 실제 쿠키·헤더 전송 검증은 별도로 진행한다.

## 긍정적 결과

- 공개 댓글 조회와 회원 전용 변경·개인 알림의 경계가 명시적이다.
- 요청의 작성자·수신자 ID 조작으로 다른 회원의 권한을 얻지 못한다.
- PR에서 새 경로의 보안 동작을 국소적으로 검증하면서 기존 API 동작을 유지한다.

## 부정적 결과와 트레이드오프

- 대상별 필터 체인에 CORS·JWT·오류 처리·CSRF 설정이 중복된다.
- 먼저 매칭되는 체인 하나만 적용되므로 Order와 matcher가 겹치면 다른 설정이 실행될 수 있다.
- 반응 변경에 추가 쿠키·헤더가 필요해 프론트 요청 계약이 복잡해진다.
- 기존 일반 Bearer API와 반응 변경의 CSRF 요구가 다르므로 matcher와 Scalar를 경로·메서드 기준으로 유지해야 한다. 서버 테스트 통과가 프론트 배포 화면의 전송 성공을 의미하지 않는다.

## 후속 결정과 재검토 조건

정책을 적용하고 유지할 때 다음 항목을 확인한다.

1. 기존 쿠키 API의 보호를 유지하면서 공통 체인과 반응별 체인의 matcher·우선순위·인증·CSRF 동작을 맞춘다.
2. 프론트 수정 병합 후 인증 복구·동시 변경 요청과 실제 화면의 쿠키·헤더 전송을 확인한다.
3. Scalar의 Bearer와 CSRF 요구가 실제 대상 경로에서만 함께 적용되는지 검증한다.
4. 최신 피드 게시·삭제·조회 코드까지 합친 상태에서 공개 조회·JWT 오류·게스트·탈퇴·소유권·CSRF 회귀 테스트를 실행한다.

쿠키 인증의 확대나 체인 중복 증가, 새로운 관리자·반응 API 도입 시 체인 구성을 다시 검토한다.
