# 2026-10-12 반응 저장과 카운터 및 알림 기록을 하나의 트랜잭션으로 묶을 것인가

- 상태: 채택
- 작성일: 2026-10-12
- 수정일: 2026-10-13
- 작성자: 아이큐
- 결정 대상: 댓글·좋아요 변경의 트랜잭션 경계, 피드 잠금 순서와 반응 수 갱신

## 배경

댓글·좋아요의 실제 행과 `feeds.comment_count`·`like_count`는 함께 변경돼야 한다. 반응 행만 저장되거나 카운터만 증가하면 목록과 상세의 수치가 달라진다. 다른 사람의 피드에 반응을 추가할 때는 인앱 알림도 같은 행동을 원인으로 기록해야 한다.

동시에 들어온 반응 요청이 같은 카운터를 덮어쓰지 않아야 하며, 피드 삭제와도 순서를 정해야 한다. 개인 일기 삭제가 일기와 연결 피드를 잠그는 흐름에서 반응 요청이 피드 다음에 일기를 잠그면 잠금 순서가 역전될 수 있다.

## 결정 요인

- 반응 저장·카운터 변경·알림 기록은 함께 커밋하거나 함께 롤백해야 한다.
- 같은 피드의 동시 변경으로 반응 수가 유실되거나 음수가 되면 안 된다.
- 댓글·좋아요 영역이 피드 CRUD 엔티티의 구현에 직접 의존하지 않아야 한다.
- 외부 푸시 전송을 반응 트랜잭션에 포함하지 않아야 한다.

## 고려한 대안

### 대안 1 반응을 저장하고 이벤트로 카운터와 알림을 나중에 변경

쓰기 요청의 잠금 시간을 줄이고 처리를 분리할 수 있다. 반면 잠시 동안 반응·카운터·알림이 불일치하며, 재시도·이벤트 중복·실패 복구를 위한 별도 설계가 필요하다. 현재 즉시 반영 계약에는 채택하지 않는다.

### 대안 2 각 서비스가 피드 엔티티를 조회해 카운터를 직접 변경

도메인 메서드와 JPA 변경 감지를 이용할 수 있다. 반면 댓글·좋아요가 같은 엔티티와 변경 규칙을 공유하고, 동시 갱신을 방지하는 규칙을 각 서비스에 일관되게 적용해야 한다.

### 대안 3 공통 반응 포트로 피드를 잠그고 한 트랜잭션에서 처리

`FeedInteractionPort`가 피드 잠금과 카운터 갱신을 제공하고, 반응 서비스가 실제 변경과 알림 기록의 순서를 조립한다. 같은 피드의 쓰기를 직렬화하는 비용이 있지만, 현재 규모에서 정합성 규칙과 실패 시 롤백 경계를 명확하게 유지할 수 있어 채택한다.

## 결정

댓글·좋아요 서비스의 `@Transactional`을 쓰기 경계로 사용한다. 반응 변경 Repository, `FeedInteractionPort`, `InAppNotificationRecorder`의 쓰기 구현은 `MANDATORY`로 호출자의 트랜잭션에 참여한다. 포트가 독립 트랜잭션으로 일부 변경만 커밋하지 않게 한다.

`MANDATORY`는 기존 트랜잭션의 존재를 확인할 뿐, `adjustCounter` 호출 전에 해당 피드를 잠갔는지 검사하지 않는다. 피드 잠금 → 실제 반응 변경 → 카운터 변경의 호출 순서는 서비스와 포트의 사용 계약으로 지킨다.

### 잠금과 변경 순서

- `FeedInteractionService.lockActive`는 JPA의 `PESSIMISTIC_WRITE`로 피드 행만 잠근다. 원본 일기와 피드 작성자의 활성 여부는 일반 조회로 확인하며 일기·회원 행을 함께 잠그지 않는다.
- 피드 잠금은 서비스 트랜잭션의 커밋·롤백까지 유지한다.
- 댓글 작성과 좋아요 추가는 실제 행 저장 → 카운터 증가 → 인앱 알림 기록 순서로 처리한다.
- 좋아요 취소는 실제 행 삭제에 성공한 경우에만 카운터를 감소시킨다.
- 댓글 삭제는 잠금 없는 최초 조회로 피드 ID를 확인한 뒤 피드를 잠그고 댓글을 다시 조회한다. 소유권을 확인하고 `deleted_at IS NULL`인 행만 소프트 삭제하며, 성공한 경우에만 카운터를 감소시킨다.
- 댓글 삭제 경로는 댓글 행을 먼저 잠근 뒤 피드를 잠그는 순서를 사용하지 않는다.
- 개인 일기 삭제는 `DiaryDeletionService`가 일기를 먼저 잠근 뒤 `FeedLifecycle`을 호출해 연결 피드를 잠그고 삭제한다. 반응 요청은 피드 다음에 일기 잠금을 추가하지 않아 이 순서를 역전시키지 않는다. 일기·연결 피드 삭제와 미발송 푸시 취소는 같은 트랜잭션에서 처리한다.

댓글 본문은 피드 잠금 전에 앞뒤 공백을 제거하고 1~100 Unicode 코드 포인트를 검증한다. UTF-16 길이나 화면에 보이는 글자 묶음 수를 기준으로 하지 않는다. NUL과 잘못된 surrogate는 저장 전에 거부하며, 일반 텍스트로 저장한 본문은 프론트에서도 텍스트로 렌더링해야 한다.

예를 들어 같은 댓글을 두 요청이 삭제하면 첫 요청만 댓글을 소프트 삭제하고 카운터를 1 줄인다. 뒤 요청은 피드 잠금을 얻은 뒤 댓글이 이미 삭제된 것을 확인해 404를 반환하며 카운터를 다시 줄이지 않는다.

### 카운터와 알림

`FeedInteractionService` 하나가 카운터 변경을 담당한다. 잠근 `Feed` 엔티티의 증가·감소 메서드를 호출하고 JPA 변경 감지로 저장한다. 정수 범위를 넘는 증가와 0에서의 감소는 거부하며, 실패 시 실제 반응 변경도 롤백한다. DB의 비음수 CHECK 제약을 추가 방어선으로 사용하되, CHECK만으로 실제 행 수와 카운터의 일치를 보장하지는 않는다.

피드 CRUD와 반응 변경이 동일한 관리 엔티티를 사용하도록 기존 native 카운터 어댑터를 제거했다. 댓글·좋아요 행을 저장하거나 삭제하는 native SQL은 유지하지만, 같은 피드의 카운터를 native SQL과 JPA 변경 감지로 각각 수정하지 않는다.

알림 기록에 실패하면 반응 행과 카운터도 롤백한다. 자기 알림 제외나 동일 행동 알림 중복은 정상 결과로 처리한다. FCM 호출은 이 경로에서 하지 않는다.

## 긍정적 결과

- 반응·카운터·인앱 알림이 일부만 저장되는 상태를 방지한다.
- 같은 피드의 댓글·좋아요 변경과 피드 삭제가 피드 잠금으로 순서를 갖는다.
- 댓글·좋아요 서비스는 공통 포트를 이용해 피드 저장 모델과 분리된다.

## 부정적 결과와 트레이드오프

- 인기 피드에 쓰기가 집중되면 같은 행 잠금 대기가 증가한다.
- 좋아요의 `ON CONFLICT`와 댓글의 `RETURNING`은 PostgreSQL에 의존한다. 새 구현에서 피드 카운터를 native SQL로 우회 변경하면 관리 엔티티의 오래된 값이 저장될 수 있으므로 공통 JPA 서비스의 갱신 책임을 유지해야 한다.
- 댓글 작성은 피드 잠금 안에서 공개 프로필을 조회한다. 느린 외부 프로필 구현을 연결하면 잠금 시간이 늘어날 수 있다.
- 피드 잠금 자체가 원본 일기 삭제를 잠그는 것은 아니다. 일기 삭제가 연결 피드도 같은 트랜잭션에서 삭제하는 생명주기 계약이 함께 지켜져야 한다.
- Repository를 직접 호출하거나 운영 SQL로 반응을 삭제하는 우회 경로의 카운터 정합성까지 자동 보장하지 않는다.

## 후속 결정과 재검토 조건

같은 피드의 잠금 대기가 운영 병목이 되면 원자적 카운터 갱신과 비동기 집계 방식을 다시 비교한다. 새 반응·삭제 경로를 연결할 때는 공통 포트의 단일 구현, 잠금 순서·엔티티 상태·갱신 책임과 활성 대상의 기준을 함께 검증한다.
