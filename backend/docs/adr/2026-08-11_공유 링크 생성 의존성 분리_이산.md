# 2026-08-11 공유 링크 생성에 필요한 다른 도메인 의존성 분리

- 작성일: 2026-08-11
- 작성자: 이산
- 결정 대상: 공유 링크 생성 Service와 일기 및 생성 도메인의 의존 관계

## 배경

공유 링크를 생성하려면 그림일기의 존재와 삭제 여부, 사용자 소유권, 연결된 `DiaryGeneration`의 존재와 상태를 확인해야 한다.
`ShareLinkService`가 `DiaryRepository`와 `DiaryGenerationRepository`를 직접 사용하면 다른 도메인의 엔티티, Repository
메서드와 패키지 구조에 강하게 결합된다.

공유 도메인의 비즈니스 흐름을 유지하면서 다른 도메인의 구현 변경이 직접 전파되는 범위를 줄일 경계가 필요하다.

## 결정 요인

- 공유 기능은 일기와 생성 도메인의 내부 구현을 가능한 한 몰라야 한다.
- 사용자 ID와 일기 ID로 소유권 및 생성 상태를 확인할 수 있어야 한다.
- 공유 Service에는 링크 생성 판단에 필요한 최소 정보만 전달해야 한다.
- 공유 링크 자체의 조회와 저장 책임은 공유 Repository에 남겨야 한다.
- 실제 일기 및 생성 Repository가 변경되어도 공유 Service의 변경 범위를 줄여야 한다.

## 고려한 대안

### 대안 1: ShareLinkService가 다른 도메인의 Repository를 직접 사용

장점은 다음과 같다.

- 별도의 인터페이스와 구현체가 필요하지 않다.
- 조회 흐름을 한 클래스에서 바로 확인할 수 있다.

단점은 다음과 같다.

- 공유 Service가 다른 도메인의 엔티티와 Repository API에 직접 결합된다.
- 다른 도메인의 구조 변경이 공유 기능에 전파된다.
- 공유 Service가 링크 생성 외에 일기 조회와 소유권 확인 책임까지 갖게 된다.

### 대안 2: ShareLinkRepository가 다른 도메인 조회까지 담당

장점은 다음과 같다.

- 공유 Service가 하나의 Repository에만 의존한다.
- 조회 쿼리를 Repository 내부에 숨길 수 있다.

단점은 다음과 같다.

- 공유 링크 저장소가 일기와 생성 도메인 조회 책임까지 갖게 된다.
- 공유 링크 자체의 영속성 책임과 공유 대상 검증 책임이 섞인다.
- Repository 이름만으로 실제 책임을 파악하기 어렵다.

### 대안 3: ShareLinkCreationReader로 다른 도메인 조회 경계 분리

장점은 다음과 같다.

- 공유 Service가 필요한 정보의 계약만 의존한다.
- 다른 도메인의 Repository 조합과 조회 방식을 구현체에 숨길 수 있다.
- `ShareLinkRepository`는 공유 링크 자체의 조회와 저장만 담당한다.

단점은 다음과 같다.

- 인터페이스와 구현체가 추가된다.
- 실제 도메인 상태와 전달 정보 사이의 매핑을 관리해야 한다.
- 지나치게 작은 기능에서는 구조가 복잡하게 느껴질 수 있다.

## 결정

대안 3을 선택한다.

```java
public interface ShareLinkCreationReader {

    ShareLinkCreationInfo read(UUID userId, UUID diaryId);
}
```

Reader는 입력받은 사용자 ID와 일기 ID를 이용해 다음 내용을 확인한다.

```text
그림일기 존재 및 삭제 여부
→ 현재 사용자의 그림일기인지 확인
→ 연결된 DiaryGeneration 조회
→ 생성 결과 ID와 상태 제공
```

`ShareLinkCreationInfo`는 공유 링크 생성 판단에 필요한 생성 결과 ID와 `GenerationStatus`만 제공한다. 상태가
`SUCCEEDED`인지 판단하고 기존 링크를 반환하거나 신규 생성하는 책임은 `ShareLinkService`가 가진다.

```text
ShareLinkService
├── ShareLinkCreationReader
│   ├── DiaryRepository
│   └── DiaryGenerationRepository
└── ShareLinkRepository
    └── share_links
```

공유 링크는 성공한 생성 결과를 공유하므로 `share_links`는 `diary_id`가 아니라 `generation_id`를 참조한다.

## 긍정적 결과

- 공유 Service가 다른 도메인의 엔티티와 Repository 구현에 직접 결합되지 않는다.
- 일기 존재, 삭제 여부와 소유권 확인 책임을 하나의 조회 경계에 모은다.
- 공유 링크 자체의 영속성 책임과 공유 대상 조회 책임이 분리된다.
- 다른 도메인의 조회 방식이 변경돼도 Reader 구현체 중심으로 수정할 수 있다.

## 부정적 결과와 트레이드오프

- Reader 인터페이스와 실제 구현체를 추가로 관리해야 한다.
- `GenerationStatus`를 직접 전달하므로 생성 도메인의 안정적인 타입에는 의존한다.
- Reader가 지나치게 많은 판단을 수행하면 Service의 비즈니스 책임과 경계가 다시 모호해질 수 있다.
- 실제 Repository를 조합한 통합 테스트가 필요하다.
