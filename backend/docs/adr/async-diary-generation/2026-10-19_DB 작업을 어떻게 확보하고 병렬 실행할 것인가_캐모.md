# 2026-10-19 DB 작업을 어떻게 확보하고 병렬 실행할 것인가

`FOR UPDATE SKIP LOCKED`로 작업을 확보한다. 저장을 확정해 DB 잠금을 푼 뒤 이미지를 생성한다.

- 상태: 설계 채택, 작업 선점 코드 작성, 실행 연결 전
- 작성일: 2026-10-19
- 작성자: 캐모
- 결정 대상: 여러 작업 처리기가 서로 다른 생성 작업을 가져가는 방법

## 배경

여러 처리기가 같은 대기 작업을 읽으면 같은 이미지를 동시에 생성할 수 있다.
이를 막으려면 누가 작업을 맡았는지 저장하는 짧은 구간을 보호해야 한다.

DB 잠금은 다른 처리기가 같은 행을 함께 바꾸지 못하게 한다. AI 호출이 끝날 때까지 잠금을 유지하면
DB 연결과 잠금을 오래 사용한다. 작업을 확보하는 구간과 실제 이미지 생성을 나눈다.

## 고려한 방법

| 방법 | 좋은 점 | 불편한 점 |
| --- | --- | --- |
| 처리기 하나가 차례로 실행 | 실행 순서와 코드가 단순하다. | 한 작업이 오래 걸리면 다음 작업도 기다린다. |
| 잠긴 작업을 기다림 | 같은 행을 동시에 바꾸지 못하게 한다. | 다른 대기 작업이 있어도 잠금이 풀리기를 기다릴 수 있다. |
| 잠긴 작업을 건너뜀 | 여러 처리기가 서로 다른 작업을 가져간다. | 먼저 등록한 작업이 항상 먼저 끝나는 것은 아니다. PostgreSQL의 기능을 사용한다. |

## 결정과 실제 처리

`FOR UPDATE`는 선택한 행을 잠근다. `SKIP LOCKED`는 다른 처리기가 잠근 행을 건너뛴다는 뜻이다.
트랜잭션은 DB 변경을 함께 저장하거나 취소하는 단위다. 이 단위를 짧게 유지한다.

1. 대기 작업을 `FOR UPDATE SKIP LOCKED`로 조회한다. 실행할 수 있는 수만큼만 가져온다.
2. 같은 트랜잭션에서 가져온 작업을 처리 중으로 바꾼다.
3. 변경을 확정하는 커밋을 한다. 이때 DB 잠금이 풀린다.
4. DB 잠금 없이 AI 호출과 이미지 저장을 실행한다.
5. 결과는 새 트랜잭션에서 같은 생성 기록에 저장한다.

다른 처리기는 대기 상태만 찾으므로 이미 처리 중으로 바뀐 기록을 가져가지 않는다.
처리기 A가 작업 123을 맡은 동안 처리기 B는 작업 124를 실행할 수 있다.
이미지를 만드는 시간 전체를 순차 처리할 필요는 없다.

## 작업 선점 단계의 구현

2026-10-20에 대기 작업을 가져오는 서비스와 조회 쿼리를 추가했다.
`PENDING`인 기록만 생성 시각과 ID 순서로 찾는다. 다른 처리기가 잠근 기록은 건너뛰고,
호출한 코드가 지정한 개수까지만 가져온다.

조회한 작업은 같은 트랜잭션에서 `PROCESSING`으로 바꾼다. 상태를 저장할 때 갱신 시각도 새로 기록한다.
기존 시간 초과 검사는 이 시각을 사용하므로 작업이 대기한 시간은 처리 시간에 포함되지 않는다.

선점 서비스에는 `REQUIRES_NEW`를 적용했다. 호출한 코드가 이미 트랜잭션을 사용 중이어도
선점은 별도 트랜잭션으로 끝낸다. 서비스가 반환될 때 상태 저장과 잠금 해제가 끝나며, 작업 ID만 반환한다.

이미지를 실행하는 작업 처리기와 생성 요청을 대기로 저장하는 API는 아직 연결하지 않았다.
자동 재시도와 서버 중단 후 복구 규칙도 이번 단계에서 추가하지 않는다.

## 불편한 점과 다시 검토할 때

잠금을 기다리는 시간은 줄지만 행을 찾고 상태를 바꾸는 비용은 남는다. 동시에 실행할 수 있는 수와
한 번에 가져오는 수는 [성능 검증](<2026-10-19_DB 큐의 부하를 어떻게 검증하고 재검토할 것인가_캐모.md>)에서 정한다.

이 방법만으로 AI 호출이 항상 한 번만 실행된다고 보장하지는 않는다. 서버가 중단된 작업의 복구 규칙은 별도 결정이 필요하다.
작업이 늘어도 DB 잠금을 AI 호출이 끝날 때까지 유지하는 방식으로 바꾸지 않는다.
