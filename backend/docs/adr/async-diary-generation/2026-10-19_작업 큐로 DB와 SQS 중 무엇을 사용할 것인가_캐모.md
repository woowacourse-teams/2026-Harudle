# 2026-10-19 작업 큐로 DB와 SQS 중 무엇을 사용할 것인가

생성할 작업은 기존 DB에 저장한다. SQS 도입은 보류하고, DB 큐의 성능을 먼저 확인한다.

- 상태: 설계 채택, 구현 전
- 작성일: 2026-10-19
- 작성자: 캐모
- 결정 대상: 이미지 생성 작업을 저장하고 작업 처리기에 전달하는 방법

## 배경

현재 서버는 이미지 생성이 끝나야 생성 요청에 응답한다. 사용자는 다른 화면으로 이동한 뒤에도
진행 상태를 확인할 수 있어야 한다. 이를 위해 요청을 받는 코드와 이미지를 생성하는 코드를 분리한다.

작업 큐는 실행을 기다리는 작업을 저장하고 가져오는 기능이다. 기존 DB로 만들 수도 있고,
AWS가 제공하는 메시지 서비스인 SQS를 사용할 수도 있다. 아직 실제 DB 부하는 측정하지 않았다.

## 고려한 방법

| 방법 | 좋은 점 | 불편한 점 |
| --- | --- | --- |
| DB 큐 | 기존 DB를 사용한다. 일기와 작업을 함께 저장할 수 있다. | 작업 조회와 상태 변경이 DB 부하에 더해진다. 처리기를 직접 만들어야 한다. |
| SQS | 메시지 보관과 재전달 기능을 제공한다. 작업 처리기를 따로 운영할 수 있다. | 추가 서비스 사용료와 관리 대상이 생긴다. DB 저장 후 SQS 전송이 빠지는 상황에도 대응해야 한다. |

SQS를 사용해도 생성 결과와 상태는 DB에 저장해야 한다. 프론트엔드의 상태 조회도 필요하다.
DB 저장과 SQS 전송 사이의 누락을 막는 방법은 [AWS Outbox 설명](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)을 참고한다.

## 결정과 실제 처리

DB 큐로 시작한다. 작업 처리기는 처음에는 같은 백엔드 앱 안에 둔다.

1. 생성 요청을 받으면 일기와 대기 작업을 함께 DB에 저장한다.
2. 저장이 확정되면 접수 결과를 반환한다.
3. 작업 처리기가 대기 작업을 찾아 이미지를 생성한다.
4. 작업 처리기가 생성 결과를 DB에 저장한다.

생성 작업을 저장하고 가져오는 기준은 [생성 테이블 결정](<2026-10-19_기존 생성 테이블을 작업 큐로 사용할 것인가_캐모.md>)을 따른다.
작업 처리기는 상태 조회 API를 호출하지 않고 DB에서 직접 작업을 찾는다.

## 불편한 점과 다시 검토할 때

DB 큐도 여러 처리기가 서로 다른 작업을 동시에 실행할 수 있다. 처리기를 늘리기 위해 SQS가 꼭 필요한 것은 아니다.
다만 작업 조회가 늘면 일기 조회 등 기존 기능과 DB 자원을 나눠 쓰게 된다.

사용료와 운영 부담을 추가하기 전에 [성능 검증 결정](<2026-10-19_DB 큐의 부하를 어떻게 검증하고 재검토할 것인가_캐모.md>)에 따라 측정한다.
DB 큐가 기존 기능을 느리게 만드는 원인이고 설정을 조정해도 해결하기 어렵다면 SQS를 다시 비교한다.
현재 부하가 작다거나 SQS보다 비용이 적다는 측정 결과가 나온 상태는 아니다.
