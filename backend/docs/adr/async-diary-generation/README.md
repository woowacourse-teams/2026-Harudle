# 이미지 비동기 생성 설계 결정

이미지 생성은 서버에서 계속 실행한다. 사용자는 다른 화면에서도 진행 상태를 확인할 수 있게 한다.
작업은 기존 DB에 저장한다. SQS 도입은 비용과 실제 성능을 확인할 때까지 보류한다.

- 작성일: 2026-10-19
- 상태: 설계 채택, DB 준비와 작업 선점 코드 작성

이 문서는 선택한 설계를 기록한다. 아래 처리 순서는 전체 구현을 마쳤을 때의 동작이다.

2026-10-20에는 `PENDING` 상태와 대기 작업 조회용 인덱스를 추가하는 V24 마이그레이션을 작성했다.
백엔드가 이 상태를 읽고 구분하도록 했다. 기존 생성 요청은 아직 동기 방식으로 처리한다.
대기 작업을 `FOR UPDATE SKIP LOCKED`로 가져와 처리 중으로 바꾸는 서비스도 추가했다.
이 서비스는 상태 저장과 잠금 해제를 끝낸 뒤 가져온 작업 ID를 반환한다.
작업 처리기, 접수 API 변경, 프론트엔드의 상태 조회는 아직 구현하지 않았다.

## 실제 처리 순서

1. 생성 요청을 받으면 일기와 대기 작업을 함께 DB에 저장한다.
2. 저장이 끝나면 요청을 보낸 화면에 접수 결과를 반환한다.
3. 서버의 작업 처리기가 DB에서 대기 작업을 찾아 실행한다.
4. 생성이 끝나면 같은 생성 기록에 결과를 저장한다.
5. 프론트엔드는 상태 조회 결과를 모달에 표시한다.

DB는 일기와 생성 상태를 저장하는 데이터베이스다.
작업 처리기는 생성 작업을 찾고 실행하는 서버 코드다. 처음에는 같은 백엔드 앱 안에 둔다.
프론트엔드가 일정한 간격으로 상태를 다시 조회하는 방식을 폴링이라고 부른다.
서버의 작업 조회와 프론트엔드의 상태 조회는 서로 다른 동작이다.
