# 이미지 비동기 생성 설계 결정

이미지 생성은 서버에서 계속 실행한다. 사용자는 다른 화면에서도 진행 상태를 확인할 수 있게 한다.
작업은 기존 DB에 저장한다. SQS 도입은 비용과 실제 성능을 확인할 때까지 보류한다.

- 작성일: 2026-10-19
- 상태: 비동기 접수와 실행 연결, HTTP 계약 전환 전

이 문서는 선택한 설계를 기록한다. 아래 처리 순서는 전체 구현을 마쳤을 때의 동작이다.

2026-10-20에는 `PENDING` 상태와 대기 작업 조회용 인덱스를 추가하는 V28 마이그레이션을 작성했다.
백엔드가 이 상태를 읽고 구분하도록 했다.
대기 작업을 `FOR UPDATE SKIP LOCKED`로 가져와 처리 중으로 바꾸는 서비스도 추가했다.
이 서비스는 상태 저장과 잠금 해제를 끝낸 뒤 가져온 작업 ID를 반환한다.
작업 처리기가 실행 스레드를 확보한 뒤 대기 작업 하나를 선점하고 기존 생성 실행기를 호출하도록 연결했다.
작업 처리기는 앱 시작 시 항상 등록한다. 환경 변수로 동시 실행 수와 확인 간격만 정한다. 기본은 동시 실행 1개, 확인 간격 5초다.
이 값은 초기 실행을 위한 기본값이며 적정 운영값은 성능 검증 후 정한다.
회원과 게스트용 `enqueue` 메서드도 추가했다. 이 메서드는 일기와 `PENDING` 작업을 저장한다.
회원 사용량 증가 또는 게스트 체험 사용도 같은 트랜잭션에서 처리한다.
회원과 게스트 생성 API를 `enqueue` 메서드에 연결했다. 저장이 끝나면 이미지를 생성하지 않고 작업 상태를 반환한다.
같은 요청을 다시 보내면 대기 상태, 처리 중 상태 또는 저장된 성공 결과를 반환한다. 실패한 요청은 기존 오류를 반환한다.
부하 테스트도 `PENDING` 작업을 저장하고 같은 처리기가 `SKIP LOCKED`로 선점한다.
일반 API는 실제 AI를 사용한다. 부하 테스트 API가 접수한 생성 ID는 메모리에서 dev 전용 가짜 AI 실행기에 연결한다.
작업 저장 트랜잭션 안에서 연결을 등록하고, 저장을 취소하거나 작업 처리가 끝나면 연결을 지운다. S3 저장은 유지한다.
DB에 작업 종류를 추가하지 않는다. 연결은 현재 백엔드 프로세스에서만 유지되므로 부하 테스트는 백엔드 한 인스턴스에서 실행한다.
재시작 후 남은 테스트 작업은 일반 작업과 구분할 수 없다.
회원과 게스트, 부하 테스트 API의 신규 접수는 `202 Accepted`로 반환한다. 같은 요청의 기존 상태와 결과는 `200 OK`로 반환한다.
응답의 일기 ID, 생성 ID, 생성 상태를 유지한다. `Location`은 기존 일기 조회 주소다.
회원은 `GET /api/v1/diary-generations/{generationId}`, 게스트는 `GET /api/v1/guest/diary-generations/{generationId}`로 상태를 조회한다.
본인의 작업만 조회할 수 있다. 게스트는 현재 세션에 연결된 일기도 확인한다. 다른 사람의 작업과 없는 작업은 같은 `404`로 반환한다.
상태 조회는 `200`으로 네 가지 상태를 반환한다. 성공 시 일기 ID, 실패 시 저장된 오류 코드를 제공하며 실패로 숨겨진 일기도 조회할 수 있다.
부하 테스트도 전용 상태 API를 사용한다. 이 조회는 작업을 선점하거나 이미지 URL을 발급하지 않는다.
일반 생성 API와 부하 테스트 API는 실행기가 준비되지 않으면 신규 접수를 거절한다. 기존 접수 결과는 반환할 수 있다.
일반 DB 통합 테스트는 처리기를 테스트용 객체로 교체한다. 처리기 자체 테스트와 전체 부하 테스트는 실제 처리기를 사용한다.
프론트엔드의 상태 조회는 아직 구현하지 않았다.

2026-10-21에는 아직 끝나지 않은 작업 수를 동시 실행 수로 제한하는 접수 정책을 채택했다.
선점 전의 대기 작업도 포함하며, 상한에 도달하면 신규 접수를 `503`으로 거절한다.
회원, 게스트, 부하 테스트의 공통 접수 경로에 이 제한을 구현했다. 개수 확인과 저장은 접수용 DB 잠금으로 보호한다.
선점 후 입력 조회에서 일시적인 DB 오류가 나면 한 번 즉시 다시 조회한다.
생성 기록과 일기를 읽는 단계 전체에 재시도 한 번을 적용한다. AI 호출 이후에는 적용하지 않는다.

## 실제 처리 순서

1. 생성 요청을 받으면 일기와 대기 작업을 함께 DB에 저장한다.
2. 저장이 끝나면 요청을 보낸 화면에 접수 결과를 반환한다.
3. 서버의 작업 처리기가 DB에서 대기 작업을 찾아 실행한다.
4. 생성이 끝나면 같은 생성 기록에 결과를 저장한다.
5. 프론트엔드는 상태 조회 결과를 모달에 표시한다.

DB는 일기와 생성 상태를 저장하는 데이터베이스다.
작업 처리기는 생성 작업을 찾고 실행하는 서버 코드다. 처음에는 같은 백엔드 앱 안에 둔다.
프론트엔드가 일정한 간격으로 상태를 다시 조회하는 방식을 폴링이라고 부른다.
서버의 작업 조회와 프론트엔드의 상태 조회는 서로 다른 동작이다.
