# 2026-10-19 진행 상태를 폴링과 SSE 중 무엇으로 전달할 것인가

프론트엔드가 생성 상태를 반복 조회하고 모달에 표시한다. 상태가 바뀐 순간에 바로 알리는 연결은 도입하지 않는다.

- 상태: 설계 채택, 백엔드 상태 조회 구현
- 작성일: 2026-10-19
- 작성자: 캐모
- 결정 대상: 화면을 이동한 뒤에도 생성 상태를 확인하는 방법

## 배경

사용자는 생성 화면을 나간 뒤에도 작업이 진행 중인지 확인할 수 있어야 한다.
완료 표시가 몇 초 늦는 것은 허용할 수 있다. 지금은 즉시 알림보다 화면 이동 후에도 상태를 확인하는 것이 중요하다.

모달은 조회한 상태를 표시하는 화면이다. 모달을 만든다고 서버의 상태를 자동으로 받는 것은 아니다.
상태를 가져오는 방법과 모달을 열고 닫는 동작을 따로 정해야 한다.

## 고려한 방법

| 방법 | 실제 동작 | 불편한 점 |
| --- | --- | --- |
| 폴링 | 프론트엔드가 일정한 간격으로 서버에 다시 묻는다. | 반복 조회가 생기고 변경을 조금 늦게 알 수 있다. |
| SSE | 서버와 연결을 유지하고 서버가 상태 변경을 보낸다. | 연결 유지와 재접속 처리가 필요하다. |
| WebSocket | 연결을 유지하며 서버와 브라우저가 양쪽으로 메시지를 보낸다. | 현재 필요한 상태 확인 외에 연결 관리가 추가된다. |

## 결정과 실제 처리

폴링을 선택한다. 생성 작업의 상태는 서버에 저장된 값을 기준으로 보여준다.

1. 생성 요청의 접수 결과에서 생성 ID를 받는다.
2. 화면이 바뀌어도 유지되는 앱 공통 영역에서 상태 조회를 시작한다.
3. 받은 상태를 저장하고 모달에 표시한다.
4. 모달을 닫거나 다른 화면으로 이동해도 진행 중인 작업의 조회는 유지한다.
5. 성공이나 최종 실패를 확인하면 해당 작업의 반복 조회를 끝낸다.

같은 시점에 여러 모달이나 화면이 각각 조회를 시작하지 않게 한다.
새로고침 후에는 서버에서 진행 중인 작업을 찾아 조회를 이어갈 수 있어야 한다.
화면의 조회 간격은 아직 정하지 않았다. 백엔드의 조회 형식은 아래와 같다.

## 백엔드 구현

회원은 `GET /api/v1/diary-generations/{generationId}`로 조회한다.
게스트는 세션 쿠키를 보내고 `GET /api/v1/guest/diary-generations/{generationId}`로 조회한다.
접수 응답의 `generation.id`를 경로에 넣는다. 다른 사람의 작업과 없는 작업은 모두 `404`로 반환한다.

조회에 성공하면 `200`과 생성 ID, 상태를 반환한다. 성공한 작업은 일기 ID를, 실패한 작업은 오류 코드를 함께 반환한다.
실패로 일기가 숨겨져도 작업의 실패 상태는 조회할 수 있다. 상태 조회에서 이미지 URL은 발급하지 않는다.
`Cache-Control: no-store`를 반환해 이전 상태를 캐시하지 않는다.

부하 테스트는 이 API를 사용한다. 프론트엔드의 공통 상태 관리와 모달 연결은 아직 구현하지 않았다.

## 불편한 점과 다시 검토할 때

완료 상태가 다음 조회 때 보일 수 있고, 진행 중인 사용자가 많으면 조회 요청도 늘어난다.
프론트엔드의 상태 조회 비용은 서버가 DB 큐에서 작업을 찾는 비용과 따로 측정한다.

즉시 상태 변경을 알려야 하는 요구가 생기거나 폴링 부담이 커지면 SSE를 다시 비교한다.
상태 전달 방법은 DB 큐와 SQS 중 무엇을 쓰는지와 별개로 바꿀 수 있다.
