# 2026-10-19 기존 생성 테이블을 작업 큐로 사용할 것인가

기존 `diary_generations`에 대기 작업과 처리 결과를 함께 저장한다. 별도 작업 테이블은 추가하지 않는다.

- 상태: 설계 채택, 구현 전
- 작성일: 2026-10-19
- 작성자: 캐모
- 결정 대상: DB 큐의 작업 기록을 저장할 위치

## 배경

현재 생성 테이블에는 일기 ID, 생성 상태, 이미지 저장 위치가 있다. 생성 기록 하나가 이미지 생성 작업 하나에 해당한다.
이 기록에 대기 상태를 추가하면 작업 처리기가 실행할 일을 찾을 수 있다.

현재 상태는 처리 중, 성공, 실패로 나뉜다. 아직 시작하지 않은 작업과 실행 중인 작업을 구분할 상태가 필요하다.

## 고려한 방법

| 방법 | 좋은 점 | 불편한 점 |
| --- | --- | --- |
| 기존 생성 테이블 확장 | 같은 생성 ID로 대기 상태부터 결과까지 확인한다. 테이블과 기록의 중복이 적다. | 결과 저장과 작업 관리가 같은 테이블에 들어간다. 작업 조회가 생성 이력 조회에 영향을 줄 수 있다. |
| 별도 작업 테이블 추가 | 작업 관리와 생성 결과를 따로 바꿀 수 있다. | 생성 기록과 작업 기록을 함께 저장하고 연결 상태를 맞춰야 한다. |

Outbox는 보통 나중에 외부로 보낼 메시지를 DB에 저장하는 방식이다. 지금은 저장한 생성 기록을 처리기가 직접 실행한다.
먼저 DB에 할 일을 남긴다는 점은 비슷하지만, 현재 구조는 DB 기반 작업 큐로 부른다.

## 결정과 실제 처리

`diary_generations`를 확장한다. 새로운 작업마다 생성 기록을 하나 만들고, 같은 기록의 상태와 결과를 바꾼다.

1. 일기와 생성 기록을 함께 저장한다. 처음 상태는 `PENDING`, 즉 실행 대기다.
2. 작업 처리기가 실행을 맡으면 `PROCESSING`, 즉 처리 중으로 바꾼다.
3. 생성이 끝나면 성공은 `SUCCEEDED`, 최종 실패는 `FAILED`로 기록한다.
4. 상태를 확인하는 화면은 같은 생성 ID의 기록을 조회한다.

대기 상태를 추가할 때 서버의 상태 목록과 DB에서 허용하는 상태 목록을 함께 바꿔야 한다.
이 문서는 저장 위치와 상태 구분을 정한다. 추가 필드의 상세 구성은 아직 정하지 않았다.

## 불편한 점과 다시 검토할 때

하나의 테이블에 결과와 작업 상태가 함께 있으므로 작업 관리 변경이 기존 조회에 영향을 줄 수 있다.
완료된 기록이 많아졌을 때 대기 작업을 찾는 비용도 [성능 검증](<2026-10-19_DB 큐의 부하를 어떻게 검증하고 재검토할 것인가_캐모.md>)에서 확인한다.

생성 하나에서 여러 종류의 작업을 따로 실행해야 하거나 외부로 메시지를 발행해야 한다면 별도 테이블을 다시 검토한다.
