# 2026-08-12 공유 링크 생성 시각은 Hibernate가 기록하고 flush 후 반환

- 작성일: 2026-08-12
- 작성자: 이산
- 결정 대상: 공유 링크 생성 시각의 생성 책임과 신규 생성 응답 시점

## 배경

공유 링크 생성 API는 공유 링크 ID와 함께 생성 시각을 응답한다. `ShareLink.createdAt`은 `@CreationTimestamp`로 매핑되어 있어
Hibernate가 엔티티 영속화 시점에 값을 기록한다.

JPA의 `save()`는 엔티티를 영속성 컨텍스트에 등록하지만 INSERT SQL을 즉시 실행한다고 보장하지 않는다. 신규 공유 링크를 저장한
직후 `createdAt`을 응답하려면 영속화와 생성 시각 반영 시점을 명확하게 정해야 한다.

현재 공유 링크 자체에는 만료 기간, 갱신 주기 또는 생성 시각을 기준으로 상태를 변경하는 도메인 규칙이 없다. 공개 조회에서 반환하는
S3 Presigned URL의 만료 시각은 공유 링크의 생성 시각과 무관하며, 이미지 접근 URL을 발급한 시점과 설정된 TTL을 기준으로
`ImageUrlProvider`가 결정한다.

## 결정 요인

- 신규 생성 응답에 `createdAt`이 반드시 포함되어야 한다.
- 생성 시각은 공유 링크의 정책 판단보다 영속성 메타데이터에 가깝다.
- 현재 공유 링크에는 생성 시각을 기준으로 판단하는 만료 또는 갱신 정책이 없다.
- 기존 엔티티에서 사용하는 `@CreationTimestamp` 방식과 일관성을 유지해야 한다.
- 생성 시각 테스트를 위해 Service에 불필요한 시간 의존성을 추가하지 않아야 한다.
- 저장 실패 시 트랜잭션 롤백이 가능해야 한다.

## 고려한 대안

### 대안 1: Clock을 주입해 애플리케이션에서 생성 시각 결정

장점은 다음과 같다.

- `save()` 직후에도 생성 시각을 사용할 수 있다.
- 고정된 `Clock`을 사용해 시간 관련 테스트를 쉽게 작성할 수 있다.
- 도메인 객체를 생성하는 순간부터 생성 시각이 존재한다.

단점은 다음과 같다.

- Service 또는 도메인 생성 메서드에 `Clock`이나 `Instant`를 전달해야 한다.
- DB 기본값 및 Hibernate 자동 생성과 시간 생성 책임이 겹칠 수 있다.
- 현재 공유 링크 생성 시각은 별도의 도메인 정책에 사용되지 않아 시간 의존성의 이점이 작다.

### 대안 2: DB 기본값을 사용하고 저장 후 다시 조회

장점은 다음과 같다.

- 데이터베이스 시간을 생성 시각의 기준으로 사용할 수 있다.
- DB에 실제 저장된 값을 응답할 수 있다.

단점은 다음과 같다.

- INSERT 이후 SELECT 또는 `EntityManager.refresh()`가 추가로 필요하다.
- 구현이 복잡해지고 데이터베이스 왕복이 증가한다.
- 같은 영속성 컨텍스트의 캐시 때문에 단순 재조회만으로 실제 DB 조회가 보장되지 않을 수 있다.

### 대안 3: CreationTimestamp와 saveAndFlush 사용

장점은 다음과 같다.

- 기존 엔티티의 생성 시각 관리 방식과 일관적이다.
- Hibernate가 영속화 시점에 생성 시각을 기록한다.
- Service에 `Clock` 의존성을 추가하지 않고 저장 직후 생성 시각을 반환할 수 있다.
- flush 이후에도 트랜잭션이 커밋되기 전이라면 오류 발생 시 롤백할 수 있다.

단점은 다음과 같다.

- 일반 `save()`보다 이른 시점에 INSERT SQL을 실행한다.
- 생성 시각을 세밀하게 제어하는 단위 테스트는 작성하기 어렵다.
- flush와 commit의 차이를 이해해야 한다.

## 결정

대안 3을 선택한다.

`ShareLink.createdAt`은 `@CreationTimestamp`로 Hibernate가 기록한다. 신규 공유 링크는 `ShareLinkRepository.saveAndFlush()`로
저장하여 INSERT SQL과 생성 시각 반영을 먼저 수행한 뒤 결과를 만든다.

현재는 공유 링크 생성 시각을 사용하는 도메인 규칙이 없으므로 Service에 `Clock`을 도입하지 않는다. S3 Presigned URL의 만료는
공유 링크의 `createdAt`으로 계산하지 않고 이미지 접근 URL 발급 책임에서 별도로 처리한다.

```java
ShareLink savedShareLink = shareLinkRepository.saveAndFlush(
        ShareLink.create(generationId)
);

return new ShareLinkCreationResult(
        savedShareLink.getId(),
        savedShareLink.getCreatedAt(),
        true
);
```

`flush`는 SQL을 데이터베이스에 전달하는 동작이며 트랜잭션을 확정하는 `commit`과 다르다. `saveAndFlush()` 이후 Service에서 예외가
발생하면 트랜잭션 전체를 롤백할 수 있다.

기존 공유 링크는 이미 생성 시각이 저장되어 있으므로 추가 flush 없이 조회된 값을 사용한다.

## 긍정적 결과

- 신규 생성 응답에 저장 시점의 `createdAt`을 안정적으로 포함할 수 있다.
- 다른 엔티티의 `@CreationTimestamp` 사용 방식과 일관성을 유지한다.
- Service에 `Clock` 또는 시간 생성 책임을 추가하지 않는다.
- 공유 링크 생성 시각을 영속성 메타데이터로 명확하게 다룬다.
- 공유 링크와 S3 Presigned URL의 서로 다른 수명 주기를 분리한다.

## 부정적 결과와 트레이드오프

- 공유 링크 생성 시 INSERT SQL이 트랜잭션 커밋보다 먼저 실행된다.
- 생성 시각을 원하는 값으로 고정하는 순수 단위 테스트는 어렵다.
- 향후 공유 링크 자체에 만료 기간이나 갱신 정책이 추가되면 `expiresAt`과 `Clock` 도입을 포함해 시간 관리 방식을 재검토해야 한다.
- DB가 생성한 시각을 직접 읽는 방식이 아니라 Hibernate가 생성한 시각을 저장하고 반환한다.
