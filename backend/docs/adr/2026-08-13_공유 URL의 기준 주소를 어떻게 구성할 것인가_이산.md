# 2026-08-13 공유 URL의 기준 주소는 환경 설정으로 주입하고 프레젠테이션 계층에서 조립

- 작성일: 2026-08-13
- 작성자: 이산
- 결정 대상: 공유 링크 API 응답의 공개 URL 구성 책임과 환경별 기준 주소 관리

## 배경

공유 링크 생성 API는 공유 링크 ID와 함께 사용자가 실제로 접속할 수 있는 `shareUrl`을 반환한다. 이 URL은 백엔드의 공개 조회 API
주소가 아니라 프론트엔드가 제공하는 공유 페이지 주소다.

프론트엔드 주소는 로컬, 개발, 운영 환경마다 달라질 수 있다. URL을 Java 코드에 직접 작성하면 배포 환경이 바뀔 때마다 코드를
수정하고 다시 빌드해야 한다. 반대로 Service가 완성된 URL을 만들면 공유 링크 생성이라는 애플리케이션 로직이 프론트엔드의 주소와
라우팅 규칙에 의존하게 된다.

따라서 환경별 공개 주소를 어디에서 관리하고, 공유 링크 ID를 완성된 URL로 변환하는 책임을 어느 계층에 둘지 결정해야 한다.

## 결정 요인

- 로컬, 개발, 운영 환경마다 다른 프론트엔드 주소를 사용할 수 있어야 한다.
- 프론트엔드의 도메인이나 라우팅 변경이 공유 링크 도메인과 Service에 영향을 주지 않아야 한다.
- 공유 링크 Service 결과는 HTTP 응답 형식과 배포 환경에 독립적이어야 한다.
- 응답에는 클라이언트가 별도 조립 없이 사용할 수 있는 완성된 URL을 제공해야 한다.
- 설정이 누락되거나 잘못된 경우 애플리케이션 시작 또는 테스트에서 빠르게 확인할 수 있어야 한다.

## 고려한 대안

### 대안 1: 공개 URL을 Java 코드에 직접 작성

장점은 다음과 같다.

- 구현이 단순하다.
- 별도의 설정 객체가 필요하지 않다.

단점은 다음과 같다.

- 환경마다 다른 주소를 사용하기 어렵다.
- 도메인이나 프론트엔드 경로가 바뀔 때 코드를 수정하고 다시 배포해야 한다.
- 테스트가 특정 운영 주소에 결합된다.

### 대안 2: Service에서 공개 URL 조립

장점은 다음과 같다.

- Controller는 Service 결과를 그대로 응답할 수 있다.
- 여러 Controller에서 같은 URL을 반환할 때 중복을 줄일 수 있다.

단점은 다음과 같다.

- Service가 프론트엔드 주소와 라우팅 규칙에 의존한다.
- 애플리케이션 계층의 결과가 HTTP 응답 표현에 가까워진다.
- 공유 링크 생성 규칙과 배포 환경 설정의 경계가 흐려진다.

### 대안 3: 기준 주소를 환경 설정으로 주입하고 프레젠테이션 계층에서 조립

장점은 다음과 같다.

- 환경 변수만 변경해 환경별 프론트엔드 주소를 사용할 수 있다.
- Service는 `shareId`, `createdAt`, 신규 생성 여부만 반환한다.
- 프론트엔드 라우팅 규칙을 API 응답 조립 책임 안에 제한할 수 있다.
- Controller 테스트에서 기준 주소와 응답 URL을 명확하게 검증할 수 있다.

단점은 다음과 같다.

- URL 설정과 응답 조립을 위한 객체가 추가된다.
- 설정값의 마지막 슬래시 여부 등 URL 결합 규칙을 일관되게 처리해야 한다.
- 다른 프레젠테이션 경계에서도 공유 URL이 필요해지면 조립 책임을 재사용할 방법이 필요하다.

## 결정

대안 3을 선택한다.

프론트엔드 공유 페이지의 기준 주소를 `application.yml`의 `harudle.share.public-base-url`로 관리하고 환경 변수
`SHARE_PUBLIC_BASE_URL`로 재정의한다.

```yaml
harudle:
  share:
    public-base-url: ${SHARE_PUBLIC_BASE_URL:http://localhost:3000/shares}
```

공유 링크 Service는 배포 환경과 무관한 결과만 반환한다.

```java
public record ShareLinkCreationResult(
        UUID shareId,
        Instant createdAt,
        boolean created
) {
}
```

프레젠테이션 계층은 설정된 기준 주소에 `shareId`를 경로로 추가해 API 응답의 `shareUrl`을 만든다.

```text
ShareLinkService 결과의 shareId
→ ShareLinkResponseAssembler
→ {publicBaseUrl}/{shareId}
→ ShareLinkResponse.shareUrl
```

신규 생성 여부는 URL 조립과 분리한다. Controller는 `created`가 `true`이면 `201 Created`, `false`이면 `200 OK`를 반환한다.

## 긍정적 결과

- Java 코드를 변경하지 않고 환경별 프론트엔드 주소를 적용할 수 있다.
- 공유 링크 Service가 HTTP 응답과 프론트엔드 라우팅 규칙에 의존하지 않는다.
- 클라이언트는 완성된 공유 URL을 그대로 사용할 수 있다.
- 공개 URL 생성 책임이 프레젠테이션 계층에 명확하게 위치한다.
- 향후 프론트엔드 도메인이 변경되어도 환경 설정만 수정할 수 있다.

## 부정적 결과와 트레이드오프

- 배포 환경에서 `SHARE_PUBLIC_BASE_URL`을 올바르게 설정해야 한다.
- 기준 주소 정규화와 URL 경로 결합 규칙을 별도로 구현해야 한다.
- 프론트엔드의 공유 페이지 경로가 바뀌면 환경 설정도 함께 변경해야 한다.
- 향후 이메일이나 알림처럼 HTTP 프레젠테이션 외부에서도 공유 URL이 필요해지면 URL 생성기를 공통 포트로 분리할 수 있다.
