# 2026-08-11 Service의 주요 협력 흐름은 통합 테스트로 검증

- 작성일: 2026-08-11
- 작성자: 이산
- 결정 대상: Service와 Repository가 협력하는 비즈니스 흐름의 테스트 방식

## 배경

Service 계층은 여러 도메인 객체와 Repository를 조합하여 하나의 비즈니스 흐름을 수행한다. Service만 격리해 테스트하려면
Mock이나 Fake로 실제 협력 객체의 동작을 테스트 코드에서 다시 정의해야 한다.

Mock은 내부 호출 방식에 테스트가 결합될 수 있고, Fake는 실제 JPA Repository와 PostgreSQL의 동작을 완전히 재현하지 못한다.
Service의 내부 구현보다 실제 협력 결과와 최종 데이터 상태를 보호할 테스트 방식을 결정해야 한다.

## 결정 요인

- 실제 JPA 엔티티 매핑과 조회 쿼리를 함께 검증해야 한다.
- 데이터베이스 고유 제약과 트랜잭션 동작을 확인해야 한다.
- 테스트가 내부 메서드 호출 횟수보다 비즈니스 결과를 보호해야 한다.
- 운영 PostgreSQL과 테스트 데이터베이스의 차이를 줄여야 한다.
- 테스트 대역이 필요한 외부 경계와 내부 Repository 협력을 구분해야 한다.

## 고려한 대안

### 대안 1: Mockito로 Service를 완전히 격리

장점은 다음과 같다.

- 테스트 실행이 빠르다.
- 예외와 경계 상황의 반환값을 쉽게 설정할 수 있다.
- 협력 메서드 호출 여부를 세밀하게 검증할 수 있다.

단점은 다음과 같다.

- `when`과 `verify`로 실제 협력 객체의 동작을 다시 정의해야 한다.
- 테스트가 메서드 호출 방식과 횟수에 결합될 수 있다.
- JPA 매핑, 실제 쿼리, DB 제약과 트랜잭션을 검증하지 못한다.

### 대안 2: 메모리 Fake Repository 사용

장점은 다음과 같다.

- 상태 기반으로 Service 결과를 검증할 수 있다.
- Mock보다 실제 Repository 사용 흐름과 유사하다.
- 테스트가 내부 호출 횟수에 덜 결합된다.

단점은 다음과 같다.

- Fake 구현을 별도로 작성하고 유지해야 한다.
- 실제 PostgreSQL의 제약, 잠금과 트랜잭션 동작이 다를 수 있다.
- 실제 구현과 Fake의 동작이 시간이 지나며 달라질 수 있다.

### 대안 3: 실제 Repository와 PostgreSQL을 사용하는 통합 테스트

장점은 다음과 같다.

- 실제 Spring Bean, JPA 매핑, 쿼리와 트랜잭션을 함께 검증한다.
- 최종 데이터 상태를 기준으로 비즈니스 흐름을 보호한다.
- 운영 환경과 테스트 환경의 차이를 줄인다.

단점은 다음과 같다.

- 컨테이너 실행 때문에 테스트가 상대적으로 느리다.
- 테스트 데이터 준비와 정리 비용이 크다.
- 실패 원인이 Service, Repository 또는 설정 중 어디인지 분리하기 어려울 수 있다.

## 결정

대안 3을 선택한다.

Service의 주요 협력 흐름은 실제 Spring Bean과 Repository를 사용하고, Testcontainers로 PostgreSQL을 실행하는 통합 테스트로
검증한다. 공유 링크 Service에서는 다음 흐름을 확인한다.

- 성공한 생성 결과에 공유 링크가 없으면 새 링크를 생성한다.
- 공유 링크가 이미 존재하면 기존 링크를 반환한다.
- 생성 상태가 `PROCESSING` 또는 `FAILED`이면 공유 링크를 생성하지 않는다.
- 다른 사용자의 그림일기이거나 삭제된 그림일기이면 공유 링크를 생성하지 않는다.
- 하나의 생성 결과에는 하나의 공유 링크만 저장된다.

도메인의 핵심 규칙과 실패 케이스는 단위 테스트로 검증한다. 복잡한 쿼리나 데이터 정합성을 독립적으로 보호해야 할 때만
Repository 테스트를 추가하고 작성 이유를 PR에 남긴다. Controller의 주요 사용자 시나리오는 인수 테스트로 검증한다.

외부 API, 이미지 저장소, 시간과 같이 테스트 환경에서 직접 사용하기 어렵거나 결과를 통제해야 하는 경계에는 Mock, Fake 또는
Stub을 사용할 수 있다.

## 긍정적 결과

- Service의 내부 호출 방식보다 실제 비즈니스 결과를 검증한다.
- JPA 매핑, 실제 쿼리와 트랜잭션 문제를 함께 발견할 수 있다.
- PostgreSQL 고유 제약 등 Fake로 재현하기 어려운 동작을 보호한다.
- 별도의 Fake Repository 유지 비용을 줄인다.

## 부정적 결과와 트레이드오프

- 단위 테스트보다 실행 시간이 길다.
- Docker를 사용할 수 없는 환경에서는 일부 테스트를 실행할 수 없다.
- 많은 시나리오가 동일한 ApplicationContext와 DB를 사용하면 테스트 격리가 복잡해질 수 있다.
- 특정 외부 경계에는 여전히 테스트 대역이 필요하다.
