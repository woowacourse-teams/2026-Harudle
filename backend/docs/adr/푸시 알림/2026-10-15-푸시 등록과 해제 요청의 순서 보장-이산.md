# 2026-10-15 푸시 등록과 해제 요청의 순서 보장

- 작성일: 2026-10-15
- 작성자: 이산
- 상태: 백엔드 구현 완료, 프론트엔드 연결 전
- 결정 대상: 첫 등록 요청과 해제 요청이 겹칠 때 남길 상태

## 배경

브라우저가 첫 등록 `PUT`을 보냈지만 서버의 응답이 늦을 수 있다. 그사이 사용자가 알림을 끄면 브라우저는 `DELETE`를 보낸다. 현재는 등록 행이 없을 때 `DELETE`가 아무 기록도 남기지 않는다. 따라서 `DELETE`가 먼저 끝나고 늦은 `PUT`이 도착하면 등록이 다시 생길 수 있다.

기존 `push_registrations.version`은 이미 만들어진 등록의 FID 변경 순서를 확인한다. 첫 등록 전이나 해제 후에는 확인할 등록 행이 없으므로 이 문제를 해결하지 못한다.

## 결정

1. 로그인 세션과 `deviceId`마다 **마지막으로 처리한 수신 선택의 `stateVersion`과 켜짐 여부**를 DB에 남긴다. 등록 행이 없어도 이 기록은 유지한다.
2. `PUT`과 `DELETE`는 모두 브라우저가 알고 있는 `stateVersion`을 함께 보낸다. 서버는 DB의 현재 `stateVersion`과 같을 때만 선택을 변경하고 값을 올린다. 값이 다르면 현재 `stateVersion`을 알려준다.
3. `DELETE`는 등록 행이 없어도 해제 상태를 남긴다. 등록이 있다면 같은 DB 트랜잭션에서 등록과 미발송 작업을 해제한다.
4. 같은 요청을 다시 보낸 경우에는 결과를 중복 변경하지 않는다. `DELETE` 이후 도착한 이전 번호의 `PUT`은 같은 FID라도 거절한다.
5. 충돌이 나면 브라우저는 **지금 사용자가 선택한 상태**를 확인한다. 여전히 끄기 상태라면 현재 `stateVersion`으로 `DELETE`를 다시 보낸다. 켜기 상태라면 현재 Firebase가 알려준 FID와 `stateVersion`으로 `PUT`을 다시 보낸다. 이전 요청 자체를 무조건 반복하지 않는다.

## 실제 요청 순서

| 서버가 처리한 요청 | DB의 `stateVersion` | 등록 상태 |
| --- | --- | --- |
| 첫 `PUT` 전 | 0 | 등록 없음 |
| `DELETE`가 먼저 도착 | 1 | 해제 |
| 뒤늦은 `PUT`, 요청 `stateVersion=0` | 1 | 거절하고 해제 유지 |
| 사용자가 다시 켠 뒤 새 `PUT`, 요청 `stateVersion=1` | 2 | 등록 |

반대로 첫 `PUT`이 먼저 끝나면 DB의 `stateVersion`은 1이 된다. `stateVersion=0`으로 보낸 `DELETE`는 충돌을 받는다. 사용자가 여전히 알림을 끄려 한다면 브라우저가 `stateVersion=1`로 `DELETE`를 다시 보내고, 서버는 등록을 해제한다.

서버는 번호 확인, 번호 변경, 등록 변경과 미발송 작업 취소를 한 DB 트랜잭션에서 처리한다. 같은 세션의 같은 `deviceId` 요청이 동시에 와도 DB에서 순서대로 처리한다. 다른 유효한 세션의 등록을 `409`로 보호하는 기존 규칙은 유지한다.

## 구현 범위

Flyway `V27`은 `push_registration_states` 테이블을 만든다. 로그인 세션과 `deviceId`마다 한 행에 `state_version`과 `enabled`를 저장한다. 기존 활성 등록은 `state_version=1`, `enabled=true`로 옮긴다. 세션과 연결되지 않은 옛 등록은 옮기지 않는다.

- 첫 `PUT`은 본문에 `stateVersion: 0`을 보낸다. 성공 응답은 기존 `id`, `version`과 새 `stateVersion`을 담는다.
- `DELETE`는 `?stateVersion=값`을 보낸다. 성공하면 `204`와 `Push-State-Version` 응답 헤더를 받는다. 등록이 없어도 해제 상태를 저장한다.
- 오래된 수신 선택은 `409 STALE_PUSH_STATE`로 거절한다. 응답에는 `currentStateVersion`과 `enabled`를 담는다.
- 기존 등록의 FID 변경에 쓰는 등록 ID와 `version`은 그대로 사용한다. `stateVersion`은 등록과 해제 요청이 처리된 순서를 확인한다.

프론트엔드는 `stateVersion`을 요청에 담고, 충돌 시 현재 사용자의 수신 선택을 확인한다. 요청 순서 판단과 오래된 등록 거절은 백엔드가 맡는다. 프론트엔드 연결은 아직 남아 있다. 로그아웃은 현재처럼 세션을 무효화해 늦은 등록을 막는다.

## 검증할 동작

- 첫 `PUT`보다 `DELETE`가 먼저 끝나도 늦은 `PUT`이 등록을 다시 만들지 않는다.
- `PUT`이 먼저 끝나면 이전 번호의 `DELETE`는 충돌을 받고, 현재 번호로 다시 보낸 `DELETE`가 등록과 미발송 작업을 해제한다.
- 같은 `PUT`이나 `DELETE`를 다시 보내도 결과가 바뀌지 않는다. 더 나중에 처리된 선택을 옛 요청이 되돌리지 못한다.
- 사용자가 다시 켠 새 `PUT`은 현재 번호로 등록할 수 있고, 이전 번호의 요청은 거절된다.
- 다른 세션의 유효한 등록은 기존처럼 보호한다.

DB 통합 테스트는 두 처리 순서, 실제 동시 요청, 중복 해제, 다시 켜기와 미발송 작업 취소를 확인한다. API 테스트는 요청 필드와 `409` 응답을 확인한다. 마이그레이션 테스트는 기존 활성 등록의 상태 이전을 확인한다.
