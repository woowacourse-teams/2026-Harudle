# 2026-08-12 실패 일기는 소프트 삭제하고 확인된 고아 이미지만 정리

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 생성 실패 시 DB 생명주기와 객체 저장소 보상 정책

## 배경

일기 행과 `PROCESSING` 생성 기록은 외부 AI 호출 전에 저장된다. AI 또는 객체 저장소 호출이 실패하면 완성된 결과가 없는 일기 행과
실패 생성 기록이 남는다. 실패 일기를 활성 상태로 두면 월간 또는 상세 조회가 완성되지 않은 결과를 다뤄야 한다. 생성 기록을 모두
지우면 같은 멱등성 키의 재요청과 장애 원인 추적이 불가능해진다.

이미지를 업로드한 뒤 완료 트랜잭션에서 예외가 발생하는 경우도 있다. 호출자는 예외를 받았지만 DB 커밋이 실제로 성공했는지 즉시
알 수 없는 commit-unknown 상황일 수 있다. 이때 이미지를 무조건 삭제하면 DB가 성공 결과로 참조하는 이미지를 잃을 수 있다.
반대로 절대 삭제하지 않으면 참조되지 않는 객체가 계속 남는다. 데이터 손실과 고아 객체 사이의 보상 기준을 결정해야 한다.

## 결정 요인

- 생성 결과가 없는 일기를 사용자 히스토리에 노출하지 않아야 한다.
- 실패 원인과 멱등 재요청을 위해 생성 기록을 보존해야 한다.
- 생성 실패 상태와 일기 비활성화가 함께 커밋되어야 한다.
- DB가 참조할 가능성이 있는 이미지를 예외만 보고 삭제하지 않아야 한다.
- 참조되지 않는 것으로 확인된 이미지는 best-effort로 정리해야 한다.
- 외부 자원을 소비한 실패 요청의 사용량을 삭제로 복구하지 않아야 한다.

## 고려한 대안

### 대안 1: 실패한 일기와 생성 기록을 모두 물리 삭제

장점은 다음과 같다.

- 사용자 조회에 실패 데이터가 남지 않는다.
- 데이터 모델에는 성공 결과만 유지된다.
- 실패 행의 장기 보관 공간이 필요하지 않다.

단점은 다음과 같다.

- 같은 멱등성 키의 실패 결과를 재현할 수 없다.
- 장애 원인과 실패 시각을 추적할 DB 근거가 사라진다.
- 재요청이 새로운 생성과 사용량 차감으로 이어질 수 있다.
- DB 삭제와 객체 저장소 삭제의 부분 실패 문제가 남는다.

### 대안 2: 실패 일기를 활성 상태로 유지

장점은 다음과 같다.

- 사용자가 실패 사실을 히스토리에서 확인할 수 있다.
- 일기 원문을 별도 복구 없이 다시 사용할 수 있다.
- 실패 기록과 일기의 연결이 그대로 유지된다.

단점은 다음과 같다.

- 월간 및 상세 조회가 실패 상태 UI까지 지원해야 한다.
- 현재 완성된 히스토리만 제공하는 조회 계약과 충돌한다.
- 새 키 재시도와 기존 실패 일기의 관계가 복잡해진다.
- 완성되지 않은 일기가 정상 일기처럼 보일 수 있다.

### 대안 3: 실패 일기는 소프트 삭제하고 생성 기록을 보존

이미지 정리는 DB 상태를 확인한 뒤 참조되지 않는 경우에만 수행한다.

장점은 다음과 같다.

- 실패 일기를 사용자 조회에서 숨기면서 멱등성 및 장애 이력을 보존한다.
- 실패 상태와 soft delete를 하나의 DB 트랜잭션으로 처리할 수 있다.
- 완료 예외 후 DB 성공 가능성이 있으면 이미지를 보존해 데이터 손실을 피한다.
- 확인된 고아 이미지는 best-effort로 정리할 수 있다.

단점은 다음과 같다.

- 실패 일기와 생성 기록이 DB에 계속 남는다.
- 상태 확인 실패 시 고아 객체를 보수적으로 남기게 된다.
- 객체 저장소 삭제 실패를 DB 트랜잭션으로 롤백할 수 없다.
- 장기적인 고아 객체 정리 작업과 모니터링이 필요할 수 있다.

## 결정

대안 3을 선택한다.

AI 또는 저장소 처리 실패 시 생성 행을 먼저 비관적 잠금으로 조회하고, 연결된 일기를 같은 순서로 잠근다. 하나의 트랜잭션에서 생성
상태를 `FAILED`로 바꾸고 오류 코드 및 완료 시각을 저장하며, 일기에는 같은 시각을 `deletedAt`으로 기록한다. 이미 실패 상태인 작업을
다시 처리하면 누락된 일기 soft delete를 복구한다.

실패 생성 기록은 삭제하지 않는다. 같은 멱등성 키의 재요청에는 저장된 실패를 반환하고 AI를 다시 호출하거나 사용량을 추가
차감하지 않는다. 새 키로 다시 시도하면 새로운 요청이므로 사용량을 새로 차감한다.

업로드 후 완료 처리에서 예외가 발생하면 생성 상태를 다시 조회하고 다음 기준으로 이미지 삭제 여부를 판단한다.

```text
생성 행 없음
→ 삭제

FAILED
→ 삭제

SUCCEEDED + 다른 Object Key 참조
→ 삭제

PROCESSING
→ 삭제 보류

SUCCEEDED + 같은 Object Key 참조
→ 삭제 보류

상태 확인 실패
→ 삭제 보류 및 경고 로그
```

객체 저장소 삭제는 best-effort 보상이다. 삭제 실패는 원래 생성 또는 완료 예외를 숨기지 않고 경고 로그로 남긴다. 불명확한
상태에서는 고아 객체가 남을 가능성을 감수하고 유효한 성공 이미지를 지우지 않는 fail-safe 방향을 선택한다.

## 긍정적 결과

- 생성 실패 상태와 미완성 일기 비노출이 하나의 트랜잭션으로 일치한다.
- 실패 기록을 이용해 같은 멱등 요청에 안정적인 결과를 반환한다.
- 완료 커밋 결과가 불명확할 때 성공 이미지의 데이터 손실을 피한다.
- 참조되지 않는 것으로 확인된 이미지는 즉시 정리를 시도한다.
- 실패나 삭제를 이용해 이미 소비한 생성 사용량을 복구하지 않는다.

## 부정적 결과와 트레이드오프

- 확인할 수 없는 상태에서는 고아 이미지가 남을 수 있다.
- 객체 저장소 삭제 실패를 자동으로 재시도하는 작업이 아직 없다.
- 실패 일기와 생성 기록의 실제 파기 시점은 별도 보존 정책이 필요하다.
- 프로세스가 업로드 직후 강제 종료되면 보상 코드 자체가 실행되지 않을 수 있다.
- DB 상태 재조회도 실패하면 원래 예외에 suppressed exception이 추가되어 장애 분석이 복잡해질 수 있다.

운영 중 고아 객체나 `PROCESSING` 잔존 건수가 의미 있게 늘어나면 객체 메타데이터 또는 저장 경로를 활용한 정리 작업, 실패 큐
또는 Outbox 기반 비동기 흐름을 추가로 검토한다. Generation ID 기반 Object Key는 기존 ADR의 결정이므로 AI 저장 어댑터를
통합할 때 해당 포트 계약과 현재 `ImageStorage` 계약을 먼저 일치시킨다.
