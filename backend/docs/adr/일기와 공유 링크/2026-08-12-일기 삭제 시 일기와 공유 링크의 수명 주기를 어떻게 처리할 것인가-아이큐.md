# 2026-08-12 일기는 소프트 삭제하고 공유 링크는 같은 트랜잭션에서 제거

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 일기, 생성 기록, 사용량과 공유 링크의 삭제 및 조회 수명 주기

## 배경

일기는 AI 생성 기록, 일일 생성 사용량과 공유 링크에 연결된다. 사용자가 일기를 삭제했을 때 모든 데이터를 물리 삭제하면 생성
실패 조사, 멱등 요청 판정과 사용량 감사 근거를 잃을 수 있다. 반대로 공유 링크까지 남기면 삭제한 일기에 외부 사용자가 계속
접근할 수 있다.

삭제 요청은 네트워크 재시도 때문에 같은 대상에 여러 번 도착할 수 있다. 이미 삭제됐거나 존재하지 않는 대상에 매번 오류를
반환하면 클라이언트가 최종 삭제 상태를 확인하기 어렵다. 데이터 이력 보존과 외부 접근 차단을 함께 만족하는 수명 주기를 결정해야
한다.

## 결정 요인

- 삭제 직후 월간 및 상세 조회에서 일기가 보이지 않아야 한다.
- 공개 공유 경로를 같은 트랜잭션에서 차단해야 한다.
- 생성 상태와 장애 조사에 필요한 기록을 보존해야 한다.
- 이미 소비한 AI 생성 사용량을 삭제로 복구하지 않아야 한다.
- 동일 DELETE 요청을 안전하게 재시도할 수 있어야 한다.
- 향후 실제 데이터 파기 정책을 적용할 수 있는 근거를 남겨야 한다.

## 고려한 대안

### 대안 1: 일기와 모든 연관 데이터를 물리 삭제

장점은 다음과 같다.

- 삭제 후 데이터가 남지 않는다.
- 조회 쿼리에 삭제 상태 조건이 필요하지 않다.
- 저장 공간을 즉시 회수할 수 있다.

단점은 다음과 같다.

- 생성 실패와 멱등 요청을 조사할 근거가 사라진다.
- 사용량 기록까지 지우면 이미 소비한 생성 비용을 복구한 것처럼 보일 수 있다.
- 객체 저장소 삭제와 DB 삭제가 원자적이지 않아 부분 실패 처리가 복잡하다.
- 연관 데이터의 FK 삭제 순서에 강하게 결합된다.

### 대안 2: 일기와 공유 링크를 모두 소프트 삭제

장점은 다음과 같다.

- 모든 데이터의 과거 상태를 보존할 수 있다.
- 복구 기능을 구현하기 쉽다.
- 물리 삭제 순서 문제를 줄일 수 있다.

단점은 다음과 같다.

- 공유 링크 조회마다 링크와 일기의 삭제 상태를 모두 확인해야 한다.
- 외부 접근 자격인 공유 링크가 데이터베이스에 계속 남는다.
- 모든 연관 테이블에 삭제 상태와 필터 정책이 필요하다.
- 현재 요구사항에 없는 복구 가능성을 위해 복잡도가 증가한다.

### 대안 3: 일기는 소프트 삭제하고 공유 링크는 즉시 제거

장점은 다음과 같다.

- 생성 및 사용량 이력을 보존하면서 일기를 사용자 조회에서 숨길 수 있다.
- 공유 링크를 물리 삭제해 공개 접근 경로를 즉시 차단한다.
- 일기 삭제와 공유 링크 제거를 하나의 DB 트랜잭션으로 처리할 수 있다.
- 이미 삭제된 대상에 대한 요청을 멱등하게 처리하기 쉽다.

단점은 다음과 같다.

- 모든 일기 조회가 `deletedAt IS NULL` 조건을 지켜야 한다.
- 소프트 삭제 데이터의 보관 기간과 실제 파기 정책이 별도로 필요하다.
- 이미 발급된 임시 이미지 URL은 자체 만료 전까지 유효할 수 있다.
- 객체 저장소 이미지는 삭제 요청만으로 즉시 제거되지 않는다.

## 결정

대안 3을 선택한다.

본인 소유의 활성 일기를 삭제하면 일기의 `deletedAt`을 기록하고, 연결된 공유 링크를 같은 트랜잭션에서 물리 삭제한다. 생성 기록과
일일 생성 사용량은 보존한다. 월간 및 상세 조회는 `deletedAt IS NULL`인 일기만 반환한다.

```text
DELETE 요청
→ 활성 일기 조회 및 소유권 확인
→ 연결된 공유 링크 삭제
→ 일기 deletedAt 기록
→ 한 트랜잭션으로 커밋
```

일기가 존재하지 않거나 이미 삭제된 경우에도 `204 No Content`를 반환한다. 다만 활성 상태인 다른 사용자의 일기를 삭제하려는
요청은 소유권 침해를 숨기지 않고 `403 FORBIDDEN`으로 처리한다.

삭제해도 이미 사용한 생성 횟수는 복구하지 않는다. 외부 AI와 저장소 자원을 이미 소비했기 때문이다.

## 긍정적 결과

- 삭제된 일기가 월간 및 상세 조회에 다시 노출되지 않는다.
- 공유 링크 제거와 일기 상태 변경이 함께 성공하거나 함께 롤백된다.
- 생성 실패, 멱등 요청과 사용량 감사에 필요한 DB 이력을 보존한다.
- 동일 DELETE 요청을 반복해도 최종 상태와 응답이 안정적이다.
- 삭제를 이용해 일일 생성 한도를 되돌리는 우회를 막는다.

## 부정적 결과와 트레이드오프

- 조회 저장소가 활성 일기 조건을 빠뜨리면 삭제 데이터가 노출될 수 있다.
- 소프트 삭제 행과 생성 이미지는 별도의 보존 기간 및 파기 작업이 필요하다.
- 공유 링크를 지워도 이미 발급된 presigned URL은 만료 전까지 직접 접근할 수 있다.
- 현재는 복구 API가 없으므로 소프트 삭제가 사용자 복구 기능을 의미하지 않는다.
- 개인정보 삭제 요청이 들어오면 운영상 soft delete와 법적 파기를 구분해 처리해야 한다.

현재 삭제 API의 목적은 사용자 히스토리와 공개 공유 경로에서 즉시 제거하는 것이다. 장기 보관 기간, 이미지 객체 정리와 완전 파기는
운영 및 개인정보 정책이 정해질 때 별도 결정한다.
