# 2026-08-12 월 전체 날짜와 생성 완료 일기를 제공하는 타임라인

- 작성일: 2026-08-12
- 작성자: 아이큐
- 결정 대상: 월간 조회의 날짜 완전성, 동일 날짜의 복수 일기, 노출 상태와 정렬 기준

## 배경

프론트엔드는 월간 달력에서 일기가 있는 날짜를 표시하고, 선택한 일기의 상세 화면으로 이동해야 한다. 서버가 일기가 있는 날짜만
반환하면 프론트엔드가 요청 연월의 날짜를 다시 생성하고 응답과 병합해야 한다. 날짜마다 단일 일기만 반환하면 같은 날짜에 여러
일기를 작성할 수 있는 현재 데이터 모델을 표현할 수 없다.

또한 일기 행은 생성 작업보다 먼저 저장된다. 생성이 아직 처리 중이거나 실패한 일기까지 히스토리에 노출하면 사용자가 열 수 없는
미완성 결과가 달력에 나타난다. 월간 응답이 어떤 날짜와 생성 상태를 포함하고, 같은 날짜의 결과 순서를 어떻게 보장할지 결정해야
한다.

## 결정 요인

- 프론트엔드가 별도의 달력 날짜 보정 없이 응답을 렌더링할 수 있어야 한다.
- 같은 날짜에 여러 일기가 있어도 모든 결과를 표현해야 한다.
- 상세 조회로 이동할 수 있도록 각 항목에 일기 ID가 있어야 한다.
- 삭제되거나 생성이 완료되지 않은 일기는 히스토리에 노출하지 않아야 한다.
- 같은 데이터의 재조회에서 항목 순서가 달라지지 않아야 한다.
- `exist`와 실제 항목 목록이 서로 모순되지 않아야 한다.

## 고려한 대안

### 대안 1: 일기가 있는 날짜만 반환

```json
[
  {
    "date": "2026-08-06",
    "items": []
  }
]
```

장점은 다음과 같다.

- 응답 크기가 가장 작다.
- 서버가 빈 날짜를 생성하지 않아도 된다.
- 히스토리 목록 용도로는 단순하다.

단점은 다음과 같다.

- 프론트엔드가 요청 월의 전체 날짜를 만들고 응답과 병합해야 한다.
- 달력 표시 로직이 클라이언트마다 중복될 수 있다.
- 빈 날짜와 응답 누락을 구분하기 어렵다.

### 대안 2: 전체 날짜를 반환하되 날짜마다 단일 nullable 일기를 제공

```json
{
  "date": "2026-08-06",
  "diary": null
}
```

장점은 다음과 같다.

- 프론트엔드가 월 전체 날짜를 바로 렌더링할 수 있다.
- 날짜별 일기가 하나라는 정책에서는 응답이 단순하다.
- 빈 날짜를 명시적으로 표현할 수 있다.

단점은 다음과 같다.

- 같은 날짜의 복수 일기를 표현할 수 없다.
- 추후 복수 일기를 허용하면 응답 형태를 깨뜨려야 한다.
- nullable 객체와 존재 여부 필드가 중복될 수 있다.

### 대안 3: 전체 날짜와 날짜별 items 목록을 반환

```json
{
  "date": "2026-08-06",
  "exist": true,
  "items": [
    {
      "id": "6b66acba-0136-4822-8a59-f355dd7c977d",
      "title": "비가 와도 나는 괜찮았다.",
      "thumbnailUrl": "https://presigned-s3-url.example/..."
    }
  ]
}
```

장점은 다음과 같다.

- 프론트엔드는 응답을 그대로 월간 달력에 매핑할 수 있다.
- 빈 날짜와 복수 일기를 모두 일관된 구조로 표현한다.
- 각 항목의 일기 ID로 상세 조회를 호출할 수 있다.
- 날짜별 항목을 추가해도 응답 구조가 바뀌지 않는다.

단점은 다음과 같다.

- 일기가 없는 날짜도 포함해 최대 31개의 날짜 객체를 반환한다.
- `exist`와 `items`를 독립적으로 만들면 값이 불일치할 수 있다.
- 어떤 생성 상태를 노출할지 별도 기준이 필요하다.

## 결정

대안 3을 선택한다.

요청한 연월의 첫날부터 마지막 날까지 모든 날짜를 오름차순으로 반환한다. 날짜별 `items`는 삭제되지 않은 사용자 일기 중 생성
상태가 `SUCCEEDED`인 결과만 포함한다. 일기 행이 있더라도 생성이 `PROCESSING` 또는 `FAILED`이면 월간 히스토리에 노출하지 않는다.

같은 날짜의 복수 일기를 허용하고 다음 순서로 정렬한다.

```text
diaryDate ASC
→ createdAt ASC
→ id ASC
```

일기 ID는 생성 시각까지 같은 경우에도 완전한 순서를 만드는 마지막 tie-breaker다. `exist`는 별도 저장 값이 아니라
`items.isEmpty()`의 반대 값으로 계산한다.

```text
items가 비어 있음
→ exist: false

items가 하나 이상 있음
→ exist: true
```

## 긍정적 결과

- 프론트엔드는 월의 날짜를 다시 계산하거나 병합하지 않고 응답을 렌더링할 수 있다.
- 일기가 없는 날짜는 `exist: false`, `items: []`로 일관되게 표현된다.
- 같은 날짜에 여러 일기가 있어도 각 ID로 상세 조회에 진입할 수 있다.
- 월간 히스토리에는 생성 완료 결과만 노출되어 미완성 썸네일이 나타나지 않는다.
- 고유 ID를 마지막 정렬 기준으로 사용해 반복 조회의 순서가 안정적이다.

## 부정적 결과와 트레이드오프

- sparse 목록보다 응답 객체 수가 많지만 한 달 최대 31개로 범위가 제한된다.
- 처리 중이거나 실패한 생성을 사용자에게 보여주려면 별도의 상태 조회 또는 계약 변경이 필요하다.
- `exist`는 `items`에서 파생할 수 있는 중복 표현이지만 프론트엔드 달력 분기를 단순화하기 위해 유지한다.
- 월간 항목에는 임시 URL 만료 시각이 없으므로 URL이 만료되면 월간 API를 다시 조회해야 한다.

월간 응답은 작업 상태 모니터가 아니라 완성된 일기 히스토리다. 향후 처리 진행률을 노출해야 한다면 이 계약에 상태를 섞지 않고 별도
생성 상태 API 또는 명시적인 응답 확장을 검토한다.
