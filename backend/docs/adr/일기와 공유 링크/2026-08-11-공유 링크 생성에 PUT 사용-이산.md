# 2026-08-11 공유 링크 생성에 PUT 사용

- 작성일: 2026-08-11
- 작성자: 이산
- 결정 대상: 그림일기별 단일 공유 링크의 생성 및 기존 링크 반환 API

## 배경

그림일기에는 하나의 공유 링크만 존재할 수 있다. 사용자가 공유 버튼을 여러 번 누르거나 네트워크 문제로 요청을 재시도하더라도
새로운 링크를 계속 생성하지 않고 기존에 생성된 동일한 링크를 반환해야 한다.

공유 링크가 없을 때 생성하고 이미 존재할 때 기존 링크를 반환하는 동작을 `POST`와 `PUT` 중 어떤 HTTP 메서드로 표현할지
결정해야 한다.

## 결정 요인

- 그림일기 하나에 공유 링크 하나만 존재해야 한다.
- 같은 요청을 반복해도 최종 서버 상태가 달라지지 않아야 한다.
- API만 보고 그림일기의 단일 하위 리소스라는 의미를 이해할 수 있어야 한다.
- 최초 생성과 기존 링크 반환을 구분할 수 있어야 한다.
- 동시 요청에도 데이터베이스에서 중복 생성을 방지해야 한다.

## 고려한 대안

### 대안 1: POST로 요청마다 새로운 공유 링크 생성

장점은 다음과 같다.

- 일반적인 컬렉션 리소스 생성 방식과 같다.
- 하나의 그림일기에 여러 공유 링크를 제공하는 요구사항으로 확장하기 쉽다.

단점은 다음과 같다.

- 요청을 반복할 때마다 새로운 링크가 생성될 수 있다.
- 그림일기와 공유 링크의 1:1 관계를 API가 표현하지 못한다.
- 중복 요청을 막기 위한 별도 멱등성 처리가 필요하다.

### 대안 2: POST로 생성하되 기존 링크가 있으면 반환

장점은 다음과 같다.

- 서버 로직으로 공유 링크를 하나만 유지할 수 있다.
- 기존 링크를 재사용한다는 요구사항을 만족한다.

단점은 다음과 같다.

- `POST` 자체는 멱등성을 보장하지 않으므로 API 의미와 실제 동작이 다르게 보일 수 있다.
- 요청 대상이 단일 공유 링크라는 점이 URI와 메서드에 충분히 드러나지 않는다.

### 대안 3: PUT으로 공유 링크가 존재하도록 보장

장점은 다음과 같다.

- 동일 요청을 반복해도 최종 상태가 같아야 한다는 의미를 표현한다.
- `/diaries/{diaryId}/share-link`를 그림일기의 단일 하위 리소스로 나타낸다.
- 기존 링크가 있으면 그대로 반환하는 동작과 자연스럽게 맞는다.

단점은 다음과 같다.

- `PUT`이 중복 방지를 자동으로 제공하지 않으므로 조회 로직과 DB 고유 제약이 필요하다.
- 서버가 공유 링크 ID를 생성하므로 완전한 리소스 대체 형태의 `PUT`과는 차이가 있다.

## 결정

대안 3을 선택한다.

```http
PUT /api/v1/diaries/{diaryId}/share-link
```

서버는 요청을 다음과 같이 처리한다.

```text
그림일기와 생성 상태 확인
→ 기존 공유 링크 조회
→ 기존 링크가 있으면 반환
→ 기존 링크가 없으면 생성 후 반환
```

새로운 공유 링크를 생성한 경우 `201 Created`, 기존 링크를 반환한 경우 `200 OK`를 사용한다. 데이터베이스의
`share_links.generation_id`에는 고유 제약을 두어 동시 요청에도 생성 결과별 공유 링크가 하나만 저장되도록 한다.

## 긍정적 결과

- 반복 요청에도 동일한 공유 링크를 제공한다.
- 그림일기별 단일 공유 링크라는 관계를 API가 표현한다.
- 클라이언트가 별도의 멱등성 키를 관리하지 않아도 된다.
- 최초 생성과 기존 링크 반환을 HTTP 상태 코드로 구분할 수 있다.

## 부정적 결과와 트레이드오프

- 기존 링크 조회와 신규 생성 사이의 동시성 충돌을 별도로 처리해야 한다.
- `PUT`을 사용하더라도 애플리케이션 로직과 DB 고유 제약 없이는 중복을 방지할 수 없다.
- 향후 그림일기 하나에 여러 공유 링크를 허용하면 URI와 메서드를 다시 검토해야 한다.
