# 운영 원본 이미지의 일일 R2 백업

자동 백업은 기본적으로 꺼져 있다. 활성화하면 매일 한국 시간 00시에 현재 운영 환경의 원본을 S3에서 R2로 복사하고 검증한다. 기본 주기는 24시간이며, 서버 시작 시 즉시 백업하지 않는다.

## 활성화

운영 경로 분리와 최초 백업 상태를 확인한 뒤 운영 서버의 환경 변수에 설정한다.

```properties
DEPLOY_ENV=prod
HARUDLE_GENERATION_ADAPTERS_ENABLED=true
R2_ENABLED=true
R2_BACKUP_SCHEDULER_ENABLED=true
R2_BACKUP_CRON=0 0 0 * * *
R2_BACKUP_ZONE=Asia/Seoul
R2_BACKUP_BATCH_SIZE=100
```

S3와 R2 버킷·endpoint·자격 증명은 [R2 설정](r2-storage-configuration.md)을 따른다. R2에는 해당 운영 백업 버킷의 객체 읽기·쓰기 권한이 필요하다. 원본 키와 폴더 구조는 유지하고 R2는 비공개로 둔다. 개발 서버에는 운영 자격 증명을 넣지 않는다.

| 변수 | 기본값 | 동작 |
| --- | --- | --- |
| `R2_BACKUP_SCHEDULER_ENABLED` | `false` | 자동 실행 활성화. S3/R2가 구성된 `prod`에서만 허용 |
| `R2_BACKUP_CRON` | `0 0 0 * * *` | Spring 6필드 cron. 기본은 매일 00시 |
| `R2_BACKUP_ZONE` | `Asia/Seoul` | 예약 시간대. 잘못된 시간대는 서버 시작 시 거절 |
| `R2_BACKUP_BATCH_SIZE` | `100` | 한 번에 조회할 대상 수. 1~1000 |

자동 백업이 꺼져 있으면 위 스케줄러 설정을 바인딩하거나 검증하지 않는다. R2 연결과 한 장의 내부 백업·복구 서비스는 기존처럼 dev에서도 테스트할 수 있다. 자동 백업을 켠 상태에서 dev 또는 S3/R2 환경 불일치, 누락된 저장소 설정, 잘못된 cron·시간대·조회 크기는 시작 단계에서 거절한다.

## 대상 조회와 처리

1. PostgreSQL advisory lock을 확보한다. 다른 서버가 백업 중이면 기다리지 않고 이번 실행을 건너뛴다. 잠금 상태를 확인하지 못하면 백업을 시작하지 않는다.
2. 실행 시작 시각을 대상 완료 시각의 상한으로 고정한다. `diary_generations`의 `SUCCEEDED` 기록 중 완료 시각이 상한 이하이고 이미지 키가 `harudle/generated/diary-images/prod/` 아래인 대상을 조회한다.
3. 완료 시각과 UUID 오름차순으로 100개씩 순회한다. 두 값으로 다음 조회 위치를 정하므로 같은 완료 시각의 대상도 빠뜨리지 않는다. 이미지 바이트와 스토리보드 전체를 DB 조회에 포함하지 않는다.
4. 각 대표 키를 기존 `ImageBackupService.backup()`에 전달한다. 원본 대표 키는 그대로 사용하고 `image-960.webp`는 같은 폴더의 PNG/JPG/WebP 원본 후보를 확인한다. 파생 이미지는 백업하지 않는다.
5. 원본 바이트와 MIME을 조건부 PUT으로 복사한다. 신규 업로드와 이미 존재하는 백업 모두 S3/R2 전체 MIME·크기·SHA-256이 같은지 확인한다. 기존 백업은 덮어쓰거나 삭제하지 않는다.
6. 한 대상의 실패나 S3 원본 없음은 별도로 집계하고 다음 대상을 처리한다. DB 조회 실패는 실행 전체를 중단한다. 종료 요청으로 스레드가 중단되면 현재 저장소 호출이 끝난 뒤 다음 대상 조회·처리를 시작하지 않는다.
7. 완료·실패·중단 후 같은 DB 연결에서 잠금을 해제한다. 해제 상태가 불명확하면 연결을 abort하여 세션 잠금을 가진 연결을 풀에 반환하지 않는다.

백업은 전용 스케줄러 스레드에서 수행하고 기존 생성 정리 작업은 기본 스케줄러에서 수행한다. 저장소 통신 동안 JPA 트랜잭션을 유지하지 않는다. 실행 잠금용 DB 연결 하나는 백업 실행 동안 보유하며, 잠금 SQL 호출에는 10초 query timeout을 설정한다.

매 실행에서 전체 대상을 다시 확인한다. 지난 24시간의 기록만 조회하지 않으므로 실패 대상은 다음 실행에서 재시도할 수 있다. 별도 백업 기록·진행 위치 테이블은 만들지 않으며, 기존 백업도 매일 S3/R2에서 읽어 검증하는 비용이 발생한다. 백업 중 새로 완료된 생성은 다음 실행에서 처리한다.

## 실행 결과 확인과 재실행

- `event=image_backup_batch_completed`: 실행 ID, 환경, S3 버킷, 대상 상한 시각, 처리·신규 업로드·기존 백업 검증·원본 없음·실패 건수와 소요 시간.
- `event=image_backup_completed`: 기존 단일 백업 로그. 대표·원본 키, S3/R2 버킷과 MIME·크기·SHA-256, 업로드 결과와 검증 결과.
- `event=image_backup_batch_target_failed`: 실행 ID, 생성 기록 UUID와 실패 코드. 예외 원문과 자격 증명을 출력하지 않는다.
- `event=image_backup_schedule_skipped reason=ALREADY_RUNNING`: 다른 실행이 잠금을 보유함.
- `event=image_backup_schedule_failed`: 잠금·배치 실행 오류. 다음 예약 실행은 유지된다.

`COMPLETED`는 모든 조회 대상 검증 완료, `PARTIAL_FAILURE`는 원본 없음 또는 개별 실패 발생, `INTERRUPTED`는 종료 요청에 따라 남은 대상을 처리하지 않음, `FAILED`는 DB 조회 등 실행 자체의 실패다. 대상이 없으면 처리 수 0의 `COMPLETED`다. 이미 존재하는 객체는 내용을 검증한 경우에만 기존 백업 검증 수에 포함한다.

서버 재시작으로 실행이 중단되면 다음 예약에서 처음부터 다시 순회한다. 조건부 PUT과 동일성 검증으로 이전에 완료한 백업을 보존한다. 서버가 예약 시각에 중단돼 있으면 지나간 예약을 자동 보충하지 않고 다음 예약에서 실행한다. 장시간 실행이 다음 예약까지 이어져도 동시 실행을 시작하지 않는다.

복구 절차는 [R2 수동 복구 가이드](image-recovery.md#r2-백업-원본으로-복구)를 따른다. 스케줄러는 S3 복구나 AI 재생성을 실행하지 않는다. 실제 운영 활성화 시 다음 예약 이후 배치 완료 로그, 대상별 검증 로그와 R2 원본의 존재를 확인한다.

## 자동 테스트

일일 예약의 다음 두 시각이 한국 시간 00시이며 24시간 간격인지 직접 계산한다. 실제 24시간을 기다리지 않는다. 배치 조회·커서·실패 후 계속 처리·원본 없음·기존 백업 검증·첫 대상 완료 후 중단과 재실행, 비활성 및 잘못된 설정, 다른 작업과 실행 스레드 분리를 검증한다.

잠금 테스트는 같은 연결의 획득·해제 순서와 실패 시 연결 abort를 확인한다. PostgreSQL 통합 테스트는 다른 세션의 실행 차단과 연결 풀 반환 후 잠금 해제, 대상 조회의 같은 시각 UUID 정렬·환경·상태·상한 시각 필터를 확인한다. 이 통합 테스트에는 Docker가 필요하며, Docker가 없는 실행 환경에서는 해당 테스트가 건너뛰어진다.
