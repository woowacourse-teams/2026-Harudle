# 프로필 이미지 기능과 처리 흐름

- 상태: 백엔드 구현 완료. 프론트엔드 연결과 실제 배포 환경 확인은 별도로 진행한다.
- 설계 결정과 이유: [프로필 이미지 ADR](<adr/profiles-and-categories/2026-10-20_프로필 이미지 선택과 개인 이미지 업로드.md>)

회원은 기본 이미지 10개 중 하나를 선택하거나 개인 사진을 업로드할 수 있다.
개인 사진은 **파일 검사와 변환, 새 파일 저장, 회원의 사진 정보 변경, 이전 파일 삭제** 순서로 처리한다.
저장 성공 후 화면에서 정보를 다시 조회하면 새 사진을 표시한다.

S3는 사진 파일을 보관하는 저장소다. DB는 회원이 어떤 사진을 사용하는지 기록하는 데이터베이스다.
이 문서는 실제 처리 순서를 설명한다. 방식을 선택한 이유와 대안은 위의 ADR에 기록한다.

## 사용할 수 있는 기능

| 기능 | 동작 |
| --- | --- |
| 신규 가입 | 기본 이미지 1~10번 중 하나를 랜덤 배정한다. |
| 기존 회원 | 현재 기본 이미지 번호를 유지한다. |
| 기본 이미지 선택 | 선택한 번호를 저장하고 개인 사진 연결을 해제한다. |
| 개인 사진 업로드 | 개인 사진을 우선해서 보여준다. 닉네임과 기본 이미지 번호는 유지한다. |
| 닉네임 수정 | 기존 별도 API로 저장한다. 이미지 변경과 함께 묶지 않는다. |
| 이전 글과 댓글 | 다시 조회하면 작성자의 현재 사진을 보여준다. |

기본 이미지 파일은 프론트엔드가 제공한다. 6~10번 파일 추가와 선택 화면은 프론트엔드 작업에서 진행한다.
백엔드는 이미 10번까지 배정하므로 배포 시점에는 해당 파일도 제공되어야 한다.

## API

| 요청 | 전달하는 값 | 성공 응답 |
| --- | --- | --- |
| `PATCH /api/v1/me/profile-image` | JSON 본문의 `imageCode` 1~10 | 본문 없는 `204` |
| `POST /api/v1/me/profile-image` | 파일 전송 형식인 `multipart/form-data`의 `image` 항목에 사진 한 장 | 본문 없는 `204` |
| `GET /api/v1/me` | 로그인 인증 정보 | `200`과 현재 프로필, 이미지 주소, 만료 시각 |

이미지 변경과 내 정보 조회는 `Authorization: Bearer {accessToken}` 헤더로 로그인 인증 정보를 보낸다.
로그인 계정이 연결되어 있고, 탈퇴하지 않았으며, 닉네임과 기본 이미지 번호가 배정된 회원만 이미지를 변경할 수 있다.
상세 요청 예시와 오류 응답은 [인증 API 명세](api-spec.md), 피드 응답은 [피드 API 명세](feed-api-spec.md)를 참고한다.

## 이미지 처리 규칙

| 항목 | 처리 |
| --- | --- |
| 원본 파일 | JPEG와 PNG를 최대 5MiB, 즉 5,242,880바이트까지 허용한다. |
| 형식 검사 | 확장자와 요청에 적힌 형식만 믿지 않고 실제 파일 내용을 읽어 확인한다. |
| 픽셀 수 | 전체 픽셀을 읽기 전에 가로와 세로를 확인한다. 두 픽셀 수를 곱한 값이 2500만을 넘으면 거절한다. |
| 자르기와 축소 | 가운데를 정사각형으로 자른 뒤 최대 512 × 512픽셀로 줄인다. 작은 사진은 확대하지 않는다. |
| 저장 형식 | 이미지 파일 형식인 WebP(웹피)로 변환한다. 품질 80과 압축 설정 `-m 6`을 사용한다. |
| 부가 정보 | 회전 보정은 하지 않으며, 위치 정보 등 원본의 부가 정보는 결과 파일에 복사하지 않는다. |
| 보관 범위 | 변환한 프로필 사진 한 장만 저장한다. 원본과 변경 이력은 보관하지 않는다. |

1600 × 800픽셀 사진은 가운데 800 × 800픽셀을 자른 뒤 512 × 512픽셀로 줄인다.
2000 × 300픽셀 사진은 가운데 300 × 300픽셀을 자르고 확대하지 않는다.
사용자가 직접 자르는 위치를 조절하는 기능은 없으므로 사진 가장자리의 내용이 잘릴 수 있다.
프로필 전용 검사는 기존 공용 업로드 제한과 별도로 적용한다.

## 개인 사진을 업로드하는 순서

1. **요청을 받는다.** `CurrentUserController`가 인증 정보에서 회원을 확인하고 `image` 파일을 받는다.
2. **회원과 원본 파일을 검사한다.** `ProfileImageUploadService`가 변경 가능한 회원인지 확인하고 파일을 읽는다. `ProfileImageProcessor`가 실제 형식과 용량, 픽셀 수를 검사한다.
3. **사진을 변환한다.** `ProfileImageProcessor`가 가운데 자르기와 축소를 처리하고, `CwebpProfileImageEncoder`가 WebP로 변환한다.
4. **새 파일을 저장한다.** `S3ProfileImageStorage`가 매번 새 경로에 파일을 저장하고 그 경로를 반환한다. 기존 파일은 유지한다.
5. **회원의 사진 정보를 바꾼다.** `ProfileImageChangeService`가 회원 상태를 다시 확인하고 DB의 사진 경로를 변경한다. 이전 개인 사진이 있으면 삭제 작업도 함께 저장한다.
6. **이전 파일을 정리한다.** DB 저장이 확정되면 `ProfileImageCleanupService`가 해당 회원의 삭제 대기 작업을 처리한다. 과거에 실패한 작업도 함께 확인한다.

DB 트랜잭션은 관련 변경을 함께 확정하거나 취소하는 처리 범위다.
회원의 사진 경로와 삭제 작업은 같은 트랜잭션으로 저장한다.
회원 정보를 잠가 동시에 들어온 DB 변경을 순서대로 처리한다.
시간이 걸리는 이미지 변환과 S3 업로드 중에는 이 잠금을 잡지 않는다.

## 기본 이미지를 선택하는 순서

1. 요청을 받은 `ProfileImageUploadService`가 `ProfileImageChangeService`를 호출해 회원과 선택한 이미지 번호를 확인한다.
2. 같은 DB 트랜잭션에서 기본 이미지 번호를 바꾸고 개인 사진 경로를 비운다. 이전 개인 사진이 있으면 삭제 작업도 기록한다.
3. DB 저장이 확정되면 `ProfileImageCleanupService`가 해당 회원의 삭제 대기 작업을 처리한다.

이 과정에서는 새 파일을 변환하거나 S3에 업로드하지 않는다. 여러 회원이 공유하는 기본 이미지 파일은 그대로 사용한다.

## DB와 S3에 남는 값

DB에는 회원이 사용하는 이미지 정보를, 기존 비공개 S3에는 실제 개인 사진 파일을 저장한다.

| 저장 위치 | 저장하는 값 |
| --- | --- |
| `users.profile_image_code` | 기본 이미지 번호 1~10. 개인 사진을 사용해도 유지한다. |
| `users.profile_image_object_key` | 개인 사진의 S3 저장 경로. 개인 사진이 없으면 값이 없음을 뜻하는 `null`이다. |
| `profile_image_cleanup_tasks` | 삭제할 파일 경로, 회원 ID, 생성 시각, 삭제 가능한 시각인 `delete_after`. |

저장 경로는 S3 안에서 파일을 찾는 값이고, 조회 주소는 브라우저가 사진을 열 때 사용하는 주소다.
개인 사진 파일은 새 파일을 구분하는 식별자인 UUID를 만들어 매번 다른 경로에 저장한다.

```text
harudle/profile-images/{DEPLOY_ENV}/{회원ID}/{새로운UUID}.webp
```

DB 구조 변경 파일은 V28~V31으로 구현했다.
V31은 기존 작업을 보존하면서 `next_attempt_at`을 `delete_after`로 바꾸고 회원별 조회 인덱스를 만든다.
로컬 테스트 DB 적용은 검증했으며, 배포 DB의 실제 적용 여부는 배포 시 확인한다.

## 중간에 실패하면 어떻게 되는가

| 실패한 단계 | 처리 |
| --- | --- |
| 검사 또는 변환 | 기존 프로필을 유지하고 S3 업로드를 시작하지 않는다. |
| S3 업로드 | 기존 프로필을 유지한다. 결과가 불명확한 새 파일은 삭제 작업에 기록하고, 1분 유예 후 해당 회원이 이미지를 다시 변경할 때 확인한다. |
| DB 저장 | 실패가 확정되면 기존 프로필을 유지하고 새 파일을 정리한다. 결과가 불명확하면 현재 사용 중인지 확인한 뒤 삭제한다. |
| 이전 사진 삭제 | 새 프로필과 실패한 작업 기록을 유지한다. 해당 회원의 다음 이미지 변경에서 다시 시도한다. |
| 조회 주소 발급 | `503 PROFILE_IMAGE_STORAGE_ERROR`를 반환한다. 저장된 프로필은 바꾸지 않는다. |

정기 실행 없이 이미지 변경 시 해당 회원의 작업 중 `delete_after`가 지난 것만 정리한다.
이 값은 삭제 가능한 시각이며, 시간이 되어도 자동 실행하지 않는다.
삭제 전 회원을 잠금 조회해 진행 중인 DB 저장을 기다리고, 현재 사용하는 사진은 삭제하지 않는다.
여러 회원이 공유하는 기본 이미지도 삭제하지 않는다.

실패한 작업은 기록을 유지하므로, 회원이 이미지를 다시 변경하지 않으면 파일이 계속 남을 수 있다.

삭제 작업은 회원이 DB에서 삭제되어도 남아 있어야 한다.
따라서 다른 테이블에 해당 회원이 존재하는지 검사하는 제약인 외래 키를 삭제 작업의 회원 ID에 두지 않는다.
DB 장애로 삭제 작업도 기록할 수 없으면 경고 로그를 남기고 파일을 보존한다.

## 사진을 조회하는 순서

1. **현재 회원 정보를 읽는다.** 내 정보는 `CurrentUserService`, 피드와 댓글 및 알림은 `DefaultPublicProfileReader`가 조회한다.
2. **사용할 사진을 고른다.** 두 경로 모두 `ProfileImageUrlResolver`를 사용한다. 개인 사진 경로가 있으면 그 사진을, 없으면 기본 이미지를 선택한다.
3. **주소와 만료 시각을 응답에 담는다.** 브라우저는 반환된 주소로 사진을 직접 가져온다.

공개 프로필은 회원 ID를 모아 한 번에 조회하고, 중복되지 않는 회원마다 주소를 만든다.

| 사용할 이미지 | 반환하는 주소 | `profileImageUrlExpiresAt` |
| --- | --- | --- |
| 개인 사진 | 정해진 시간 동안 비공개 사진에 접근할 수 있는 서명 URL | 주소 만료 시각 |
| 기본 이미지 | `PROFILE_IMAGE_BASE_URL`과 번호로 만든 고정 주소 | `null` |

기본 이미지 번호와 개인 사진 경로가 모두 없으면 내 정보의 이미지 주소와 만료 시각은 모두 `null`이다.
DB에는 저장 경로만 보관하고 서명 URL은 조회할 때 새로 만든다.
주소 발급 시 백엔드가 S3에서 사진 파일을 내려받지는 않는다.
개인 사진 주소의 기본 유효 시간은 15분이며 `S3_ACCESS_URL_TTL` 설정을 따른다.

| 응답 위치 | 이미지 주소 | 만료 시각 |
| --- | --- | --- |
| 내 정보 | `profileImageUrl` | `profileImageUrlExpiresAt` |
| 피드와 댓글의 작성자 | `author.profileImageUrl` | `author.profileImageUrlExpiresAt` |
| 알림을 발생시킨 회원 | `actor.profileImageUrl` | `actor.profileImageUrlExpiresAt` |

탈퇴 회원의 댓글은 이미지 주소와 만료 시각이 모두 `null`이고, 알림의 탈퇴한 행위자는 `actor: null`이다.

프론트엔드는 저장 성공 후 `GET /api/v1/me`와 피드를 다시 조회해 새 사진을 반영한다.
개인 사진 주소가 만료되면 사진을 보여주는 해당 API를 다시 조회해 새 주소를 받는다.
이 화면 처리는 프론트엔드에서 연결할 부분이다. 다른 사람이 이미 열어둔 화면은 실시간으로 갱신하지 않는다.

## 실행 설정

기존 `S3_BUCKET`, `DEPLOY_ENV`, `S3_ACCESS_URL_TTL`, `PROFILE_IMAGE_BASE_URL`을 사용한다.
프로필 경로를 위한 별도 환경 변수는 추가하지 않는다.
S3 프로필 저장소는 기존 연결과 같이 `harudle.generation.adapters.enabled=true`일 때 등록된다.
WebP 변환 도구인 `cwebp`는 배포용 Docker 이미지에 포함되어 있고, 로컬 실행 환경에도 필요하다.
실제 S3 업로드, 반환 주소로 사진 열기, 교체 후 이전 파일 삭제는 개발 배포 환경에서 별도로 확인한다.
