# 생성 이미지 정리

업로드마다 `generated-prefix/{generationId}/{uploadAttemptId}/image.{ext}` 키를 새로 만든다.
요청 멱등키는 변경하지 않으며, SDK 내부 재시도는 같은 업로드 키를 사용한다.
PUT 성공 뒤 생성 완료 트랜잭션에서 해당 키를 그대로 채택한다. 별도의 COPY나 테이블은 없다.
PUT 예외 시 즉시 DELETE하지 않는다. 서버에서 PUT이 나중에 완료될 수 있기 때문이다.

## 정리 작업

- 생성 어댑터가 활성화되면 정리 스케줄러도 활성화된다.
- 기본 10분 간격으로 전체 prefix를 100개씩 페이지 조회한다. 실행마다 처음부터 다시 순회한다.
- S3 LastModified 기준 1시간 이상 지난 객체만 검사한다. 최소 나이는 `ORPHAN_IMAGE_MINIMUM_AGE`,
  실행 간격은 `ORPHAN_IMAGE_CLEANUP_INTERVAL`로 조절한다.
- 기존 `{generationId}/image.{ext}` 형식도 인식한다. 다른 파일명, 경로, 확장자는 삭제하지 않는다.
- PROCESSING은 보류하고 기존 만료 스케줄러가 먼저 실패로 확정하도록 한다.
- FAILED, 생성 기록 없음, SUCCEEDED의 미채택 키만 삭제 후보로 삼는다.
- 다른 생성 기록 또는 프롬프트가 참조하는 객체는 유지한다. 삭제된 일기의 성공 이미지도 참조가 남으면 유지한다.
- DB 조회 또는 삭제 실패 시 보류한다. 다음 실행에서 다시 시도한다.
- 성공한 DELETE 이후 늦은 PUT이 나타나더라도 이후 전체 순회에서 다시 발견한다.

안전성은 생성의 최종 상태가 다시 PROCESSING으로 바뀌지 않고, 생성 키를 다른 작업이 재사용하지 않는
현재 흐름에 의존한다. generated-prefix는 생성 이미지 전용으로 유지한다.
다른 DB를 사용하는 운영/개발 환경은 버킷 또는 prefix를 분리해야 한다.
다른 환경의 객체는 현재 DB에 생성 기록이 없는 것으로 판단되기 때문이다.
운영 중 폐기된 키를 수동으로 다른 생성/프롬프트에 연결하는 작업은 정리 작업과 동시에 하지 않는다.

## 배포 확인

애플리케이션 IAM 역할에 기존 객체 접근 권한 외에 버킷 ARN 대상 `s3:ListBucket`이 필요하다.
가능하면 `s3:prefix` 조건으로 `${generated-prefix}/` 조회만 허용한다.
`s3:DeleteObject`는 해당 prefix의 객체 ARN에 허용한다. 실제 IAM 변경은 별도 배포 작업이다.

버킷 Versioning이 활성화되어 있으면 DELETE는 과거 버전까지 영구 삭제하지 않는다.
저장 비용 회수에는 비현재 버전 Lifecycle 정책이 별도로 필요하다.
정상 이미지도 같은 prefix를 사용하므로 해당 prefix 전체에 현재 객체 만료 정책을 걸지 않는다.

전체 조회와 객체별 DB 조회 비용은 이미지 수에 비례한다. 규모가 커지면 업로드 시도 기록과
정리 큐를 도입하고 전체 순회의 빈도를 낮출 수 있다.
