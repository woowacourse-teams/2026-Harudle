# 사용자·콘텐츠 신고 접수 (#424)

사용자·콘텐츠 신고 접수의 정책과 코드 흐름을 설명한다.
관리자의 신고 조회·심사·제재는 후속 #427에서 구현한다.

## 차단보다 먼저 구현하는 이유

신고는 접수와 보존이라는 한 경로를 추가한다. 차단은 피드 목록·상세·댓글·공유·알림의 노출 규칙,
페이지네이션과 캐시까지 바꿔야 하므로 영향 범위가 더 넓다. 신고 접수만으로 노출이나 계정 상태를 바꾸지 않는다.

## 이번 정책

| 항목 | 동작 |
| --- | --- |
| 신고자 | OAuth가 연결된 현재 활성 회원. 클라이언트가 보낸 신고자 ID를 사용하지 않음 |
| 대상 | 사용자, 공개 피드, 공개 피드의 댓글 |
| 작성자 | 서버가 대상에서 조회. 본인과 본인 콘텐츠에 대한 신고는 거절 |
| 사유 | 스팸·광고, 괴롭힘·욕설, 부적절한 콘텐츠, 기타 |
| 상세 | 선택 입력. 앞뒤 공백 제거 후 최대 500 코드 포인트. NUL·고립 서로게이트는 거절 |
| 중복 | 같은 회원·유형·대상이면 기존 접수 ID를 반환. 최초 사유와 상세는 보존 |
| 대상 삭제 | 새 접수 시 공개 대상을 확인. 접수 뒤 삭제돼도 대상 ID와 작성자 ID의 기록은 보존 |
| 탈퇴 댓글 | 공개 댓글의 콘텐츠 신고는 허용. 탈퇴한 작성자 자체를 신고하는 메뉴는 표시하지 않음 |
| 신고자 삭제 | 물리 삭제 시 신고자 FK만 NULL로 변경하고 접수는 보존. 실제 보존·파기 정책은 운영 검토 대상 |
| 공개 범위 | 접수 응답에 신고자·사유·상세를 넣지 않음. 일반 사용자용 신고 조회 API 없음 |

신고를 위해 일기 원문·댓글 본문·사용자 프로필을 새 테이블에 복사하지 않는다. 따라서 대상이 이미
삭제되었다면 후속 심사에서 원문을 복원할 수 있다고 가정하지 않는다. dev의 테스트 계정 분리는
기존 댓글·좋아요 쓰기와 맞춘다.

## HTTP 계약

`POST /api/v1/reports`에 Bearer와 CSRF 쿠키·`X-XSRF-TOKEN` 헤더가 필요하다.

```json
{
  "targetType": "FEED",
  "targetId": "00000000-0000-4000-8000-000000000001",
  "reason": "SPAM",
  "description": "반복적인 광고 게시물입니다."
}
```

최초 접수는 201, 기존 접수는 200이며 모두 `Cache-Control: no-store`다.

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "status": "RECEIVED",
  "duplicate": false
}
```

형식·열거형·길이는 `VALIDATION_ERROR`(400), 자기신고는 `INVALID_REPORT`(400),
없는 대상·삭제/비공개 대상은 `REPORT_TARGET_NOT_FOUND`(404)다. 인증 없음은 401,
CSRF 누락·불일치는 `INVALID_CSRF_TOKEN`(403)이다.

## 코드를 읽는 순서

1. `report/presentation/SubmitReportRequest`와 `ReportController`: 화면에서 대상·사유·상세만 받고,
   JWT의 회원 ID를 신고자로 사용한다.
2. `report/domain/ReportSubmission`: 필수값·문자·길이를 검증하고 상세 내용을 정규화한다.
3. `report/service/ReportService`: 활성 회원 검사, 본인의 기존 접수 확인, 대상 작성자 조회,
   자기신고 거절, 저장 순서다. 이미 접수한 대상이 사라져도 본인의 기존 접수는 안내한다.
4. `report/infrastructure/JpaReportTargetReader`: 사용자·피드·댓글의 실제 작성자와 공개성을 DB에서 확인한다.
5. `report/infrastructure/JpaReportRepository`: UNIQUE와 `ON CONFLICT DO NOTHING`으로 동시 중복을 막는다.
   경쟁 요청이 먼저 저장했다면 READ COMMITTED의 후속 조회로 그 접수 ID를 읽는다. 기존 행을 덮어쓰지 않는다.
6. `frontend/web/src/domain/reports/reportSubmission.ts`: 인증·CSRF와 API 응답 검증을 담당한다.
   로그인 토큰 복원 중 CSRF가 바뀌는 경우, 저장 전에 거절된 `INVALID_CSRF_TOKEN`에 한해 한 번 재시도한다.
7. `frontend/web/src/shared/report/ReportDialog.tsx`: 사유 선택·입력·접수 중 잠금·실패 재시도·성공 안내를 담당한다.
   피드 목록·상세와 댓글의 더보기 메뉴에서 같은 신고창을 사용한다.

백엔드 경로는 `backend/src/main/java/com/harudle/` 기준이다.

## 마이그레이션과 병렬 작업

`V29__create_reports.sql`은 새 신고 테이블만 생성한다. 암호화 #442가 V28을 사용하므로 번호를 분리했다.
개발·코드 리뷰는 독립적으로 진행할 수 있지만, **운영에 V29만 먼저 적용하고 이후 V28을 추가하면
Flyway의 순서 검증에 걸릴 수 있다.** 배포 묶음에 V28·V29가 함께 포함되거나 V28이 이미 적용된 상태인지
실제 이력을 확인한 뒤 적용한다. 적용을 위해 `outOfOrder`를 켜거나 기존 V28을 수정하지 않는다.

## 검증

신고 모델·서비스·실제 인증/CSRF 필터를 거치는 컨트롤러와 OpenAPI 요구를 단위·슬라이스 테스트로 확인한다.
DB 테스트는 동시 8건의 단일 저장, 첫 사유 보존, 롤백, 삭제 후 보존, 공개성, 문자와 DB 제약을 확인한다.
프론트는 MSW를 이용한 실제 제출·실패·재시도·중복 안내와 기존 삭제 기능의 회귀를 확인한다.

새 DB 통합 테스트는 CI에서 PostgreSQL 18 컨테이너를 사용한다. Docker 없는 로컬에서는
`HARUDLE_REPORT_TEST_DATABASE_URL=jdbc:postgresql://127.0.0.1:<port>/harudle_report_test`로 전용 임시 DB만
지정할 수 있다. 다른 호스트·DB명·옵션은 거절하며 운영 설정으로 대체하지 않는다.
현재 로컬 실제 DB 검증은 PostgreSQL 15.13에서 수행했다. HTTP부터 DB까지의 실제 접수·중복·삭제 후
재조회와 위조한 신고자/작성자 ID를 무시하는 검증을 포함해 백엔드 선택 검증 103개가 통과했다.
프론트 전체 검사(타입·린트·서식·테스트·빌드)와 401개 테스트도 통과했으며, 로컬 MSW 화면에서
신고 입력·접수·중복 안내를 확인했다. PostgreSQL 18 CI는 PR 준비 후 별도로 확인한다.
