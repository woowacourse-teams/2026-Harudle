# 사용자·콘텐츠 신고 접수 (#424)

다른 회원의 피드나 댓글에서 문제가 보이면, 해당 콘텐츠 또는 작성자를 신고할 수 있다.
이번 기능은 신고를 접수해 보관하는 단계까지 제공한다.
신고가 접수돼도 콘텐츠를 자동으로 숨기거나 계정을 제재하지 않는다.
관리자의 신고 조회·심사·조치는 후속 #427에서 다룬다.

## 사용자는 이렇게 신고한다

1. 다른 사람의 피드나 댓글에서 더보기를 열고, 콘텐츠 신고 또는 작성자 신고를 선택한다.
2. 로그인하지 않았다면 로그인 안내를 받는다.
3. 스팸·광고, 괴롭힘·욕설, 부적절한 콘텐츠, 기타 중 사유를 고른다.
4. 필요하면 상세 내용을 적는다. 상세는 선택 사항이며 앞뒤 공백을 뺀 뒤 최대 500자다.
   기본 이모지 `😀`는 한 글자로 센다.
5. 접수하면 결과를 안내한다. 실패하면 사유와 입력 내용을 유지한 채 다시 시도할 수 있다.

본인 콘텐츠의 더보기에는 기존 삭제 메뉴를 유지한다. 본인과 본인 콘텐츠는 신고할 수 없다.
탈퇴한 작성자의 댓글이 공개 상태로 남아 있다면 댓글은 신고할 수 있지만,
그 작성자를 신고하는 메뉴는 제공하지 않는다.

## 서버는 이렇게 처리한다

1. **신고할 수 있는 회원인지 확인한다.** 로그인 정보를 기준으로 신고자를 확인하고,
   OAuth 계정이 연결된 활성 회원만 접수한다.
2. **본인이 이미 신고한 대상인지 확인한다.** 같은 회원이 같은 종류의 같은 대상을 신고했다면
   기존 접수 번호를 안내하고, 처음 제출한 사유와 상세를 유지한다.
3. **새 신고라면 대상을 확인한다.** 사용자·피드·댓글이 실제로 존재하는지 확인하고,
   콘텐츠의 공개 상태와 작성자를 DB에서 조회한다. 화면에서 보낸 신고자나 작성자 ID는 사용하지 않는다.
4. **접수를 저장한다.** 본인 신고를 거절한 뒤 접수 번호와 `RECEIVED` 상태를 반환한다.
   동시에 같은 신고를 보내도 접수는 한 건만 저장한다.

화면에 보내는 결과에는 접수 번호·상태·중복 여부만 담는다.
신고자·사유·상세를 반환하는 일반 사용자용 신고 조회 API는 제공하지 않는다.

### 같은 대상을 다시 신고했을 때

> [!NOTE]
> **현재 정책:** 같은 회원이 같은 종류의 같은 대상을 다시 신고하면
> 기존 접수 번호를 반환하고, 최초 사유와 상세를 변경하지 않는다.

| 상황 | 처리 결과 |
| --- | --- |
| 처음 신고하는 공개 대상 | 새 접수 번호를 안내한다. |
| 사유나 상세를 바꿔 같은 대상을 다시 신고 | 기존 접수를 안내하며 첫 사유와 상세를 유지한다. |
| 본인이 신고한 뒤 대상이 삭제됨 | 본인의 기존 접수는 계속 안내한다. |
| 두 요청이 겹쳐 첫 조회 후 접수와 대상 삭제가 완료됨 | 대상 조회에 실패해도 본인의 접수를 다시 확인해 같은 번호를 안내한다. |
| 처음 신고하려는데 대상이 이미 삭제되거나 공개 해제됨 | 새 신고를 접수하지 않는다. |
| 대상 확인에 성공한 직후 콘텐츠가 삭제됨 | 확인했던 대상과 작성자의 ID로 접수를 보존한다. |

심사 종결 뒤의 재신고 규칙은 아직 정하지 않았다. 현재 동작을 유지하며,
관리자 심사 기능을 도입할 때 별도의 정책 변경으로 논의한다.

## 무엇을 보관하는가

신고자·대상 종류·대상 ID·대상 작성자 ID·사유·상세·접수 상태·접수 시각을 저장한다.
대상 ID와 작성자 ID는 접수할 때 확인한 기록이므로, 이후 대상이 삭제돼도 접수와 함께 남는다.

신고를 위해 일기 원문·댓글 본문·사용자 프로필을 신고 테이블에 복사하지 않는다.
따라서 대상이 삭제된 뒤에도 심사에 필요한 원문을 항상 확인할 수 있다고 가정하지 않는다.

신고자 회원 레코드를 물리적으로 삭제하면 신고와 회원의 연결을 해제하고 접수는 보존한다.
이 동작만으로 보존 기간이나 탈퇴 시 개인정보 처리 정책이 확정되는 것은 아니며,
사유·상세와 대상 식별자의 처리 기준은 아래 운영 논의에 포함한다.

## 운영 전에 논의할 정책 (#427)

다음 항목은 **현재 구현과 구분되는 논의 제안**이며, 기간이나 처리 기한을 확정한 내용이 아니다.

| 논의할 일 | 현재 구현 | 논의 제안 |
| --- | --- | --- |
| 누가 어디서 접수를 확인하는가 | 신고는 DB에 보관되며 관리자 조회·심사 화면은 아직 없다. | 접수 확인 담당자, 접근 권한, 확인 경로와 조치 기록 방법을 정하고 #427에 연결한다. |
| 언제까지 보관하고 탈퇴 시 무엇을 지우는가 | 신고자 물리 삭제 시 회원 연결만 해제한다. 사유·상세와 대상 식별자는 남는다. | 각 정보의 사용 목적과 조회 권한, 보존·파기 시점, 탈퇴 시 식별자 처리 기준을 함께 합의한다. 정해진 보존 기간은 아직 없다. |
| 대상이 삭제된 뒤 어떤 근거로 심사하는가 | 신고 테이블에 콘텐츠 원문 사본을 두지 않는다. | 수집 범위를 줄이는 현재 선택과 삭제 후 심사 근거가 줄어드는 점을 함께 검토한다. 증거 보관이 필요하다면 대상 정보·접근 권한·보존 기준을 정한 뒤 별도로 변경한다. |
| 심사가 끝난 대상도 기존 접수만 안내할 것인가 | 같은 회원·같은 종류·같은 대상은 해제 시점 없이 한 접수로 유지한다. | 현재 규칙을 유지할지, 종결 뒤 새 문제가 발생한 경우 재신고를 허용할지 #427의 심사 상태와 함께 정한다. |

## 검증한 동작

검증은 “신고가 저장되는가”뿐 아니라, 반복 요청과 실패 뒤에도 정책이 유지되는지를 확인했다.

| 확인한 상황 | 결과 |
| --- | --- |
| 비회원·본인·삭제된 대상을 새로 신고 | 접수를 거절한다. 신고자와 작성자는 서버에서 확인한다. |
| 같은 대상을 반복하거나 동시에 신고 | 한 건만 저장하고 같은 접수 번호를 안내한다. 최초 사유와 상세를 유지한다. |
| 접수 후 대상 삭제 / 저장 중 실패 | 대상이 삭제돼도 접수는 보존한다. 저장 작업이 실패하면 접수도 함께 취소된다. |
| 신고 입력·실패·재시도 | 길이와 문자를 검사하고, 실패해도 입력을 유지한다. 전송 중에는 중복 제출과 창 닫기를 막는다. |
| 기존 삭제·로그인·인증 갱신 | 본인 삭제와 비회원 로그인 안내를 유지한다. 인증 갱신 중 생긴 CSRF 오류만 한 번 재시도한다. |

검증 수치와 실행 환경은 아래 접힌 설명에서 확인할 수 있다.

<details>
<summary>API 요청과 응답 자세히 보기</summary>

`POST /api/v1/reports`에 Bearer 인증과 CSRF 쿠키·`X-XSRF-TOKEN` 헤더가 필요하다.

```json
{
  "targetType": "FEED",
  "targetId": "00000000-0000-4000-8000-000000000001",
  "reason": "SPAM",
  "description": "반복적인 광고 게시물입니다."
}
```

최초 접수는 201, 기존 접수는 200이며 모두 `Cache-Control: no-store`다.

```json
{
  "id": "00000000-0000-4000-8000-000000000002",
  "status": "RECEIVED",
  "duplicate": false
}
```

| 오류 | 응답 |
| --- | --- |
| 필수값·유형·문자·길이 오류 | `VALIDATION_ERROR` (400) |
| 본인 신고 | `INVALID_REPORT` (400) |
| 없는 대상·삭제 또는 공개 해제된 대상의 새 접수 | `REPORT_TARGET_NOT_FOUND` (404) |
| 인증 없음 | 401 |
| CSRF 누락·불일치 | `INVALID_CSRF_TOKEN` (403) |

상세의 정확한 길이 단위는 Unicode 코드 포인트다. NUL과 짝이 맞지 않는 UTF-16 문자는 거절한다.

<summary>개발·검증 환경 자세히 보기</summary>

- `V30__create_reports.sql`은 새 신고 테이블만 생성한다.
  기준 브랜치의 V28은 비동기 생성 대기, V29는 생성 상태 인덱스다.
  신고는 원문 암호화 #442를 포함하거나 요구하지 않는다.
- 마이그레이션 번호는 병합 전에 다시 확인한다. 이미 적용된 파일을 수정하거나
  `outOfOrder`를 켜서 번호 충돌을 우회하지 않는다.
- 중복 확인 쿼리는 접수 ID만 읽으며 사유·상세·접수 시각을 읽거나 기존 행을 덮어쓰지 않는다.
- dev의 테스트 계정 분리는 기존 댓글·좋아요 쓰기 정책을 따른다.
- DB 검증은 실제 쿼리·동시 저장·롤백·삭제 후 보존을 포함한다.
  로컬에서는 전용 임시 PostgreSQL 15.13으로 확인했고, CI는 PostgreSQL 18 컨테이너를 사용한다.
- Docker 없는 로컬에서는 다음 주소 형식의 전용 DB만 지정할 수 있다.
  다른 호스트·DB명·접속 옵션은 거절하며 운영 설정으로 대체하지 않는다.

```text
HARUDLE_REPORT_TEST_DATABASE_URL=jdbc:postgresql://127.0.0.1:<port>/harudle_report_test
```

확인한 로컬 검증 결과는 다음과 같다. CI 실행 결과는 별도로 확인한다.

| 검증 범위 | 확인한 결과 |
| --- | --- |
| 백엔드 선택 검증 | 신고·실제 PostgreSQL 15.13·공통 API 테스트 110개 통과 |
| 프론트 전체 검사 | 타입·린트·서식·빌드와 408개 테스트 통과 |
| 실제 Chrome 화면 | 전체 90개 실행 후 피드 테스트 2개를 보정해 재검증. 최종 86개 통과, 기존 dev의 일기 상세 4개 실패 |
| 최신 기준 브랜치 통합 | dev `52777333`과 develop-backend `cff1206b`를 실제 작업 브랜치에 함께 병합 |

브라우저 테스트는 최신 공유 링크의 UTM 값과 본인 삭제 메뉴의 버튼 선택을 보정했다.
남은 일기 상세 4개 실패(월 선택 복귀 1개, 삭제 메뉴 탐색 3개)는
원본 dev `52777333`의 별도 사본에서도 동일하게 재현했다. 해당 일기 화면 코드는 이번 통합에서 변경하지 않았다.

화면 자동 검증은 MSW로 서버 응답을 재현하므로, 실제 서버와 DB 검증 결과와 구분한다.

> [!NOTE]

| 용어 | 이 기능에서의 의미 |
| --- | --- |
| UNIQUE | 같은 신고자·대상 종류·대상 ID 조합이 DB에 두 번 저장되지 않게 하는 규칙이다. |

| READ COMMITTED | 다른 요청의 저장이 끝난 뒤 다시 조회하면 그 접수 번호를 읽을 수 있는 DB 조회 방식이다. 동시 중복 요청에서 먼저 저장된 접수를 안내하는 데 사용한다. |
