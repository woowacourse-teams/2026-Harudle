# 관리자 신고 심사·제재 (#427)

관리자는 기존 대시보드에서 신고를 확인하고, 필요하면 콘텐츠를 숨기거나 계정을 제재한 뒤 심사를 종결한다. **신고 심사, 계정 제재, 콘텐츠 숨김은 서로 독립적인 상태**다.

## 확정한 정책

- 신고는 `접수 → 반려 / 처리 완료`로 종결한다. 사유는 필수이며 최대 500자다. 최초 처리자·시각·사유를 보존하고 종결을 다시 변경하지 않는다.
- 같은 신고의 같은 결정·사유를 재전송하면 기존 결과를 반환한다. 이미 다른 결과로 종결됐으면 최신 상태를 확인하게 한다.
- 계정 제재는 관리자가 해제할 때까지 로그인·토큰 갱신·회원 API 이용을 막는다. 기존 Access Token도 다음 회원 요청에서 잠금 없이 DB에 커밋된 최신 제재 상태를 확인한다. 토큰 발급·회전은 제재와의 경합을 막는 사용자 공유 잠금을 유지한다. 비로그인 공개 열람은 유지한다.
- 정지 시 Refresh Token을 폐기한다. 이미 통과한 요청과 접수된 이미지 생성 작업의 강제 취소까지 보장하지 않는다. 해제는 제재를 없애며, 이미 폐기한 Refresh Token을 되살리지 않는다. 남은 Access Token은 기존 만료 규칙을 따른다.
- 콘텐츠 조치는 별도의 **관리자 숨김·해제**다. 원본과 작성자의 삭제 상태를 변경하지 않는다. 해제해도 작성자가 삭제한 콘텐츠는 공개되지 않는다.
- 계정 제재·해제와 콘텐츠 숨김·해제는 사유·처리자·시각과 변경 이력을 남긴다. 관리자 자신과 다른 관리자 계정은 제재 대상으로 삼지 않는다.

## 관리자는 이렇게 처리한다

1. 신고 상태를 골라 목록을 확인하고 대상을 연다.
2. 신고 사유와 대상의 현재 상태를 확인한다. 삭제된 원본이 DB에 남아 있으면 관리자에게 보여 주고, 물리 삭제된 원본은 확인할 수 없다고 표시한다.
3. 필요한 조치를 선택해 사유를 입력하고 확인한다. 계정 제재와 콘텐츠 숨김은 각각 적용한다.
4. 판단 근거를 적고 반려 또는 처리 완료로 종결한다.

조치가 성공한 뒤 목록 갱신에 실패해도 성공을 취소하거나 같은 조치를 자동 반복하지 않는다. 화면에서 조회만 다시 시도한다. 다른 관리자가 먼저 변경했다면 최신 상태를 확인한 뒤 다시 결정한다.

## 일반 사용자의 신고는 그대로 유지한다

심사가 끝난 뒤에도 같은 회원·같은 대상은 기존 접수를 안내한다. 최초 신고 사유·상세를 덮어쓰지 않는다. 일반 신고 응답의 `RECEIVED`는 접수 확인 계약이며, 실제 관리자 심사 상태는 관리자 전용 응답으로만 제공한다.

관리자 상세는 신고된 피드의 생성 제목·이미지와 댓글 본문을 확인한다. **비공개 일기 원문은 조회하거나 반환하지 않는다.** 신고자·처리자가 물리 삭제돼도 신고·조치 기록은 남으며 회원 연결만 해제한다. 보존 기간과 추가 증거 수집 정책을 이번 구현으로 새로 정하지 않는다.

## 노출과 제한의 범위

피드 숨김은 같은 일기의 공개 피드·댓글·접촉·알림·공유 링크에 적용한다. 피드를 삭제한 뒤 같은 일기를 다시 게시해도 숨김을 우회할 수 없다. 댓글 숨김은 해당 댓글과 관련 알림에 적용한다. 작성자 본인의 비공개 일기 조회나 기존 콘텐츠 삭제 권한을 관리자 숨김으로 없애지 않는다.

기존 반응과 저장된 좋아요·댓글 수를 소급 삭제·재집계하지 않으므로 공개 목록의 전체 수와 보이는 댓글 수가 다를 수 있다. 이미 발급한 이미지 접근 URL이나 다운로드한 파일은 즉시 회수하지 못하며 URL은 기존 만료 시간을 따른다.

상황별 분기와 API는 [시나리오 문서](admin-moderation-scenarios.md)에서 확인한다.

관리자 기능은 백엔드 반영 뒤 프론트를 배포한다. 프론트 MSW 검증과 실제 PostgreSQL·서버 통합 검증은 구분한다.
