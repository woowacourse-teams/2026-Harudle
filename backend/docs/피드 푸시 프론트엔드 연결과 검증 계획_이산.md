# 피드 푸시 프론트엔드 연결과 검증 계획

- 작성일: 2026-10-15
- 작성자: 이산
- 대상: 프론트엔드에서 푸시를 등록하고 실제 브라우저 수신을 확인하는 작업

## 지금 상태

백엔드는 피드 게시 시 수신 기기마다 발송 작업을 저장한다. 워커는 로그인 세션과 기기 등록이 유효한지 확인한 뒤 FCM에 전송한다. 백엔드 전체 테스트는 통과했다. 다만 프론트엔드에는 아직 Firebase 등록과 수신 코드가 없다. 그래서 실제 브라우저 알림은 확인하지 못했다.

첫 버전은 사용자가 로그인 후 푸시 수신을 선택하면 등록한다. 로그인만으로 알림 권한을 요청하지 않는다. 마이페이지에서 알림을 켜고 끄는 기능은 이번 범위에 넣지 않는다.

## 프론트엔드에서 구현할 일

### 1. Firebase 웹 앱 준비

- Firebase 웹 SDK를 설치하고 현재 Firebase 프로젝트의 웹 앱 설정을 연결한다. 웹 설정 값과 공개 VAPID 키를 프론트엔드 환경 변수로 전달한다. **서비스 계정 인증 파일은 프론트엔드에 넣지 않는다.**
- Firebase 콘솔의 Cloud Messaging에서 웹 푸시 인증서의 공개 VAPID 키를 확인한다. 등록에는 `getToken()` 대신 `register()`와 `onRegistered()`를 사용한다.
- 사이트 루트에서 `/firebase-messaging-sw.js`가 열리도록 서비스 워커를 준비한다. 현재 [`webpack.config.js`](../../frontend/web/webpack.config.js)의 파일 복사 목록에는 이 파일이 없으므로 빌드 결과에도 포함해야 한다.

### 2. 로그인 후 사용자에게 수신 여부 묻기

- [`AuthCallbackPage.tsx`](../../frontend/web/src/pages/login/AuthCallbackPage.tsx)에서 인증을 마친 뒤, 로그인한 사용자에게 푸시 수신 안내를 보여준다. 안내 화면이나 컴포넌트의 위치는 프론트엔드 화면 흐름에 맞춰 정한다.
- 사용자가 받기를 선택했을 때만 브라우저 알림 권한을 요청한다. 권한을 거절하면 Firebase 등록 API와 백엔드 등록 API를 호출하지 않는다.
- 수신 선택은 **사용자 ID별로** 해당 환경의 `localStorage`에 기록한다. [`profile.ts`](../../frontend/web/src/domain/user/profile.ts)의 `id`를 사용할 수 있다. 브라우저 권한이 이미 허용되어 있어도 다른 계정의 선택을 대신하지 않는다.
- 등록이 실패하면 설정 완료로 표시하지 않는다. 사용자가 다시 시도할 수 있게 결과를 보여준다.

### 3. FID를 백엔드에 등록하기

- 브라우저나 설치된 PWA의 저장 환경마다 `deviceId` UUID를 한 번 만들고 계속 사용한다. FID가 바뀌어도 같은 `deviceId`를 보낸다.
- `register()`를 호출하기 전에 `onRegistered()`를 연결한다. 이 콜백이 알려주는 최신 FID를 백엔드에 보낸다. 앱을 다시 열었을 때도 사용자가 수신을 선택한 상태이고 브라우저 권한이 허용되어 있으면 등록 상태를 확인한다.
- 인증이 필요한 요청은 기존 [`authFetch()`](../../frontend/web/src/shared/auth.ts)를 사용한다. API 코드는 `src/domain/` 아래 푸시 도메인에 두고, 화면에서는 그 코드를 호출한다.

```http
PUT /api/v1/me/push-registrations/{deviceId}
Content-Type: application/json

{"fid":"현재 FID"}
```

첫 요청은 `fid`만 보낸다. 성공하면 응답의 `id`와 `version`을 현재 사용자와 `deviceId`에 연결해 저장한다. 이후 FID를 변경할 때는 `fid`, `registrationId`, `version`을 함께 보낸다. 같은 요청을 다시 보내면 백엔드는 등록을 하나만 유지한다. 등록 정보가 바뀐 경우 서버는 `409`와 `code=STALE_PUSH_REGISTRATION`을 반환하며, `current`에는 현재 등록 ID와 버전이 들어간다. 현재 등록이 없으면 `current`는 `null`이다. 이때 **지금 Firebase가 알려준 최신 FID**로 다시 요청한다. 오래된 FID를 새 버전으로 재시도하지 않는다. 다른 유효한 세션의 등록과 충돌한 `PUSH_REGISTRATION_CONFLICT`는 자동으로 바꾸지 않는다.

응답을 못 받은 타임아웃, 네트워크 오류, `5xx`는 같은 요청을 다시 보낸다. 최초 요청을 포함해 최대 3회 시도하고 간격을 늘린다. `429`에 `Retry-After`가 있으면 그 시간을 따른다. 권한 거절, `400`, 다른 세션과의 충돌은 자동 재시도하지 않는다. `401`이면 기존 로그인 만료 처리 흐름을 따른다.

### 4. 권한 변경과 로그아웃 처리

- 사용자가 나중에 브라우저 설정에서 알림 권한을 차단했다면, 로그인 상태로 앱을 다시 열 때 `Notification.permission`을 확인한다. 차단된 경우 현재 `deviceId`에 대해 `DELETE /api/v1/me/push-registrations/{deviceId}`를 호출하고 해당 사용자의 수신 선택을 지운다. 앱을 열기 전까지 서버가 브라우저 설정 변경을 바로 알 수는 없다.
- [`useLogout.ts`](../../frontend/web/src/pages/setting/useLogout.ts)의 로그아웃이 성공하면 백엔드가 그 로그인 세션의 푸시 등록과 미발송 작업을 정리한다. 프론트엔드는 해당 사용자의 수신 선택과 등록 ID, 버전을 지운다. `deviceId`는 같은 환경을 다시 찾을 수 있도록 유지한다.
- 로그아웃해도 브라우저의 사이트 알림 권한은 그대로 남는다. 다음 계정이 로그인하면 그 계정에 다시 수신 여부를 묻는다.

### 5. 알림 받기

- 페이지가 뒤에 있거나 닫혀 있을 때는 서비스 워커가 `notification` 메시지의 알림을 표시할 수 있게 한다. 같은 메시지를 직접 `showNotification()`으로 한 번 더 띄우지 않는다.
- 페이지가 앞에 있을 때는 `onMessage()`로 수신을 확인한다. 첫 버전에서 앞 화면에 별도 배너를 보여줄지는 프론트엔드와 합의한다.
- 백엔드는 `data`에 `eventId`, `type=FEED_PUBLISHED`, `feedId`를 넣고, 웹 알림의 `tag`에 `eventId`를 넣는다. `tag`는 화면에 남아 있는 같은 알림을 교체한다. 닫은 알림이 재전송 후 다시 뜨는 것까지 막지는 않는다.
- 배포 환경에서는 알림 클릭 시 피드 상세 페이지가 열리는지 확인한다. 백엔드는 피드 주소가 HTTPS일 때만 클릭 주소를 넣는다. 로컬 HTTP 주소에서는 클릭 이동을 확인할 수 없다.

## 함께 확인할 순서

1. 프론트엔드 단위 테스트에서 수신 선택, 권한 거절, FID 변경, 같은 요청 재시도, `409`의 `current` 처리, 로그아웃 후 저장 값 삭제를 확인한다.
2. 로컬에서 프론트엔드와 백엔드를 실행한다. 백엔드에는 `HARUDLE_PUSH_FCM_ENABLED=true`, `FIREBASE_PROJECT_ID`, Google 인증 정보를 설정한다. 인증 파일은 저장소에 올리지 않는다.
3. A 계정이 브라우저에서 푸시를 등록한다. 다른 B 계정으로 피드를 게시한다. A가 작성자라면 A에게는 알림을 예약하지 않으므로 계정을 나눠야 한다.
4. DB에서 A 기기의 작업이 `PENDING`에서 `SENT`로 바뀌는지 확인한다. 브라우저를 뒤에 둔 상태에서 알림이 표시되는지도 확인한다. `SENT`는 FCM의 수락 기록이며, 브라우저 표시 자체를 증명하지는 않는다.
5. A가 로그아웃한 뒤 새 피드를 게시해 A 기기에 새 알림이 오지 않는지 확인한다. 그다음 dev 환경에 반영해 HTTPS에서 알림 클릭과 피드 상세 이동도 확인한다.
